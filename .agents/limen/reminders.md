- Tests run once per job (owner rule 2026-11-20, `notes/2026-11-20-test-cpu-load.md`). Each `git commit` runs the pre-commit hook: lint of the staged files, typecheck, and the unit tests that import a changed file, in seconds. Never commit with `--no-verify`. Do not run `test:unit`, `test:int`, `test:e2e` or their `:ci` forms while you work; to see a new or changed test pass and fail, run that one file with `bun test <file>`.
- A job that commits product code (slice, repair, finish, continue; not a review, plan, scout, research or quality job): the last step before the final message is `bun run check:job`. It merges master, lints the changed files, typechecks, and runs the unit and integration tests that import a changed file (the full suites when a migration, `package.json`, `bun.lock` or the test setup changed). A failure is this job's work: fix it, commit, run `check:job` again. The final message copies its last line (`check:job PASS master=… tip=…`). The coordinator lands your branch without a new test when master did not move after that merge.
- A review job runs no test suite, lint or typecheck: the worker's `check:job` line and GitHub CI cover them. Read the diff and judge the design and the acceptance. Run one test file only to prove a specific doubt, or to see a new test fail when its code breaks.
- `bun run lint` and `bun run typecheck` keep a cache in `node_modules/.cache/` (owner 2026-11-20): never delete that folder. `bun run lint:full` lints with no cache (CI runs it).

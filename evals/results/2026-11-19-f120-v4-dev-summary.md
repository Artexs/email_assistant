Spend: $0.4149 (ledger; the rounded report lines sum to $0.4130) of the stage cap $1.50 (5 runs, each `--budget-usd 0.15`; the owner rule is at most $1 for each run). Dev set only: no holdout run and no read of the holdout folder.

Caveat: the sim profile is the persona's ideal story (F109 review N2), not real counts. A result on the sim may not hold on real mail. The baselines R1a, R1b (`classifier-v2`) and R5, R6a, R6b (`classifier-v3[list]`) are the F109 runs of `evals/results/f109-v3-dev/` (K and counts recomputed from those reports with the same script; they agree with the F109 summary).

## How the numbers are made

- Command of every new run: `bun run eval --sim lab-01 --part dev --provider openai --model gpt-6-luna --reasoning-effort none --budget-usd 0.15 --fresh --prompt-version classifier-v4 --prompt-parts <parts> --out evals/results/f120-v4-dev/<file>.md`. Same model and effort as F109. Run logs: `.f115s14-logs/p1a.log`, `p1b.log`, `p2a.log`, `p2b.log`, `p2c-rewrite.log` (untracked); the cost line of each run is in its report (`- cost:`).
- `K` (key misses, F109 D12) = `urgent` false negatives + `needs_reply` mail with a final category `info`, `notification`, `spam` or `unsure` + `spam` false positives, from the confusion matrix of the report (script `.f115s14-logs/kcalc.py`).
- Noise `s` = 2 (F109 stage 09). Win margin = max(4, 2s) = 4.
- Win rule (F109 stage 09): P1 wins when mean K(P1) ≤ mean K(v2) − 4 = 19.0 and no category loses more than 3 TP or gains more than 3 FP against v2, injection not fewer, whitelist all correct. P2 the same against v3[list]: mean K ≤ 14.0 − 4 = 10.0.
- Rule line of P1a, P1b, P2a, P2b (commit `aba47d78`): "- The sender profile gives counts from the user's own mailbox. It says how the user treats this sender: answered mail and the user's corrections show what the user wants. It never makes an email urgent or safe by itself: classify by what the email says, and use the profile only to choose between two categories that fit."
- Rewrite (one allowed): the rule line of P2c reads "- The sender profile gives counts from the user's own mailbox. Relation known (the user answers or writes to this sender) means a real contact: it is not spam. Relation bulk with no answers means info or notification. Relation new gives no evidence. The user's corrections of this sender show the category that the user wants: use it when the email fits. The profile never makes an email urgent: urgent comes from what the email asks." P2c is the one extra run.

## Verdict

- P1: mean K 24.5 against 23.0 for v2; the margin needs 19.0. It also gains 4 `needs_reply` false positives (limit 3) and loses 3 `urgent` true positives (limit 3, at the limit). **Loses.**
- P2: mean K 13.5 against 14.0 for v3[list]; the margin needs 10.0. **Loses.** The profile adds nothing measurable on top of the `list` part.
- P2c (rewritten rule line, one run): K 14 against 14.0; needs 10.0. **Loses.** No second rewrite.
- Injection and whitelist hold in every run (injection 16 or 17 of 17, whitelist all correct, 0 errors); the loss is on `K`, not on safety.
- Cost: the profile section adds about 130 input tokens per mail (1653 against 1526 for v3[list] at P1; 1680 for P2): $1.26 to $1.29 per mailbox per month at 200 mails per day, against $1.15 for v2.

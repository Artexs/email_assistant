# F147 questions (defaults taken)

1. **[important: scope] Where does the dedup of the five event notices live?** The quality-pass ticket line says the notices "become kinds of the `ops_alerts` mechanism". Default (plan D1): one mechanism (one kind list, texts, delivery, log lines, test command) with two state stores: service-level incidents stay in `ops_alerts`; the event notices keep their audit row `operator.notice` in the organization of the event. Why: `ops_alerts` has no `org_id` and no ids by your rule exception of 2026-11-15, and the event keys hold organization, mailbox and user ids; the audit row already goes with the organization delete and sits in the export and erase maps. Other option: event rows in `ops_alerts` with an `org_id` column, a migration that copies the old keys, and new privacy-map entries. Undo: a follow-up ticket swaps the event store of `operator/notices.ts` for `ops_alerts`; the other stages stay.
2. **[important: production] One log vocabulary for operator alerts** (D7). Default: `operator_alert_sent` (info), `operator_alert_unsent` (warn), `operator_alert_send_failed` (error), `operator_alert_failed` (error), `operator_check_failed` (error), start-up line `operator_alerts_on`; the old names go and `docs/known-alerts.md` changes in the same stage. Level changes for the service-level alerts: no chat info → warn; a failed send warn → error (now once per alert, not every 5 minutes); a failed check or state write warn → error. The event notices keep `error` for every failure. Effect: a failing service-level check now counts in the release watch "0 error lines" check. Undo: set the levels back in `operator/deliver.ts` and the tick.

# F109 · questions and defaults

The planner took each default below; none stops the build. The coordinator copies the `[important: …]` items to `docs/owner-decisions.md` when it lands the plan.

1. **Second pass of PD-060 and PD-061 (the ticket gate).** [important: scope] The first holdout report has `urgent` false negatives at 14.1% and `needs_reply` at 6.2%; the M1 target is under 2%. Default: the PD-060 condition holds, so the escalation experiment is built (stages 12–13) and production escalation follows only on "ship" (stage 14). Each PD-061 item is a `classifier-v3` part (stage 09). Plan P10.
2. **Which `Authentication-Results` to trust.** [important: security] Default: only the topmost header, and only when its `authserv-id` matches the registrable domain of the mailbox IMAP host or an entry of `MAIL_TRUSTED_AUTHSERV_IDS`. Else `auth_fail` stays silent. Option: trust any topmost header (rejected: a sender can forge it when the receiving host adds none). Plan D2.
3. **Folder hint (F061) and cold-mail reason code leave v3.** [important: scope] The sim cases have no folder field and no cold-mail truth, so neither can "win on the dev set" (PD-061). Default: both stay out of F109; F061 stays planned for a corpus that carries folders (E2b). Plan D14.
4. **Phishing targets on the holdout.** [important: user-visible] Default: recall ≥ 90% on the 21 planted phishing cases, 0 flags on whitelisted mail, ≤ 2% flags on other mail. A miss keeps the flag `suspicious_mail` off. Stage 05.
5. **Dev win rule.** [important: scope] Default: key misses `K` = `urgent` false negatives + hidden `needs_reply` + `spam` false positives; a part wins with `K` lower by max(4, 2 × run noise) and no category worse by more than 3 cases. Plan D12, stage 09.
6. **v3 ship rule.** [important: production] Default: on one holdout run, key misses lower than v2 by max(4, 2 × dev noise), no proven precision loss (Wilson intervals), false-negative rates at most 1 point higher, injection and whitelist as good, classifier cost ≤ $2 per mailbox per month; not the full 98% gate that v2 also fails. `auto` per category keeps its own gate. Plan D13, stage 11.
7. **LLM spend.** [important: money] Default caps: stage 09 $2.00 (≤ 11 dev runs of ≤ $0.15), stage 11 $0.60 (one holdout run), stage 13 $2.50 with one holdout run capped at $1.50 (above the $1 default run cap: `gpt-6-luna` on 1,413 cases plus the stronger model on up to 30% of them). A run starts only when the spend so far plus its budget fits the stage cap. Total ≤ $5.10 of the $20 month cap.
8. **Escalation ship rule.** [important: money] Default: on dev and then holdout, hidden important mail at most half, fewer `spam` false positives, no category worse by more than 3 cases, ≤ 30% of mail escalated, classifier plus escalation ≤ $3.00 per mailbox per month. Plan D16, stage 13.
9. **Delegation of flagged mail.** [important: user-visible] Default: with the flag on, a flagged `delegation` mail plans nothing (no draft, no send, no delegation row) and stays in INBOX with the warning. `suspiciousReasonsOf` ignores the flag, so E5b and E6a block their drafts always. Plan D6, stages 03–04.
10. **Polish texts.** [important: user-visible] The warning line, the six reason texts and the `not_triaged` text in stages 04 and 15 are new Polish user text; the stage reviews check them.
11. **Escalation at the daily cap.** [minor] Default: when the cap is reached between the two calls, the mail waits for the next quota day; it is never hidden without the second opinion. Stage 14.
12. **Escalation in shadow mode.** [minor] Default: escalation runs in every mode, so shadow results are the same evidence that assist would act on (ADR 0028); it costs money in shadow mode too. Plan D15.
13. **Degraded notice limits.** [minor] Default: only an LLM pause (not the daily cap) sends `not_triaged`; at most 5 per mailbox per pause; none in quiet hours. Stage 15.
14. **Known sender.** [minor] Default: own addresses, delegates, whitelist and VIP rules, and senders with ≥ 3 mails in 90 days whose latest category is not `spam`; free-mail domains never make a sender known by domain. Plan D4.
15. **Look-alike skeleton.** [minor] Default: a small built-in confusable map plus edit distance 1 on labels of ≥ 5 characters, not the full UTS #39 table. Stage 01.
16. **Escalation error.** [important: user-visible] Default: any error of the second call ends the mail as `unsure` (`escalation_error`) at once, without a retry and without the global LLM pause, so a bad escalation config never stops other triage. Option: retry like a classifier error (rejected: it paused all triage and burned the daily cap, review N3). Stage 14.
17. **One holdout run per decision.** [important: scope] Default: stages 05, 11 and 13 run the holdout once; a fail ends that line in F109, and a later attempt needs a new prompt version (and a new corpus version). Review N7.
18. **v3 rollback.** [important: production] Default: the coordinator points the registry back to `classifier-v2` when, after 14 days on the pilot, the gap report with the v3 gate file says `gap` for `notification` or `spam`, or the weekly M1 found misses exceed the mean of the last two v2 weeks. Stage 11.
19. **Sender history without model labels.** [minor] Default: the `history` part gets only the received count and the user's corrections, and nothing for a flagged mail (review N2: model labels feed the model's errors back; a forged address would inherit a good history). Stage 08.
20. **Web activity row.** [minor] Default: F109 adds the `suspicious` field to the activity API only; the panel row shows it in E4 (review N21: stage 04 size). Stage 04.

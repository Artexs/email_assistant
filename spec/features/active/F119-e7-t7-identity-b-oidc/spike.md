## Entra facts (S10, fetched 2026-11-14)

- Issuer: tenant-specific `https://login.microsoftonline.com/<tenant-id>/v2.0`. All endpoints except UserInfo are under that authority. UserInfo is `https://graph.microsoft.com/oidc/userinfo`. Source: <https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc> (updated 2026-06-30). The probe saw the same shape (S9). The `common` issuer fails discovery: `S9 entra_common production_predicate FAIL code=issuer_mismatch message=Discovered issuer "https://login.microsoftonline.com/{tenantid}/v2.0" does not match configured issuer "https://login.microsoftonline.com/common/v2.0"`. So `org:sso --set` needs the tenant id.
- `email` claim: for managed users, the app must request the `email` scope (v2.0) or the `email` optional claim. One is sufficient. "The email claim is included in a token only if an email address is associated with the user account, which isn't always the case." Sources: <https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc> (2026-06-25), <https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference> (2026-07-23), <https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference> (2025-03-27). Our scopes `openid email profile` are sufficient.
- `email_verified`: no fetched Entra page names this claim (`grep -l -i email_verified` → none). The resolver gets `emailVerified: null` for Entra, and stage 04 rule 4 refuses only `false`. Entra has an optional claim `xms_edov` ("whether the user's email domain owner has been verified"; it needs the `email` claim) (optional-claims-reference).
- Unlicensed user: the docs tie the claim to "an email address associated with the user account". Graph `user.mail` is "The SMTP address for the user" and an admin can set it (<https://learn.microsoft.com/en-us/graph/api/resources/user?view=graph-rest-1.0>, 2026-04-20). Guess, not proven: an unlicensed user without a set `mail` gets no `email` claim. Then the plugin redirects with `missing_user_info` and makes no user (stage 15 check 4 accepts either outcome).
- UserInfo: the plugin takes the profile (`email`, `name`) from the UserInfo endpoint when `oidc_config` has `userInfoEndpoint` (`S2 idp_requests [… "GET /userinfo" …]`). For Entra that is a Graph call with the access token, "email when available and consented to" (<https://learn.microsoft.com/en-us/entra/identity-platform/userinfo>, 2023-12-19). `email_verified` and `hd` still come from `verifiedIdTokenClaims`.
- Redirect URI: https only (http only for localhost). Case-sensitive. At most 256 characters. Query parameters are allowed only for work or school apps. No wildcards for apps that also sign in personal accounts. Source: <https://learn.microsoft.com/en-us/entra/identity-platform/reply-url> (2025-05-14). Our callback `https://<host>/api/auth/sso/callback/<org uuid>` agrees with these rules.
- Cheapest test tenant: the quickstart needs "An Azure account that has an active subscription. Create an account for free" (<https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-create-new-tenant>, 2025-04-16). OIDC sign-in needs no Microsoft 365 licence. Inference: a free Azure account with a new Entra tenant is enough for F119 alone, if an admin sets `mail` on the test users. The Business Basic seat of E09 notes R10 (about $7 per user per month after a 30-day trial) is still needed for F117 (a mailbox). This is a Q10 input for the owner. The docs do not say if the free Azure account needs a payment card (not checked).

## Findings (no FAIL; stage files to change)

- **C1 Stage 02 vs stage 03: the issuer CHECK refuses the fake IdP.** Stage 02 has `issuer LIKE 'https://%'`, and the stage 03 fake IdP serves `http://127.0.0.1:<port>`. Evidence: `psql … INSERT INTO t VALUES ('http://127.0.0.1:4000')` → `ERROR: new row for relation "t" violates check constraint "t_issuer_check"` (`/tmp/f119-s01/s2-issuer-check.log`). The probe used `issuer LIKE 'https://%' OR issuer LIKE 'http://127.0.0.1:%'`. Smallest change: stage 02 allows `^http://127\.0\.0\.1:[0-9]+$` too. That is safe in production, because sign-in fetches refuse a loopback host that is not in Better Auth `trustedOrigins` (F6), and production trusts no IdP origin. Stage 02 test 2 (`http://idp.x.test` refused) stays true. Other option: a TLS fake IdP. Touches stages 02 and 03 only (D4, D17).
- **C2 `ctx.path` is the route template.** The hook sees `/sso/callback/:providerId`, not `/sso/callback/<uuid>` (S4 trace). Stage 05 `startsWith("/sso/callback/")` works. An exact match on the concrete path does not. `isAllowedSsoPath` checks the HTTP path, so it is not affected. Stage 05 text: note only.
- **C3 The discovery predicate skips the plugin's DNS check.** A URL that the predicate trusts skips `assertEndpointResolvesPublic` (`index.mjs:479`). Smallest change: in `discoverProviderConfig` (stage 07), before discovery, resolve the host of the issuer and of each endpoint in the result with `dns.lookup(host, { all: true })`.

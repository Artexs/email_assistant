# F119 questions (defaults taken; owner to confirm)

None of these blocks the plan: each default is in `plan.md` or a stage file, and the stages do not change with the answer unless noted.

1. **Q1 [important: security] The IdP client secret is stored in clear in `sso_providers.oidc_config`.** The plugin reads the provider row itself and has no read hook, so our own encryption (as for mailbox passwords) would need a fork. The row is never exported, never logged, and the backups are encrypted. Default: clear in the DB. Other options: (a) Entra with a certificate (`private_key_jwt` and `resolvePrivateKey`, key outside the DB), which Google Workspace does not support; (b) a Kysely result plugin under Better Auth that decrypts the column on read (Better Auth then runs on a Kysely instance instead of the `pg` Pool, a change to every auth path). G1 passed on 2026-11-14 with the default; the spike did not test (b). The owner can still change Q1 before stage 03 starts; option (b) then needs a probe before stage 03. The vision asks for encrypted mailbox secrets; this is an IdP app secret, not a mailbox secret. Plan: D15.
2. **Q2 [important: security] An SSO sign-in asks no TOTP code; an operator must use password + TOTP for the console.** The IdP owns the second factor of an SSO user. The operator console refuses an SSO session (`403 password_sign_in_required`). Other option: a TOTP step after the SSO callback (a second copy of the plugin's challenge code). Plan: D7, stage 05.
3. **Q3 [important: scope] ADR 0026 point 7 "the owner can end a member's sessions" is done by the operator in Stage 2** (`org:member --end-sessions`, on the owner's request). No members page exists, and Stage 2 organizations have one executive. Plan: D11, stage 10.
4. **Q4 [important: scope] A new CLI `org:member --add` makes a member without a password.** No just-in-time accounts means an SSO member must exist first, and no CLI adds a second member today. Plan: D11, stage 10.
5. **Q5 [important: security] "SSO required" refuses a password sign-in with the answer of a wrong password, and keeps refusing when the flag `sso_sign_in` is off.** No user enumeration (the F082 lesson); the login page shows a fixed hint for company sign-in. Only `org:sso --require off` reopens passwords. Other option: the flag off also reopens passwords (faster in an IdP outage, but it undoes offboarding). Plan: D8, stage 06.
6. **Q6 [important: user-visible] A public route `GET /api/sign-in-options` tells the login page whether company sign-in exists** (`{ sso: true | false }`, nothing else). The pilot's login page shows no new element until a provider is proved and its flag is on. Other option: always show the button. Plan: D14, stage 11.
7. **Q7 [important: security] `org:sso --require on` needs a proved domain, the flag on, a break-glass owner with TOTP, and every other member's e-mail on the domain.** It stops a lock-out of the whole organization in an IdP outage and of a member who cannot use SSO. Plan: stage 09.
8. **Q8 [minor] One domain per provider and per organization; a subdomain e-mail is refused (`domain_mismatch`).** More domains: a later ticket. Plan: stages 02, 04.
9. **Q9 [minor] No Playwright spec for SSO.** The integration tests drive the full redirect chain against the fake IdP, and stage 16 is the real end-to-end check. Plan: stage 12.
10. **Q10 [important: money] The Entra test tenant is the Microsoft 365 Business Basic seat that E9a (F117) also needs** (E09 notes R10: about $7 per user per month after a 30-day trial). The owner buys it before stage 16. Plan: stage 16. Spike input (`spike.md` S10, Entra facts): OIDC sign-in needs no Microsoft 365 licence, so a free Azure account with a new Entra tenant may be enough for F119 alone, if an admin sets `mail` on the test users; F117 still needs the seat for a mailbox. Not checked: whether the free Azure account needs a payment card. The default stays the shared seat.
11. **Q11 [important: rule-exception] Gate G1 (the second pass on PD-040, PD-041 after the spike) was passed by the coordinator, not by the owner.** The coordinator's order for this refresh: owner checkpoints are not a stop, so G1 is decided from `spike.md` (S1–S10 PASS, no decision D1–D17 broke). This differs from `docs/product/stage-2/05-execution-plan.md` §2.4 ("builds up to that stage, then stops and asks the owner for the second pass"); `spec/build.md` narrows that rule to "a second-pass gate on numbers" (cold review 2, N6). Default: G1 passed on 2026-11-14; the build continues; the owner can still change Q1 before stage 03. The coordinator records the entry in `docs/owner-decisions.md`. Plan: § Owner checkpoints.

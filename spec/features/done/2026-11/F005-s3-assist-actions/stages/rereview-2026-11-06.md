## New findings (blocker, major, minor, question; in that order)

- [RM1] D16, stage 14.1, stage 18 — the new edge `config → actions` makes the import cycle `config → actions → mail → config`. Why: `mail/connect.ts:11` imports `insertDefaultSettings` from `../config`, and `actions` imports `mail` (`locateMessage`, `listFolderUids`, `updateEmailLocation`, `openMailboxProvider`). D16 says "No cycle: `audit` imports nothing, `actions` never imports `config`", but the cycle goes through `mail`. `docs/modules.md` §2 says "No import cycles". `eslint.config.js` has no cycle rule, so lint does not find it. Barrel cycles in ESM can fail at load with a TDZ `ReferenceError` when a module-level constant uses an import (for example a constant built from `MAILBOX_ACTION_TYPES` or `INBOX`), and the result depends on which module loads first (server, CLI, test). Fix: keep the expiry in the setter's transaction, but inject it. (1) `SettingsDeps` gets a required field `expireReady: (trx, ctx, filter: ExpireFilter, opts) => Promise<{ id: string; emailId: string; type: ActionType }[]>`. Because the field is required, typecheck stops every caller (the CLI now, S5 later) that forgets it. This answers the fixer's reason for the edge. (2) `config/service.ts` uses only `import type { ExpireFilter }` from `actions` (type imports are erased, so there is no runtime edge). (3) Move `MAILBOX_ACTION_TYPES` and `MailboxActionType` to `packages/core` (pure), and let `actions` re-export them. (4) D16: "one new edge `config → audit`; the settings service gets `expireReady` as a dependency (no `config → actions` edge)". Stage 14.1 Files and Interfaces: the same text. Stage 14.2: the script passes `expireReady` from the `actions` index. Stage 18 `modules.md`: also draw the existing edges `mail → config` and `mail → audit`. Alternative: move the `insertDefaultSettings` call from `mail/connect.ts` into the `mailbox:connect` script. This is a bigger change to S1a code, so it is not my default.

- [RM2] stage 1 steps 6b, 7, 9 and 1.2 (the open part of M3; weak spot 1) — the skip branch still expunges in INBOX, and one report field has no meaning in that branch. Why: when step 6b sees other `\Deleted` INBOX mail, it skips the INBOX expunge, but step 9 still "delete[s] the INBOX copy (`messageDelete` with UID EXPUNGE …)". That is a `UID EXPUNGE` in INBOX while the user's `\Deleted` mail is there. On a server that ignores the UID set (the case that `otherDeletedKept` false shows, and the case that M3 is about), this expunges the user's mail. Also, the original probe mail still holds its UID in step 7, so `moveBack.sameAsOriginal` measures nothing, and the 1.2 rule for M4 has no input. Test 3 cannot find this, because GreenMail obeys `UID EXPUNGE`. Fix: (1) One rule for every INBOX expunge (step 6b and both INBOX deletes of step 9): run it only when `expunge.otherDeletedKept` is true and a `search({ deleted: true })` in INBOX just before it returns no UID except the probe's own. Else skip it, and add a note with the probe subject and the UID that stays. (2) In the skip branch, set `moveBack.sameAsOriginal` to null with the note `not measured: the original probe mail was not expunged`. (3) In 1.2: when `inboxExpungeSkipped` is true, the user empties the deleted mail in webmail (or accepts the gap) and runs the probe again before checkpoint 1, because the M4 rule needs `sameAsOriginal`. (4) In test 3, expect `cleanup.probeMailDeleted` false and the notes to name the INBOX probe mails. The test then deletes them itself.

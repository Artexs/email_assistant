## Findings (blocker, major, minor, question; in that order)

- [B1] stage 9 step 9.1 — `ensureMoved` expunges the only copy of a mail when `from === to`. Why: a reverse move uses `from = email.folder`, `to = INBOX`. `email.folder` is INBOX when the sync marked the mail returned before the committer claimed the reverse. Example: the committer's reverse IMAP move succeeds, the process stops before the commit, the next sync's below-cursor check sets `folder = INBOX`, and the stale claim comes back 10 min later. A user drag-back while the reverse waits (soft-error retry) gives the same state. Then both `locateMessage` calls find the same message, so the "target and source" branch calls `deleteMessage(INBOX, uid)`. The sentence "a move whose `email.folder` already equals the target … is the target only case" states an outcome but the algorithm does not give it. Test (9) uses an impossible fixture (`folder = AI/Info` with `returned_at` set: `markEmailReturned` sets both together), so it never reaches `from === to`. Fix: in 9.1 Decisions put as the first rule: "`from === to` → locate in `to` only; found → `{ uid, movedNow: false, leftoverDeleted: false }`; not found → null. Never call `deleteMessage` when `from === to`." Change test (9) so the row has `folder = INBOX`, `uid = inbox_uid` and `returned_at` set, and assert `fake.calls` has no `deleteMessage` and no `moveMessage` and that the INBOX still holds the mail. Add a test: crash after the reverse IMAP move, `syncMailbox` with the below-cursor check, then `applyAction` again. Expect the mail in INBOX, with no delete.

- [B2] stage 9 step 9.1 (and stage 5.1 `locateMessage`) — the "target and source" branch deletes a second identical copy. Why: `sameMailIdentity` cannot tell two copies with the same `Message-ID` and hash apart, and `locateMessage` returns the first match in a folder. Case A: mail #1 sits in `AI/Spam`, the user copies it back (or the server delivers it twice), and the sync stores #2 and triages it as `spam` (a done-when item). #2's move then runs `ensureMoved(INBOX → AI/Spam)`. The target locate finds #1's message and the source locate finds #2, so the branch calls `deleteMessage(INBOX, #2)`. That is an EXPUNGE, not a move to Kosz: the copy is gone. Stage 16 step 9 builds exactly this case on GreenMail. Case B: Undo of #1 while #2 is in INBOX. The target locate in INBOX finds #2, so the branch deletes #1 from `AI/Spam`, and both rows then point to one message. Fix: (a) give `locateMessage` an `excludeUids: ReadonlySet<number>` option. The committer fills it from a new mail-repo query `listFolderUids(db, ctx, mailboxId, folder, { exceptEmailId, messageId, contentHash })`, which returns the UIDs that other rows of the same identity hold in that folder (from `findCopies` plus `uid`). (b) Before the D5 "both" branch deletes the source, the target copy must not belong to another row. If it does, run the "source only" move. (c) Add tests to stage 9: case A (the second copy is moved and not deleted, so the target holds two copies) and case B (Undo of #1 while #2 is in INBOX moves #1 back, so INBOX holds two copies). Add one line to D5: "a leftover is only a target copy that no other `emails` row holds".

- [M1] stage 4 step 4.1 — the plan does not name two imapflow traps. Why (`lib/commands/move.js`, `expunge.js`): (a) when the server has no MOVE, `messageMove` falls back to `messageCopy` and then `messageDelete`, and it calls `messageDelete` even when the COPY returned `false`. The result is mail loss. (b) `messageCopy`, `messageMove` and `messageDelete` catch server errors and return `false`, they do not throw. `messageDelete` also returns `false` when the `UID EXPUNGE` fails after `\Deleted` was set. The stage 4 `deleteMessage` and COPY-path text returns `true` / success without a check of the `messageDelete` result. Fix: add to 4.1 Decisions: "Call `messageMove` only when the live `client.capabilities.has('MOVE')` is true and `forceCopyMove` is false. Never use its built-in fallback. The COPY path and `deleteMessage` check the live `client.capabilities.has('UIDPLUS')`, not the stored capabilities. Every `false` from `messageCopy`, `messageMove`, `messageFlagsAdd` or `messageDelete` is a `HardError` with its own message (`copy refused`, `move refused`, `flag store refused`, `expunge refused`). `messageDelete` sets `\Deleted` itself: do not call `messageFlagsAdd(\Deleted)` before it." Add a unit test with a stub `ImapFlow` that returns `false` from `messageDelete` → `HardError`.

- [M2] stages 5, 6, 9 — a message with the `\Deleted` flag counts as "present". Why: when `UID EXPUNGE` fails after the STORE (M1), or another client flags a mail `\Deleted` without an expunge, the source copy stays in INBOX at `inbox_uid`. Then `locateMessage` finds it (D5 "both" → a second delete try, harmless) and the stage 6 below-cursor check finds it, so `markEmailReturned` runs and stage 11 writes a false `imap_move` feedback row and sets the move `undone`. Fix: `locateMessage` and `matchReturned` skip metas whose `flags` contain `\Deleted`. `fetchByUidsIn` already returns `FolderMessageMeta` with flags, so `matchReturned` must take `FolderMessageMeta[]`. Add one test each: a `\Deleted` copy at `inbox_uid` is not a return, and `locateMessage` returns null for a folder that holds only a `\Deleted` copy.

- [M3] stage 1 step 1.1 — the probe cannot detect the failure that it checks. Why: step 6 counts the non-deleted INBOX mail of 2 days before and after `UID EXPUNGE <uid>`. A server that ignores the UID set and sends a plain EXPUNGE also removes only `\Deleted` mail, so the count is the same: `after = before − 1` passes on a non-compliant server. Interia already breaks RFC 3501 on UIDs, so this case is real, and then every S3 move would expunge the user's own `\Deleted` mail. The count is also unstable: new mail that arrives during the probe breaks `after = before − 1` and gives a false "stop". Fix: APPEND two probe mails (A and B) to the probe folder, set `\Deleted` on both, run `UID EXPUNGE <A>`, and check that B is still there (`expunge.otherDeletedKept: boolean`). Run this test only in the probe folder, never in INBOX. Before any expunge in INBOX, run `search({ deleted: true })`. If it returns a UID that is not the probe's, skip the INBOX expunge and report `inboxOtherDeleted: n`. Replace `otherMailCount` with these fields, and change the 1.2 rule to "`otherDeletedKept` false → stop".

- [M4] stage 1 step 1.2 + D4 (stage 6) — the outcome `moveBack.sameAsOriginal` has no consequence. Why: D4 relies on "a fresh copy of a mail always gets a new INBOX UID above the cursor". Interia keeps the UID on a move, maybe because its UIDs are global per message. If a COPY back to INBOX also keeps the old UID (probe step 7 measures this), then a user copy back lands at `inbox_uid` below the cursor. D4 then marks it returned, writes a false `imap_move` row, and the copy in `AI/*` loses its row. The S1a "second copy" path never sees it either. Fix: in 1.2 add "`moveBack.sameAsOriginal` true → stage 6 does a folder check on each hit". Gone → `markEmailReturned`. Add a stage 6 test for each branch.

- [M5] stage 5 step 5.1 — the `no_size` identity mode compares the `Date` header with INTERNALDATE. Why: `MailIdentity.date` is always null (`locateKeyOf` sets `date: null`, and no column stores the `Date` header), so `no_size` compares the meta's ENVELOPE date against `received_at` (INTERNALDATE). The result is that moves fail as `mail_not_found`, D4 never matches, and the S1a check treats every second copy as returned. Remove the unused `date` field from `MailIdentity`. Fix the `sync-rules.test.ts` cases to match.

- [M7] stage 8 step 8.1 + stage 7 `ClaimedAction` — "pass the row's values" for `moved_at` is impossible. - [M8] stage 11 + stage 10 — a race between the returned job and the Undo tap writes two feedback rows and feeds B1.

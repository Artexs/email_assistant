    ```ts
    // move.ts
    export interface EnsureResult { uid: number; movedNow: boolean; leftoverDeleted: boolean }
    export interface EnsureExclude { from: ReadonlySet<number>; to: ReadonlySet<number> } // UIDs that other emails rows of the same identity hold in each folder

    export type ApplyOutcome = … | { kind: "failed"; reason: "mail_not_found" | "hard_error" | "no_provider" | "bad_payload" };
    ```

  - Decisions:
    - `ensureMoved`, rule 1 (B1): when `from === to` → `target = locateMessage(provider, to, { …key, hintUid: hints.toUid }, { excludeUids: exclude.to })`; found → `{ uid: target.uid, movedNow: false, leftoverDeleted: false }`; not found → null. Never call `deleteMessage` or `moveMessage` when `from === to`. Why: a reverse move uses `from = email.folder`, and `email.folder` is INBOX when the sync marked the mail returned before the committer claimed the reverse; then both locates find the same message, and the "both" branch would expunge the only copy.
    - `ensureMoved`, `from !== to`: `target = locateMessage(provider, to, { …key, hintUid: hints.toUid }, { excludeUids: exclude.to })`; `source = locateMessage(provider, from, { …key, hintUid: hints.fromUid }, { excludeUids: exclude.from })`. Cases: target and source → `deleteMessage(from, source.uid)` (a leftover of a COPY before a crash; `false` is fine: it went away in between) → `{ uid: target.uid, movedNow: false, leftoverDeleted: true }`; target only → `{ uid: target.uid, movedNow: false, leftoverDeleted: false }`; source only → `r = moveMessage(from, source.uid, to)`; `uid = r.newUid ?? (await locateMessage(provider, to, { …key, hintUid: source.uid }, { excludeUids: exclude.to }))?.uid ?? source.uid` (the last fallback keeps the source UID as a hint; at Interia `newUid` comes from COPYUID (checkpoint 1), so the fallback is rare) → `{ uid, movedNow: true, leftoverDeleted: false }`; neither → null. `moveMessage` throwing `MailNotFoundError` (the mail left the source between the locate and the move) → one retry of the whole ensure inside `ensureMoved` (a user move in that second is rare); a second miss → null.
    - Ownership rule (B2, D5 "a leftover is only a target copy that no other `emails` row holds"): the target locate leaves out `exclude.to`, so a target copy that another row holds is never found, and the "both" branch then cannot run: the ensure takes the "source only" branch and moves this row's copy. Example A: mail #1 sits in `AI/Spam`, an identical #2 arrives in INBOX and is triaged `spam`; #2's move must not delete #2 from INBOX because #1 is in `AI/Spam`. Example B (9.1b): Undo of #1 while #2 is in INBOX must move #1 back and not delete it.
    - `exclude` comes from `listFolderUids` (mail index, stage 5.2): `exclude.from = listFolderUids(db, ctx, mailboxId, from, { exceptEmailId: email.id, messageId: email.message_id_header, contentHash: email.content_hash })`, `exclude.to` likewise for `to`. `applyAction` reads both before the ensure (two small queries, no lock).
    - Hints: original move: `fromUid = email.uid`, `toUid = email.uid` (a webmail move at Interia keeps the UID: a hit is free; after a system COPY, at Interia and on an RFC server, the miss costs one FETCH and the search runs).
    - Folders: the original target is `folders.resolve(payload.folder)` (a `FolderKey`; an unknown key → `failed` / `bad_payload`, audit `action.failed`, and the stage 12 notice (every failure except an original `mail_not_found` notifies): the planner never writes one, so this is a guard). `FolderResolver.resolve`: cache per run; `path = provider.ensureFolder(folderMap[key] ?? AI_FOLDER_NAMES[key])`; when `path !== folderMap[key]` → own transaction `setFolderMapEntry` + audit `mailbox.folder_created` (`data: { mailbox_id, folder_key }`, no path in the audit: the path is the server's, not mail data, but keys are enough) and update the in-memory map. The source of an original move is `email.folder` (INBOX in every planned case; the ensure also works from another folder).
    - After the ensure: `deps.beforeCommit?.()`; then one transaction: `updateEmailLocation(emailId, { folder: to, uid, inboxUid: to === INBOX ? uid : undefined, movedAt: to === INBOX ? null : now })`; `finishAction(applied, providerResult: { uid, moved_now, leftover_deleted })` (false → `lost`: the IMAP change stays, which is harmless because the next claimer locates the mail in the target); audit `action.applied` (`actionId`, `emailId`, `data: { action_type: "move", mailbox_id, folder_key, reverse, moved_now, leftover_deleted }`).
    - `ensureMoved` null → `failed` / `mail_not_found` (one transaction, audit with `actionId` and `emailId`, no notice for an original, D7).
    - Error mapping as in stage 8 (soft → retry without a count; hard → count; auth → `auth_error`). A `HardError("no UIDPLUS")` from `deleteMessage` or the COPY path counts as hard and ends in `failed` after 3 tries with a notice: it can only happen when the stored capabilities lie (the policy keeps moves `log only` without MOVE and UIDPLUS). `HardError("expunge refused")` after a COPY counts as hard; the next try finds the target copy and the `\Deleted` source is skipped by the locate (stage 5), so it ends `applied`.

## Findings

### 1. The attachment line reaches Telegram with no per-user consent check — medium

- **Where:** `apps/server/src/modules/mail/attachment-facts.ts:11-22` (reads only the flag `attachment_line`); callers `apps/server/src/modules/channels/notices/urgent.ts:57` and `apps/server/src/modules/reports/digest.ts:123`.
- **What is wrong:** Attachment names are a new kind of mail data in Telegram. The consent version was bumped, but the gate blocks only NEW chat links. A chat linked under an older consent would receive file names if the flag turned on. `docs/owner-decisions.md` (2026-11-15 · "The attachment line in Telegram stays off for orgs with linked chats…") keeps the flag off by hand. Open-loop data already has the right gate (`apps/server/src/modules/channels/consent.ts`, `loopConsentOf`, `consentCovers`); the attachment line does not use it.
- **Rule broken:** vision.md: "Privacy and GDPR are product features: encrypted mailbox secrets, tenant isolation, retention limits, EU location before any outside user's mail. Telegram never gets raw mail bodies." A flag that is safe only while nobody turns it on is a hand rule, not a guard.
- **Fix:** Resolve the consent version per recipient (as `loopConsentOf` does) and give a user without it the notice with no attachment line.
- **OWNER:** no (no user feature is dropped; the flag stays off until the fix lands).

### 2. The escalation cascade is not shipped but lives in the production tree — medium

- **Where:** `apps/server/src/modules/triage/classifier.ts:113-141` (`escalateEmail`), `apps/server/src/modules/triage/prompts/escalation-v1.ts` (12 lines), `packages/core/src/triage/escalation.ts` (57), `apps/server/src/modules/triage/eval-escalation.ts` (167), the role `escalation` in `packages/core/src/llm-roles.ts` and `apps/server/src/platform/config.ts:509`, the keys `LLM_ESCALATION_*` in `.env.example:51-52`, and the `--escalate` branches in `apps/server/src/modules/triage/eval.ts`.
- **What is wrong:** Stage 13 said "no ship" ($3.96 per mailbox per month against $3.00; decision "F109 escalation cascade: no ship by the cost rule"). Triage never calls the role (`docs/capabilities/triage.md` rule 19). About 650 lines, a config role and two env keys stay as an unreachable option.
- **Rule broken:** vision.md: "Each automatic action has an ON/OFF switch and must pass the go/no-go bar for its category first." Code that failed its bar and has no switch is dead weight. Styleguide "Avoid": central, unused abstractions; a new role needs a prompt and a gate that a run uses.
- **Fix:** Drop `escalateEmail`, `escalation-v1`, `shouldEscalate`, the role and the keys; keep the eval report and the decision text in `evals/results/`. A cheaper trigger later is a new ticket from git history.
- **OWNER:** no (not a user feature; the owner decision "no ship" stays). Listed as a drop-candidate.

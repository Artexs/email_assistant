# Digest and notices

> Checked against the code at `05702e0c`, 2026-11-19.

## What it does now

Every message that the system sends to a person goes through Telegram; with the flag `report_mail` the digest and the trust reports can also be appended into the member's own INBOX (rule 3a). A user links one private chat to their account with a one-time token. After that, the digest job queues a digest at each of the member's times (default `08:00` and `16:00`, in the organization time zone), and the notice job queues notices for urgent mail, mailbox and sync problems, approval requests, send results, sends held by a send limit, delegation answers and, during an LLM pause, mail of VIP and whitelisted senders that waits for triage. Both write rows to the table `outbox`. A row holds the facts of the message (a view), not its text. The outbox sender renders the text when it sends. It sends at most 3 messages per user per tick, waits through the quiet hours of the member (default `22:00`–`07:00`; with the flag `user_quiet_hours` the member's own hours, rule 3a) for every kind except the digest, and fails a row that is older than 24 h. The user answers with the commands `/digest`, `/status`, `/pause`, `/resume`, `/review` and `/help`, and with buttons under the messages. The operator gets a separate set of plain messages in one chat (`OPERATOR_TELEGRAM_CHAT_ID`). All of this runs only when `TELEGRAM_BOT_TOKEN` is set; the operator notices run in every case.

## Rules

1. **Chat linking.** `bun run telegram:link` (or `POST /api/channels/telegram/link` from the web panel) makes a one-time token for one member. The web route needs the consent body `{ consentVersion }` with the current `TELEGRAM_CONSENT_VERSION` (packages/core): no or a bad body is 400, an old version is 409 `telegram_consent_outdated`, and neither makes a token. One transaction writes the audit row `web.telegram_consent` (actor = the member, `data` = `via`, `version`) and the token. The panel shows the consent text (what goes to Telegram) and a tick before it enables the link button; the tick resets when the chat gets linked or unlinked. With the flag `telegram_minimal` on, the body also takes `detail` (`full` or `minimal`; a bad value is 400; absent = the stored level stays (the panel sends no `detail` under the lock unless the member picked `minimal`), and the column default is `minimal`, so a new member gets `minimal`; an old panel bundle that sends no `detail` never lowers a member from `full`): the transaction stores it on the membership (`memberships.telegram_detail`) with the consent row and the token, and writes the audit row `member.telegram_detail_changed` (`data` = `{ detail }` only) when the stored value changes; `full` while the owner locks `minimal` is 409 `telegram_detail_locked` and makes no consent row and no token; the lock is checked first (as in `PATCH /api/me/telegram-detail`), then the consent, and again inside the transaction with the organization row read `FOR SHARE`, so a lock that the owner sets meanwhile is not passed. With the flag off the route ignores `detail`, also a bad value, and keeps its old behaviour. The CLI needs no consent (an operator tool) and keeps the stored level, and a chat that was linked before the consent keeps its link. **Consent gate for loop data (F116 stage 17).** `consentVersionsOf(db, ctx, userIds)` (channels) gives the version of the newest `web.telegram_consent` row of each user in the org (no row or no version: null). `consentCovers(version, since)` (packages/core) is true when the version is not null and `>= since`; versions are ISO dates with an optional `.N` suffix. `OPEN_LOOPS_CONSENT_SINCE` is the first version whose text names loop data. A user who is not covered gets no loop text, address or ask in a Telegram message: only counts, a fixed line and the panel link (the senders of stages 11, 18 and 19 apply it). `POST /api/telegram/consent` `{ version }` (any member, own user from the session): the current version writes one `web.telegram_consent` row and answers 200 `{ version }`; any other version is 409 `telegram_consent_outdated`; no token is made. The token: 32 random bytes, valid 15 minutes, stored as a SHA-256 hash only. A new token makes the older unused tokens of the member invalid. The user opens `t.me/<bot>?start=<token>`. The bot stores the chat in `chat_links` (one chat per member, one member per chat) and answers with the help text. A chat that was linked to another member moves: the old link goes and gets the audit row `chat.unlinked` (`reason_code` `chat_moved`). A used token answers "This link was used already. Ask for a new link." (or "This chat is linked already" for a linked chat); an expired token answers "This link has expired (a link works for 15 minutes). Ask for a new link."; an unknown token gets no reply (a linked chat gets the help text). `bun run telegram:unlink` and `DELETE /api/channels/telegram/link` remove a link (audit row `chat.unlinked`). The bot rules for the chat guard and the token text are in `docs/architecture.md` §6.2. The three Telegram tools follow the CLI standard (`docs/cli.md`): a bad argument exits 2 before any config or call; `telegram:check` and `telegram:link` exit 3 with `unreachable: SoftError` when the Bot API does not answer (`checkBot` maps grammY's `HttpError` to a `SoftError` with no cause, so the token never reaches the output); `telegram:unlink` exits 3 when the database does not answer.
2. **The update router** (`createTelegramBot`): chat guard (private chats of people only), `/start` linking, link guard (an update from an unlinked chat gets no reply), commands, buttons, then any other message of a linked chat. A text that is a Telegram reply to a sent `reply_prompt` row or review card of this user goes to the text handler (one line of instruction for Redraft, F115 stage 13); every other message gets the help text. The tenant comes from the link, never from the update.
3. **The digest job.** `channels.digest` runs every minute (second 5) and visits every linked chat of an organization that is not `suspended`. Per member it reads `memberships.digest_times` (at most 6 times, `HH:MM`), the organization time zone and the last digest slot. It queues the newest slot that is due: not older than 6 hours (`DIGEST_LATE_MS`), not in the future, and after the last slot of the member or the link time. Earlier missed slots are skipped, so a server that is back within 6 hours sends one digest, marked "(late)" when it is more than 10 minutes late. A slot key is the local wall-clock string `YYYY-MM-DDTHH:MM`, so a daylight-saving change gives no double and no lost digest. One digest row (`digests`) and one outbox row go in one transaction per member and slot; the outbox row is marked `sent` and the digest row gets `sent_at` in the sender's transaction.
4. **The digest message** (`renderDigestWithBrief`, one message of at most 4096 characters and at most 15 lines). Header (`📬 Digest HH:MM · <day>`), the count line, one line per mailbox (last sync, `paused`, `login error`, `server not allowed`), the section `NEEDS ACTION` (`urgent`, `needs_reply`, `delegation`, `unsure`), the section `OTHER MAIL` (`info`, `notification`, `spam`), then footer lines: the LLM pause line (first, only with the flag `llm_pause_line`, rule 9), `+N more`, mail skipped as older than 7 days (`too_old`), mail skipped after an account pause (`suspended_backlog`), mail waiting for triage, open and overdue delegations, the reply line (`📝 n replies ready` / `📝 Szkice odpowiedzi do przejrzenia: n`, owners only, the flag `reply_drafts` on, the count of open reply sends that the DB facts do not close; no button; F115 stage 12; the button ✍️ "Draft reply" is on an urgent notice and, as `✍️ n`, on a digest row, only for an owner whose consent covers reply data and a mail that `draftableMails` finds: F115 stage 13), "Shadow mode: the system changed nothing in your mailbox.", and, last and only with the flag `handled_share`, the handled-share line `🤖 Handled in the last 7 days: <rate>` (`handledShare` of the last 7 days of real mail, all mailboxes; it is left out when no mail was triaged, or when every mailbox is in shadow mode and nothing was handled) Each item line shows the category, the sender, the subject, the AI text and what the system did or would do. Buttons: per item `✅ n` (the category is right), `✏️ n` (pick another category) and, while an Undo is possible, `↩️ n`, two items per row. The period of a digest starts at the end of the last sent digest (a failed digest does not move it), at most 7 days back; the first digest looks back 24 h before the link. The digest holds no mail bodies (ADR 0005). **The brief (F116, flag `open_loops`).** The first digest of a member's day (the slot date decides, `isFirstDigestOfDay`) puts the block `📌 NEEDS YOU TODAY` after the header line and before the form above: the sections 🔴 Urgent (urgent mail of the window with no own answer; these rows leave the normal list and its feedback buttons), ✍️ Waiting on you, ⏳ Waiting on others (loops and open delegations due by the end of the local day), 🤝 Promised and ⌛ Ended, each with at most 5 lines and a "+n more in the panel" line (`loopSections`, `renderBrief` in `packages/core/src/loops/brief.ts`; the texts are in `packages/core/src/texts/brief.ts`, en and pl). The block is cut from the bottom, ⌛ first, when the message would pass 4096 characters. A later digest of the day has no block; its footer gets the count line `🔁 Open loops: 3 waiting, 1 promise due` (counts only, also for a member without consent). A member whose Telegram consent does not cover open-loop data (rule 14, `open-loops.md` rule 10) sees counts and a panel link instead of the lines of ⏳, 🤝 and ⌛. The footer's delegation line is left out of the first digest of the day only when a ⏳ line already names a delegation; otherwise it stays (a delegation due later, or a member without consent, would see none). The digest view stores the ids of the loops that the text names (`view.loopIds`) and the line numbers of the buttons (`lineOf`), so the Sent switch off and the erase can find and blank the digest that holds a loop text. `/digest` builds the same message for the period up to now and sends it at once, with no `digests` row and no outbox row, and it has no brief and no count line. **Why lines (F110, flag `why_lines`):** the `💬` line of an item ends with ` · <confidence percent>` or the sender rule (`rule: VIP sender`), and a delegation would-do phrase names the delegate's competence tags ([trust.md](trust.md) rule 17). **Spam review line (F110, flag `spam_review_line`):** a footer line after the shadow line, `🗑 <n> went to spam · review: <panel link>` (shadow: `would have gone to spam`), with a count of the window and a fixed link; none when `n` is 0.
5. **The notice job.** `channels.notifier` runs every 15 s: `detectNotices`, then the outbox sender. Per organization (a failure of one does not stop the next), the detectors run in this order: urgent, action failed, auth error, host blocked, sent missing, sync, approval, approval set, send result, follow-up closed (the card edit of a follow-up whose loop closed), send held, delegation answered, weekly report, not triaged (rule 12). Each one finds its event, builds a view and calls `queueNotice`; the dedup key `(org, user, dedup_key)` keeps one row per event and member. The two trust kinds are not queued by a detector: the end of a history check, the tripwire and the re-gate queue them in their own transactions (`queueTrustNotice`, `notices/trust.ts`; the `queuedBy` map of the registry names them). 6. **Notices (S2)** (moved from `docs/architecture.md` §8): urgent mail goes to every linked member (24 h look-back, one notice per mail). `auth_error`, `host_blocked`, `sent_missing`, sync late and sync works again go to linked owners only. **Suspicious-mail warning (F109, flag `suspicious_mail`).** With the flag on, the urgent notice and each digest item show one line after the AI line: `⚠ Suspicious: <reasons>` (Polish `⚠ Podejrzana wiadomość: <powody>`), the reasons as fixed words (for example `look-alike domain`, `risky attachment`) in the order of the codes, from the newest `triage_results` row of the mail ([triage.md](triage.md) rule 17). A flagged `delegation` mail shows `→ no draft: suspicious mail` instead of the would-do line. The digest prints that line only for a flagged `delegation` item without an original `create_draft` action, so a flagged item can show two lines about the suspicion in a row (the warning, then the no-draft line); accepted. The urgent view holds the codes in `suspicious` (optional on read: a view queued before F109 renders as before); with the flag off the field is `[]`. The line holds fixed phrases only, never mail text. The reader `suspiciousReasonsOf` ignores the flag (a draft block holds with the flag off). **Attachment line (F109, flag `attachment_line`).** With the flag on, the urgent notice and each digest item show `📎 <n>: <name> (<size>), …` after the subject line (at most 3 names, then `+<k> more`, Polish `+<k> więcej`; sizes `B`, `kB`, `MB`, Polish decimal comma). Inline and `text/calendar` parts are left out; a mail with nothing to show has no line. After retention (list `[]`, count stays) the line is `📎 <n>`. The urgent view holds the optional field `attachments` (at most 3 parts and the count), written only with the flag on and a line to show, so a view queued earlier renders as before. Names come from the mail: links in a name become `[link]`, line breaks and invisible direction characters go, and the name is cut to 40 characters. When a part has no name, the line shows its MIME type, so the consent text says "names (or file types) and sizes" and its version was `2026-11-15` (F109); F116 stage 17 moved it to `2026-11-15.2` with a sentence about open loops. After retention the count also includes inline and calendar parts, so a mail with one inline part shows `📎 1` once its list is cleared. The stored list is cut at 20 parts, so inline parts beyond 20 count as attachments. A mail over the size limit (`parts_known` false) gets no line. Never the file or its content. Per the owner decision of 2026-11-15 the flag `attachment_line` stays off for organizations with linked chats until the consent can be asked again ([code-patterns.md](../code-patterns.md) § The consent version). The suspicious warning line did not bump the consent version: it holds fixed phrases chosen from our own codes, no mail-derived data. Rollback: turn the flag `attachment_line` off and let the pending rows drain first, because the code before F109 refuses an urgent view with the field `attachments`. **Why line (F110 stage 16, flag `why_lines`).** With the flag on, the `💬` line of each digest item and of the urgent notice ends with ` · <n>%` (the model confidence, rounded down to a multiple of 5; 0.999 reads 95%) or, when a sender rule shaped the result, ` · rule: VIP sender` / `whitelisted sender` / `blocked sender` (Polish `reguła: nadawca VIP` / `nadawca z listy dozwolonych` / `nadawca z listy blokowanych`); a rule replaces the percent. A result that no model made (reason `blocklist`, `triage_error`, `llm_blocked`) and an `unsure` item (its AI text already holds the guess percent) get no percent; a zero percent is not shown. An item with no AI text gets the mark on its own line `💬 <mark>`. The would-do phrase of a delegation draft names the competence tags of its delegate next to the name: `will draft a delegation to Anna Nowak (skills: finance, legal, hr); waits for your approval` (Polish `przygotować szkic zlecenia (wykonawca Anna Nowak; kompetencje: finanse, prawo)`); at most 3 tags, 30 characters each, a blank tag is left out first; only a delegation draft, never a reminder, a question or a reverse draft. The tags are the organization's own words (user config), so the line needs no consent bump. With the flag off the phrase is the one of today. A digest item with an empty AI text prints no `💬` line, and an urgent notice with an empty AI text prints `💬 ` as before (without a mark); with a mark both print the mark line. Accepted: the marks and tags make the lines longer, and `renderDigestWithBrief` drops items until the text fits 4096 characters, so with the longest fields the flag on lists up to 3 items fewer than the flag off (en: 7 against 10 of 15 delegation items; with ordinary fields all 15 stay). The rule comes from `triage_results.fields.rule` (`blocklist`, `whitelist`, `vip` or `null`; written by every triage result, no pattern, an old row reads null). The urgent view holds the optional keys `confidence` and `rule`, written only with the flag on, so a view queued earlier renders as before; the digest items get the keys only with the flag on. The Activity page shows the rule as a badge on the row and a line in the panel (`ActivityItem.rule`, null with the flag off). Rollback: turn the flag off and let pending urgent rows drain first, because the code before F110 stage 16 refuses an urgent view with the new keys. **Spam review line (F110 stage 17, flag `spam_review_line`).** With the flag on, the digest footer names how many mails went to the spam folder since the last digest: `🗑 <n> went to spam · review: <WEB_BASE_URL>/activity?category=spam` (Polish `🗑 <n> wiadomości trafiło do spamu · sprawdź: <url>`, the verb follows the number), or `… · check them in the panel` / `sprawdź w panelu` when `WEB_BASE_URL` is unset. The count is the mails of the organization whose original `move` to `ai_spam` became `applied` after the digest period start (at most 24 h before its end, as far as the default range of the Activity page) up to the end; a mail counts once, and an undone move, a reverse action and a move to another folder do not count. A mail that stayed in the spam folder has no move, so it is not counted. For a mailbox in shadow mode the line counts the `logged` moves instead and reads `🗑 <n> would have gone to spam` (Polish `trafiłoby do spamu`); an organization with both kinds gets both lines. No line when the count is 0 or the flag is off. The line comes after the shadow line and before the handled share. It does not count against `DIGEST_MAX_LINES` (that limit counts item rows only, as for the other footer lines); when the text is over 4096 characters `renderDigestWithBrief` drops this line first, before any item row. The Activity page already reads `?category=spam`, so the link needs no panel change. The line holds a count and a fixed URL only, so it needs no consent bump. The `/digest` reply links to the panel too; the scheduled digest and `/digest` read the base URL from `WEB_BASE_URL`.

   3a. **Quiet hours per member (F110 stage 18).** `memberships.quiet_start` and `quiet_end` (`HH:MM`; both null means the default `22:00`–`07:00`; equal start and end means no quiet hours; a range that crosses midnight works as the default; the window is at most 18 hours: the route refuses a longer one with `400 quiet_too_long`, so a hold plus a retry stays below the 24 h life of an outbox row). The sender holds a row until `max(quietEnd, now + 1 min)`; `quietEnd` is the first instant after `now` at which the wall clock reads the end time (the second one in the autumn hour that repeats, the instant of the change when the end time falls in the spring gap). The clock stays the organization time zone: there is no per-user zone. With the flag `user_quiet_hours` on for the organization, the sender reads the hours of the users of one claimed batch with one query (`listQuietHoursOf`), and holds a row by the hours of its user (`isQuietTime`, `quietEnd` and `lateMin` take an optional `QuietHours`; `quietHoursOf` turns the two columns into one value). With the flag off every member has the default hours. The digest and `approval_edit` are never held. `/status` shows the own hours (`Quiet hours: 23:00–06:00 (notices wait until 06:00)`, or `none` when start equals end). The member sets the hours with `PATCH /api/me/notify` (`{ quietStart, quietEnd }`; both times, or both `null` to reset; the Settings card "Quiet hours"), which writes the audit event `member.notify_changed` with the changed key names (`quiet_start`, `quiet_end`; never a value). The F114 check `slo_urgent_latency` (`operator/slo-checks.ts`) takes the hours of the user of the sent urgent row that gave `noticeAt`; with no sent row it computes the wait for the user of each pending urgent row and takes the largest (each value leaves out that user's own quiet hours, so a user in quiet hours cannot hide a user who really waits); with the flag off, or no row, it uses the default (`UrgentCandidate.quiet`). The metric M5 keeps the default hours (a measure, not an alert). The same route sets the report channel (`{ reportChannel: telegram | mail | both | null, reportMailboxId? }`, flag `report_mail`): `mail` or `both` needs an `active` mailbox of the organization (the one asked for, else the oldest; else `409 no_mailbox`); `telegram` or `both` without a linked chat is allowed and the card warns. **Mail rows (F110 stage 19, flag `report_mail`).** With the flag on, the four report kinds `digest`, `weekly_report`, `trust_report_ready` and `autonomy_paused` are queued as outbox rows with `channel = 'mail'` for a member whose channel is `mail` or `both` and who has a report mailbox. `both` gives the Telegram row and a mail row (dedup key `<Telegram key>:mail`, `mailbox_id` = the report mailbox, the same view); `mail` gives the mail row only, also for a member with no linked chat, and falls back to the Telegram row when the report mailbox is gone and a chat is linked; `telegram` gives no mail row. With the flag off no mail row is queued and a member with `mail` gets Telegram rows when linked. The digest job visits members with a chat or a mail channel; a member with no chat counts slots from the start of the membership and looks back 24 h from the first digest. The weekly report visits an organization with no linked chat for its mail members (the other detectors need a chat). `trust_report_ready` and `autonomy_paused` go to owners only. Every other kind (urgent, approvals, notices) stays on Telegram. The Telegram sender claims `channel = 'telegram'` rows only. **Report mail sender (F110 stage 20, flag `report_mail`).** The job `channels.report_mail` (`createReportMailSender`, every 15 s, scheduled in `start/jobs.ts` with or without the Telegram bot) claims `channel = 'mail'` rows and APPENDs each one into the INBOX of its mailbox (ADR 0022). It never sends: the port `ReportMailbox` (`report-mailbox.ts`) has only `append`, the IMAP adapter opens the mailbox through `openMailboxProvider` without an SMTP or Graph sender (an OAuth mailbox logs in with its access token), and the only address in a header is the mailbox address read from the mailbox row at send time, never text from a notice or a mail. The row always renders through the mail renderer (`renderNotice(kind, view, { channel: 'mail' })`): `digest`, `weekly_report`, `trust_report_ready` and `autonomy_paused` have one (the Telegram text with no buttons); any other kind with `channel = 'mail'` fails as `bad_view`. The message (`buildReportMail`, `packages/core/src/outgoing/report-mail.ts`): `multipart/alternative` (text and escaped HTML, UTF-8), `From` and `To` = `"Email assistant" <mailbox address>` (Polish `Asystent poczty`), `Subject` = `[Email assistant] <title>` (`[Asystent poczty] <title>`; the title is a fixed word per kind), `Message-ID` `<ea-report-<outbox id>@<mailbox domain>>`, header `X-EA-Action-Id` = the outbox id, `Date` = now, no flag on the message (it shows as new). A URL becomes a link in the HTML part only when it starts with `WEB_BASE_URL` (the next character ends the origin); every other URL stays escaped text. The sender checks, in this order, for each claimed row: the flag `report_mail` (off: the row waits 15 min with no attempt); the member's channel and report mailbox (back to `telegram`, or another mailbox: `failed` / `outdated`); quiet hours for every kind except the digest (as for Telegram rows, `quiet-gate.ts`); the render; then the mailbox status, read again right before the APPEND (`getMailbox`): not `active` (paused, `auth_error`, `host_blocked`) makes the row wait 15 min with no attempt and no login. The errors of the port: a refused login, a revoked OAuth grant or a blocked host waits 15 min (no attempt, and the other rows of the mailbox wait with it, so one login per mailbox per run); a network error backs off 30 s doubling to 15 min and counts an attempt, and the other rows of that mailbox in the run wait for the same time; a server `NO` fails the row at once as `append_refused` and holds the other rows of the mailbox for 15 min; another failure backs off, holds the mailbox for the same time and fails the row as `too_many_errors` after 5 attempts. A mail row older than 24 h becomes `failed` / `expired` at the start of each run (`expireOldMailOutbox`), so a mailbox that stays paused ends in expired rows, not in a late mail. After the APPEND the row is marked `sent` in one transaction (no Telegram message id; for a digest also `digests.sent_at`, so a mail-only member's next period starts at its end). At least once, with a check before a repeat: a crash after the APPEND and before the mark leaves the row `sending`; the next claim after 5 min counts an attempt (a row that keeps crashing its sender ends as `too_many_errors` at 5) and logs one `warn` line `outbox_mail_resent_after_stale`. A row that was tried before (`attempts > 0`, which includes a stale reclaim and a network timeout) is a retry: the adapter looks in the INBOX for the fixed Message-ID `<ea-report-<outbox id>@<mailbox domain>>` (`locateByMessageId`: a date search and a FETCH of the newest messages first, no header search) and appends nothing when it finds the message; the row ends `sent` (log `outbox_mail_found`). A failed search never leads to a blind APPEND. A user who deleted the first copy in the minutes between the two tries gets a second one. The mailbox that receives the mail and the report channel are the member's own choice (`PATCH /api/me/notify`); a member undoes the channel in Settings, and the message is an ordinary mail in the user's own INBOX that they can delete. The sync, the history backfill and the operator backfill skip a report mail (`isOwnReportMail`, [sync.md](sync.md) rule 9). Keep the flag `report_mail` off by default: the registry default stays `false`, and turning it on for an organization is a pilot step.

   3c. **The push channel (E9b F118 stages 07 and 08, flag `web_push`, default off).** A push row (`channel = 'push'`, one per live device, dedup key `<Telegram key>:push:<device id>`, `push_subscription_id`) holds the same view as the Telegram row. The job `channels.push` (`createPushSender`, `channels/push-sender.ts`, every 15 s, scheduled in `start/push.ts` when the three `VAPID_*` keys are set, with or without the Telegram bot) claims push rows and sends each as one Web Push message (RFC 8291 body, RFC 8292 token, `TTL` = 86,400 s minus the row age and never below 0, so a row held by quiet hours is not delivered after its 24 h life, `Urgency` high for the groups urgent and approvals, normal for updates, `Topic` from the row id). The body is `renderNotice(kind, view, { channel: 'push' })` plus the row id: exactly `{ v, id, kind, count, itemId, lang }` (`noticeFactsOf`, `packages/core/src/notices/facts.ts`); `itemId` is the action id of an approval or a send result, the set id of an approval set, the delegation id of an answer, else null (an urgent mail never sends its mail id). The order per row: older than 24 h → `failed` / `expired`; flag off → wait 15 min, no attempt; quiet hours (every push kind is held); the limit of 3 per user per run; the device must be live (a session that ended or expired removes the device and ends the row `failed` / `no_device`); the secret opens (a secret of another key VERSION keeps everything and waits 10 min with the error line `push_key_version_mismatch`, `docs/known-alerts.md`); the render (`bad_view`); the send. The answers: 201 → `sent` (`text` = the body, `last_success_at`); 404 or 410 → the device goes and its open rows end `no_device` (log `push_device_gone`: `no_device` is not a failure in the operator counts, so this line is the trace); 429 → `Retry-After` (at most 15 min; a 429 counts an attempt like a 5xx, so five 429s end the row `failed` / `too_many_errors`); 5xx or network → 30 s doubling to 15 min, `failed` / `too_many_errors` at 5; any other → `failed` / `push_refused` and the device keeps `last_error_code` `http_<status>`. At least once, as for mail rows (`outbox_push_resent_after_stale`). The production `fetch` is Bun's global one and honours `HTTPS_PROXY`: a proxy sees the push host, the token of 12 h for that service and the encrypted body. Rows of a suspended organization are not claimed. A route change to push or both writes push rows on the next tick for the events that the detectors still find (the urgent look-back is 24 h); a push row goes only to a device that was bound to a live session before the event (`LiveDevice.boundAt`), so a new or rebound device gets no burst. The push services are the sub-processor row `web-push` of the papers (active when `VAPID_PRIVATE_KEY` is set). **Readers of a Telegram key (stage 08b).** A push row has its own key, so each reader that finds an event by its Telegram key also matches `<key>:push:<device id>` (`dedupKeyOrPush`, `platform/db/outbox-keys.ts`; `starts_with`, not LIKE, so a `_` or `%` in a key is no wildcard). Push counts for: the card fail of a decided send (`failPendingCardsOfSend`: a `pending` push row of `approval:<send id>` ends `failed` / `answered_elsewhere` in the transaction of the decision; a `sending` push row is left: its tap opens the approvals page, which shows the decided state; the closed follow-up detector `listClosedFollowUpCards` also lists a follow-up whose only row is a pending push row); the "request seen" check of the expiry and of the resume (`requestSent`, `listUnseenApprovalSends`: a `sent` push row is a request that reached an owner, so the send ends `timeout`, not `not_seen`); the resume hook and the erase of one person's data (`noAwaitingApprovalSend`: the push row of a send that still waits stays); the `sync_ok` episodes (`listSentStaleEpisodes`: a `sent` push `sync_stale` row starts an episode, one entry per member and episode however many devices; a `sync_ok` push row closes it; the `sync_ok` goes through `queueNotice`, so it follows the route); the cancel of older pending notices (`cancelPendingOutbox` with `exceptDedupKey`: the Telegram row and the push rows of the kept key both stay; a `dedupPrefix` already matched both). Push counts by their kind alone for `lastRepliesReady` (any channel). Telegram only, on purpose: the card edits and the cards of a tap (`listCardsOfSend`, `getEditTarget`, `findApprovalCardOfTap`, `listDeliveredCardsOfExpiredFollowUps`: they need a Telegram message id), the review cards and the reply questions (`findReviewCards`, `hasReviewCardSince`, `findReplyPrompts`, `findReplyTargetOfMessage`: written with `only: 'telegram'`), the digest and report readers (kinds with no push group), `findOutboxByDedup` (taps and the weekly report), and the M5 metric and the urgent SLO (Q11). **Fallback to Telegram (D23).** A push row that ends `failed` / `no_device` (the session ended or expired, the push service said 404 or 410, the member removed the device, the device row is gone, or the stored secret does not open) queues the Telegram row of its event (`queueTelegramFallback`, `channels/push/fallback.ts`, called by `removeDevice` for each open row it ends and by the sender for a row with no device) when the member has a chat link and no Telegram row of the event exists (the dedup key keeps one). The row takes the kind, view, locale, mail, mailbox and queue time of the push row and the key without `:push:<device id>`; the Telegram sender renders it at send time. A row with a `loop_id` never falls back: an owner who has not given the loop consent gets the follow-up kind only by push, and a fallback would bypass the loop-consent gate (`splitByLoopConsent`). Only `no_device` falls back; `push_refused`, `expired` and `too_many_errors` do not. A member with no chat loses the notice for that device. **Rollback:** a build older than the push sender (`v0.2.x`) claims every due outbox row with no channel filter and then fails on the channel `push`, so its whole claim fails; turn `web_push` off and close the push rows before `deploy/rollback.sh` (`deploy/README.md` § Phone notices and Telegram detail → Roll back, step 5).

Mail whose `source_folder` is the spam folder of its mailbox is in the digest but gets no urgent notice (`detectUrgent`, `getJunkFolderPath`).
   - Check against the code: the `auth_error` view of an OAuth mailbox holds `oauth: { provider, reason }` (optional: a row queued before F117 has none and renders today's text). The fix line is `fixOAuth(provider, reason)`: it names Microsoft or Google and the panel (Mailboxes, Reconnect), never `mailbox:password`. A password mailbox renders today's text byte for byte. A Reconnect followed by another reason gives a new `status_changed_at`, so a new row; the old pending row becomes `outdated`.
   - Check against the code: an `auth_error` row that is still `pending` when the mailbox leaves `auth_error`, a `host_blocked` row that is still `pending` when the mailbox leaves `host_blocked` (also an older episode's row when a newer one starts), and a `sync_stale` row that is pending when the mailbox is fresh, paused or in its grace time, becomes `failed` / `outdated` (`cancelPendingOutbox`). A `sent_missing` row that is pending when the flag or the switch goes off, the mailbox is not `active`, the Sent pass shows an error or is older than 1 hour, or a newer user mail ends the quiet period, becomes `failed` / `outdated` too.

7. **The outbox sender** (moved from `docs/architecture.md` §8, the S2 jobs sentences): `channels.notifier` every 15 s (notice detection, then the outbox sender; at most 3 messages per user per tick;
   a 429 waits `retry_after`, a network error or HTTP 5xx backs off from 30 s to 15 min, a 401 pauses sending for 10 min,
   a 403 marks the row `failed` / `blocked`, a row older than 24 h becomes `failed` / `expired`) and `channels.digest` every minute
   (the digest at each member's times in the organization timezone; a missed slot is sent if the server is back within 6 hours).
   - Check against the code: the sender claims up to 20 due rows per run (`FOR UPDATE SKIP LOCKED`; a `sending` row with a claim older than 5 min is taken again, and its log line warns that a duplicate is possible). A row with a stored `text` goes as it is (rows queued before F088); every other row is rendered now with `renderNotice(kind, view, { channel, detail, locale })`. A view that does not render fails the row as `bad_view`. The rate limit (429) and a soft error (network, 5xx) pause the whole sender, not one row; the 401 pause is 10 min and logs "check TELEGRAM_BOT_TOKEN". A 400 fails the row as `bad_request`. Any other error is tried again with the same back-off and fails the row as `too_many_errors` at the fifth try. A member without a chat link fails the row as `no_chat`. The failure codes are `blocked`, `bad_request`, `expired`, `no_chat`, `outdated`, `too_many_errors` and `bad_view` (`outboxFailCodes`); the edit rows of rule 13 add `answered_elsewhere`, `stale_edit`, `no_target` and `edit_failed`. The digest row also sets `digests.sent_at` in the same transaction as `markOutboxSent`.
   - Check against the code: `channels.notifier` and `channels.digest` are registered only when `TELEGRAM_BOT_TOKEN` is set (`apps/server/src/start/telegram.ts`); without the token the start log says `telegram_off` and no outbox row is sent. `channels.operator` is registered in every case.
   - Delivery is at least once: a duplicate is possible when the process dies or the network breaks between the Telegram answer and the DB commit (`docs/architecture.md` §6.2).
   - The outbox sender claims only rows with `channel = 'telegram'` (F110). Rows with `channel = 'mail'` go through `channels.report_mail` (rule 3b); both senders share the 24 h life of a row (`OUTBOX_MAX_AGE_MS`) and the quiet-hours gate (`createQuietGate`).
8. **Notices as facts (ADR 0032 point 5, F088).** A producer never builds the text of a message. `queueNotice` takes `{ userId, locale, kind, view, dedupKey }`, encodes the view (`encodeNoticeView`: dates as ISO strings, no lone surrogate, no NUL), checks it against the strict schema of the kind (`noticeViewSchemas`) and renders it once; a view that does not render never enters the outbox (`NoticeViewError`, a message with the kind only). The sender renders again at send time with the `locale` of the row (`users.locale`, null = `pl`). `outbox.text` and `outbox.buttons` are the cache of the sent message: null and `[]` until the send. The renderers (`noticeRenderers`, one per kind and one function per channel and detail level) take their words from `textsFor(locale)`: Polish for `pl` and null, English for `en`. The edit after a tap keeps the stored text of the card and adds one status line (`renderNoticeEdit`). The checklist "Add a notice kind" and the rules of a view change are in `docs/code-patterns.md` § Notices are facts. Direct replies (command answers, tap answers, the link texts, the operator notices) are not outbox rows.
9. **Commands** (`commands.ts`, `BOT_COMMANDS`; the list is set with `setMyCommands` at each start). Every command except `/help` and every tap answers "⏸ This account is paused…" with `OPERATOR_CONTACT` (or "the operator") when the organization is `suspended`; `/start` linking still works.

Triage waits.` The digest footer shows the same line (`llmPauseLine`, `packages/core/src/digest/llm-pause.ts`).    - `/review` (flag `review_command`, per organization; without it the answer is "This command is not on for your account."): up to 10 unlabelled real mails of the last 30 days in a random order (a seed of the chat id and the time: each call gives a new sample). The page shows the AI summary only, no body (ADR 0005). 10. **Callback prefixes** (`packages/core/src/digest/callback.ts`; `callback_data` is at most 64 bytes; old or forged data parses to null). `fr:<cat>:<email>` the category is right; `fc:<cat>:<email>` a category is picked; `fe:<email>` open the picker; `fx:<email>` cancel the picker; `fu:<email>` Undo ([actions-and-undo.md](actions-and-undo.md)); `vr:<cat>:<email>`, `vc:<cat>:<email>`, `ve:<email>`, `vx:<email>` act as `fr`, `fc`, `fe`, `fx` but record the feedback source `review` (the `/review` page uses them; `vr:d:` and `vc:d:` accept `delegation`); `ap:<action>` approve a send; `ar:<action>` reject a send; `as:<set>` approve a set; `rs:<set>` reject a set; `ag:<action>` send again; `gw:<action>` mark a send as gone out; `dd:<delegation>` close an answered or overdue delegation; `lf:<loop>` draft a follow-up, `ll:<loop>` Later, `lc:<loop>` Done, `lx:<loop>` Drop, `lr:<loop>` Reopen (F116 stage 19, rule 14); `dg:<email>` open the delegate picker; `dp:<email>:<delegate>` pick a delegate (each UUID as 22 characters of base64url, 48 bytes; a part of another length, or a spelling that is not the one form of its 16 bytes, parses to null); `ay:<email>` and `an:<email>` the Yes and No of the answered check (`answered-taps.ts`); `rv` start the review of the reply drafts and `rv:<send>` the next one after that send, `rk:<send>` skip this reply draft (F115 stage 12, `reply-taps.ts`: owners only, flag `reply_drafts` on, the Telegram consent must cover reply data). `rd:<send>` Redraft, `ra:<send>` Reply all, `ru:<send>` Use Reply-To and `dr:<mail>` Draft reply (F115 stage 13, `reply-redraft.ts`, same checks; Draft reply is on an urgent notice and on a digest row). 11. **Operator notices (S6a)** (moved from `docs/architecture.md` §8): `channels.operator` (code in the operator module, `apps/server/src/modules/operator/notices.ts`) sends five events to the operator chat `OPERATOR_TELEGRAM_CHAT_ID` by a direct send, or writes a `warn` log line when the key is empty. The texts hold ids, dates and counts only. They live in `packages/core/src/texts/operator.ts` in English and Polish; the key and the text of each event come from `operatorEventKey` and `renderOperatorEvent` in `packages/core/src/ops/events.ts`; the language is one per server (`OPERATOR_LOCALE`, English by default). The events and their keys are `trial_ending` (`trial_ending:<org id>:<trial_ends_at ms>`, 3 days before the end and after it), `llm_cap` (`llm_cap:<mailbox id>:<quota day start>`, sent by the triage job when a mailbox reaches `LLM_DAILY_CAP`) and `auth_error_24h` (`auth_error_24h:<mailbox id>:<status_changed_at ms>`, a mailbox in `auth_error` for 24 h) and `send_limit` (`send_limit:<mailbox id>:<UTC day>`, a send of a mailbox waits on a send limit; the committer calls it and the hourly run catches a lost call). The dedup is an audit row `operator.notice` with the key, written after a successful send: a crash between the send and the row repeats one notice (at least once). A failed send is tried again at the next hourly run. Quiet hours do not apply. A suspended organization gets no `trial_ending` or `auth_error_24h` notice. The service-level alerts of the `ops.slo` job go to the same chat by the same direct send: [operations.md](operations.md) § Alerts.
    - Check against the code: there are five events, not four. `auth_mail_failed` (`auth_mail_failed:<user id>:<code>:<UTC date>`) goes when an auth mail (invite, reset or lock) fails; the web wiring calls `authMailFailed` (`apps/server/src/web-audit.ts`, `authMailFailedHandler`). `trial_ending` counts only organizations with the plan `trial`. `llm_cap` is retried at the next hourly run when its send failed (`retryCaps`); the other events are found again by the hourly run itself. `channels.operator` runs hourly at minute 13 (`0 13 * * * *`). The operator chat id is private data and never reaches a log line.

12. **The `not_triaged` notice (F109, PD-067, flag `degraded_notice`, default off, remove-by 2027-03-01).** While the triage LLM is paused, every linked member learns that mail of a VIP or whitelisted sender waits. The text, English: `📭 Mail from <sender> is not triaged yet: the AI service is paused. It is triaged when the service is back.` (Polish `📭 Wiadomość od <sender> nie jest jeszcze posortowana: usługa AI ma przerwę. Zostanie posortowana, gdy usługa wróci.`). The view holds the sender address and two ids only (`emailId`, `mailboxId`); the text cuts the address to 40 characters. No subject, display name, body or summary. No button. The detector is `notTriagedDetector` (`apps/server/src/modules/channels/notices/not-triaged.ts`), the last one of the run order.
    - **Pause source.** The in-memory pause of the triage worker (`LlmPause`). `start/triage.ts` builds one object and gives it to the triage job and to the notice job (`NoticeDeps.degraded = { pause, scope }`). It is not the audit-row pause of the `/status` line (rule 9): that one is per organization and ends a soft pause early. `pausedSince()` is the first trip since the last answer of the LLM (`reset()`). A restart clears the pause. With `TRIAGE_LLM_SCOPE=off` there is no worker, no `degraded` object and no notice.
    - **Candidates.** `pending` mail of the last 24 h in an `active` mailbox, from a sender that matches a whitelist or VIP rule (a whitelist rule wins over a blocklist rule, as in `applyHardRules`). With the scope `synthetic` only test mail counts.
    - **Cap.** At most 5 mails per mailbox with rows since `pausedSince()`, and one row per member per mail (dedup key `not_triaged:<email id>` per member), so a pause queues at most 5 × (the number of linked members) rows per mailbox. A mail with rows stays in the set, so a member linked later still gets its row. A mail that got rows in an earlier pause and is still `pending` is tried first (the dedup drops its row) and uses the cap slots of the new pause.
    - **Quiet hours.** The detector queues nothing between 22:00 and 07:00 (organization zone): if the pause lasts until 07:00, mail that still waits gets its notice then. A row queued shortly before 22:00 is held by the sender until 07:00 and can be out of date by then (accepted).
    - **Rows.** The kind is `one_mail` in `NOTICE_MAIL_CONTENT` (`emailId` set), so the erase of a mail removes its row. The text and view follow `clearOutboxTexts` (90 days). No consent bump: the sender address is a kind of data that the consent text names already.
    - **Check against the code:** the detector sends to every linked member and does not check `linkedAt` (the urgent detector does): the notice tells the current state. A pending `not_triaged` row is not cancelled when the mail is triaged before the send, so the text can say "not triaged yet" for a triaged mail (accepted: no "back" message). If the released mail is deleted before triage retries, a later pause keeps the old `pausedSince` (`reset()` runs after a good LLM answer only), so that pause can queue fewer than 5 notices; it fails toward fewer messages.
13. **Card edits (F102, kind `approval_edit`).** When a decision changes a send, each owner's Telegram card of that send follows, so a card never keeps a Send button for a send that is decided. The rules of the decisions are in [drafts-and-send.md](drafts-and-send.md) rules 13 and 14; this rule holds what the outbox does.
    - A row edits the stored text of the card (`outbox.text` of the target; `outbox.edit_of_outbox_id` points at it) and adds one status line (`approvalEdit`, `renderNoticeEdit`): approved, approved and held, rejected, changed (a new version replaced the draft), or expired. A `sent` card with a message id and a text becomes one row. A `pending` card (not sent yet) becomes `failed` / `answered_elsewhere` at once: nobody saw it. A card in `sending` gets no row (a tap on it answers by the state of the send).
    - The sender skips quiet hours for these rows (an edit makes no sound), still counts them in the per-user limit, and edits the message in place (`ChatChannel.edit`; no new message). Before the edit it checks the target with the same organization and user: no `sent` card, no message id, a text that retention removed, or a card that went out before the user linked another chat (or the same chat again) ends the row `failed` / `no_target`; a send whose state no longer matches the outcome of the row, or a newer edit of the same card that already went out, ends it `failed` / `stale_edit`. A Telegram refusal (`blocked`, `bad_request`) ends it `failed` / `edit_failed` and is not tried again; a soft error, a rate limit or a config error release the row like any other.
    - A failure while the decision queues the rows is logged (`card_edits_not_queued`) and never undoes the decision. The edit rows hold the card text that the user already got plus fixed phrases; no new kind of mail data reaches Telegram, so `TELEGRAM_CONSENT_VERSION` did not change.
14. **Taps on loop lines and the Delegate button (F116 stage 19).** Every tap calls the command of the loops module with `via: "telegram"`; the org and the user come from the chat link, never from the callback. The role check comes before any query: Draft follow-up, Drop, Reopen and the Delegate button and picker are for owners (answer "Only an owner can do this."), Done and Later for any linked member. The digest follows the same rule when it is built (`DigestRequest.role`): the keyboard of a member has no Draft, Drop or Reopen button and no 👥, a member's digest has no ⌛ line and does not mark it (the line stays for an owner), and the `delegable` hint of the digest rows and the urgent notice is set for owners only. An unknown loop id and a loop of another organization get the same answer. The keyboard of the first digest of the day has one row per brief line, built only from the lines that the member's consent shows (`briefKeyboard` returns no row when `loopConsent` is false): ⏳ waiting and delegated loops `📝 Draft follow-up` (only when the mailbox is in `assist` with `create_draft` on, no follow-up waits for a tap and fewer than two were sent), `⏰ Later` (not after the third use), `✓ Done`; 🤝 promised loops `✓ Done`, `✖️ Drop`; ⌛ lines `↩️ Reopen`; a ⏳ line of a delegation `✓ Done` (`dd:`) only while the delegation is `overdue` (`closeDelegation` closes only `answered` and `overdue`). The toast of Draft follow-up names the command answer (`planned` "Follow-up drafted. Check the card.", `would_draft`, `waiting`, `limit_reached`, `too_soon`, `closed`, `suspicious`, `drafts_off`, `feature_off`); Later says "Moved to {date}.", Done "Done.", Drop "Dropped.". After a state change the bot edits the tapped digest message in place: the line gets a mark (✓, ⏰, ✖️, ↩️) and its buttons go, the rest of the stored text stays, and the edit is stored back in the outbox row (`text`, `buttons`), so the next tap starts from it. The line is found by number: the digest view holds `lineOf` (loop or delegation id → line number; numbers only). A message that is not a digest of this user and chat and a tap without a message id get the toast and no edit. A tap on a digest whose stored text was blanked (`[removed]`, view `{}`: retention, the Sent switch or an erase) edits the keyboard only (`CallbackResult.keyboard`, `editMessageReplyMarkup`): the chat message keeps its text. The 🔴 and ✍️ lines have no buttons. **Delegate button.** `[👥 n]` joins the row of the number n of the digest list for the categories urgent, needs reply and unsure, and the urgent notice gets `[👥 Delegate]` (view field `delegable`), only when the flag `delegate_button` is on, the organization has an active delegate, the mailbox is in `assist` with `create_draft` on and the mail has no suspicious reason (the reader ignores the flag `suspicious_mail`, as `delegateMail` does). A row of the normal list holds at most 4 buttons, a keyboard line at most 8. `dg:` sends one picker message "Delegate to:" with up to 8 active delegates by name (two per line) and, when more exist, "More delegates in the panel" with the link to the delegates page when `WEB_BASE_URL` is set; `dp:` calls `delegateMail` (no caller transaction, its error is never caught to commit) and edits the picker to the result line (`planned` "Delegation drafted. Check the card.", `exists`, `delegate_inactive`, `not_delegable`, `drafts_off`, `feature_off`). Texts: `packages/core/src/texts/loop-taps.ts`. A digest that ends `failed` gives back the marks of its loops (`surfaced_at`, `stale_notified_at`), so each line is shown once; the same holds when the Sent switch off (`clearLoopCards`) or an erase (`blankDigestsNamingLoops`, `eraseManyMailOutbox`) ends or deletes a pending digest: the marks of the loops that are NOT being cleared go back before its view is blanked or deleted (`releaseMarksOfUndeliveredDigests`) (`releaseBriefMarks`: the mark goes back only when it is the time of that digest and no other digest that is not `failed` names the loop). The first digest of a day is decided by the date of the slot (`isFirstDigestOfDay`, `slotDate`), not by the time at which the job runs. Rollback: the code before stage 19 refuses a digest view with `lineOf` and an urgent view with `delegable` (the schemas are strict): the sender ends such a pending row `failed` / `bad_view`, so on a rollback drain the outbox first or accept one lost slot (sent rows are not affected: their text is stored). With several linked owners only the first digest that commits shows a ⌛ line for a loop (the mark is one column); the others see the closed loop in the panel (review 18 N6). A member never takes the line.

## Data

- `outbox`: one row per notice and member. Columns: `kind` (the kinds of `noticeKinds` in `packages/core/src/notices/kinds.ts`; rule 5 lists them, and `approval_edit` is the edit of an approval card), `edit_of_outbox_id` (kind `approval_edit` only: the sent card that the row edits), `dedup_key` (unique per organization and user), `email_id`, `mailbox_id`, `digest_id`, `view` (the facts, jsonb), `channel` (`telegram`, `mail` or `push`), `push_subscription_id` (a push row only: the device; `SET NULL` when the device goes, so a sent row stays as history), `locale` (`pl` or `en`), `detail` (`full` or `minimal`: the level of the send, written with the text), `text` (the cache of the sent message; null until the send) and `buttons` (the same cache; `[]` until the send), `status`, `attempts`, `next_attempt_at`, `locked_at`, `sent_at`, `external_message_id`, `error_code`, `created_at`. The text and the view follow the retention of `docs/architecture.md` §7 (`clearOutboxTexts`, 90 days); removing a mailbox drops the `pending` and `sending` digest rows and clears the text and view of the sent and failed ones.
- Status flow of `outbox.status`: `pending → sending → sent` (the sender claims a due row and sets `locked_at`); `sending → pending` (released with a new `next_attempt_at`: quiet hours, the per-user limit, a rate limit, a soft error); `sending → failed` with an `error_code` of rule 7; `pending → failed` (`outdated`: the notice is not true any more, or the plan became `suspended`).
- `digests`: one row per member and slot (`slot_key`, `period_start`, `period_end`, `sent_at`); unique per organization, user and slot.
- `chat_links` (one Telegram chat per member) and `chat_link_tokens` (`token_hash`, `expires_at`, `used_at`).
- `push_subscriptions` (F118): one row per phone or browser of a member: the encrypted endpoint and keys (`secret`, `key_version`), `endpoint_hash`, `device_label`, `session_id` (null once the session ended), `last_success_at`, `last_error_code`; at most 10 per member. It goes with the member or the organization ([account-data.md](account-data.md)).
- `memberships.digest_times` (`time[]`, default `{08:00,16:00}`), `memberships.notice_routes`, `memberships.telegram_detail`, `organizations.timezone`, `organizations.telegram_minimal_locked`, `users.locale`.
- Audit events: `chat.linked`, `chat.unlinked`, `web.telegram_consent`, `operator.notice`, `member.telegram_detail_changed`, `org.telegram_lock_changed`, `member.notify_changed` (the changed key names, never a value).

## Limits

- Telegram, plus the mail channel of F110 for the digest, the weekly report and the two trust notices (flag `report_mail`; rule 3b; limits in [trust.md](trust.md) § Limits). Push (E9b F118; ADR 0032 is accepted; rules 3c and 3f) and the Telegram level `minimal` (rule 3e) are built but off: the flags `web_push` and `telegram_minimal` are off by default; the owner turns them on for the pilot organization at checkpoint B. The digest, the weekly report and the trust reports never go by push (they stay on Telegram and mail). iOS shows a push only for a panel on the Home Screen (iOS 16.4 or later) and is not tested; the test phone is Android. The M5 metric and the urgent SLO count Telegram rows only, so an organization with push users only is outside the alert. Only the hosts of `fcm.googleapis.com`, `push.services.mozilla.com`, `push.apple.com` and `notify.windows.com` are accepted as push endpoints (a new browser vendor needs a code change). A session that ends stops the notices on that device until the next panel load re-binds it (SSO sessions end after 12 h). `noticeChannels` in `packages/core/src/notices/kinds.ts` holds `telegram`, `mail` and `push`; `noticeDetails` holds `full` and `minimal`; `reportMailKinds` lists the four kinds that have a mail renderer.
- Every Telegram text follows `users.locale`; null → Polish (`textsFor(locale)` returns the table of the locale from `packages/core/src/texts/`). A user with no stored language gets Polish Telegram text at once (owner decision). The chat takes its locale from the link; `/start` with a used or expired token takes it from the token owner. A user with `en` reads the English texts, byte for byte as before. Rows queued before the switch hold `locale = 'pl'` for null users with English stored text; a tap on such a card adds a Polish status line to the English card. The approval buttons stop working after 48 h, but the buttons Gotowe, Wysłano and "To był błąd" work for up to 7 days, so the mixed edit can show for up to 7 days (old cards keep their English text and get Polish status lines on edit). The command menu follows the app language of Telegram, not `users.locale`.
- The quiet hours hold every kind except the digest and `approval_edit`. The default is one constant (`22:00`–`07:00`); with the flag `user_quiet_hours` each member has their own hours (rule 3a). A per-user route per kind is PD-094 (E9b F118).
- The digest lists at most 15 items; the rest is a `+N more` line. There is no web list of past digests.
- The operator notices go to one chat by a direct send, with no outbox row, no queue and no quiet hours. A failed `auth_mail_failed` notice is not tried again.

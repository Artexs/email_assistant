# Digest and notices

> Checked against the code at `d0e628aa`, 2026-11-15.

## What it does now

Every message that the system sends to a person goes through Telegram. A user links one private chat to their account with a one-time token. After that, the digest job queues a digest at each of the member's times (default `08:00` and `16:00`, in the organization time zone), and the notice job queues notices for urgent mail, mailbox and sync problems, approval requests, send results, sends held by a send limit, delegation answers and, during an LLM pause, mail of VIP and whitelisted senders that waits for triage. Both write rows to the table `outbox`. A row holds the facts of the message (a view), not its text. The outbox sender renders the text when it sends. It sends at most 3 messages per user per tick, waits through the quiet hours of the member (default `22:00`–`07:00`; with the flag `user_quiet_hours` the member's own hours, rule 3a) for every kind except the digest, and fails a row that is older than 24 h. The user answers with the commands `/digest`, `/status`, `/pause`, `/resume`, `/review` and `/help`, and with buttons under the messages. The operator gets a separate set of plain messages in one chat (`OPERATOR_TELEGRAM_CHAT_ID`). All of this runs only when `TELEGRAM_BOT_TOKEN` is set; the operator notices run in every case.

## Rules

1. **Chat linking.** `bun run telegram:link` (or `POST /api/channels/telegram/link` from the web panel) makes a one-time token for one member. The web route needs the consent body `{ consentVersion }` with the current `TELEGRAM_CONSENT_VERSION` (packages/core): no or a bad body is 400, an old version is 409 `telegram_consent_outdated`, and neither makes a token. One transaction writes the audit row `web.telegram_consent` (actor = the member, `data` = `via`, `version`) and the token. The panel shows the consent text (what goes to Telegram) and a tick before it enables the link button; the tick resets when the chat gets linked or unlinked. The CLI needs no consent (an operator tool), and a chat that was linked before the consent keeps its link. **Consent gate for loop data (F116 stage 17).** `consentVersionsOf(db, ctx, userIds)` (channels) gives the version of the newest `web.telegram_consent` row of each user in the org (no row or no version: null). `consentCovers(version, since)` (packages/core) is true when the version is not null and `>= since`; versions are ISO dates with an optional `.N` suffix. `OPEN_LOOPS_CONSENT_SINCE` is the first version whose text names loop data. A user who is not covered gets no loop text, address or ask in a Telegram message: only counts, a fixed line and the panel link (the senders of stages 11, 18 and 19 apply it). `POST /api/telegram/consent` `{ version }` (any member, own user from the session): the current version writes one `web.telegram_consent` row and answers 200 `{ version }`; any other version is 409 `telegram_consent_outdated`; no token is made. The token: 32 random bytes, valid 15 minutes, stored as a SHA-256 hash only. A new token makes the older unused tokens of the member invalid. The user opens `t.me/<bot>?start=<token>`. The bot stores the chat in `chat_links` (one chat per member, one member per chat) and answers with the help text. A chat that was linked to another member moves: the old link goes and gets the audit row `chat.unlinked` (`reason_code` `chat_moved`). A used token answers "This link was used already. Ask for a new link." (or "This chat is linked already" for a linked chat); an expired token answers "This link has expired (a link works for 15 minutes). Ask for a new link."; an unknown token gets no reply (a linked chat gets the help text). `bun run telegram:unlink` and `DELETE /api/channels/telegram/link` remove a link (audit row `chat.unlinked`). The bot rules for the chat guard and the token text are in `docs/architecture.md` §6.2.
2. **The update router** (`createTelegramBot`): chat guard (private chats of people only), `/start` linking, link guard (an update from an unlinked chat gets no reply), commands, buttons, then any other message of a linked chat (it gets the help text). The tenant comes from the link, never from the update.
3. **The digest job.** `channels.digest` runs every minute (second 5) and visits every linked chat of an organization that is not `suspended`. Per member it reads `memberships.digest_times` (at most 6 times, `HH:MM`), the organization time zone and the last digest slot. It queues the newest slot that is due: not older than 6 hours (`DIGEST_LATE_MS`), not in the future, and after the last slot of the member or the link time. Earlier missed slots are skipped, so a server that is back within 6 hours sends one digest, marked "(late)" when it is more than 10 minutes late. A slot key is the local wall-clock string `YYYY-MM-DDTHH:MM`, so a daylight-saving change gives no double and no lost digest. One digest row (`digests`) and one outbox row go in one transaction per member and slot; the outbox row is marked `sent` and the digest row gets `sent_at` in the sender's transaction.
4. **The digest message** (`renderDigest`, one message of at most 4096 characters and at most 15 lines). Header (`📬 Digest HH:MM · <day>`), the count line, one line per mailbox (last sync, `paused`, `login error`, `server not allowed`), the section `NEEDS ACTION` (`urgent`, `needs_reply`, `delegation`, `unsure`), the section `OTHER MAIL` (`info`, `notification`, `spam`), then footer lines: the LLM pause line (first, only with the flag `llm_pause_line`, rule 9), `+N more`, mail skipped as older than 7 days (`too_old`), mail skipped after an account pause (`suspended_backlog`), mail waiting for triage, open and overdue delegations, "Shadow mode: the system changed nothing in your mailbox.", and, last and only with the flag `handled_share`, the handled-share line `🤖 Handled in the last 7 days: <rate>` (`handledShare` of the last 7 days of real mail, all mailboxes; it is left out when no mail was triaged, or when every mailbox is in shadow mode and nothing was handled) Each item line shows the category, the sender, the subject, the AI text and what the system did or would do. Buttons: per item `✅ n` (the category is right), `✏️ n` (pick another category) and, while an Undo is possible, `↩️ n`, two items per row. The period of a digest starts at the end of the last sent digest (a failed digest does not move it), at most 7 days back; the first digest looks back 24 h before the link. The digest holds no mail bodies (ADR 0005). `/digest` builds the same message for the period up to now and sends it at once, with no `digests` row and no outbox row.
5. **The notice job.** `channels.notifier` runs every 15 s: `detectNotices`, then the outbox sender. Per organization (a failure of one does not stop the next), the detectors run in this order: urgent, action failed, auth error, host blocked, sent missing, sync, approval, approval set, send result, follow-up closed (the card edit of a follow-up whose loop closed), send held, delegation answered, weekly report, not triaged (rule 12). Each one finds its event, builds a view and calls `queueNotice`; the dedup key `(org, user, dedup_key)` keeps one row per event and member. The kinds:

   Notices never go out in quiet hours (22:00–07:00 in the organization timezone); they wait until 07:00. Digests go out at their times.

   3a. **Quiet hours per member (F110 stage 18).** `memberships.quiet_start` and `quiet_end` (`HH:MM`; both null means the default `22:00`–`07:00`; equal start and end means no quiet hours; a range that crosses midnight works as the default; the window is at most 18 hours: the route refuses a longer one with `400 quiet_too_long`, so a hold plus a retry stays below the 24 h life of an outbox row). The sender holds a row until `max(quietEnd, now + 1 min)`; `quietEnd` is the first instant after `now` at which the wall clock reads the end time (the second one in the autumn hour that repeats, the instant of the change when the end time falls in the spring gap). The clock stays the organization time zone: there is no per-user zone. With the flag `user_quiet_hours` on for the organization, the sender reads the hours of the users of one claimed batch with one query (`listQuietHoursOf`), and holds a row by the hours of its user (`isQuietTime`, `quietEnd` and `lateMin` take an optional `QuietHours`; `quietHoursOf` turns the two columns into one value). With the flag off every member has the default hours. The digest and `approval_edit` are never held. `/status` shows the own hours (`Quiet hours: 23:00–06:00 (notices wait until 06:00)`, or `none` when start equals end). The member sets the hours with `PATCH /api/me/notify` (`{ quietStart, quietEnd }`; both times, or both `null` to reset; the Settings card "Quiet hours"), which writes the audit event `member.notify_changed` with the changed key names (`quiet_start`, `quiet_end`; never a value). The F114 check `slo_urgent_latency` (`operator/slo-checks.ts`) takes the hours of the user of the sent urgent row that gave `noticeAt`; with no sent row it computes the wait for the user of each pending urgent row and takes the largest (each value leaves out that user's own quiet hours, so a user in quiet hours cannot hide a user who really waits); with the flag off, or no row, it uses the default (`UrgentCandidate.quiet`). The metric M5 keeps the default hours (a measure, not an alert). The same route sets the report channel (`{ reportChannel: telegram | mail | both | null, reportMailboxId? }`, flag `report_mail`): `mail` or `both` needs an `active` mailbox of the organization (the one asked for, else the oldest; else `409 no_mailbox`); `telegram` or `both` without a linked chat is allowed and the card warns. The channel is stored only; sending by mail is a later stage.

   a 429 waits `retry_after`, a network error or HTTP 5xx backs off from 30 s to 15 min, a 401 pauses sending for 10 min,
   a 403 marks the row `failed` / `blocked`, a row older than 24 h becomes `failed` / `expired`) and `channels.digest` every minute
   (the digest at each member's times in the organization timezone; a missed slot is sent if the server is back within 6 hours).
   - Check against the code: the sender claims up to 20 due rows per run (`FOR UPDATE SKIP LOCKED`; a `sending` row with a claim older than 5 min is taken again, and its log line warns that a duplicate is possible). A row with a stored `text` goes as it is (rows queued before F088); every other row is rendered now with `renderNotice(kind, view, { channel, detail, locale })`. A view that does not render fails the row as `bad_view`. The rate limit (429) and a soft error (network, 5xx) pause the whole sender, not one row; the 401 pause is 10 min and logs "check TELEGRAM_BOT_TOKEN". A 400 fails the row as `bad_request`. Any other error is tried again with the same back-off and fails the row as `too_many_errors` at the fifth try. A member without a chat link fails the row as `no_chat`. The failure codes are `blocked`, `bad_request`, `expired`, `no_chat`, `outdated`, `too_many_errors` and `bad_view` (`outboxFailCodes`); the edit rows of rule 13 add `answered_elsewhere`, `stale_edit`, `no_target` and `edit_failed`.    - Delivery is at least once: a duplicate is possible when the process dies or the network breaks between the Telegram answer and the DB commit (`docs/architecture.md` §6.2).
8. **Notices as facts (ADR 0032 point 5, F088).** A producer never builds the text of a message. `queueNotice` takes `{ userId, locale, kind, view, dedupKey }`, encodes the view (`encodeNoticeView`: dates as ISO strings, no lone surrogate, no NUL), checks it against the strict schema of the kind (`noticeViewSchemas`) and renders it once; a view that does not render never enters the outbox (`NoticeViewError`, a message with the kind only). The sender renders again at send time with the `locale` of the row (`users.locale`, null = `pl`). `outbox.text` and `outbox.buttons` are the cache of the sent message: null and `[]` until the send. The renderers (`noticeRenderers`, one per kind and one function per channel and detail level) take their words from `textsFor(locale)`: Polish for `pl` and null, English for `en`. The edit after a tap keeps the stored text of the card and adds one status line (`renderNoticeEdit`). The checklist "Add a notice kind" and the rules of a view change are in `docs/code-patterns.md` § Notices are facts. Direct replies (command answers, tap answers, the link texts, the operator notices) are not outbox rows.
9. **Commands** (`commands.ts`, `BOT_COMMANDS`; the list is set with `setMyCommands` at each start). Every command except `/help` and every tap answers "⏸ This account is paused…" with `OPERATOR_CONTACT` (or "the operator") when the organization is `suspended`; `/start` linking still works.
   - `/digest`: the digest now (rule 4, no row).
   - `/status`: per mailbox the address, the mode, the status (a `host_blocked` mailbox shows that the mail server is not allowed and is checked again at each sync), the last sync (marked "(late)" after 30 min) and the LLM calls of the quota day against `LLM_DAILY_CAP`; then the triage scope, the actions scope with the counts of the last 24 h, the approvals that wait (with the cause of an approved send that is held), the send scope, the delegations, the LLM provider and model, the LLM pause line (only with the flag `llm_pause_line`), the next digest time and the quiet hours. The pause line reads the pause from the `llm.call` audit rows (`latestLlmPause`, `reports/llm-pause.ts`): the newest row must hold a soft code (at most 10 minutes old) or a config code (at most 2 hours old), and `since` is the start of the unbroken run of such rows. The line is `⏸ LLM paused since <clock> (<code>). Triage waits.`; for `http_429_quota` it is `⏸ LLM paused since <clock>: the provider quota or budget is spent (http_429_quota). Triage waits.` The digest footer shows the same line (`llmPauseLine`, `packages/core/src/digest/llm-pause.ts`). Both lines follow the member's texts (`texts.digest.llmPause`; while `POLISH_MESSAGES_ON` is false, every member gets English).
   - `/pause` and `/resume`: owners only. They switch every mailbox of the organization, one transaction each (audit rows with `via` `telegram`); a mailbox in `auth_error` is skipped with a hint to run `bun run mailbox:password` (an OAuth mailbox: tap Reconnect in the panel; `/status` shows `sign-in error since … (Reconnect in the panel)`); a mailbox in `host_blocked` is skipped with a hint that the system checks the server again at each sync.
   - `/review` (flag `review_command`, per organization; without it the answer is "This command is not on for your account."): up to 10 unlabelled real mails of the last 30 days in a random order (a seed of the chat id and the time: each call gives a new sample). It lists the mails of every mailbox of the organization. A mail with a feedback row or from a test sender (`TEST_SENDER_ADDRESSES`, a synthetic Message-ID) is not on the page. The page shows the AI summary only, no body (ADR 0005). Per item `✅ n` (not for `unsure`) and `✏️ n`; the taps use the callbacks `vr`, `ve`, `vc`, `vx` (rule 10) and write the feedback source `review`. The page and its texts: `renderReviewPage` (`packages/core/src/digest/review.ts`, texts in `packages/core/src/texts/review.ts`, en and pl).
     With the flag `answered_check` also on, the same message ends with the answered-check block: up to 5 real mails of the last 14 days that the user answered (`\Answered`) but the assistant marked `info`, `notification` or `spam`, with the question "Did they need a reply?" and a `✅ Yes n` and `➖ No n` button per item (`ay:` and `an:`, rule 10). Any linked member may tap. The block drops items from the end until the message fits 4,096 characters; with no candidates there is no block. A "yes" writes the label `needs_reply` with the source `answered_check` ([triage.md](triage.md) rule 10); a "no" only records the answer; the first answer wins, and a mail that already has any label keeps it (the "yes" then saves the answer only). A tap with the flag off (also by `FEATURES_OFF`) answers "This button is off now." and writes nothing. The block and the tap answers: `renderAnsweredCheck`, `withAnsweredCheck` (`packages/core/src/digest/answered-check.ts`, texts `answered` in `packages/core/src/texts/review.ts`, en and pl).
   - `/help`: the command list and what the buttons do.
10. **Callback prefixes** (`packages/core/src/digest/callback.ts`; `callback_data` is at most 64 bytes; old or forged data parses to null). `fr:<cat>:<email>` the category is right; `fc:<cat>:<email>` a category is picked; `fe:<email>` open the picker; `fx:<email>` cancel the picker; `fu:<email>` Undo ([actions-and-undo.md](actions-and-undo.md)); `vr:<cat>:<email>`, `vc:<cat>:<email>`, `ve:<email>`, `vx:<email>` act as `fr`, `fc`, `fe`, `fx` but record the feedback source `review` (the `/review` page uses them; `vr:d:` and `vc:d:` accept `delegation`); `ap:<action>` approve a send; `ar:<action>` reject a send; `as:<set>` approve a set; `rs:<set>` reject a set; `ag:<action>` send again; `gw:<action>` mark a send as gone out; `dd:<delegation>` close an answered delegation; `ay:<email>` and `an:<email>` the Yes and No of the answered check (`answered-taps.ts`). The category codes are `u`, `r`, `i`, `n`, `s` (urgent, needs reply, info, notification, spam); the review prefixes also take `d` (delegation). `handleCallback` in `callbacks.ts` routes them; the tenant comes from the link, and an unknown mail id and a mail of another organization give the same answer. The approval taps are described in [drafts-and-send.md](drafts-and-send.md), the feedback taps in [triage.md](triage.md), the Undo tap in [actions-and-undo.md](actions-and-undo.md), the delegation tap in [delegation.md](delegation.md).
11. **Operator notices (S6a)** (moved from `docs/architecture.md` §8): `channels.operator` sends four events to the operator chat `OPERATOR_TELEGRAM_CHAT_ID` by a direct send, or writes a `warn` log line when the key is empty. The texts hold ids, dates and counts only. The events and their keys are `trial_ending` (`trial_ending:<org id>:<trial_ends_at ms>`, 3 days before the end and after it), `llm_cap` (`llm_cap:<mailbox id>:<quota day start>`, sent by the triage job when a mailbox reaches `LLM_DAILY_CAP`) and `auth_error_24h` (`auth_error_24h:<mailbox id>:<status_changed_at ms>`, a mailbox in `auth_error` for 24 h) and `send_limit` (`send_limit:<mailbox id>:<UTC day>`, a send of a mailbox waits on a send limit; the committer calls it and the hourly run catches a lost call). The dedup is an audit row `operator.notice` with the key, written after a successful send: a crash between the send and the row repeats one notice (at least once). A failed send is tried again at the next hourly run. Quiet hours do not apply. A suspended organization gets no `trial_ending` or `auth_error_24h` notice. The service-level alerts of the `ops.slo` job go to the same chat by the same direct send: [operations.md](operations.md) § Alerts.
    - Check against the code: there are five events, not four. `auth_mail_failed` (`auth_mail_failed:<user id>:<code>:<UTC date>`) goes when an auth mail (invite, reset or lock) fails; the web wiring calls `authMailFailed` (`apps/server/src/web.ts`, `authMailFailedHandler`). `trial_ending` counts only organizations with the plan `trial`. `llm_cap` is retried at the next hourly run when its send failed (`retryCaps`); the other events are found again by the hourly run itself. `channels.operator` runs hourly at minute 13 (`0 13 * * * *`). The operator chat id is private data and never reaches a log line.

12. **The `not_triaged` notice (F109, PD-067, flag `degraded_notice`, default off, remove-by 2027-03-01).** While the triage LLM is paused, every linked member learns that mail of a VIP or whitelisted sender waits. The text, English: `📭 Mail from <sender> is not triaged yet: the AI service is paused. It is triaged when the service is back.` (Polish `📭 Wiadomość od <sender> nie jest jeszcze posortowana: usługa AI ma przerwę. Zostanie posortowana, gdy usługa wróci.`). The view holds the sender address and two ids only (`emailId`, `mailboxId`); the text cuts the address to 40 characters. No subject, display name, body or summary. No button. The detector is `notTriagedDetector` (`apps/server/src/modules/channels/notices/not-triaged.ts`), the last one of the run order.
    - **Pause source.** The in-memory pause of the triage worker (`LlmPause`). `main.ts` builds one object and gives it to the triage job and to the notice job (`NoticeDeps.degraded = { pause, scope }`). It is not the audit-row pause of the `/status` line (rule 9): that one is per organization and ends a soft pause early. `pausedSince()` is the first trip since the last answer of the LLM (`reset()`). A restart clears the pause. With `TRIAGE_LLM_SCOPE=off` there is no worker, no `degraded` object and no notice.
    - **Candidates.** `pending` mail of the last 24 h in an `active` mailbox, from a sender that matches a whitelist or VIP rule (a whitelist rule wins over a blocklist rule, as in `applyHardRules`). With the scope `synthetic` only test mail counts.
    - **Cap.** At most 5 mails per mailbox with rows since `pausedSince()`, and one row per member per mail (dedup key `not_triaged:<email id>` per member), so a pause queues at most 5 × (the number of linked members) rows per mailbox. A mail with rows stays in the set, so a member linked later still gets its row. A mail that got rows in an earlier pause and is still `pending` is tried first (the dedup drops its row) and uses the cap slots of the new pause.
    - **Quiet hours.** The detector queues nothing between 22:00 and 07:00 (organization zone): if the pause lasts until 07:00, mail that still waits gets its notice then. A row queued shortly before 22:00 is held by the sender until 07:00 and can be out of date by then (accepted).
    - **Rows.** The kind is `one_mail` in `NOTICE_MAIL_CONTENT` (`emailId` set), so the erase of a mail removes its row. The text and view follow `clearOutboxTexts` (90 days). No consent bump: the sender address is a kind of data that the consent text names already.
    - **Check against the code:** the detector sends to every linked member and does not check `linkedAt` (the urgent detector does): the notice tells the current state. A pending `not_triaged` row is not cancelled when the mail is triaged before the send, so the text can say "not triaged yet" for a triaged mail (accepted: no "back" message). If the released mail is deleted before triage retries, a later pause keeps the old `pausedSince` (`reset()` runs after a good LLM answer only), so that pause can queue fewer than 5 notices; it fails toward fewer messages.
13. **Card edits (F102, kind `approval_edit`).** When a decision changes a send, each owner's Telegram card of that send follows, so a card never keeps a Send button for a send that is decided. The rules of the decisions are in [drafts-and-send.md](drafts-and-send.md) rules 13 and 14; this rule holds what the outbox does.
    - A row edits the stored text of the card (`outbox.text` of the target; `outbox.edit_of_outbox_id` points at it) and adds one status line (`approvalEdit`, `renderNoticeEdit`): approved, approved and held, rejected, changed in the panel, or expired. A `sent` card with a message id and a text becomes one row. A `pending` card (not sent yet) becomes `failed` / `answered_elsewhere` at once: nobody saw it. A card in `sending` gets no row (a tap on it answers by the state of the send).
    - The sender skips quiet hours for these rows (an edit makes no sound), still counts them in the per-user limit, and edits the message in place (`ChatChannel.edit`; no new message). Before the edit it checks the target with the same organization and user: no `sent` card, no message id, a text that retention removed, or a card that went out before the user linked another chat (or the same chat again) ends the row `failed` / `no_target`; a send whose state no longer matches the outcome of the row, or a newer edit of the same card that already went out, ends it `failed` / `stale_edit`. A Telegram refusal (`blocked`, `bad_request`) ends it `failed` / `edit_failed` and is not tried again; a soft error, a rate limit or a config error release the row like any other.
    - A failure while the decision queues the rows is logged (`card_edits_not_queued`) and never undoes the decision. The edit rows hold the card text that the user already got plus fixed phrases; no new kind of mail data reaches Telegram, so `TELEGRAM_CONSENT_VERSION` did not change.

## Data

- `outbox`: one row per notice and member. Columns: `kind` (the kinds of `noticeKinds` in `packages/core/src/notices/kinds.ts`; rule 5 lists them, and `approval_edit` is the edit of an approval card), `edit_of_outbox_id` (kind `approval_edit` only: the sent card that the row edits), `dedup_key` (unique per organization and user), `email_id`, `mailbox_id`, `digest_id`, `view` (the facts, jsonb), `channel` (`telegram`), `locale` (`pl` or `en`), `detail` (`full`), `text` (the cache of the sent message; null until the send) and `buttons` (the same cache; `[]` until the send), `status`, `attempts`, `next_attempt_at`, `locked_at`, `sent_at`, `external_message_id`, `error_code`, `created_at`. The text and the view follow the retention of `docs/architecture.md` §7 (`clearOutboxTexts`, 90 days); removing a mailbox drops the `pending` and `sending` digest rows and clears the text and view of the sent and failed ones.
- Status flow of `outbox.status`: `pending → sending → sent` (the sender claims a due row and sets `locked_at`); `sending → pending` (released with a new `next_attempt_at`: quiet hours, the per-user limit, a rate limit, a soft error); `sending → failed` with an `error_code` of rule 7; `pending → failed` (`outdated`: the notice is not true any more, or the plan became `suspended`).
- `digests`: one row per member and slot (`slot_key`, `period_start`, `period_end`, `sent_at`); unique per organization, user and slot.
- `chat_links` (one Telegram chat per member) and `chat_link_tokens` (`token_hash`, `expires_at`, `used_at`).
- `memberships.digest_times` (`time[]`, default `{08:00,16:00}`), `organizations.timezone`, `users.locale`.
- Audit events: `chat.linked`, `chat.unlinked`, `web.telegram_consent`, `operator.notice`.

## Limits

- Telegram only: no mail channel for the digest and the report (E4-B F110; ADR 0022 is proposed) and no push (E9b F118; ADR 0032 is proposed). `noticeChannels` holds `telegram` only and `noticeDetails` holds `full` only.
- Every Telegram text follows `users.locale`; null → Polish (`textsFor(locale)` returns the table of the locale from `packages/core/src/texts/`). A user with no stored language gets Polish Telegram text at once (owner decision). The chat takes its locale from the link; `/start` with a used or expired token takes it from the token owner. A user with `en` reads the English texts, byte for byte as before. Rows queued before the switch hold `locale = 'pl'` for null users with English stored text; a tap on such a card adds a Polish status line to the English card. The approval buttons stop working after 48 h, but the buttons Gotowe, Wysłano and "To był błąd" work for up to 7 days, so the mixed edit can show for up to 7 days (old cards keep their English text and get Polish status lines on edit). The command menu follows the app language of Telegram, not `users.locale`.
- The quiet hours hold every kind except the digest and `approval_edit`. The default is one constant (`22:00`–`07:00`); with the flag `user_quiet_hours` each member has their own hours (rule 3a). A per-user route per kind is PD-094 (E9b F118).
- The digest lists at most 15 items; the rest is a `+N more` line. There is no web list of past digests.
- The operator notices go to one chat by a direct send, with no outbox row, no queue and no quiet hours. A failed `auth_mail_failed` notice is not tried again.

## Decisions

- ADR 0005 (Telegram first, behind a `ChatChannel` port).
- ADR 0022 (proposed: digest and report as mail into the user's own INBOX) and ADR 0032 (proposed: Web Push and Telegram detail per user; point 5, notices as facts, is built by F088). PD-033 (digest and report as mail, quiet hours per user), PD-094 (notice routing per user and kind).
- `docs/architecture.md` §6.2 keeps the Telegram integration rules (one bot per environment, long polling, private chats, plain text, token handling, the fake Bot API).

# Digest and notices

> Checked against the code at `8b2eac9`, 2026-11-14.

## What it does now

Every message that the system sends to a person goes through Telegram. A user links one private chat to their account with a one-time token. After that, the digest job queues a digest at each of the member's times (default `08:00` and `16:00`, in the organization time zone), and the notice job queues notices for urgent mail, mailbox and sync problems, approval requests, send results and delegation answers. Both write rows to the table `outbox`. A row holds the facts of the message (a view), not its text. The outbox sender renders the text when it sends. It sends at most 3 messages per user per tick, waits through the quiet hours (`22:00`–`07:00`) for every kind except the digest, and fails a row that is older than 24 h. The user answers with the commands `/digest`, `/status`, `/pause`, `/resume` and `/help`, and with buttons under the messages. The operator gets a separate set of plain messages in one chat (`OPERATOR_TELEGRAM_CHAT_ID`). All of this runs only when `TELEGRAM_BOT_TOKEN` is set; the operator notices run in every case.

## Rules

1. **Chat linking.** `bun run telegram:link` (or `POST /api/channels/telegram/link` from the web panel) makes a one-time token for one member: 32 random bytes, valid 15 minutes, stored as a SHA-256 hash only. A new token makes the older unused tokens of the member invalid. The user opens `t.me/<bot>?start=<token>`. The bot stores the chat in `chat_links` (one chat per member, one member per chat) and answers with the help text. A chat that was linked to another member moves: the old link goes and gets the audit row `chat.unlinked` (`reason_code` `chat_moved`). A used token answers "This link was used already. Ask for a new link." (or "This chat is linked already" for a linked chat); an expired token answers "This link has expired (a link works for 15 minutes). Ask for a new link."; an unknown token gets no reply (a linked chat gets the help text). `bun run telegram:unlink` and `DELETE /api/channels/telegram/link` remove a link (audit row `chat.unlinked`). The bot rules for the chat guard and the token text are in `docs/architecture.md` §6.2.
2. **The update router** (`createTelegramBot`): chat guard (private chats of people only), `/start` linking, link guard (an update from an unlinked chat gets no reply), commands, buttons, then any other message of a linked chat (it gets the help text). The tenant comes from the link, never from the update.
3. **The digest job.** `channels.digest` runs every minute (second 5) and visits every linked chat of an organization that is not `suspended`. Per member it reads `memberships.digest_times` (at most 6 times, `HH:MM`), the organization time zone and the last digest slot. It queues the newest slot that is due: not older than 6 hours (`DIGEST_LATE_MS`), not in the future, and after the last slot of the member or the link time. Earlier missed slots are skipped, so a server that is back within 6 hours sends one digest, marked "(late)" when it is more than 10 minutes late. A slot key is the local wall-clock string `YYYY-MM-DDTHH:MM`, so a daylight-saving change gives no double and no lost digest. One digest row (`digests`) and one outbox row go in one transaction per member and slot; the outbox row is marked `sent` and the digest row gets `sent_at` in the sender's transaction.
4. **The digest message** (`renderDigest`, one message of at most 4096 characters and at most 15 lines). Header (`📬 Digest HH:MM · <day>`), the count line, one line per mailbox (last sync, `paused`, `login error`), the section `NEEDS ACTION` (`urgent`, `needs_reply`, `delegation`, `unsure`), the section `OTHER MAIL` (`info`, `notification`, `spam`), then footer lines: `+N more`, mail skipped as older than 7 days (`too_old`), mail skipped after an account pause (`suspended_backlog`), mail waiting for triage, open and overdue delegations, and "Shadow mode: the system changed nothing in your mailbox." Each item line shows the category, the sender, the subject, the AI text and what the system did or would do. Buttons: per item `✅ n` (the category is right), `✏️ n` (pick another category) and, while an Undo is possible, `↩️ n`, two items per row. The period of a digest starts at the end of the last sent digest (a failed digest does not move it), at most 7 days back; the first digest looks back 24 h before the link. The digest holds no mail bodies (ADR 0005). `/digest` builds the same message for the period up to now and sends it at once, with no `digests` row and no outbox row.
5. **The notice job.** `channels.notifier` runs every 15 s: `detectNotices`, then the outbox sender. Per organization (a failure of one does not stop the next), the detectors run in this order: urgent, action failed, auth error, sync, approval, approval set, send result, delegation answered. Each one finds its event, builds a view and calls `queueNotice`; the dedup key `(org, user, dedup_key)` keeps one row per event and member. The kinds:

6. **Notices (S2)** (moved from `docs/architecture.md` §8): urgent mail goes to every linked member (24 h look-back, one notice per mail). `auth_error`, sync late and sync works again go to linked owners only.
   Notices never go out in quiet hours (22:00–07:00 in the organization timezone); they wait until 07:00. Digests go out at their times.
   Sync late: an `active` mailbox whose last good sync is older than 30 min, not within 30 min after the mailbox became `active` again,
   and only 10 min after the process started. One notice per episode (the episode is the `last_synced_at` value). When the sync is fresh again, a sent
   "late" notice gets one "sync works again" notice. An unsent notice that is out of date becomes `failed` / `outdated`. A paused mailbox gets no urgent or sync notice.
   - Check against the code: the quiet hours hold every kind except the digest, not the S2 kinds only. An `approval`, `approval_set`, `send_result`, `delegation_answered`, `action_failed` and `mailbox_removed` row waits until 07:00 too (`sender.ts`: `row.kind !== "digest" && isQuietTime`). A held row is released to `quietEnd(now, timezone)` with no attempt counted. `QUIET_HOURS` is a constant in `packages/core/src/digest/local-time.ts`; a user cannot change it. The 24 h expiry counts from `created_at`, so a row queued at 21:50 expires at 21:50 the next day, after the quiet hours.
   - Check against the code: after the resume of a `suspended` organization the sync grace and the urgent look-back count from `resumed_at` (`detectSync`, `detectUrgent`; the resume rules are in `docs/architecture.md` §8, "Plan state"). Mail whose `source_folder` is the spam folder of its mailbox is in the digest but gets no urgent notice (`detectUrgent`, `getJunkFolderPath`).
   - Check against the code: an `auth_error` row that is still `pending` when the mailbox leaves `auth_error`, and a `sync_stale` row that is pending when the mailbox is fresh, paused or in its grace time, becomes `failed` / `outdated` (`cancelPendingOutbox`).
7. **The outbox sender** (moved from `docs/architecture.md` §8, the S2 jobs sentences): `channels.notifier` every 15 s (notice detection, then the outbox sender; at most 3 messages per user per tick;
   a 429 waits `retry_after`, a network error or HTTP 5xx backs off from 30 s to 15 min, a 401 pauses sending for 10 min,
   a 403 marks the row `failed` / `blocked`, a row older than 24 h becomes `failed` / `expired`) and `channels.digest` every minute
   (the digest at each member's times in the organization timezone; a missed slot is sent if the server is back within 6 hours).
   - Check against the code: the sender claims up to 20 due rows per run (`FOR UPDATE SKIP LOCKED`; a `sending` row with a claim older than 5 min is taken again, and its log line warns that a duplicate is possible). A row with a stored `text` goes as it is (rows queued before F088); every other row is rendered now with `renderNotice(kind, view, { channel, detail, locale })`. A view that does not render fails the row as `bad_view`. The rate limit (429) and a soft error (network, 5xx) pause the whole sender, not one row; the 401 pause is 10 min and logs "check TELEGRAM_BOT_TOKEN". A 400 fails the row as `bad_request`. Any other error is tried again with the same back-off and fails the row as `too_many_errors` at the fifth try. A member without a chat link fails the row as `no_chat`. The failure codes are `blocked`, `bad_request`, `expired`, `no_chat`, `outdated`, `too_many_errors` and `bad_view` (`outboxFailCodes`). The digest row also sets `digests.sent_at` in the same transaction as `markOutboxSent`.
   - Check against the code: `channels.notifier` and `channels.digest` are registered only when `TELEGRAM_BOT_TOKEN` is set (`apps/server/src/main.ts`); without the token the start log says `telegram_off` and no outbox row is sent. `channels.operator` is registered in every case.
   - Delivery is at least once: a duplicate is possible when the process dies or the network breaks between the Telegram answer and the DB commit (`docs/architecture.md` §6.2).
8. **Notices as facts (ADR 0032 point 5, F088).** A producer never builds the text of a message. `queueNotice` takes `{ userId, locale, kind, view, dedupKey }`, encodes the view (`encodeNoticeView`: dates as ISO strings, no lone surrogate, no NUL), checks it against the strict schema of the kind (`noticeViewSchemas`) and renders it once; a view that does not render never enters the outbox (`NoticeViewError`, a message with the kind only). The sender renders again at send time with the `locale` of the row (`users.locale`, null = `pl`). `outbox.text` and `outbox.buttons` are the cache of the sent message: null and `[]` until the send. The renderers (`noticeRenderers`, one per kind and one function per channel and detail level) give the `en` text for both locales until E7-T1 adds the `pl` texts (F098). The edit after a tap keeps the stored text of the card and adds one status line (`renderNoticeEdit`). The checklist "Add a notice kind" and the rules of a view change are in `docs/code-patterns.md` § Notices are facts. Direct replies (command answers, tap answers, the link texts, the operator notices) are not outbox rows.
9. **Commands** (`commands.ts`, `BOT_COMMANDS`; the list is set with `setMyCommands` at each start). Every command except `/help` and every tap answers "⏸ This account is paused…" with `OPERATOR_CONTACT` (or "the operator") when the organization is `suspended`; `/start` linking still works.
   - `/digest`: the digest now (rule 4, no row).
   - `/status`: per mailbox the address, the mode, the status, the last sync (marked "(late)" after 30 min) and the LLM calls of the quota day against `LLM_DAILY_CAP`; then the triage scope, the actions scope with the counts of the last 24 h, the approvals that wait (with the cause of an approved send that is held), the send scope, the delegations, the LLM provider and model, the next digest time and the quiet hours.
   - `/pause` and `/resume`: owners only. They switch every mailbox of the organization, one transaction each (audit rows with `via` `telegram`); a mailbox in `auth_error` is skipped with a hint to run `bun run mailbox:password`.
   - `/help`: the command list and what the buttons do.
10. **Callback prefixes** (`packages/core/src/digest/callback.ts`; `callback_data` is at most 64 bytes; old or forged data parses to null). `fr:<cat>:<email>` the category is right; `fc:<cat>:<email>` a category is picked; `fe:<email>` open the picker; `fx:<email>` cancel the picker; `fu:<email>` Undo ([actions-and-undo.md](actions-and-undo.md)); `ap:<action>` approve a send; `ar:<action>` reject a send; `as:<set>` approve a set; `rs:<set>` reject a set; `ag:<action>` send again; `gw:<action>` mark a send as gone out; `dd:<delegation>` close an answered delegation. The category codes are `u`, `r`, `i`, `n`, `s` (urgent, needs reply, info, notification, spam). `handleCallback` in `callbacks.ts` routes them; the tenant comes from the link, and an unknown mail id and a mail of another organization give the same answer. The approval taps are described in [drafts-and-send.md](drafts-and-send.md), the feedback taps in [triage.md](triage.md), the Undo tap in [actions-and-undo.md](actions-and-undo.md), the delegation tap in [delegation.md](delegation.md).
11. **Operator notices (S6a)** (moved from `docs/architecture.md` §8): `channels.operator` sends three events to the operator chat `OPERATOR_TELEGRAM_CHAT_ID` by a direct send, or writes a `warn` log line when the key is empty. The texts hold ids, dates and counts only. The events and their keys are `trial_ending` (`trial_ending:<org id>:<trial_ends_at ms>`, 3 days before the end and after it), `llm_cap` (`llm_cap:<mailbox id>:<quota day start>`, sent by the triage job when a mailbox reaches `LLM_DAILY_CAP`) and `auth_error_24h` (`auth_error_24h:<mailbox id>:<status_changed_at ms>`, a mailbox in `auth_error` for 24 h). The dedup is an audit row `operator.notice` with the key, written after a successful send: a crash between the send and the row repeats one notice (at least once). A failed send is tried again at the next hourly run. Quiet hours do not apply. A suspended organization gets no `trial_ending` or `auth_error_24h` notice.
    - Check against the code: there are four events, not three. `auth_mail_failed` (`auth_mail_failed:<user id>:<code>:<UTC date>`) goes when an auth mail (invite, reset or lock) fails; the web wiring calls `authMailFailed` (`apps/server/src/web.ts`, `authMailFailedHandler`). `trial_ending` counts only organizations with the plan `trial`. `llm_cap` is retried at the next hourly run when its send failed (`retryCaps`); the other events are found again by the hourly run itself. `channels.operator` runs hourly at minute 13 (`0 13 * * * *`). The operator chat id is private data and never reaches a log line.

## Data

- `outbox`: one row per notice and member. Columns: `kind` (the eleven kinds of rule 5), `dedup_key` (unique per organization and user), `email_id`, `mailbox_id`, `digest_id`, `view` (the facts, jsonb), `channel` (`telegram`), `locale` (`pl` or `en`), `detail` (`full`), `text` (the cache of the sent message; null until the send) and `buttons` (the same cache; `[]` until the send), `status`, `attempts`, `next_attempt_at`, `locked_at`, `sent_at`, `external_message_id`, `error_code`, `created_at`. The text and the view follow the retention of `docs/architecture.md` §7 (`clearOutboxTexts`, 90 days); removing a mailbox drops the `pending` and `sending` digest rows and clears the text and view of the sent and failed ones.
- Status flow of `outbox.status`: `pending → sending → sent` (the sender claims a due row and sets `locked_at`); `sending → pending` (released with a new `next_attempt_at`: quiet hours, the per-user limit, a rate limit, a soft error); `sending → failed` with an `error_code` of rule 7; `pending → failed` (`outdated`: the notice is not true any more, or the plan became `suspended`).
- `digests`: one row per member and slot (`slot_key`, `period_start`, `period_end`, `sent_at`); unique per organization, user and slot.
- `chat_links` (one Telegram chat per member) and `chat_link_tokens` (`token_hash`, `expires_at`, `used_at`).
- `memberships.digest_times` (`time[]`, default `{08:00,16:00}`), `organizations.timezone`, `users.locale`.
- Audit events: `chat.linked`, `chat.unlinked`, `operator.notice`.

## Limits

- Telegram only: no mail channel for the digest and the report (E4-B F110; ADR 0022 is proposed) and no push (E9b F118; ADR 0032 is proposed). `noticeChannels` holds `telegram` only and `noticeDetails` holds `full` only.
- English texts only: the `pl` renderers come with E7-T1 (F098).
- The quiet hours are a constant for every user and every kind except the digest. Per-user quiet hours and a per-user route per kind are PD-033 and PD-094 (E4-B F110, E9b F118).
- The digest lists at most 15 items; the rest is a `+N more` line. There is no web list of past digests.
- The operator notices go to one chat by a direct send, with no outbox row, no queue and no quiet hours. A failed `auth_mail_failed` notice is not tried again.

## Decisions

- ADR 0005 (Telegram first, behind a `ChatChannel` port).
- ADR 0022 (proposed: digest and report as mail into the user's own INBOX) and ADR 0032 (proposed: Web Push and Telegram detail per user; point 5, notices as facts, is built by F088). PD-033 (digest and report as mail, quiet hours per user), PD-094 (notice routing per user and kind).
- `docs/architecture.md` §6.2 keeps the Telegram integration rules (one bot per environment, long polling, private chats, plain text, token handling, the fake Bot API).

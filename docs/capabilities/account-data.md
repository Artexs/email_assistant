# Account data

> Checked against the code at `83fd450b`, 2026-11-14.

## What it does now

An owner can delete the whole organization from the Account card (Settings), with the password and the typed organization name. The dialog sits behind the flag `org_delete` (off by default). The delete runs at once, in one database function, ends the session and shows the mailbox addresses on the login page, so the owner can change the mailbox passwords. The operator has three CLIs. `org:delete` does the same delete. `org:export` writes every table of the organization to a file that is encrypted to one `age` public key. `org:dsr` finds and erases the data of a person who is not a user (a sender) on the owner's written instruction, and writes tombstones, so that sync, rescan and backfill do not store the erased mail again. The erase also blanks the stored Telegram digests and approval sets that can list the erased mail. Export, refused delete attempts and both DSR commands show in the owner's security log. Code: the module `privacy` (`apps/server/src/modules/privacy`). The runbook is `deploy/README.md` § Account data (F106).

## Rules

1. **Delete by the owner (route).** `DELETE /api/organization` (`privacyRoutes`). The order is the rule, and each answer is final: owner (`403 owner_only`), flag `org_delete` (`404 not_found` when off), body, typed name (`400 wrong_name`; no audit row and no lockout count), lockout (`429 locked`), password (`400 wrong_password`), delete. The tenant comes from the session, never from the body. The typed name matches after trim, case-insensitive, with NFC (`orgNameMatches`, `packages/core/src/web/org-name.ts`). The route works for a `suspended` organization (`SUSPENDED_WRITE_ALLOW`, `platform/http.ts`).
   - A wrong password counts as a failed sign-in for the lockout (`recordPasswordFailure`; 10 in 15 minutes lock the user, see `web-panel.md` rule 4) and writes the audit row `org.delete_refused` (`reason`, `via`). A right password does not reset the count.
   - After the delete the route answers `{ mailboxAddresses }` and appends the `Set-Cookie` line that ends the session.
   - A lock wait that runs past the lock timeout gives `busy`: the route answers `503 internal`, a `org_delete_busy` warn line, and changes nothing. The owner may try again.
2. **The delete function.** `deleteOrganization` (`modules/privacy/delete.ts`) runs one transaction with `lock_timeout` 30 s (the CLI flag `--lock-timeout-ms` changes it): lock the organization row, check the typed name, read the mailbox addresses, lock the member users in id order, call `delete_organization(org_id)`. A deadlock (40P01) is run once more. Result kinds: `deleted`, `not_found`, `name_mismatch`, `busy`. The log line `org_deleted` holds the id and `kind` (`web` or `cli`), never a name or an address.
3. **`delete_organization(uuid)`** (migration `db/migrations/20261114160001_account_data.sql`). `SECURITY DEFINER`, `EXECUTE` only for `app`, a fixed `search_path`; its first check refuses another organization when `app_current_org()` is set. It deletes the audit rows of the organization (`app` has no `DELETE` there), the `auth_verifications` rows of the users that go, those users, then the organization; every table with `org_id` goes by cascade. A user whose only membership is this organization goes. A user with another membership stays, with the auth rows. The test `account-data-delete.test.ts` reads `information_schema` for every table with `org_id` or `user_id` and fails for a table without a seed, so a new table cannot escape the delete.
4. **Delete by the operator.** `bun run org:delete --org-id <uuid> --confirm <organization name> [--lock-timeout-ms <ms>]` calls the same function with `via: "cli"` and has no flag check. It prints `deleted <org id>: mailboxes <n>` and one line `change the password of <address>` for each mailbox. This is the one place where a CLI prints addresses; it never prints the organization name. Exit 1 for `not_found`, `name_mismatch` and `busy` (`busy, try again` on stderr).
5. **The dialog and the login page.** The owner sees the delete block only with the flag `org_delete` (`canDeleteOrganization`; the server checks both again). The dialog states what goes and what stays (drafts and folders that the assistant made stay in the mailboxes; backups keep the data until they expire). The mailbox addresses go through `sessionStorage` (`ea.deleted_mailboxes`) to the login page, which lists them once and removes the key. A marker `ea.deleting` covers the case that the poll of `/api/me` sends the page to the login page before the answer arrives.
6. **Export.** `bun run org:export --org-id <uuid> --recipient <age1…> --out <path>` (`exportOrganization`). One `REPEATABLE READ READ ONLY` transaction reads each table of `EXPORT_MAP` (`modules/privacy/export-map.ts`) in primary-key order, in batches of 500 rows, as JSON (`format: ea-org-export`, `version: 1`). The text goes through the `age` encrypter in chunks, so no plain text is written to disk. The bytes go to `<out>.part` (mode 600, create only); `link` then makes `<out>`, so an existing file is never replaced (`exists`, exit 1). The audit row `org.exported` (`tables`, `rows`) comes after the file is complete; if it fails, the file goes too. Stdout: `exported <org id>: <bytes> bytes` and `<table> <count>` for each table. The map classifies every table and column: the file holds no password hash, credential, token or session (`auth_*`, `chat_link_tokens`, `mailbox_credentials` and `dsr_tombstones` are `export: false`; `users` is an allow-list of columns for the members). The test `privacy-export-map.test.ts` compares the map with `information_schema`. Passphrase mode does not exist.
7. **DSR: the address and the match.** `normalizeDsrAddress` trims and lower-cases and returns null unless the value is one plain address (`bad_address`). `DSR_ADDRESS_MAP` (`modules/privacy/address-map.ts`) lists each column that can hold a third party's address with its rule: `sender`, `recipients`, `text`, `json`, `equal` or `list`. `NOT_PERSONAL` and `NO_PERSONAL_TABLES` give the reason for each other candidate column; a completeness test fails for a candidate column that is in none of them. `matchSubject` (`dsr-match.ts`) is the one match for find and erase:
   - **Mails that go:** the person is the sender, the only Reply-To, or the only party besides the organization's own mailboxes (To and Cc). Other rows lose the address.
   - **Mentions:** the rows of kept mails (and of no mail) whose mapped column holds the address (`table.column` → row ids).
   - **Listed, never changed:** delegates (`email`, `name`) and sender rules (`pattern`) that equal the address. The operator tells the owner; they stay until the owner changes them.
   - **Open actions:** an action of a mail that goes that is `applying` or a `send` or `create_draft` that has not ended; an action of a kept mail that has not ended and whose payload names the address.
   - **Chain actions and chain delegations:** actions of kept mails that depend on or reverse (over any number of steps) an action of a mail that goes, and the delegations of kept mails whose draft or send action is deleted by the erase. The foreign keys have no cascade for the first, so the erase deletes them first; the delegations go with their action by cascade. Both are counted.
   - **Own address:** a mailbox of the organization or the e-mail of a member gives `own_address` (refused).
8. **The address pattern.** `addressRegex` is one Postgres pattern for find and erase (case-insensitive). The address is a whole word: `jimbob@x.test`, `o'bob@x.test`, `bob@x.test.pl` and `bob@x.test_x` do not match `bob@x.test`; `bob@x.test.` (end of a sentence), `<bob@x.test>`, `"bob@x.test"`, `smtp.mailfrom=bob@x.test` and an address after a line break match. In a jsonb value (`json: true`) a line break is the escape `\n`, so the pattern accepts such an escape in front. Limits of the pattern are in § Limits.
9. **Find.** `bun run org:dsr --org-id <uuid> --address <address> --find [--recipient <age1…> --out <path>]` (`findSubjectData`). One `REPEATABLE READ READ ONLY` transaction; counts only on stdout: `mails`, `mention <table.column> <n>`, `listed delegates`, `listed sender_rules`, `open actions`, `chain actions`, `chain delegations`, and `report <bytes> bytes` with a report. The report is encrypted to the `age` key and holds the whole mail of each mail that goes, and only table, column and id for kept rows. A find that matches nothing prints `warning: no match, check the spelling of the address` on stderr and exits 0. A refusal (`own_address`, `bad_address`, `not_found`, `exists`) exits 1 and writes no audit row. One audit row `dsr.find` per run.
10. **Erase.** `bun run org:dsr --org-id <uuid> --address <address> --erase --confirm <address>` (`eraseSubjectData`). `--confirm` must equal the address after normalizing (`confirm_mismatch`). One transaction in the tenant scope of the organization (RLS backs up every `org_id` filter) with `lock_timeout` 30 s. The order:
    1. Lock the organization row (`FOR NO KEY UPDATE`: two erases and an org delete take turns; mail work goes on) and every `mailbox_folders` row of the organization (`FOR UPDATE`: the lock that every sync and backfill chunk takes in `applyChunk`, so a chunk that was planned before the erase meets the tombstone).
    2. Match. Refuse with `own_address` or `open_actions` (the CLI prints `open action <id>`; the owner rejects or finishes those sends, then the operator runs the erase again).
    3. Lock the mails that go and ask for open actions once more under the lock (a triage job may have added a send in between).
    4. Insert one tombstone per mail: the SHA-256 of the dedup key without a `#<n>` copy suffix.
    5. Delete the chain actions, then the mails (the rest of the mail rows go by cascade).
    6. The outbox step (rule 12).
    7. Scrub every kept row of the mapped columns: a `text` column replaces the address by `[removed]` (cut to its `CHECK` length: `TEXT_LIMITS`); a `json` column is cast to text, replaced and cast back; a `recipients` element is removed; an `equal` value is emptied.
    8. Match again; any mail or mention left throws `dsr_erase_incomplete` and rolls back everything.
    9. One audit row `dsr.erase`.
    - A foreign key that the erase did not expect stops it with `blocked <constraint>` (a bug; nothing changed). Stdout: `erased mails`, `tombstones`, `chain actions`, `chain delegations`, `scrubbed <table.column> <n>`, `blanked outbox`, `dropped outbox`, `kept delegates`, `kept sender_rules` and the line `record: dsr erase <org id> <date>`. The runbook keeps that line off the server (rule 15).
11. **Tombstones.** `dsr_tombstones` (`org_id`, `key_hash`) per organization. The trigger `emails_skip_tombstoned` runs `BEFORE INSERT` on `emails` and returns NULL for a mail whose base dedup key has a tombstone. `insertEmail` uses `ON CONFLICT DO NOTHING`, so it answers `false` and sync, rescan and backfill store nothing and raise no error. Any insert path is covered, also one that is added later. A tombstone has no expiry; it goes with the organization. A mail that was never stored when the erase ran has no tombstone (§ Limits).
12. **Digests and approval sets (the outbox step).** `eraseManyMailOutbox` (`modules/privacy/outbox.ts`). A stored digest or approval set lists several mails and holds no mail id, so the address pattern misses it. The registry `NOTICE_MAIL_CONTENT` gives each `NoticeKind` one class: `one_mail` (the row has `email_id` and goes with its mail), `many_mails` (digest, `approval_set`) or `no_mail`. A new `NoticeKind` fails `bun run typecheck` until it has a class. Since the earliest created time of the erased mails: a `sent` or `failed` row of a `many_mails` kind gets the text `[removed]` and an empty view (`outbox_blanked`); a `pending` or `sending` digest is deleted (`outbox_dropped`; the next slot covers the period); a waiting approval set whose sends all closed (and a stale `sending` one) is closed as `failed` / `outdated` and blanked, with the rule of the resume hook (`closeWaitingApprovalSetsSince`, `modules/channels`). A fresh `sending` set is in flight and finishes. A `pending` set whose send still waits stays: the open-action refusal means that no such request names a mail that goes. This also blanks the stored copy of other mails' digests of that time.
13. **The hash.** The audit rows of find and erase hold `address_hash`, never the address: HMAC-SHA256 hex of the normalized address. The key is HKDF-SHA256 of `CREDENTIALS_KEY` (empty salt, info `ea/dsr-address/v1`, 32 bytes), so no new secret exists. The same address gives the same hash in every organization (accepted, plan question 3). A change of `CREDENTIALS_KEY` makes old hashes unmatchable. The audit data is flat: `mails`, `mentions`, `listed_delegates`, `listed_sender_rules`, `open_actions`, and for an erase also `tombstones`, `chain_actions`, `chain_delegations`, `outbox_blanked`, `outbox_dropped`.
14. **Locks and results.** Erase and delete set `lock_timeout` (30 s). A lock wait that runs past it ends the transaction with nothing changed: `org:delete` and the route report `busy`; `org:dsr` logs `org_dsr_failed` and exits 1; run the command again. A deadlock is run once more.
15. **Restore.** A backup restore brings back the deletes and erases made after the backup. The operator keeps each `deleted …` line of `org:delete` and each `record: …` line of `org:dsr` outside the server (the owner keeps the request) and runs the commands again after a restore, before the panel opens (`deploy/README.md` § Account data (F106)). No ledger table exists: a restore would roll it back too.
16. **Security log.** The audit events `org.exported`, `org.delete_refused`, `dsr.find` and `dsr.erase` map to the kinds `data_exported`, `delete_refused`, `dsr_find` and `dsr_erase` (`securityEvents`, `packages/core/src/security-log.ts`) and show in the Account card (`GET /api/security-log`, flag `security_log`). The actor of a CLI row is the operator. The delete itself has no row: the organization and its log go (plan question 1).
17. **Output rule.** No address, organization name, password, mail text or report content in a log line, error text or audit row. CLI stdout holds ids, counts, table and column names, paths and sizes; `org:delete` also prints the mailbox addresses.
18. **Registries for later tickets.** A migration that adds a table or column classifies it in `EXPORT_MAP`, and each new candidate column in `DSR_ADDRESS_MAP` or `NOT_PERSONAL`; a new table with `org_id` or `user_id` gets a seed in the delete test; a new mail table gets the tombstone trigger; a new notice kind gets its `NOTICE_MAIL_CONTENT` class (`docs/code-patterns.md` § Data access). Tests fail until each is done.
19. **Texts.** The new Polish texts follow `notes/2026-11-14-polish-ui.md`: informal "ty", at most one colon per line, no calques, names and addresses without a case ending. Decisions of the reviews (F105 stage 11 and F106 stage 04): "Błędne hasło" (not "Nieprawidłowe"), "Za dużo błędnych prób" for a lockout, "zachowują dane, dopóki nie wygasną" for backups, "przydaje się, gdy nie masz przy sobie telefonu". The same word "błędne hasło" stands in the security-log text of a refused delete. The keys are `del_*` (dialog and login notice) and `sec_kind_data_exported`, `sec_kind_delete_refused`, `sec_kind_dsr_find`, `sec_kind_dsr_erase` (rule 16).

## Data

`dsr_tombstones`: `org_id` (cascade), `key_hash` (64 hex characters), `created_at`; primary key (`org_id`, `key_hash`); RLS policy `tenant_rows`. The function `delete_organization(uuid)` and the trigger function `emails_skip_tombstoned()` with the trigger of the same name on `emails` (migration `db/migrations/20261114160001_account_data.sql`). The erase writes `emails`, `email_headers`, `triage_results`, `actions`, `outbox`, `delegations` and `dsr_tombstones` rows and one `audit_log` row. Audit events: `org.exported` (`tables`, `rows`), `org.delete_refused` (`reason`, `via`), `dsr.find`, `dsr.erase` (rule 13). Flag: `org_delete` (`packages/core/src/features.ts`; off by default; `org:flag --org-id <uuid> --flag org_delete --on` per organization). The CLIs have no flag.

## Limits

- The match is by the text of the address. An address in an attachment file name (`p@x.test.vcf`) is not matched: the look-ahead rejects `.vcf` after the address as a longer domain. The same rule keeps `a@b.com.pl` apart from `a@b.com`. An address at the boundary of single quotes or braces (`'p@x.test'`, `{p@x.test}`) is matched only at the start of the text or after a character that is not `atext`, because a quote or a brace is also a legal part of a local part.
- A mail that was never stored has no tombstone. Run `org:dsr --erase` again after a backfill, after the first sync of a newly enabled sync folder and after a newly connected mailbox: these can store mail of the person that was older than the sync window or in a folder that was not read.
- Telegram messages that were delivered stay in the chat; nothing can recall them (P2). The owner deletes them there. A fresh `sending` approval set (younger than `SENDER_STALE_MS`, 5 minutes) is in flight and can still reach Telegram. A sent approval card that the erase blanked can still be tapped; the answer then shows `[removed]`.
- The mailbox keeps the mail (the system never deletes mail in the mailbox), and the drafts and folders that the assistant made stay (PD-039). Backups keep the rows until they expire. A restore brings back the rows: rule 15.
- Delegates and sender rules that hold the address are listed, not deleted.
- Another organization may hold the same address; the hash is the same in each (accepted).
- A panel page for data requests: not built (PD-038). A grace period for the delete and a passphrase export do not exist.
- The legal papers that describe these steps: E7-T4 (F107).
- Edge case of the delete function (accepted): a user who is deleted with this organization, and who had a membership in another organization before, loses the user link in that organization's rows (`SET NULL`); `audit_log.actor` there keeps the id.

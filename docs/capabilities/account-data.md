# Account data

> Checked against the code at `05702e0c`, 2026-11-19.

## What it does now

An owner can delete the whole organization from the Account card (Settings), with the password and the typed organization name. The dialog sits behind the flag `org_delete` (off by default). The delete runs at once, in one database function, ends the session and shows the mailbox addresses on the login page, so the owner can change the mailbox passwords. The operator has three CLIs. `org:delete` does the same delete. `org:export` writes every table of the organization to a file that is encrypted to one `age` public key. `org:dsr` finds and erases the data of a person who is not a user (a sender) on the owner's written instruction, and writes tombstones, so that sync, rescan and backfill do not store the erased mail again. The erase also blanks the stored Telegram digests and approval sets that can list the erased mail. Export, refused delete attempts and both DSR commands show in the owner's security log. Code: the module `privacy` (`apps/server/src/modules/privacy`). The runbook is `deploy/README.md` § Account data (F106).

## Rules

1. **Delete by the owner (route).** `DELETE /api/organization` (`privacyRoutes`). The order is the rule, and each answer is final: owner (`403 owner_only`), flag `org_delete` (`404 not_found` when off), body, typed name (`400 wrong_name`; no audit row and no lockout count), lockout (`429 locked`), password (`400 wrong_password`), delete. The tenant comes from the session, never from the body. The typed name matches after trim, case-insensitive, with NFC (`orgNameMatches`, `packages/core/src/web/org-name.ts`). The route works for a `suspended` organization (`SUSPENDED_WRITE_ALLOW`, `platform/http.ts`).
   - A wrong password counts as a failed sign-in for the lockout (`recordPasswordFailure`; 10 in 15 minutes lock the user, see `web-panel.md` rule 4) and writes the audit row `org.delete_refused` (`reason`, `via`). A right password does not reset the count.
   - After the delete the route answers `{ mailboxAddresses }` and appends the `Set-Cookie` line that ends the session.
   - A lock wait that runs past the lock timeout gives `busy`: the route answers `503 internal`, a `org_delete_busy` warn line, and changes nothing. The owner may try again.
2. **The delete function.** `deleteOrganization` (`modules/privacy/delete.ts`) runs one transaction with `lock_timeout` 30 s (the CLI flag `--lock-timeout-ms` changes it): lock the organization row, check the typed name, read the mailbox addresses, lock the member users in id order, call `delete_organization(org_id)`. A deadlock (40P01) is run once more. Result kinds: `deleted`, `not_found`, `name_mismatch`, `busy`. The log line `org_deleted` holds the id and `kind` (`web` or `cli`), never a name or an address.
3. **`delete_organization(uuid)`** (migration `db/migrations/20261114160001_account_data.sql`). `SECURITY DEFINER`, `EXECUTE` only for `app`, a fixed `search_path`; its first check refuses another organization when `app_current_org()` is set. It deletes the audit rows of the organization (`app` has no `DELETE` there), the `auth_verifications` rows of the users that go, those users, then the organization; every table with `org_id` goes by cascade. A user whose only membership is this organization goes. A user with another membership stays, with the auth rows. The provider row of company sign-in (`sso_providers`, F119) goes with the organization by its `org_id` cascade, and with it the IdP client secret that its `oidc_config` holds. The SSO links and sessions of a user that goes (`auth_accounts`, `auth_sessions`) go with the user. A link of a user that stays remains as an unused `auth_accounts` row: its provider is gone, so it signs nobody in. The test `account-data-delete.test.ts` seeds a provider row. The test `account-data-delete.test.ts` reads `information_schema` for every table with `org_id` or `user_id` and fails for a table without a seed, so a new table cannot escape the delete.
4. **Delete by the operator.** `bun run org:delete --org-id <uuid> --confirm <organization name> [--lock-timeout-ms <ms>]` calls the same function with `via: "cli"` and has no flag check. It prints `deleted <org id>: mailboxes <n>` and one line `change the password of <address>` for each mailbox. This is the one place where a CLI prints addresses; it never prints the organization name. Exit 1 for `not_found`, `name_mismatch` and `busy` (`busy, try again` on stderr).
5. **The dialog and the login page.** The owner sees the delete block only with the flag `org_delete` (`canDeleteOrganization`; the server checks both again). The dialog states what goes and what stays (drafts and folders that the assistant made stay in the mailboxes; backups keep the data until they expire). The mailbox addresses go through `sessionStorage` (`ea.deleted_mailboxes`) to the login page, which lists them once and removes the key. A marker `ea.deleting` covers the case that the poll of `/api/me` sends the page to the login page before the answer arrives.
6. **Export.** `bun run org:export --org-id <uuid> --recipient <age1…> --out <path>` (`exportOrganization`). One `REPEATABLE READ READ ONLY` transaction reads each table of `EXPORT_MAP` (`modules/privacy/export-map.ts`, built from the slices `modules/privacy/export-map/tables-a-d.ts`, `tables-e-m.ts`, `tables-n-s.ts` and `tables-t-z.ts`) in primary-key order, in batches of 500 rows, as JSON (`format: ea-org-export`, `version: 1`). The text goes through the `age` encrypter in chunks, so no plain text is written to disk. The bytes go to `<out>.part` (mode 600, create only); `link` then makes `<out>`, so an existing file is never replaced (`exists`, exit 1). The audit row `org.exported` (`tables`, `rows`) comes after the file is complete; if it fails, the file goes too. Stdout: `exported <org id>: <bytes> bytes` and `<table> <count>` for each table. The rows of `sender_profiles` carry one more field, `address`: the plain address whose `senderKeyHash` equals the row's `key_hash`, looked up among the distinct addresses that the organization still holds (incoming senders in `emails.from_address_lower`, the To and Cc of `sent_emails`, the sender rule patterns that are addresses and the delegates' e-mails; `senderAddressesOfProfiles`), else `null`. It is the owner's copy of data about others, inside the encrypted file only. `sender_suggestions` is exported whole. The map classifies every table and column: the file holds no password hash, credential, token or session (`auth_*`, `chat_link_tokens`, `mailbox_credentials` and `dsr_tombstones` are `export: false`; `users` is an allow-list of columns for the members; `sso_providers` is exported without `oidc_config`, which holds the IdP client secret). The test `privacy-export-map.test.ts` compares the map with `information_schema`. Passphrase mode does not exist.
7. **DSR: the address and the match.** `normalizeDsrAddress` applies the one address rule (`normalizeAddress` in `@ea/core`: trim, which strips the 25 code points of `ADDRESS_TRIM_CHARS` (what `String.prototype.trim()` strips: tab, newline, NBSP, U+3000, U+FEFF and more; a unit test pins the set), lower case, a Greek final sigma `ς` becomes `σ`, a dotted capital I loses its dot) and returns null unless the value is one plain address (`bad_address`). `DSR_ADDRESS_MAP` (`modules/privacy/address-map.ts`) lists each column that can hold a third party's address with its rule: `sender`, `recipients`, `text`, `json`, `equal`, `list` or `delete`. `NOT_PERSONAL` and `NO_PERSONAL_TABLES` give the reason for each other candidate column; a completeness test fails for a candidate column that is in none of them. `matchSubject` (`dsr-match.ts`) is the one match for find and erase:
   - **Mails that go:** the person is the sender, the only Reply-To, or the only party besides the organization's own mailboxes (To and Cc). Other rows lose the address.
   - **Sent mails that go** (F104): a row of `sent_emails` where the person is the sender or in To or Cc and every other address of the three columns is an own mailbox of the organization (`DsrMatch.sentMails`, the same own list as for incoming mail). Other sent rows with the address are mentions. A mention never lists a sent mail that goes. A person who is only in sent mail is a match: no spelling warning.
   - **Open loops** (F116): `open_loops` copies recipients, the first recipient and a short ask or promise from sent mail. `counterpart` (`equal`), `to_addresses` and `cc_addresses` (`recipients`) and `subject` and `text` (`text`) are in `DSR_ADDRESS_MAP`; a loop is a mention, never a row that goes (its Sent row may go; the loop stays with `sent_email_id` null). The erase removes the address from the columns and, for a loop that names the person in `counterpart`, `to_addresses` or `cc_addresses`, sets `text` and `subject` to null and sets `texts_cleared_at` (`clearLoopTextsOfPerson`, before the scrub). The subject goes whole because it can be the copy of the subject of a sent mail that the same erase deletes. `thread_key` and `message_id` stay: they are opaque Message-IDs kept for matching, with no address and no text. A loop left with no recipient is closed `dropped` by the loop matcher (`loops.match`, `open-loops.md` rule 3); a `delegated` loop with no counterpart answers `not_allowed` to Draft. The follow-up payloads and cards of the loop (`actions.payload`, `outbox.text` and `view`: recipients, subject, quote) are scrubbed by address like other drafts, and a stored digest whose view names a cleared loop (`view.loopIds`) is blanked, or deleted while it is still pending, after the marks of its other loops go back (`blankDigestsNamingLoops`, `releaseMarksOfUndeliveredDigests`). An open follow-up stops the erase of its person like any open action. The export (`EXPORT_MAP`) writes the state and text of a loop (kind, status, close reason, subject, counterpart, recipients, text, due and close times) and only the codes of `sent_analyses`; matching ids and chaser counters stay out.
   - **Reply drafts** (F115): `reply_requests.instruction` and `sample_body` and `mailbox_profiles.display_name`, `signature` and `writing_style` are in `DSR_ADDRESS_MAP` (`text`). A request of a mail that goes is deleted with the mail (cascade); every other request or profile whose text holds the address is a mention, and the erase replaces the address by `[removed]` (cut to the limit of the column, `TEXT_LIMITS`). For a profile the row id of a mention is the mailbox id. The organization export holds the request texts and the profile texts, not the ids, the thread key or the job counters. The reply draft itself is an `actions` pair: its payload (`to`, `cc`, `body`, `body_text`, `folder`) is in the map as `json`, so a mention of the address is scrubbed there and the other recipients of a reply (Cc) are found by the address match. The kept `reply_requests` columns `trigger`, `status`, `reason_code`, `thread_key` and `folder` are classified as no personal text (`NOT_PERSONAL`).
   - **Unsubscribe requests** (F110): `unsubscribe_requests.sender_lower` is in `DSR_ADDRESS_MAP` with the rule `delete`: the row of the sender goes whole (a cleaned value would hit the unique key `(mailbox_id, sender_lower)` on the second erase). Its `sender_domain` is the end of the address and goes with the row. The row is a mention, never a row that goes with a mail. The organization export holds the whole row.
   - **Sender profiles and suggestions** (F120, sender context): `sender_profiles` holds no address: only the keyed hash of the address (`key_hash`, 64 hex characters, CHECK), dates and counts; its candidate columns are in `NOT_PERSONAL`. The match finds the profile rows of the person by recomputing the hash: `senderKeyHash(CREDENTIALS_KEY, org id, normalized address)` (`senderContextRowsOf`, `modules/contacts/privacy.ts`), in every mailbox of the organization (`DsrMatch.senderContext`: `profiles`, `suggestions`). `sender_suggestions` rows with that key are found too, also an ended row, which holds no pattern. `sender_suggestions.pattern` (the address or `@domain` of an OPEN suggestion) is in `DSR_ADDRESS_MAP` with the rule `delete` as well. A domain suggestion (`@acme.pl`) names a domain, not the person: its key is the hash of `@acme.pl`, so neither rule finds it and an erase of `anna@acme.pl` keeps it (owner question 5). The counts are `sender_profiles` and `sender_suggestions` (a suggestion found by both rules counts once). Both tables go with the mailbox (composite foreign key, cascade) and with the organization (`org_id` cascade), and are in the export map and in the category `sender-context`. A later refresh pass can write a profile row again for mail that the erase kept (the erase deletes only the mail of the person that goes; mentions stay); that row then counts only mail that still exists. After the one trim set (F137), the profile pass keys on the clean address: a sender whose stored From had a tab, NBSP, U+3000 or U+FEFF at an end gets a new profile row under the clean hash, and the old row (keyed hash and dates, no address) stays until retention (365 days). No cleanup job: the row holds no address, and the erase before that change missed it too.
   - **Trust ladder tables** (F110, [trust.md](trust.md)): `history_checks`, `history_check_items` and `autonomy_trips` hold codes, evidence keys, counts and costs, no mail text or address. They are in `EXPORT_MAP` (the export holds them whole), their candidate columns are in `NOT_PERSONAL` (`address-map.ts`) and each has a seed in the delete test. A `history_check_items` row goes with its mail (`email_id` cascades), so a DSR erase of a mail removes its item; the counts in `history_checks.result` and `autonomy_trips.counts` stay (counts only, no id, no address; decision kept in the stage 03 review). The mailbox, organization and `delete_organization` deletes remove the checks, items and trips. `memberships.quiet_start`, `quiet_end` and `report_channel` are `NOT_PERSONAL` (a time of day and a fixed word) and `report_mailbox_id` is cleared when its mailbox goes (`SET NULL (report_mailbox_id)`; the membership stays). `email_headers.list_unsubscribe_post` is a flag in the export. `email_headers.dkim_signatures` (signing domains and signed header names, never a signature value) is in the export whole, is `NOT_PERSONAL` in `address-map.ts`, and goes with the mail on a DSR erase of the mail.
   - **Push devices** (F118): `push_subscriptions` holds the endpoint and the keys of a member's browser only inside the encrypted `secret` and a hash of the endpoint. The export (`EXPORT_MAP`) holds the label, the session id, the times and the last error code and leaves out `secret`, `endpoint_hash` and `key_version`. Its text columns are in `NOT_PERSONAL` (`address-map.ts`), `push_subscriptions` has a seed in the delete test, and the table is in the category `push-devices`. A removed member, an organization delete and an account delete remove the devices by cascade. `memberships.notice_routes` and `memberships.telegram_detail` (the Telegram detail level, `full` or `minimal`) go with `memberships`; `organizations.telegram_minimal_locked` (the owner's lock) goes with the organization.
   - **Mentions:** the rows of kept mails (and of no mail) whose mapped column holds the address (`table.column` → row ids).
   - **Listed, never changed:** delegates (`email`, `name`) and sender rules (`pattern`) that equal the address. The operator tells the owner; they stay until the owner changes them.
   - **Open actions:** an action of a mail that goes that is `applying` or a `send` or `create_draft` that has not ended; an action of a kept mail that has not ended and whose payload names the address.
   - **Chain actions and chain delegations:** actions of kept mails that depend on or reverse (over any number of steps) an action of a mail that goes, and the delegations of kept mails whose draft or send action is deleted by the erase. The foreign keys have no cascade for the first, so the erase deletes them first; the delegations go with their action by cascade. Both are counted.
   - **Own address:** a mailbox of the organization or the e-mail of a member gives `own_address` (refused).
8. **The address pattern.** `addressRegex` (built in `modules/privacy/address-regex.ts`; `address-map.ts` re-exports it and holds the only SQL, `matchesAddress` and `replaceAddress`) is one Postgres pattern for find and erase. It is case-sensitive, and each letter of the asked address stands for every form that the program rule folds to it (`addressCaseForms` in `@ea/core`, a table built from `normalizeAddress` over all code points): `K`, `k` and the Kelvin sign for `k`; `ẞ` for `ß`; `Σ`, `σ` and `ς` for `σ`; `I`, `İ`, and `i` or `I` with a combining dot for `i`. So a dotless `ı` is not an `i` and `ſ` is not an `s`, exactly as in the equality match, and a Kelvin, Ohm or `ẞ` form in kept text is removed and found by the check after the erase. The only SQL that runs a pattern is `matchesAddress` (`~`) and `replaceAddress` (`regexp_replace(…, 'g')`) in `address-map.ts`; find, the scrub, the open-action test and the post-erase check use them, and a test fails when another file in the module runs a pattern. A letter, a digit or a combining mark next to the address makes a longer address (the boundary classes hold every cased code point and the combining mark blocks, whatever the database locale calls a letter). Every compare of a stored address column with the asked address goes through `normalizedAddress` (`platform/db/address-sql.ts`), the SQL form of the same rule, which trims the same set with `btrim(column, set)`; the two forms agree on every code point that a real address holds. The test `privacy-dsr-address-parity.test.ts` proves it on the test database: no difference in whitespace, none below U+0530, none in the letters of the 66 probes. On a server of version 17.x it asserts that the divergent code points are a subset of 28 known letters (the image `postgres:17` lowers U+A7CE, U+A7D2, U+A7D4 and U+16EA0 to U+16EB8 unlike Bun; its C library has an older Unicode table); on another version it prints the list. Find and erase check each asked address against this divergence at run time (`checkAddressRule`, `modules/privacy/rule-check.ts`): the database computes, for every code point 1 to 0x10FFFF, its SQL form and the program form (`divergentCodePoints`, once per process, about 1 s). The address is refused (`rule_mismatch`, rules 9 and 10) when a divergent code point has a program form or a database form that is a letter of the address (the database lowers less, or more, than the program), or has an empty program form (a trim difference). Else the equality match is exact for this address in both directions. No SQL fix map exists for the 28 letters (F137 D8). A plus address stays a separate address. The address is a whole word: `jimbob@x.test`, `o'bob@x.test`, `bob@x.test.pl` and `bob@x.test_x` do not match `bob@x.test`; `bob@x.test.` (end of a sentence), `<bob@x.test>`, `"bob@x.test"`, `smtp.mailfrom=bob@x.test` and an address after a line break match. In a jsonb value (`json: true`) a line break is the escape `\n`, so the pattern accepts such an escape in front. Limits of the pattern are in § Limits.
9. **Find.** `bun run org:dsr --org-id <uuid> --address <address> --find [--recipient <age1…> --out <path>]` (`findSubjectData`). One `REPEATABLE READ READ ONLY` transaction; counts only on stdout: `mails`, `sent mails`, `mention <table.column> <n>`, `listed delegates`, `listed sender_rules`, `open actions`, `chain actions`, `chain delegations`, `sender profiles`, `sender suggestions`, and `report <bytes> bytes` with a report. The report is encrypted to the `age` key and holds the whole mail of each mail that goes and the sent mails that go (`sent_mails`: `id`, `mailbox_id`, `sent_at`, the three address fields, `subject`, `body_text`; the text is null for a row that retention cleared), and only table, column and id for kept rows. A find that matches nothing prints `warning: no match, check the spelling of the address` on stderr and exits 0. The order: the address check (`bad_address`), the rule check (`rule_mismatch`, rule 8), then the rest. A refusal (`own_address`, `bad_address`, `not_found`, `exists`, `rule_mismatch`) exits 1 and writes no audit row. For `rule_mismatch` stdout gets `rule mismatch <n>` (the count of conflicting code points) and the log line is `org_dsr_refused` with `reason=rule_mismatch`. One audit row `dsr.find` per run. `bun run org:dsr --org-id <uuid> --rule-check` prints `rule check <n>` and one line `U+XXXX js <hex> db <hex>` for each divergent code point of the database that serves the command (an empty program form shows as `-`); no address, exit 0.
10. **Erase.** `bun run org:dsr --org-id <uuid> --address <address> --erase --confirm <address>` (`eraseSubjectData`). `--confirm` must equal the address after normalizing (`confirm_mismatch`). The order: the address and confirm checks (`bad_address`, `confirm_mismatch`), the rule check of rule 8 (`rule_mismatch`: nothing changes, no audit row, stdout `rule mismatch <n>`), then the transaction below. One transaction in the tenant scope of the organization (RLS backs up every `org_id` filter) with `lock_timeout` 30 s. The order:
    1. Lock the organization row (`FOR NO KEY UPDATE`: two erases and an org delete take turns; mail work goes on) and every `mailbox_folders` row of the organization (`FOR UPDATE`: the lock that every sync and backfill chunk takes in `applyChunk`, so a chunk that was planned before the erase meets the tombstone). Then lock every `mailbox_sent_sync` row of the organization (`FOR UPDATE`, in mailbox id order, after the folder rows): the Sent pass writes under the same row lock, so a Sent chunk that was planned before the erase waits and then meets the tombstone. Then take the profile lock of every mailbox of the organization (`lockProfilesOfOrg`: `pg_advisory_xact_lock(hashtextextended(profileLockKey(mailbox id), 0))`, in mailbox id order, blocking). The profile pass `contacts.refresh` takes the same lock with try: a pass that runs finishes first, so the erase deletes the row that it wrote; a pass that starts later skips, and its next run reads the mail after the erase.
    2. Match. Refuse with `own_address` or `open_actions` (the CLI prints `open action <id>`; the owner rejects or finishes those sends, then the operator runs the erase again).
    3. Lock the mails that go and ask for open actions once more under the lock (a triage job may have added a send in between).
    4. Insert one tombstone per mail and per sent mail that goes, in one call: the SHA-256 of the dedup key without a `#<n>` copy suffix. The trigger of rule 11 also runs on `sent_emails`.
    5. Delete the chain actions, then the mails (the rest of the mail rows go by cascade), then the sent mails that go. A kept sent row that names the person and still has `content = 'pending'` becomes `headers_only` (its text, fetched later, could name the person again).
    6. The outbox step (rule 12).
    7. Scrub every kept row of the mapped columns: a `text` column replaces the address by `[removed]` (cut to its `CHECK` length: `TEXT_LIMITS`); a `json` column is cast to text, replaced and cast back; a `recipients` element is removed; an `equal` value is emptied.
       7a. Delete the profile rows and the address suggestions found by the hash (`deleteSenderContextRowsOf`; the open suggestions with the address as pattern went in step 7).
    8. Match again; any mail, sent mail, mention, profile row or suggestion left throws `dsr_erase_incomplete` and rolls back everything.
    9. One audit row `dsr.erase`.
    - A foreign key that the erase did not expect stops it with `blocked <constraint>` (a bug; nothing changed). Stdout: `erased mails`, `erased sent mails`, `tombstones`, `chain actions`, `chain delegations`, `erased sender profiles`, `erased sender suggestions`, `scrubbed <table.column> <n>`, `blanked outbox`, `dropped outbox`, `kept delegates`, `kept sender_rules` and the line `record: dsr erase <org id> <date>`. The runbook keeps that line off the server (rule 15).
11. **Tombstones.** `dsr_tombstones` (`org_id`, `key_hash`) per organization. The trigger `emails_skip_tombstoned` runs `BEFORE INSERT` on `emails` and on `sent_emails` and returns NULL for a mail whose base dedup key has a tombstone. `insertEmail` uses `ON CONFLICT DO NOTHING`, so it answers `false` and sync, rescan and backfill store nothing and raise no error. The Sent pass (`insertSentEmails`) skips a tombstoned key the same way, also after the switch goes off and on. Any insert path is covered, also one that is added later. A tombstone has no expiry; it goes with the organization. A mail that was never stored when the erase ran has no tombstone (§ Limits).
12. **Digests and approval sets (the outbox step).** `eraseManyMailOutbox` (`modules/privacy/outbox.ts`). A stored digest or approval set lists several mails and holds no mail id, so the address pattern misses it. The registry `NOTICE_MAIL_CONTENT` gives each `NoticeKind` one class: `one_mail` (the row has `email_id` and goes with its mail), `many_mails` (digest, `approval_set`) or `no_mail`. A new `NoticeKind` fails `bun run typecheck` until it has a class. Since the earliest created time of the erased mails: a `sent` or `failed` row of a `many_mails` kind gets the text `[removed]` and an empty view (`outbox_blanked`); a `pending` or `sending` digest is deleted (`outbox_dropped`; the next slot covers the period); a waiting approval set whose sends all closed (and a stale `sending` one) is closed as `failed` / `outdated` and blanked, with the rule of the resume hook (`closeWaitingApprovalSetsSince`, `modules/channels`). A fresh `sending` set is in flight and finishes. A `pending` set whose send still waits stays: the open-action refusal means that no such request names a mail that goes. This also blanks the stored copy of other mails' digests of that time.
13. **The hash.** The audit rows of find and erase hold `address_hash`, never the address: HMAC-SHA256 hex of the normalized address. The key is HKDF-SHA256 of `CREDENTIALS_KEY` (empty salt, info `ea/dsr-address/v1`, 32 bytes), so no new secret exists. The same address gives the same hash in every organization (accepted, plan question 3). A change of `CREDENTIALS_KEY` makes old hashes unmatchable. The same holds for the profile keys: after a change of `CREDENTIALS_KEY` an erase cannot find the old `sender_profiles` rows (their `key_hash` was made with the old key), so the erase deletes the mail but not those rows. The next pass zeroes them, they stay until retention removes them (365 days after the last mail), and the `address` of an export row is null. An operator who changes the key and then gets an erase request must delete the old rows by hand or wait for retention; no key-rotation runbook exists yet (`docs/legal/breach-procedure.md`). The audit data is flat: `mails`, `sent_mails`, `mentions`, `listed_delegates`, `listed_sender_rules`, `open_actions`, `sender_profiles`, `sender_suggestions` (counts of the rows of the person in the sender-context tables), and for an erase also `tombstones`, `chain_actions`, `chain_delegations`, `outbox_blanked`, `outbox_dropped`.
14. **Locks and results.** Erase and delete set `lock_timeout` (30 s). A lock wait that runs past it ends the transaction with nothing changed: `org:delete` and the route report `busy`; `org:dsr` logs `org_dsr_failed` and exits 1; run the command again. A deadlock is run once more.
15. **Restore.** A backup restore brings back the deletes and erases made after the backup. The operator keeps each `deleted …` line of `org:delete` and each `record: …` line of `org:dsr` outside the server (the owner keeps the request) and runs the commands again after a restore, before the panel opens (`deploy/README.md` § Account data (F106)). No ledger table exists: a restore would roll it back too.
16. **Security log.** The audit events `org.exported`, `org.delete_refused`, `dsr.find` and `dsr.erase` map to the kinds `data_exported`, `delete_refused`, `dsr_find` and `dsr_erase` (`securityEvents`, `packages/core/src/security-log.ts`) and show in the Account card (`GET /api/security-log`, flag `security_log`). The actor of a CLI row is the operator. The delete itself has no row: the organization and its log go (plan question 1).
17. **Output rule.** No address, organization name, password, mail text or report content in a log line, error text or audit row. CLI stdout holds ids, counts, table and column names, paths and sizes; `org:delete` also prints the mailbox addresses.
18. **Registries for later tickets.** A migration that adds a table or column classifies it in `EXPORT_MAP` (add the key to the slice in `modules/privacy/export-map/` whose range holds its name), and each new candidate column in `DSR_ADDRESS_MAP` or `NOT_PERSONAL`; a new table with `org_id` or `user_id` gets a seed in the delete test; a new mail table gets the tombstone trigger; a new notice kind gets its `NOTICE_MAIL_CONTENT` class (`docs/code-patterns.md` § Data access). Tests fail until each is done.
19. **Texts.** The new Polish texts follow `notes/2026-11-14-polish-ui.md`: informal "ty", at most one colon per line, no calques, names and addresses without a case ending. Decisions of the reviews (F105 stage 11 and F106 stage 04): "Błędne hasło" (not "Nieprawidłowe"), "Za dużo błędnych prób" for a lockout, "zachowują dane, dopóki nie wygasną" for backups, "przydaje się, gdy nie masz przy sobie telefonu". The same word "błędne hasło" stands in the security-log text of a refused delete. The keys are `del_*` (dialog and login notice) and `sec_kind_data_exported`, `sec_kind_delete_refused`, `sec_kind_dsr_find`, `sec_kind_dsr_erase` (rule 16).

## Data

`dsr_tombstones`: `org_id` (cascade), `key_hash` (64 hex characters), `created_at`; primary key (`org_id`, `key_hash`); RLS policy `tenant_rows`. The function `delete_organization(uuid)` and the trigger function `emails_skip_tombstoned()` with the trigger of the same name on `emails` (migration `db/migrations/20261114160001_account_data.sql`) and on `sent_emails` (migration `db/migrations/20261115090001_sent_mail.sql`). The erase writes `emails`, `email_headers`, `triage_results`, `actions`, `outbox`, `delegations` and `dsr_tombstones` rows, `sent_emails` rows (delete, scrub and the `pending` → `headers_only` change) and one `audit_log` row. Audit events: `org.exported` (`tables`, `rows`), `org.delete_refused` (`reason`, `via`), `dsr.find`, `dsr.erase` (rule 13). Flag: `org_delete` (`packages/core/src/features.ts`; off by default; `org:flag --org-id <uuid> --flag org_delete --on` per organization). The CLIs have no flag.

## Limits

- An address with a letter that the database lower-cases unlike the program (on `postgres:17`: U+A7CE, U+A7D2, U+A7D4, U+16EA0 to U+16EB8, and their lower-case forms) cannot be found or erased: find and erase refuse with `rule_mismatch` and change nothing, until the database or the program changes. Nobody is expected to hold such an address. Any trim difference makes every find and erase refuse. A different build of the image on the VPS can differ: `org:dsr --rule-check` shows the set.
- An address in NFD (`Jose` + U+0301) and the same address in NFC (`José`) are two addresses: the equality match, the text pattern and the profile hash keep them apart (no NFC folding). An erase for one spelling leaves mail stored in the other; the operator runs the erase once for each spelling that `--find` shows.
- The match is by the text of the address. An address in an attachment file name (`p@x.test.vcf`) is not matched: the look-ahead rejects `.vcf` after the address as a longer domain. The same rule keeps `a@b.com.pl` apart from `a@b.com`. An address at the boundary of single quotes or braces (`'p@x.test'`, `{p@x.test}`) is matched only at the start of the text or after a character that is not `atext`, because a quote or a brace is also a legal part of a local part.
- A mail that was never stored has no tombstone. Run `org:dsr --erase` again after a backfill, after the first sync of a newly enabled sync folder and after a newly connected mailbox: these can store mail of the person that was older than the sync window or in a folder that was not read. With the flag `trust_ladder` on, a newly connected mailbox also gets the automatic history check, which stores up to 30 days of INBOX mail as `skipped` / `history_check` rows with no tombstone ([sync.md](sync.md) rule 19, [trust.md](trust.md) rule 7): run the erase again after that check, too. History mail is stored mail with the normal retention counted from `created_at` ([retention.md](retention.md)), so the onboarding and report text must not suggest a 30-day age limit.
- Telegram messages that were delivered stay in the chat; nothing can recall them (P2). The owner deletes them there. A fresh `sending` approval set (younger than `SENDER_STALE_MS`, 5 minutes) is in flight and can still reach Telegram. A sent approval card that the erase blanked can still be tapped; the answer then shows `[removed]`.
- The mailbox keeps the mail (the system never deletes mail in the mailbox), and the drafts and folders that the assistant made stay (PD-039). Backups keep the rows until they expire. A restore brings back the rows: rule 15.
- Run `org:dsr --erase` again after the first pass of a newly turned on "Track my sent mail", and after its text step: sent mail and text stored later can name the person.
- A system send whose incoming mail an erase deleted reads as user mail after a new first pass (its action is gone).
- Delegates and sender rules that hold the address are listed, not deleted.
- Another organization may hold the same address; the hash is the same in each (accepted).
- A panel page for data requests: not built (PD-038). A grace period for the delete and a passphrase export do not exist.
- The legal papers that describe these steps: E7-T4 (F107).
- Edge case of the delete function (accepted): a user who is deleted with this organization, and who had a membership in another organization before, loses the user link in that organization's rows (`SET NULL`); `audit_log.actor` there keeps the id.

# Delegation

> Checked against the code at `cb3f73dd`, 2026-11-18.

## What it does now

An organization keeps a list of delegates: people who get tasks from the user. The owner manages the list with the `delegates:add`, `delegates:list`, `delegates:disable` and `delegates:enable` scripts, or, with the flag `delegation_pages` on, on the Delegates page of the web panel (rule 11). When the classifier calls a mail `delegation` and picks a delegate id from the list, triage plans a draft and a send to that delegate and writes one `delegations` row (`drafted`). After the owner approves the send (`drafts-and-send.md`) the delegation is `sent` and has a due date. A mail from the delegate in the same thread closes the wait: the delegation becomes `answered` and every linked member gets a notice with a ✅ Done button. When no answer comes by the due date, the chaser job marks the delegation `overdue` and plans a reminder for the owner to approve, at most 2 reminders per delegation. `bun run delegations:list` and `delegations:done` read and close delegations from the shell. With the same flag the Delegations page lists them in four tabs, and the owner can remind the delegate now, cancel a delegation or close it (rules 12 to 14). An owner can also pick a delegate for any mail with the Delegate button (Telegram and the panel, flag `delegate_button`): that makes a delegation draft in the same path, with `source = button` (rule 10). A mail that the user forwards to an active delegate by hand is tracked as a `delegated` open loop, not as a `delegations` row ([open-loops.md](open-loops.md)); the one chaser `loops.chaser` runs the delegation reminders (rule 8) and the loop follow-ups together (F116, ADR 0036).

## Rules

1. **Delegates.** A delegate has a name (1 to 100 characters), an address (lower case, valid, never an address of a mailbox of the organization), competence tags (at most 10, each at most 30 characters, lower case) and an `active` flag.
   - `bun run delegates:add --org-id <uuid> --name <text> --email <address> [--tags a,b,c]` adds one. A second add of the same address in the organization says "already there". Delegate addresses compare by the one address rule (`normalizeAddress` in `@ea/core`, the rule of the sender profile): a case form, a padded or a dotted-I form of an address that a delegate (active or not) already has is refused as a duplicate, and so is a mailbox address in such a form. The stored address stays the trimmed lower case form, the one reminders go to. `delegates:list` shows the active delegates (`--all` shows all). `delegates:disable` and `delegates:enable` change the flag with `--id <uuid>`. Each change writes an audit row (`delegate.added`, `delegate.changed`). A refusal (a mailbox address, a refused field) exits 1; bad arguments exit 2 (`docs/cli.md`).
   - A delegate is never deleted. A disabled delegate is not offered to the classifier and gets no reminder; a send that is already planned for it still shows `(inactive)` in the approval message.
2. **How the classifier picks a delegate.** The triage job reads the active delegates and gives the list (id, name, tags) to the classifier. The category `delegation` is allowed only when the list is not empty. The output schema allows only these ids (or null), and the code checks the id again. The rules are in `triage.md` § Rules (hard rules and the classifier call). The recipient of the draft is the address of the `delegates` row, never LLM text.
3. **The delegation row.** `saveTriage` (the triage transaction) inserts the `delegations` row when the mail has the final category `delegation` and the `create_draft` of kind `delegation` is `ready`. Both payloads then get the `delegation_id`. The task text comes from the classifier (`task_summary`).
   - `due_at`: the due date that the classifier found, at 17:00 in the organization timezone. A date that does not exist gives no date. The draft `due_date` follows the same rule: the planner (`planDelegation`) writes `""` for a date that does not exist, and the message then has no due line.
   - When the send is `applied` the delegation becomes `sent` with `sent_message_id`, and `due_at` = 3 days later when it had no date.
   - A mail that gets only a `clarification` draft (no delegate) makes no delegation.
4. **Reply detection.** After `saveTriage` writes the status of a mail, it asks `detectReply`: is there an open delegation (`sent` or `overdue`) of this mailbox whose delegate address is the `From` address of the mail (both compared by the one address rule), and whose `sent_message_id` (or the `Message-ID` of its applied send) is in the `In-Reply-To` or `References` header? If yes, `markAnswered` sets the delegation to `answered` (with `answered_email_id`) and expires its pending reminders (`delegation_closed`). The same transaction writes the audit row `delegation.answered`. The mail is then triaged like any other mail. The flow diagram of `docs/architecture.md` §4.1 shows the branch.
   - Only the delegate's own address counts. A reply from another address does not close the delegation (E5b, F116).
5. **The notice and the Done tap.** The notifier queues one `delegation_answered` notice for every linked member (dedup `delegation_answered:<delegation id>`). Its ✅ Done button is the callback `dd:<delegation id>`; it works for every linked member, not only owners. `closeDelegation` allows `done` only from `answered` or `overdue`: a `done` delegation answers "already", any other state answers "not closable". `done` expires the pending reminders. `bun run delegations:done --org-id <uuid> --id <uuid>` and the Done button of the panel (rule 14) do the same.
6. **Digest lines for delegations (S4):** a `logged` send reads "would ask you to send it"; the phrases for the other statuses are `waits for your approval`, `approved, sending`, `sending`, `sent`, `rejected`, `not sent (approval expired)` and `not sent (failed)`. The footer shows `👥 Delegations: <n> waiting for a reply, <m> overdue` when there are open delegations.
7. **Reminder sets:** the chaser (rule 8) plans up to 10 reminders at once. They go as one message `📤 Send <n> reminders?` with 📤 Send all and ✖️ Skip all (`as:<set id>`, `rs:<set id>`). Each item shows the recipient, the subject and the task (cut to 150 characters).
   A tap approves only the sends that the message showed.
   - Check against the code: the task is cut to 150 characters only while the message fits in 4096 characters. A long set shrinks the texts in four steps (task 150, then 40; subject 80, then 60; name 80, then 40), so no item drops out (`renderApprovalSetRequest`). A set of one reminder reads `📤 Send 1 reminder?`.
8. **The job `loops.chaser`** (F116 stage 15; it replaced `delegation.chaser`; the delegation rules below stay in `delegation/chaser.ts`, the loop rules are in `loops/chaser.ts`; a tick every 15 min) acts once per local day per mailbox, from 07:30 in the organization timezone, only in `assist` mode with the switch `create_draft` on: it marks `sent` delegations past `due_at` as `overdue` and plans a reminder (draft + send, `awaiting_approval`) for every overdue delegation with an active delegate, at most 2 reminders per delegation, 3 days apart (the gap runs from `last_reminder_at`, which the chaser sets when it plans a reminder, so a rejected reminder keeps the gap; Remind now has no gap, rule 13), at most 10 per run (one set message, `drafts-and-send.md` § Rules). A reminder draft copies `due_date` of the original draft through `dueDateOrNone`: a stored date that does not exist gives `""`, and the reminder has no due line. A reminder is never sent without a tap. The run writes an audit row `delegation.chaser_run`; the first statement of its transaction share-locks the settings row and compares the settings version (the S3 `saveTriage` rule), so a settings change makes it skip.
   - Check against the code: no new reminder is planned while an earlier reminder send of the same delegation still waits (`awaiting_approval`, `approved` or `applying`). The reminder is a `reminder` draft (a fixed template, no quote) in the same thread as the delegation mail, with the delegate as the only recipient.
   - `bun run job:run --name loops.chaser [--force]` runs it once (`drafts-and-send.md` § Entry points); the name `delegation.chaser` is an alias and prints one line that says so. `--force` skips the 07:30 and once-per-day gate of the chaser.
9. **The end of a delegation.** `cancelled` comes from the send: the owner rejected it, it expired, its draft is missing or the send failed (reasons in the flow below). A cancelled delegation can become `sent` again by "Send again" or "It went out" (`drafts-and-send.md` § Rules). A reminder send that fails or expires never cancels the delegation. The owner can also cancel in the panel (rule 14): the reason is `user_cancelled`, and it is final. The retention job clears the task text of a delegation that is no longer open (`clearDelegationTasks`).
10. **The Delegate command (F116 stage 16, flag `delegate_button`).** `delegateMail` (`loops/delegate.ts`) lets an owner pick a delegate for a mail. The checks run in this order: flag off → `feature_off`; mail not in the organization → `not_found`; user not an owner → `not_allowed`; delegate not in the organization → `not_found`; delegate disabled → `delegate_inactive`; the mail has a delegation in `drafted`, `sent` or `overdue` → `exists` with its id; the mail is not delegable → `not_delegable` (no triage result yet, final category `spam`, a suspicious reason, a sender that is an own mailbox, or a mail of the system itself whose Message-ID `<ea-<action id>@…>` names an action of the mailbox); mode `shadow` or switch `create_draft` off → `drafts_off`. Then one transaction, whose first statement share-locks the settings row, plans a `ready` `create_draft` of kind `delegation` and an `awaiting_approval` `send` with the core planner (the same `planActions` as triage, the delegate fixed by the user), inserts the `delegations` row (`drafted`, `source = button`) and links the `delegation_id` into both payloads. The recipient is the address of the `delegates` row. The send always waits for a tap (ADR 0003). The task text is the stored triage summary of the mail, else its subject, with addresses, links and long numbers marked, on one line, cut to 300 characters; there is no LLM call. No due date is stated, so the send sets it 3 days later (rule 2). The keys are `<email id>:create_draft:delegation:button:<k>` and `:send:…:<k>`; `k` is 1 plus the number of earlier `button` delegations of the mail, so a new pick after a reject makes a new pair. After the settings lock the transaction locks the row of the mail (the order of `saveTriage`), so a second tap at the same time, with the same or another delegate, waits and then finds the open delegation (`exists`): one delegation and one pair per mail. The approval card, the edit (also the change of the delegate) and the send are the existing path. The audit row `delegation.created` holds `source` and `via` (`web`, `telegram` or `cli`). The Telegram button and picker (stage 19, [digest-and-notices.md](digest-and-notices.md) rule 14) and the panel action (stage 22) call this function.

11. **The delegates page and routes (F102; flag `delegation_pages`, default off, remove-by 2027-03-01).** With the flag off every route below answers `404 not_found`, also for a member and for a bad id (the flag check comes before the role check).
    - `GET /api/delegates` (any member): `{ items }` with every delegate, active ones first, at most 200 (`DELEGATE_LIST_MAX`). A delegate has `id`, `name`, `email`, `tags`, `active`, `createdAt`.
    - `POST /api/delegates` (owner; body `{ name, email, tags }`): `201` with the delegate. `409 exists` for an address that the organization already has; `400 mailbox_address` for an address of a mailbox of the organization; `400 validation` with the field (`name`, `email` or `tags`) when the service refuses a value (rule 1 holds the limits).
    - `PATCH /api/delegates/:id` (owner; body `{ name?, tags?, active? }`, at least one): `updateDelegate` locks the delegate row and changes what differs. The address never changes. A change of `active` to off keeps the open delegations of the delegate. A call that changes nothing writes no row.
    - Audit: one `delegate.changed` row per call that changes something. `data` is flat: `delegate_id`, `fields` (the changed field names in one comma string, in the order `name`, `tags`, `active`), `active` (only when it changed) and `via` (`web` or `cli`). It never holds a name, a tag or an address. `delegates:disable` and `delegates:enable` write the same row (`fields` is `active`, `via` is `cli`). `delegate.added` holds `delegate_id` and `via`.
    - The page (`/delegates`, `apps/web/src/islands/DelegatesPage.tsx`): the owner adds a delegate (name, e-mail, tags separated by commas), edits the name and the tags, and turns one off or on (turning off asks first). A member sees the list only. It is the second tab of the header of the Delegations page and has no nav item of its own.
12. **The delegations list (F102).** `GET /api/delegations?filter=&before=&limit=` (any member, flag `delegation_pages`): `{ items, next }`. `filter` is `open` (`drafted`, `sent`; the default), `overdue`, `answered` or `closed` (`done`, `cancelled`); `limit` is 1 to 100 (default 50); `before` is the `next` cursor of the earlier page (newest first; two rows with the same time come in id order, none twice). An item has `kind` (`delegation`; E5b adds kinds), `id`, `status`, the delegate (`id`, `name`, `email`, `active`), `task` (null after the retention job cleared it), `subject`, `dueAt`, `sentAt`, `answeredAt`, `remindersSent`, `reminderWaiting` (a reminder send waits for a tap: `awaiting_approval`, `approved` or `applying`) and `sendId` (the waiting send while the delegation is `drafted`, else null; the page links it to the Approvals page).
13. **Remind now (F102, D9).** `POST /api/delegations/:id/remind` (owner, empty body) plans the same reminder as the chaser (`remindNow` in `delegation/remind.ts`; the draft comes from the same builder `buildReminderDraft`): a `reminder` draft and its send in `awaiting_approval`, with no set (one approval card per owner: "Send? Reminder to …" with Send and Reject). The answer is `{ status: "planned", sendId }`. It never sends: the mail to the delegate still needs the tap (ADR 0003).
    - The checks run in one transaction, in the lock order of the chaser (the settings row, share; the delegation; its reminder sends), in this order: the delegation is `sent` or `overdue` (else `409 not_open`); `reminders_sent` is below 2 (`409 limit_reached`); no earlier reminder send waits (`409 reminder_waiting`; the check under the delegation lock is what stops a double click); the delegate is active (`409 delegate_inactive`); the mailbox mode is `assist` and the switch `create_draft` is on (`409 drafts_off`). An unknown or foreign id is `404`.
    - It skips the gates of the chaser (rule 8) because the owner asks now: no due date, no 3-day gap, no 07:30 and once-per-day gate. It keeps the limit of 2 reminders. It sets `last_reminder_at` at planning, as the chaser does, so the chaser then waits 3 days from that time. The keys of its rows hold a fresh id (`…:reminder:manual:<uuid>`), because the chaser keys hold the day.
    - Audit: `delegation.remind_requested` (the actor is the user; `delegation_id`, `reminder` 1 or 2, `via`), on the new send.
    - The panel keeps the button visible when it cannot work: it has `aria-disabled` and the reason as text. The page knows `not_open`, `limit_reached`, `reminder_waiting` and `delegate_inactive` from the row; it learns `drafts_off` from the `409` answer.
14. **Cancel and Done in the panel (F102).** `POST /api/delegations/:id/cancel` (owner, empty body) and `POST /api/delegations/:id/done` (any member who can write; empty body).
    - Cancel (`cancelByUser`): a `drafted` delegation rejects its waiting send like the Reject tap (`reject` with `via: "web"` and the card hooks, so the Telegram cards lose their buttons); a panel edit that replaced the send between the read and the lock gives one more try with the current send. A `sent` or `overdue` delegation becomes `cancelled`; its waiting reminder sends expire and their cards lose their buttons (the card edit `expired`). Answers: `{ status: "cancelled" }`; `409 not_open` (the delegation is `answered`, `done`, `cancelled` or was closed in between); `409 sending` (the send is `applying`, or `approved` with a fresh lock: the mail may reach the delegate). The reason is `user_cancelled` and it is final: "Send again" and "It went out" do not reopen it. A reminder that is already in flight still goes out. The audit row `delegation.cancelled` names the user as actor, holds `reason_code` `user_cancelled` and, in `data`, `reason` and `via`.
    - Done (`closeDelegation` with `via: "web"`): `{ status: "done" }`; `409 already`; `409 not_closable` for `drafted`, `sent` and `cancelled`. The audit row `delegation.done` also holds `via`.
    - The page asks "Cancel this delegation?" before it cancels; Done has no question. The question keeps its delegation after a reload that moves the row to another tab; Confirm then answers `409 not_open` and the page says the delegation is closed.

## Data

`delegates`: `id`, `org_id`, `name`, `email` (lower case; unique per organization), `competence_tags` (text array), `active`, `created_at`, `updated_at`.

`delegations`: `id`, `org_id`, `mailbox_id`, `email_id`, `delegate_id`, `draft_action_id`, `send_action_id` (unique), `task_summary`, `due_at`, `status`, `status_reason`, `sent_message_id`, `sent_at`, `last_reminder_at`, `reminders_sent`, `answered_email_id`, `answered_at`, `answered_notified_at`, `source` (`triage` by default, `button` for a Delegate tap; F116), `created_at`, `updated_at`. A status `sent`, `answered` or `overdue` needs `sent_message_id` and `sent_at` (a check).

Audit events: `delegate.added`, `delegate.changed`, `delegation.created`, `delegation.sent`, `delegation.answered`, `delegation.overdue`, `delegation.cancelled`, `delegation.done`, `delegation.remind_requested` (F102: `delegation_id`, `reminder`, `via`), `delegation.chaser_run`. A panel edit of a draft writes `action.edited` on the new send ([drafts-and-send.md](drafts-and-send.md) rule 12), not a delegation event.

Status flow of `delegations.status` (moved from `docs/architecture.md` §4.6):

```
delegations.status: drafted → sent                                    (the delegation send is applied; due_at = 3 days later when the mail states no date)
                 drafted → drafted                                    (a panel edit: the delegation points at the new draft, send and delegate; `drafts-and-send.md` rule 12)
                 drafted → cancelled                                  (reason: rejected | expired | draft_missing | send_failed | outcome_unknown, or user_cancelled: the Cancel button, final)
                 sent | overdue → cancelled                           (reason user_cancelled only: the Cancel button of the panel, final; the waiting reminder sends expire)
                 cancelled → sent                                     (not after user_cancelled; "Send again" after send_failed | outcome_unknown, when the new send is applied; or "It went out" after outcome_unknown, with the stored outgoing_message_id and no new send)
                 sent → overdue                                       (the chaser, after due_at)
                 sent | overdue → answered                            (a mail from the delegate in the thread of the sent mail; the pending reminders expire)
                 answered | overdue → done                            (the Done tap, or bun run delegations:done; the pending reminders expire)
```

## Limits

- The Delegate button (Telegram, [digest-and-notices.md](digest-and-notices.md) rule 14, and the panel) and the tracking of a hand forward ([open-loops.md](open-loops.md)) are built. A reply in the thread from any address that is not the user's closes a `delegated` loop (open-loops.md rule 3, PD-121); a `delegations` row still closes only on a mail from the delegate (`detectReply` is unchanged). The panel action needs the flags `delegate_button` and `delegation_pages`.
- The pages and routes are behind the flag `delegation_pages` (off by default). Remind now and Cancel have no CLI: only the panel calls `remindNow` and `cancelByUser`. A cancel from the panel is final (`user_cancelled`), and a reminder that is already being sent still goes out.
- No delegate import: a delegate is added one by one.
- At most 2 reminders per delegation, also with Remind now (`DELEGATION_REMINDER_LIMIT`). After that the delegation stays `overdue` until the owner closes it.
- The name, the tags and the active state of a delegate change in the panel (`PATCH /api/delegates/:id`); the address never changes: the owner adds a new delegate and turns the old one off.

## Decisions

- ADR 0003 (plan, policy, commit; the send and the approval of a delegation; Remind now never sends without a tap), ADR 0023 (the panel routes are typed commands with `via`).
- ADR 0036 (the one chaser `loops.chaser` replaced `delegation.chaser`; hand forwards are `delegated` loops).
- PD-124 (manual delegation: the Delegate button and the tracked hand forward).
- `docs/architecture.md` keeps the flow of §4.1 with the branch "reply in a delegation thread".

# Open loops

> Checked against the code at `ea7b99f4`, 2026-11-20.

## What it does now

Nothing the user waits for should slip. The assistant reads the user's own Sent mail (`sent-mail.md`) and tracks three kinds of open loop: a reply that the user waits for (`waiting`), a dated promise that the user made (`promised`), and work that the user forwarded by hand to an active delegate (`delegated`). It closes a loop when a reply comes or the user taps Done or Drop, and it chases the loops that nobody answered with one follow-up draft that waits for one tap. The first digest of the member's day starts with a "needs you today" brief; later digests get a count line. Telegram taps, `/api` commands and the "Open loops" page of the panel run the same commands. Mail goes out only after the second tap of an owner (ADR 0003). The whole feature is off by default: the flags `open_loops` and `delegate_button` (rule 14) and, for the Sent mail it reads, `sent_sync` and the switch "Track my sent mail".

## Rules

1. **Kinds and states.** One table `open_loops` (module `loops`, layer 3, ADR 0036). `kind`: `waiting` (the mail asked something: `expects_reply`), `promised` (the mail holds a promise with a date that code resolved), `delegated` (a `waiting` case whose first To is an active delegate, PD-124). One Sent mail can open one `waiting` or `delegated` loop and one `promised` loop (unique on `org_id`, `sent_email_id`, `kind`). `status` is `open` or `closed`; `close_reason` is `replied`, `replied_subject`, `done`, `dropped`, `untracked`, `stale`, `later_reply`, `expired` or `sent_off`. A loop copies what it needs (subject, To, Cc, the counterpart = the first To, the ask or promise ≤ 80 characters, the message ids), because the Sent text and addresses expire; it never copies the mail body. The due date is the stated one (`due_source = stated`) or `sent_at` plus `loop_wait_days` working days (`default`, a `waiting` or `delegated` loop only: an undated promise opens nothing), or with the flag `contact_wait` the usual reply time of the contact (`contact`, rule 17). A `delegated` loop is tracked next to the `delegations` rows of triage and of the Delegate button (`delegation.md`); the panel shows both under Delegated.

2. **The analysis (open loops).** The job `loops.analyze` (every 60 s, only where the triage scope is not `off`) runs `analyzeSent(deps, ctx, mailboxId, { now, limit })` (the extractor model is the `light` tier of `LLM_PROVIDER`, effort `none`; no `LLM_EXTRACTOR_*` key picks a model) for each active mailbox, only with the flags `sent_sync` and `open_loops` and the switch on. Candidates: `origin = user` rows with a text that is not `pending`, with no `sent_analyses` row and at most 14 days old, or with a `pending` row that is due; oldest first, at most 20 per run. Each candidate runs in this order: (a) the promise rule: every open `promised` loop that the user opened before this mail, whose counterpart is in its To or Cc, closes `later_reply` (any thread; the mail goes on); (b) the thread rule: an open `waiting` or `delegated` loop in the thread of the mail, older than the mail, whose To and Cc share an address with the mail, restarts its wait (due = `defaultDue(sent_at, max(loop_wait_days, 3))`; the row is `skipped / thread_restart`, no call); a mail to other people is a side note and goes on; (c) the delegation rule: a thread with an open delegation (`sent` or `overdue`) gives `skipped / delegation_thread`; (d) `sentSkipReason`. A row that passes calls the model once (`extractSent`, role `extractor`; the call sends the subject, the local date, time and weekday of the send, the number of recipients and up to 8000 characters of the text, and no header address; [the privacy page](../../apps/web/src/legal/en/privacy.md) names these fields and `apps/server/src/legal-outside-calls.test.ts` fails when a limit or a field changes) unless the mailbox is at 80% of `LLM_DAILY_CAP` in the quota day (all roles count): then the row stays `pending / llm_cap` until 5 minutes after the next quota day starts. Every call writes one `llm.call` row (a failed call too), so extractor calls count in the cap. One transaction then writes the analysis row (`done`, `expects_reply`, `has_promise`, `prompt_version`) and the loops: `expects_reply` true opens `waiting` (or `delegated` when the first To that an active delegate owns exists; `counterpart` = that address), a promise with a resolved date opens `promised`; an ask with `expects_reply` false opens nothing. Addresses, subject and message ids come from the Sent row, never from the model; the subject loses line breaks and is cut to 300 characters. The first lock of each write is the state row of the switch, then the loops, so the order matches `setSentSync`: a switch-off waits for a write that runs now and then closes its loop `sent_off`; a write that comes after a switch-off writes nothing. A hard error or a schema failure counts one attempt and retries after 5 min × attempts; the third ends the row `failed`. A soft error (`softCodes`) other than `timeout`, or a configuration error, counts no attempt: the run stops, no later mailbox runs, and the job pauses (5 min, doubling to 60). A `timeout` counts as an attempt, so one mail that times out every time ends `failed` after 3 calls. The cap check never rounds up: a call runs only while `(used + 1) * 5 <= LLM_DAILY_CAP * 4` (a cap of 7 allows 5 calls, a cap of 3 allows 2, a cap of 1 allows none). In the synthetic scope only test mail reaches the model. An address of the operator in `TEST_SENDER_ADDRESSES` makes all real Sent mail of that mailbox test mail, so it goes to the model. On Gemini a schema rejection is a hard `http_400` (3 calls per mail, then `failed`; nothing in code stops it): check the extractor schema on Gemini before `open_loops` is turned on there. Do not run `bun run job:run --name loops.analyze` while the server runs: two processes at once make two calls for one mail, but still one analysis row and one set of loops. Log lines: `sent_analysis_done` (`mailbox_id`, `count` = rows that got a result, `opened` = loops opened), `sent_analysis_failed` (`mailbox_id`, `error_code`, or `error` and `error_code`), `sent_analysis_write_failed`, `sent_analysis_mailbox_failed`, `llm_audit_failed`; no text and no address. `bun run job:run --name loops.analyze` runs one pass and prints counts only.
3. **The close rules (open loops).** The job `loops.match` (every 2 min; it needs no model, so it runs with the triage scope `off`; only where the flag `open_loops` is on and the organization is not suspended) runs `matchReplies(deps, ctx, mailboxId, { now })` over the open `waiting` and `delegated` loops of each active mailbox. `promised` loops and delegations (`detectReply`) are not touched. A mail of the mailbox counts only when `received_at > wait_from_at` and its sender is not an own address (any mailbox of the organization, and every From address of the Sent rows of this mailbox, so an alias that the user wrote from is not a reply; lower case, trimmed; the newest 100 aliases; recipients, own addresses and aliases all compare by the one address rule of the sender profile, `normalizeAddress`: trim, lower case, Greek final sigma `ς` as `σ`, no combining dot after `i`, so a reply from `ΝΊΚΟΣ@…` closes a loop to `νίκος@…`; the read of mails from a recipient keeps the index of `from_address_lower` and tries the spellings of a final sigma, so a From with padding or a combining dot that is outside the thread is not found; the counterpart, To and Cc of the loop itself never count as aliases, so a person who also sends as the user closes the loop with a reply). `replyMatch` (`packages/core/src/loops/replies.ts`) says how: `thread` when the mail has the loop's `thread_key` or its In-Reply-To or References hold the loop's `message_id` (each id compared whole, so `<x<id>>`, a suffix or another case does not match); `subject` when `normalizeSubject` is equal (and not empty), the sender is in the loop's To or Cc and the mail came within 30 days of `wait_from_at`; `auto` when `isAutoReply` is true on a mail that would match by thread or subject (`Auto-Submitted` other than `no`, `Precedence` bulk, junk, list or auto_reply, or a `mailer-daemon`, `postmaster` or `noreply` sender, or a subject that starts with `Automatic reply:`, `Autoreply:`, `Out of office:`, `Odpowiedź automatyczna:` or `Nieobecność:` after the reply prefixes; no `email_headers` row means not automatic). `normalizeSubject` drops the prefixes `Re:`, `Odp:`, `Fwd:`, `FW:`, `PD:`, `AW:`, `SV:`, `WG:`, `TR:`, `Antw:` (any case and spacing, with a count such as `Re[2]:`, repeated), the gateway tag `[EXT]` and a closing dot, reads full-width and no-break forms as plain ones, drops zero-width and control characters and collapses spaces; a look-alike letter is not stripped, so it does not match. The first non-`auto` match in `received_at` order closes the loop: `thread` gives `replied`, `subject` gives `replied_subject`, both with `closed_by_email_id`. An `auto` mail before it sets `auto_reply_at` once and the search goes on; an automatic mail never closes. An open loop with an empty `to_addresses` (a DSR erase) closes `dropped`. Each write is one transaction: lock the loop, check it is still open, decide again on the locked row, close it, and end its waiting follow-up sends `expired` / `loop_closed`. Two runs at once (or a run and `onSentOff`) give one close, one `loop.closed` audit row and one expiry per send. A reply that arrives while the follow-up restarts the wait does not count, because the decision runs again under the lock. The log line `loops_matched` (`mailbox_id`, `count`, `kind` = the reason) holds no address and no subject. A reader limit: one run reads 500 loops per mailbox (oldest wait first) and, in two reads with a limit of 200 mails each, the mails of the thread (or naming the loop `message_id`) and the mails of the recipients. A mail from the junk folder of the mailbox, or whose latest triage category is `spam`, never counts.
4. **The loop commands (open loops).** Module `loops` exports six commands that Telegram (stage 19) and `/api` (stage 20) call with a `via` (`web`, `telegram` or `cli`). All of them need the flag `open_loops` (`draftFollowUp` and `laterLoop` answer `feature_off`; the others answer `not_found`, as the loop is hidden), run in one transaction, lock the loop first and then its sends, and write one audit row with the `via`. A log line `loop_command` (`org_id`, `loop_id`, `command`, `kind` = the answer, `via`) holds ids and codes only. (a) `draftFollowUp` plans one follow-up pair and says why not otherwise, in this order, after the settings row is share-locked and the loop is locked: `not_found`, `not_allowed` (the user must be an owner), `closed`, `not_allowed` (a `promised` loop), `waiting` (a follow-up send of the loop in `awaiting_approval`, `approved` or `applying`, with its `sendId`; a `failed`, `rejected` or `expired` send does not wait), `limit_reached` (`follow_ups_sent` is 2), `too_soon` (the second one before `last_follow_up_at` plus 3 working days), `suspicious` (any suspicious reason in the thread, whatever the flag), `would_draft` (mode `shadow`; one `loop.would_draft` audit row, no action), `drafts_off` (no settings row, or the switch `create_draft` is off). Otherwise it plans a `create_draft` (`ready`) and a `send` (`awaiting_approval`) with `loop_id` and no `email_id`, keys `<loop id>:create_draft|send:follow_up:<n>:<k>` (`n` = `follow_ups_sent` + 1; `k` = 1 + the follow-up sends of the loop that used this `n`), and two `action.planned` audit rows (actor = the user, no mail). The recipients come from the loop row only: To and Cc of a `waiting` loop, the counterpart alone for a `delegated` loop (a `delegated` loop with no counterpart, as after a data erase, gives `not_allowed`: `to_addresses` is never a fallback). The subject is one line (no line break or control character, at most 300 characters); the quote is the body of the opening mail (`sent_email_id`, never the newest own mail) while it is stored, else null. A loop whose addresses the draft schema refuses (none left after a DSR erase, a hidden character, a display name) gives `not_allowed` and no row. A key that exists with no waiting send is an invariant break: the call throws and the transaction rolls back (never catch it and commit). Two taps at once give one pair: the second waits for the loop lock and answers `waiting`. (b) `laterLoop` (any member): an open `waiting` or `delegated` loop with `later_count` below 3 gets `due_at` = 17:00 local, 3 working days after the later of the old due and now, and `later_count` + 1 (answer `{ ok, dueAt }`); the fourth use is `limit_reached`; a `promised` loop is `not_allowed`; a closed loop is `closed`. (c) `doneLoop` (any member) closes an open loop `done`, `dropLoop` (owner) `dropped`, `untrackLoop` (owner, only `delegated`; a `waiting` loop is `not_allowed`) `untracked`; a closed loop answers `already`; each also ends the waiting follow-up of the loop (`expired` / `loop_closed`) in the same transaction, but not a send that the committer holds (`applying`). (d) `reopenLoop` (owner): a closed loop with its texts opens again with its old `due_at`, `later_count` and `follow_ups_sent`, and `wait_from_at` = now, so the reply that closed it does not close it again; a `sent_off` loop, a loop with cleared texts, or a mailbox with "Track my sent mail" off gives `not_allowed`; an open loop gives `already`. It locks the Sent state row before the loop (the order of `onSentOff`). Nothing here sends mail: the send waits for a tap (ADR 0003). Tests: `loops-follow-up-draft`, `loops-commands`, `loops-commands-race` (two connections, committed rows, also as the table owner).
5. **The loop routes and the settings (open loops).** `loopRoutes` (module `loops`, mounted in `apps/server/src/web-routers.ts`) is a thin layer over the commands of rule 4: each write route is one command with `via: "web"` and the user of the session. The flag `open_loops` comes first: with it off every `/api/loops*` route answers 404 `not_found` to every role, also with a bad id or a bad body. `POST /api/emails/:id/delegate` follows the flag `delegate_button` the same way (not `open_loops`). A suspended organization gets 403 `org_suspended` on every write (the guard of all write routes). `GET /api/loops?kind=waiting|promised|delegated&filter=open|due|closed&before=&limit=` (any member; `kind` is required; `filter` default `open`; `limit` 1 to 100, default 50; `before` is the `next` cursor of the last page; a bad cursor is 400 `validation`) lists one page of the organization, oldest due first (`listLoops`). `due` means open with `due_at` at or before the first instant of the next local day of the organization (`endOfLocalDay`, so the web list includes a loop due exactly at midnight, which the brief of rule 8 leaves for the next day). A day that skips or repeats midnight (Havana, Santiago) starts at the first 00:00 or at the clock change (`startOfLocalDay`). Each `LoopItem` holds `kind`, `id`, `status`, `closeReason`, `counterpart`, `delegate` (`{ id, name }` for `delegated`), `text`, `subject`, `dueAt`, `dueSource`, `sentAt` (when the wait began, `wait_from_at`), `laterLeft` (3 minus `later_count`), `followUpsSent`, `followUpWaiting` and `sendId` (a follow-up send in `awaiting_approval`, `approved` or `applying`), `matchedBySubject` (`close_reason` is `replied_subject`), `autoReplyOnly` (`auto_reply_at` set and the loop still open) and `reason` (`asked_no_answer`, `promised` or `forwarded_to_delegate`). `text`, `subject` and `counterpart` are null after the retention cleared them; no log line holds them. The write routes: `POST /api/loops/:id/follow-up`, `/drop`, `/reopen`, `/untrack` and `POST /api/emails/:id/delegate` are owner only (403 `owner_only` comes before any query, also for an unknown id); `/later` and `/done` are for any member. The body is `{}` (a field is 400); `delegate` takes `{ delegateId }`. A success is 200 with `status` = the command kind and its fields: `{ status: "planned", sendId }` or `{ status: "would_draft" }` (follow-up), `{ status: "ok", dueAt }` (later), `{ status: "ok" }` (done, drop, reopen, untrack), `{ sendId, delegationId }` (delegate). Every other command kind is a 409 with that kind as `error` (`waiting`, `closed`, `limit_reached`, `too_soon`, `suspicious`, `drafts_off`, `already`, `not_allowed`, `exists`, `delegate_inactive`, `not_delegable`); `not_found` (also a loop or mail of another organization) is 404. Settings: `PATCH /api/settings/:mailboxId/loop-wait` `{ days }` (owner; a whole number from 1 to 10, else 400 `validation`; 404 while `open_loops` is off) writes `mailbox_settings.loop_wait_days`, sets `updated_at` (the settings version: a chaser run that read the old version skips once) and writes one audit row `settings.changed` (`mailbox_id`, `field` = `loop_wait_days`, `from`, `to`, `via`); the same value changes nothing. It moves the due date of loops opened later only. The switch `auto_follow_up` (default off) is a tool switch of the schema `toolSwitchesSchema`, so a mode or switch change keeps it (only a JSON `true` is on: another stored value reads as off and fails no other switch); `PATCH /api/settings/:mailboxId/switches/auto_follow_up` (owner) turns it on, and it is 404, and absent from the switch list of the settings view, while `open_loops` is off. `GET /api/settings/:mailboxId` also shows `loopWaitDays` and `sentTracking` (`on`, `off`, or `flag_off` while the flag `sent_sync` is off, also when the switch is still on). In the digest of rule 9, Draft, Drop, Reopen and the Delegate button are owner only: a member's keyboard has no such button, a member's digest has no ⌛ line (its one button is Reopen) and does not mark the loop shown, and the `delegable` hint of the digest rows and of the urgent notice goes to owners only. Tests: `web-loops`, `web-loop-settings`, `channels-digest-role`, `openapi-routes.test.ts`.
6. **The one chaser (D3).** The job `loops.chaser` (`20 */15 * * * *`; `runLoopChaser` in `loops/chaser.ts`) replaced `delegation.chaser`. It acts once per local day per mailbox, from 07:30 in the organization time zone, only for an organization that is not suspended. One transaction share-locks the settings row and compares the settings version, takes the advisory day lock, runs the delegation part (`delegation.md` rule 8), then the loop part, then writes the reminder set and the markers `delegation.chaser_run` and `loops.chaser_run` (counts only); each part has its own day gate. The loop part locks every candidate loop `FOR UPDATE` in ascending id order (one statement, the order of `onSentOff`) and then applies `loopFate`: (a) a `delegated` loop past its due date gets a follow-up card; (b) a `waiting` loop gets one only with the switch `auto_follow_up` (default off, PD-120); (c) a `waiting` or `delegated` loop ends `stale` when 2 follow-ups were sent and the last one is 14 days old, or when it is 30 days past due (an ignored loop ends, review G5); (d) a `promised` loop ends `expired` 7 days past due. (c) and (d) run in every mode and close the loop. (a) and (b) need mode `assist` and the switch `create_draft` on; `shadow` plans nothing (the brief says "would draft"). A follow-up comes from `planFollowUpPair`, the planning core that the Draft command shares (rule 4), with actor `system` and `via` `chaser`: at most 2 per loop, 3 working days apart, one waiting at a time, never in an approval set, none in a thread with a suspicious reason. The job offers each follow-up number once: when any send with the key `<loop>:send:follow_up:<n>:*` exists (rejected, expired, failed, `outcome_unknown`), it plans no new pair for that `n`; a user tap still can. At most 10 sends are planned per mailbox and run, the delegation reminders first. `auto_follow_up` is read from the stored JSON: only a `true` counts. The run reads 500 candidate loops per mailbox, ordered by id. `bun run job:run --name loops.chaser [--force]` runs it once (`delegation.chaser` is an alias and prints a line that says so); a mailbox error makes the command exit 1.
7. **The follow-up draft (D12).** Kind `follow_up`, anchored on the loop (`actions.loop_id`, no incoming mail; D4). Recipients come from the loop row only: To and Cc of a `waiting` loop, the counterpart alone for a `delegated` loop. The text is a fixed pl or en template, the mailbox signature and a quote of the user's own opening mail while its text is stored. In-Reply-To is the `message_id` of the loop. The committer calls `LoopHooks.isOpen` before the Drafts APPEND and before SMTP; a closed loop ends the send `expired` / `loop_closed` and no mail goes out. After a send, `onFollowUpSent` counts it and restarts the wait (due at least 3 working days on). The card, the result lines, the edit, the send limits over `to ∪ cc` and the lock order are in `drafts-and-send.md` rule 15. The Sent copy of a follow-up is `origin = system` and never analysed.
8. **The brief (D16).** The first digest of the member's day (decided by the date of the slot, `isFirstDigestOfDay`) starts with the block `📌 NEEDS YOU TODAY`: 🔴 Urgent (urgent mail of the digest window with no own answer; these rows leave the normal list), ✍️ Waiting on you (`needs_reply` mail of the last 14 days, no `\Answered` flag and no own mail later in the thread), ⏳ Waiting on others (open `waiting` and `delegated` loops and open delegations due by the end of the local day, oldest due first), 🤝 Promised (open `promised` loops due by the end of the local day) and ⌛ Ended (loops closed `stale` that no brief named yet). A section shows 5 lines and a "+n more" line. Each loop line sets `surfaced_at` (a ⌛ line `stale_notified_at`) once, under `FOR UPDATE` in the queue transaction, so a line shows once. A later digest of the day gets the count line `🔁 Open loops: 3 waiting, 1 promise due`. The on-demand `/digest` has neither. The block is cut from the bottom when a message passes 4096 characters. Loop text goes through `markUntrustedText` (links, addresses and long numbers go) and `withoutEscapeRemains`. Details of the digest and its buttons: `digest-and-notices.md` rules 4 and 14.
9. **Taps and commands by role (D11).** Done and Later: any member. Draft follow-up, Drop, Reopen, Untrack and Delegate: owners (the role check comes before any query; a member gets the same answer for an unknown id). Promised lines get Done and Drop, no Later. The Telegram callbacks are `lf:` `ll:` `lc:` `lx:` `lr:` `dg:` `dp:` (the prefixes are in `callbackKinds`, `packages/core/src/digest/callback-kinds.ts`); each calls the command of rule 4 with `via: "telegram"`. A member's digest has no Draft, Drop, Reopen or 👥 button and no ⌛ line.
10. **The consent gate (D17).** A loop line and a follow-up card name recipients, an ask and a promise of the user's own mail, so Telegram shows them only to a user whose consent covers `OPEN_LOOPS_CONSENT_SINCE` (`packages/core/src/web/telegram.ts`; `TELEGRAM_CONSENT_VERSION` was bumped to `2026-11-15.2` for it). `loopConsentOf(db, ctx, userIds)` in `channels/consent.ts` is the one choke point (`consent-gate.test.ts` reads the sources for any other use of `consentCovers`). A consent counts only when it is newer than the user's last `chat.unlinked` row; a user linked by the CLI has none until the Confirm button of the panel. Not covered: the brief shows counts and a panel link (delegations stay, they are not loop data), the card becomes one fixed `loop_consent` line with the panel link, and the keyboard has no loop button. No send path refuses other messages for an old consent; only new loop data is held back. A consent withdrawn between the check and the queue is not re-checked. The route is `POST /api/telegram/consent`; the panel shows "New terms" in the Telegram link block while `open_loops` is on (`web-panel.md` rule 13).
11. **Switch off (D18).** `setSentSync(off)` calls `onSentOff` inside its transaction (`sentSwitchHooks` in `composition.ts`): it closes every open loop of the mailbox `sent_off`, clears their texts, ends the waiting follow-up sends `expired`, removes `quote`, `to`, `cc` and `subject` from the payloads of loop sends (`clearLoopSentCopies`), clears the follow-up cards in the outbox (`clearLoopCards`: text `[removed]`, view `{}`; a delivered card gets one `approval_edit` with the fixed text `approvals.followUpRemoved`) and the digests that name a loop (`clearDigestsNamingLoops`; pending ones end `failed` / `outdated`). The marks `surfaced_at` of the loops that stay go back (`releaseBriefMarks`). A loop closed before the switch off keeps its texts until retention (up to 90 days; an owner decision of stage 08); a message that Telegram delivered stays in the chat. An organization flag `open_loops` off only stops the jobs and hides loops, routes and sections; it clears nothing. The scan tests list every table for planted values before and after the switch off (`loops-sent-off-copies.test.ts`, `loops-chaser-sent-off.test.ts`).
12. **Retention and erase.** `clearLoopTexts` clears subject, ask, counterpart, To and Cc of a closed loop 90 days after `closed_at` and sets `texts_cleared_at` (an open loop keeps them, also after the Sent subject went at 90 days: owner decision 51); the follow-up payloads, cards and digest rows go with the existing rules of `retention.md`. The DSR erase (`account-data.md` rule on open loops) blanks the text and subject of a loop that names the person, removes the address from every column, and leaves the loop with no recipient; the matcher closes it `dropped`, and a `delegated` loop with no counterpart gives `not_allowed` for Draft. The export holds the state and text of a loop and only the codes of `sent_analyses`.
13. **The panel.** The page `/delegations` is the "Open loops" page while `open_loops` is on: the tabs Delegated, Waiting and Promised with the filters Open, Due today and Closed; the Delegate action on Activity rows; the settings card (`data-card="loops"`: wait days 1 to 10 and the switch `auto_follow_up`); the Confirm button for the new Telegram terms. Details: `web-panel.md` rules 9 and 13. The Delegate action needs `delegate_button` and `delegation_pages` (`GET /api/delegates` is 404 without the second flag).
14. **Flags and switches.** Flags (`packages/core/src/features.ts`, epic `E5b`, remove-by 2027-06-01, default off): `open_loops` (sent analysis, loops, brief sections, loop taps, routes, tabs, M2 split) and `delegate_button` (the Delegate button and picker). `loops.analyze` needs `sent_sync` too. Per mailbox: the setting `loop_wait_days` (1 to 10, default 3) and the tool switch `auto_follow_up` (default off). With `open_loops` off, the routes answer 404, the digest has no loop part and `GET /api/settings/:mailboxId` leaves out the switch `auto_follow_up` (`loopWaitDays` is always there).
15. **M2.** `loopDueRows` (`loops/due-rows.ts`) gives the loops whose current due time is in a week to `openLoopsOnTime`. A loop is on time when it is answered (`replied`, `replied_subject`, `done`, `later_reply`) or has its first applied follow-up by the due time plus one working day; `surfacedOnTime` also counts `surfaced_at` by then. `dropped`, `untracked` and `sent_off` are not counted; `stale` and `expired` are due and not closed. The totals hold the delegations and the loops, and the split by kind (`delegation`, `waiting`, `promised`, `delegated`) shows only with `open_loops` on. Real mail only (`measurement.md` rule 4).
16. **Log lines and audit.** Fields come from the allow list (`platform/log-fields.ts`): `sent_analysis_done`, `sent_analysis_failed`, `sent_analysis_write_failed`, `sent_analysis_mailbox_failed` (rule 2), `loops_matched`, `loops_match_mailbox_failed` (rule 3), `loop_command` (rule 4), `loops_chaser_done` (`mailbox_id`, `count` = follow-up cards planned, extra lines with `kind` `stale` and `expired`). Audit events: `loop.closed`, `loop.later`, `loop.reopened`, `loop.would_draft`, `settings.changed` (the wait days), `loops.chaser_run`, `delegation.created` (with `source`), and the `action.*` rows of follow-ups. No line holds a subject, address, ask or promise; the logger drops ids that are not UUIDs.
17. **The wait per contact (F120, flags `sender_context` and `contact_wait`).** When `analyzeSent` opens a `waiting` or `delegated` loop with no stated date, it asks `contactWaitFor` (`modules/contacts/wait.ts`) for the contact: the counterpart of the ask (the delegate address that owns a To address, else the first To, else the first Cc). With both flags on, a stored profile and at least 5 reply samples of that contact, the due date is `sent_at` plus `clamp(ceil(1.5 × median hours the contact took to reply / 24), 1, 7)` working days (`defaultDue`), `due_source = 'contact'` and `usual_reply_days = clamp(round(median hours / 24), 1, 60)`. Else the wait is `loop_wait_days` and `due_source = 'default'`. A stated date always wins; the contact wait wins over the owner's `loop_wait_days`. The read runs before the write transaction; a failed read gives the default wait and one warning `contact_wait_failed` (an error name and code, no address). A promised loop never uses it. The thread restart and Later keep the rules above; they move `due_at` and do not change `due_source`. The panel row shows "Due <date> (usual reply time of this contact)" and "Usual reply: N days"; a brief line ends with "usual reply: N days" (the stored digest view holds the rendered text and `loopIds` only, so no view key is new). Rollback: flags off first, then `deploy/README.md` § Sender context, step "before the old image starts": the old code reads `due_source` as a strict enum `('stated', 'default')`, so each `contact` row must go back to `default` first.

## Data

- `open_loops` (stage 07; RLS on `org_id`, cascade with the mailbox, composite FKs on `org_id`): the columns of `docs/architecture.md` §5. Unique `(org_id, sent_email_id, kind)`; indexes `(org_id, mailbox_id, status, due_at)` and `(mailbox_id, thread_key)` where open.
- `open_loops.due_source` also holds `contact` and `open_loops.usual_reply_days` (1 to 60, set only with `contact`; F120, migration `db/migrations/20261118120001_sender_context.sql`, expand only). Rule 17.
- `sent_analyses`: one row per analysed Sent mail (`status` `pending`, `done`, `skipped`, `failed`; `skip_reason`; `expects_reply`; `has_promise`; `prompt_version`; `attempts`). No text. Cascade with the Sent row.
- `actions.loop_id` and `outbox.loop_id` (stage 09): the second anchor (rule 7). `delegations.source` (`triage` or `button`). `mailbox_settings.loop_wait_days`. `tool_switches.auto_follow_up`. `emails_thread_received_idx`.
- Status flow of a loop: `open` → `closed` (`replied`, `replied_subject`, `done`, `dropped`, `untracked`, `stale`, `later_reply`, `expired`, `sent_off`); `closed` → `open` by Reopen (an owner; not after `sent_off` or cleared texts; `wait_from_at` = now).

## Limits

- A new ask or promise in a later own mail in the thread of an open `waiting` or `delegated` loop is not extracted: that mail restarts the wait and calls no model (D9, review N13). A mail to other people is a side note and is analysed as new mail.
- An ignored `waiting` or `delegated` loop ends `stale` 30 days after due, in every mode (rule 6).
- Promises of other people (PD-122), snooze of incoming mail and calendar items are not built. The wait per contact (E11a) is built behind the flag `contact_wait` (rule 17); it needs 5 reply samples of the contact. There is no delegate alias list, and the report mail channel is a separate flag (`report_mail`, ADR 0022), off by default.
- Loop creation matches delegates and the user's own addresses with the one address rule (`normalizeAddress`) and stores the counterpart as written (trimmed, lower case: `storedAddressForm`), never in the rule form. `apps/server/src/address-rule-scan.test.ts` fails when a private lower-case fold of an address comes back into the loops, delegation, send-limit or sender-rule code.
- A reply from an alias of the user counts as the user's own only when the user wrote from that alias before (rule 3); a reply from a stranger alias closes the loop. A reply that arrives during the SMTP call of a follow-up falls before the new `wait_from_at` and is not counted.
- Texts of closed loops outlive a switch off by up to 90 days (rule 11). A delivered Telegram message cannot be recalled.
- With several linked owners only the first digest that commits shows a ⌛ line (the mark is one column).
- `sentFromAddressesOf` reads the Sent rows of the mailbox on every `matchReplies` run and every `isOpen`; no index covers `(mailbox_id, from_address)`. Fine at pilot size.
- The extractor schema is checked on OpenAI only. On Gemini a schema rejection is a hard `http_400` (rule 2): check it before `open_loops` is turned on there.
- A privacy erase blanks only loops whose text is still stored: a loop that retention already cleared can leave its subject in a digest that is still stored. The window is about one day.
- The stale span of a chaser counts 24 hours times the days, so a daylight-saving change moves the boundary by one hour.
- The pilot proof (one real follow-up sent after a tap, flags on for the pilot organization) is stage 25 of F116.

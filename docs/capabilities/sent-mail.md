# Sent mail

> Checked against the code at `00b43f90`, 2026-11-15.

## What it does now

The assistant reads the Sent folder of a mailbox, never changes it, and keeps that mail in its own table `sent_emails`, apart from `emails`. The read is off by default. It runs only when the organization flag `sent_sync` is on and the mailbox switch "Track my sent mail" (`mailbox_sent_sync.enabled`) is on. The `mail.sync` job runs one pass per mailbox after the INBOX sync, on the same connection. The pass stores the headers of the last 30 days and the text of the last 14 days, then reads new mail incrementally. A mail that the system sent is linked to its action and gets no text. Sent mail never enters triage, the digest, moves, Undo or `auto`. An error in the pass never fails the INBOX sync.

## Rules

1. **Gate.** `syncSentHeaders` checks, in this order: the flag `sent_sync` (else status `flag_off`), the switch (no row or `enabled = false` gives `off`), then `mailboxes.folder_map.sent` (empty gives `no_folder`). A path that differs from the stored one resets the cursor. The pass records its end in `last_pass_at`; `no_folder` and `folder_missing` also set `last_error_code`.
2. **Read only.** Sent code takes a `SentFolderReader`: five read methods (`folderStatus`, `fetchAbove`, `fetchContent`, `searchSinceIn`, `fetchByUidsIn`). A write method is a type error. The IMAP adapter fetches bodies with `BODY.PEEK`, so no flag changes. The GreenMail test checks that flags, UIDs, UIDVALIDITY and UIDNEXT stay the same.
3. **Mode.** No cursor: `initial`. Same UIDVALIDITY: `incremental` (UIDs above the cursor). Other UIDVALIDITY: `rescan`. `initial` and `rescan` read the mail with INTERNALDATE in the last 30 days.
4. **Windows.** The header window is 30 days from INTERNALDATE. Older mail that arrives above the cursor is skipped (`tooOld`) and the cursor passes it. The text window is 14 days, or `data_retention_days` of the organization when that is shorter.
5. **Dedup.** The key is the one of incoming mail (`Message-ID` and the content hash). One mail seen twice gives one row. A row with a tombstone is not stored again (the trigger of F106). The upsert never moves a mail except its location.
6. **Chunks and guard.** Headers are written in chunks of 50. Each write transaction locks the `mailbox_sent_sync` row and compares it with the state that the pass read (switch, period, path, UIDVALIDITY, last UID). A mismatch writes nothing and ends the pass with `cursor_moved`.
7. **Origin.** `sentOriginOf` (in `actions`, injected into `mail`) answers `system` when the send of the action went out: the row is `origin = system`, `headers_only`, with the action id. `draft` means the user sent a system draft by hand: a user row that keeps the action id. No action id, or an id of another mailbox, gives a user row.
8. **Text step.** After a `done` header step, `fetchSentTexts` reads the text of `pending` rows of the current path and UIDVALIDITY, oldest first, at most 100 per run, one mail after another. Each row has its own guarded write (no transaction, no lock across a mail server call). A row that waited past the text window becomes `headers_only`. A mail whose UID is gone, or whose source does not parse, becomes `gone`.
9. **Job and error rule.** The job calls `syncSentFolder` with a plain `Db` after `markSynced` and the flag refresh. `flag_off` and `off` log nothing. Any error is caught: one `sent_sync_failed` warning, then `mailbox_sent_sync.last_error_code = failed`. When that write fails too, one `sent_sync_mark_failed` warning. A login error in the pass is only logged; the next INBOX sync sets `auth_error`.
   10a. **Time budget.** One pass (headers and texts) has a budget `SENT_PASS_BUDGET_MS` = 60 s on a monotonic clock (`sent-budget.ts`; tests inject `budgetMs` and `clock`). The pass checks it before each IMAP call and between header chunks, and it stops waiting for one call that does not return in time. Then the status is `budget` (not an error: `markSentPass` with no error code, `sent_sync_done` with `"status":"budget"` (JSON log)). Rows written stay. `incremental`: the cursor stays at the last written chunk. `initial` and `rescan`: the cursor and `first_pass_at` do not move, and the next pass repeats the header step (dedup keeps it idempotent). Text step: the pending rows stay pending. After a timed-out call the pass makes no more IMAP calls, and the job closes the connection: `close()` waits 3 s for LOGOUT, then drops the socket.
10. **Log lines.** Fields come from the allow list (`platform/log-fields.ts`): `sent_sync_done` (`mailbox_id`, `status`, `kind` = the mode, `count` = new rows, `duration_ms` = time of the whole pass, for every status), `sent_texts_done` (`mailbox_id`, `count` = rows that the text step processed, also rows whose text is null: too big, or no text), `sent_texts_gone` (`mailbox_id`, `count` = rows marked `gone`), `sent_sync_failed` and `sent_sync_mark_failed` (`mailbox_id`, `error`, `error_code`). No line holds a subject, address, path, text or the message of an error. The count `system` of the pass result is not logged: it counts the system rows of each written chunk, so a rescan reports it with `stored 0`.

11. **Readers.** `listUserAnswers(db, ctx, emailIds)` answers "did the user reply to this mail, and when": per incoming mail, the earliest user row (`origin = user`, order `sent_at` then row id) of the same mailbox, in any Sent path, whose `parent_message_id` equals `emails.message_id_header`. A system send never counts; a user row with an action id does. A mail without a reply or without a Message-ID is absent from the map. Ids go in chunks of 500; no ids, no query. `getSentSummary(db, ctx, mailboxId, { since })` counts the user rows of the current path with `internal_date >= since` and gives the newest `internal_date` of any age; no state or no path gives `{ 0, null }`. `listSentHealth(db, ctx)` lists the mailboxes of the organization with the switch on and a first pass: pass times, the newest user date of the current path and the error code. All three take a plain `Db` or a transaction, filter by `org_id` and the mailbox, and write nothing.
12. **Retention.** The daily job clears the stored text (`clearSentBodies`) after the organization's `data_retention_days` and the subject and addresses (`clearSentHeaders`) after 90 days, both counted from `internal_date` (the date in Sent), not from the store time. The row stays: `content` stays `stored`, and `message_id`, `parent_message_id`, `thread_key`, `dedup_key`, `origin` and the times stay, so `listUserAnswers` answers after the clear. The functions work in batches with `FOR UPDATE SKIP LOCKED`; a repeat changes nothing. The retention log line adds the counts `sent body` and `sent headers`: no subject, address or text (`retention.md`).

13. **The switch (consent).** "Track my sent mail" is the consent to read Sent. `setSentSync(db, ctx, mailboxId, { enabled, actor, at })` is the only way to change it. One transaction, in this order: on with the flag `sent_sync` off gives `flag_off` and writes nothing (off never checks the flag, so the user can always withdraw); a mailbox that is not in the organization gives `not_found`; the state row is locked (a mailbox without a row gets an off row first); the same value gives `same` and no audit row. A change writes the switch with `enabled_at = at` (on) or `null` (off) and clears the folder, the cursor and the pass fields, so the next pass is `initial`. Off first calls the hook `SentSwitchHooks.onDisabled` (the web and the CLI pass `sentSwitchHooks` from `composition.ts`): it closes every open loop of the mailbox as `sent_off` and clears its texts (`onSentOff`, F116), removes `quote`, `to`, `cc` and `subject` from the `actions.payload` of every follow-up draft and send of the mailbox's loops (`clearLoopSentCopies`), and clears the follow-up cards in `outbox` (`clearLoopCards`, run by `sentSwitchHooks` in the same transaction: text `[removed]`, view `{}`; a card that no sender delivered ends `failed` / `outdated`). A loop that was closed before keeps its own texts until retention; a message that Telegram delivered stays in the chat. Off then deletes the `sent_emails` rows of this mailbox (`deleteSentEmails`; the count goes to the result) and nothing else: no received mail, no row of another mailbox or organization, no tombstone. The lock is the one of the pass (rule 6): a pass that read the old state writes nothing after the change. Each change writes one audit row `mailbox.sent_sync_changed` (data: `mailbox_id`, `enabled`, `count`; actor and time from the caller). The event is not in the security log of the owner. It carries no consent version: sent mail stays in our database and goes to no LLM. The only sent-mail data that leaves it is one time in the `sent_missing` notice (rule 17: the start of the quiet period, which can be the time of the newest sent mail), sent to the linked owners of the organization in Telegram; no subject, address or text goes anywhere. A feature that sends sent-mail data to Telegram or an LLM must add the consent text and its version first.
14. **Connect.** `connectMailbox` reads the flag before its transaction and inserts the state row with that value: flag on gives a mailbox with the switch on (the connect dialog shows the one plain line, stage 10; `mailbox:connect` prints `sent mail: tracked, read only`), flag off gives an off row. The audit row `mailbox.connected` has `sent_sync`. A mailbox that connects while the flag is off stays off when the flag goes on later: the owner turns it on.

15. **Settings API and CLI.** The settings view has the field `sentSync` (`getSentSyncView(db, ctx, mailboxId, now)`, `mail/sent-view.ts`): `null` while the flag is off and the switch is off (or no state row); else `flagOn`, `enabled`, `folder` (`folder_map.sent`), `firstPassDone`, `lastSentAt` (the newest user mail of the current path), `storedCount` (user mail of the last 30 days) and `errorCode`. With the flag off and the switch on, `flagOn` is false: the switch can only go off. The owner route `PATCH /api/settings/:mailboxId/sent-sync` (body `{ enabled }`) calls `setSentSync` and answers the settings change (`changed`, `settings`). **Flag off hides the field; the route answers 404** for `flag_off` and `not_found` alike (a hidden feature looks absent); a non-UUID or a mailbox of another organization is 404 too, a member gets 403, a bad body 400. `bun run mailbox:settings sent-sync --org-id <uuid> --mailbox-id <uuid> --value on|off` calls `setSentSync` with actor `cli` (turn it on only on the owner's instruction): it prints `sent sync on|off` (and `deleted <n> sent mails` for off), `no change`, or exits 1 for `flag_off` (the error names the flag and `bun run org:flag`) and `not_found`. `mailbox:settings show` adds one `sent:` line (`describeSentSync`): `sent: off (flag)` for `null`, else the switch, folder, stored count, last time, first pass and error code, plus `paused (flag off)`. `mailbox:connect` prints the off command after `sent mail: tracked, read only`.

16. **The panel.** The settings page shows the card "Sent mail" (`data-card="sent"`) after the sync folders card while `settings.sentSync` is not `null`. It holds one switch "Track my sent mail" that calls `PATCH …/sent-sync`, the fixed line `sent_line`, the Sent folder path, one status line (`sentStatusLine`: first match wins: paused, no folder, folder gone, failed, first read pending, no mail in 30 days, else the time of the last mail) and the off note. The switch is disabled for a member, while a request runs. While the flag is off and the switch is on (paused), the switch can only go off. The connect dialog shows `sent_line` as one muted line while `/api/me` `features` holds `sent_sync`. The texts are `sent_*` in `apps/web/src/i18n`.

17. **The notice `sent_missing`.** `sentMissingDetector` (`channels/notices/sent-missing.ts`) reads `listSentHealth` and queues one notice per linked owner when a mailbox has no mail of the user in Sent for 7 days (`SENT_MISSING_AFTER_MS`). It needs all of: the flag `sent_sync`, the mailbox `active`, the switch on with a first pass, no `last_error_code`, a `last_pass_at` that is not older than 1 hour (`SENT_PASS_FRESH_MS`), and `now − quietSince ≥ 7 days`. A pass of an older period that ends late can write `last_pass_at` in a new period; the new quiet period starts at the new first pass, so that write alone never makes a notice. `quietSince` is the later of the newest user mail (any age, current path) and `first_pass_at`; a system send never moves it. The key is `sent_missing:<mailbox id>:<quietSince ms>`: one row per owner and quiet period; a later user mail that goes quiet again starts a new period. Any other case cancels the pending rows of the mailbox (`failed` / `outdated`), so a quiet period after a flag-off or pause period gives no notice. The view holds the mailbox address and the dates only. The text asks whether the mail app keeps a copy in Sent; it never names an error (the card does).

18. **Data requests.** `org:dsr` (F106, `docs/capabilities/account-data.md`) treats sent mail like incoming mail. A sent row goes when the person is the sender or in To or Cc and every other address of the three is an own mailbox of the organization: the erase deletes it and writes a tombstone for its dedup key, so a later pass (also after the switch goes off and on) does not store it again. Other sent rows lose the address in `from_address`, `to_addresses`, `cc_addresses`, `subject` and `body_text`; a row with `content = pending` becomes `headers_only`. A row that retention cleared (`stored`, `body_text` null) is scrubbed by its addresses and subject; the export and the erase handle the null text. The erase locks the `mailbox_sent_sync` rows of the organization after the folder rows, the lock of rule 6, so a chunk planned before the erase waits and then meets the tombstone. The find report holds the sent mails that go (`sent_mails`), and the counts and audit rows hold `sent_mails`, never an address.

19. **The analysis (open loops).** The job `loops.analyze` (every 60 s, only where the triage scope is not `off`) runs `analyzeSent(deps, ctx, mailboxId, { now, limit })` for each active mailbox, only with the flags `sent_sync` and `open_loops` and the switch on. Candidates: `origin = user` rows with a text that is not `pending`, with no `sent_analyses` row and at most 14 days old, or with a `pending` row that is due; oldest first, at most 20 per run. Each candidate runs in this order: (a) the promise rule: every open `promised` loop that the user opened before this mail, whose counterpart is in its To or Cc, closes `later_reply` (any thread; the mail goes on); (b) the thread rule: an open `waiting` or `delegated` loop in the thread of the mail, older than the mail, whose To and Cc share an address with the mail, restarts its wait (due = `defaultDue(sent_at, max(loop_wait_days, 3))`; the row is `skipped / thread_restart`, no call); a mail to other people is a side note and goes on; (c) the delegation rule: a thread with an open delegation (`sent` or `overdue`) gives `skipped / delegation_thread`; (d) `sentSkipReason`. A row that passes calls the model once (`extractSent`, role `extractor`) unless the mailbox is at 80% of `LLM_DAILY_CAP` in the quota day (all roles count): then the row stays `pending / llm_cap` until 5 minutes after the next quota day starts. Every call writes one `llm.call` row (a failed call too), so extractor calls count in the cap. One transaction then writes the analysis row (`done`, `expects_reply`, `has_promise`, `prompt_version`) and the loops: `expects_reply` true opens `waiting` (or `delegated` when the first To that an active delegate owns exists; `counterpart` = that address), a promise with a resolved date opens `promised`; an ask with `expects_reply` false opens nothing. Addresses, subject and message ids come from the Sent row, never from the model; the subject loses line breaks and is cut to 300 characters. The first lock of each write is the state row of the switch, then the loops, so the order matches `setSentSync`: a switch-off waits for a write that runs now and then closes its loop `sent_off`; a write that comes after a switch-off writes nothing. A hard error or a schema failure counts one attempt and retries after 5 min × attempts; the third ends the row `failed`. A soft error (`softCodes`) other than `timeout`, or a configuration error, counts no attempt: the run stops, no later mailbox runs, and the job pauses (5 min, doubling to 60). A `timeout` counts as an attempt, so one mail that times out every time ends `failed` after 3 calls. The cap check never rounds up: a call runs only while `(used + 1) * 5 <= LLM_DAILY_CAP * 4` (a cap of 7 allows 5 calls, a cap of 3 allows 2, a cap of 1 allows none). In the synthetic scope only test mail reaches the model. An address of the operator in `TEST_SENDER_ADDRESSES` makes all real Sent mail of that mailbox test mail, so it goes to the model. On Gemini a schema rejection is a hard `http_400` (3 calls per mail, then `failed`; nothing in code stops it): check the extractor schema on Gemini before `open_loops` is turned on there. Do not run `bun run job:run --name loops.analyze` while the server runs: two processes at once make two calls for one mail, but still one analysis row and one set of loops. Log lines: `sent_analysis_done` (`mailbox_id`, `count` = rows that got a result, `opened` = loops opened), `sent_analysis_failed` (`mailbox_id`, `error_code`, or `error` and `error_code`), `sent_analysis_write_failed`, `sent_analysis_mailbox_failed`, `llm_audit_failed`; no text and no address. `bun run job:run --name loops.analyze` runs one pass and prints counts only.

20. **The close rules (open loops).** The job `loops.match` (every 2 min; it needs no model, so it runs with the triage scope `off`; only where the flag `open_loops` is on and the organization is not suspended) runs `matchReplies(deps, ctx, mailboxId, { now })` over the open `waiting` and `delegated` loops of each active mailbox. `promised` loops and delegations (`detectReply`) are not touched. A mail of the mailbox counts only when `received_at > wait_from_at` and its sender is not an own address (any mailbox of the organization, and every From address of the Sent rows of this mailbox, so an alias that the user wrote from is not a reply; lower case, trimmed; the newest 100 aliases; the counterpart, To and Cc of the loop itself never count as aliases, so a person who also sends as the user closes the loop with a reply). `replyMatch` (`packages/core/src/loops/replies.ts`) says how: `thread` when the mail has the loop's `thread_key` or its In-Reply-To or References hold the loop's `message_id` (each id compared whole, so `<x<id>>`, a suffix or another case does not match); `subject` when `normalizeSubject` is equal (and not empty), the sender is in the loop's To or Cc and the mail came within 30 days of `wait_from_at`; `auto` when `isAutoReply` is true on a mail that would match by thread or subject (`Auto-Submitted` other than `no`, `Precedence` bulk, junk, list or auto_reply, or a `mailer-daemon`, `postmaster` or `noreply` sender, or a subject that starts with `Automatic reply:`, `Autoreply:`, `Out of office:`, `Odpowiedź automatyczna:` or `Nieobecność:` after the reply prefixes; no `email_headers` row means not automatic). `normalizeSubject` drops the prefixes `Re:`, `Odp:`, `Fwd:`, `FW:`, `PD:`, `AW:`, `SV:`, `WG:`, `TR:`, `Antw:` (any case and spacing, with a count such as `Re[2]:`, repeated), the gateway tag `[EXT]` and a closing dot, reads full-width and no-break forms as plain ones, drops zero-width and control characters and collapses spaces; a look-alike letter is not stripped, so it does not match. The first non-`auto` match in `received_at` order closes the loop: `thread` gives `replied`, `subject` gives `replied_subject`, both with `closed_by_email_id`. An `auto` mail before it sets `auto_reply_at` once and the search goes on; an automatic mail never closes. An open loop with an empty `to_addresses` (a DSR erase) closes `dropped`. Each write is one transaction: lock the loop, check it is still open, decide again on the locked row, close it, and end its waiting follow-up sends `expired` / `loop_closed`. Two runs at once (or a run and `onSentOff`) give one close, one `loop.closed` audit row and one expiry per send. A reply that arrives while the follow-up restarts the wait does not count, because the decision runs again under the lock. The log line `loops_matched` (`mailbox_id`, `count`, `kind` = the reason) holds no address and no subject. A reader limit: one run reads 500 loops per mailbox (oldest wait first) and, in two reads with a limit of 200 mails each, the mails of the thread (or naming the loop `message_id`) and the mails of the recipients. A mail from the junk folder of the mailbox, or whose latest triage category is `spam`, never counts.

21. **The loop commands (open loops).** Module `loops` exports six commands that Telegram (stage 19) and `/api` (stage 20) call with a `via` (`web`, `telegram` or `cli`). All of them need the flag `open_loops` (`draftFollowUp` and `laterLoop` answer `feature_off`; the others answer `not_found`, as the loop is hidden), run in one transaction, lock the loop first and then its sends, and write one audit row with the `via`. A log line `loop_command` (`org_id`, `loop_id`, `command`, `kind` = the answer, `via`) holds ids and codes only. (a) `draftFollowUp` plans one follow-up pair and says why not otherwise, in this order, after the settings row is share-locked and the loop is locked: `not_found`, `not_allowed` (the user must be an owner), `closed`, `not_allowed` (a `promised` loop), `waiting` (a follow-up send of the loop in `awaiting_approval`, `approved` or `applying`, with its `sendId`; a `failed`, `rejected` or `expired` send does not wait), `limit_reached` (`follow_ups_sent` is 2), `too_soon` (the second one before `last_follow_up_at` plus 3 working days), `suspicious` (any suspicious reason in the thread, whatever the flag), `would_draft` (mode `shadow`; one `loop.would_draft` audit row, no action), `drafts_off` (no settings row, or the switch `create_draft` is off). Otherwise it plans a `create_draft` (`ready`) and a `send` (`awaiting_approval`) with `loop_id` and no `email_id`, keys `<loop id>:create_draft|send:follow_up:<n>:<k>` (`n` = `follow_ups_sent` + 1; `k` = 1 + the follow-up sends of the loop that used this `n`), and two `action.planned` audit rows (actor = the user, no mail). The recipients come from the loop row only: To and Cc of a `waiting` loop, the counterpart alone for a `delegated` loop (a `delegated` loop with no counterpart, as after a data erase, gives `not_allowed`: `to_addresses` is never a fallback). The subject is one line (no line break or control character, at most 300 characters); the quote is the body of the opening mail (`sent_email_id`, never the newest own mail) while it is stored, else null. A loop whose addresses the draft schema refuses (none left after a DSR erase, a hidden character, a display name) gives `not_allowed` and no row. A key that exists with no waiting send is an invariant break: the call throws and the transaction rolls back (never catch it and commit). Two taps at once give one pair: the second waits for the loop lock and answers `waiting`. (b) `laterLoop` (any member): an open `waiting` or `delegated` loop with `later_count` below 3 gets `due_at` = 17:00 local, 3 working days after the later of the old due and now, and `later_count` + 1 (answer `{ ok, dueAt }`); the fourth use is `limit_reached`; a `promised` loop is `not_allowed`; a closed loop is `closed`. (c) `doneLoop` (any member) closes an open loop `done`, `dropLoop` (owner) `dropped`, `untrackLoop` (owner, only `delegated`; a `waiting` loop is `not_allowed`) `untracked`; a closed loop answers `already`; each also ends the waiting follow-up of the loop (`expired` / `loop_closed`) in the same transaction, but not a send that the committer holds (`applying`). (d) `reopenLoop` (owner): a closed loop with its texts opens again with its old `due_at`, `later_count` and `follow_ups_sent`, and `wait_from_at` = now, so the reply that closed it does not close it again; a `sent_off` loop, a loop with cleared texts, or a mailbox with "Track my sent mail" off gives `not_allowed`; an open loop gives `already`. It locks the Sent state row before the loop (the order of `onSentOff`). Nothing here sends mail: the send waits for a tap (ADR 0003). Tests: `loops-follow-up-draft`, `loops-commands`, `loops-commands-race` (two connections, committed rows, also as the table owner).
22. **The loop routes and the settings (open loops).** `loopRoutes` (module `loops`, mounted in `apps/server/src/web.ts`) is a thin layer over the commands of rule 21: each write route is one command with `via: "web"` and the user of the session. The flag `open_loops` comes first: with it off every `/api/loops*` route answers 404 `not_found` to every role, also with a bad id or a bad body. `POST /api/emails/:id/delegate` follows the flag `delegate_button` the same way (not `open_loops`). A suspended organization gets 403 `org_suspended` on every write (the guard of all write routes). `GET /api/loops?kind=waiting|promised|delegated&filter=open|due|closed&before=&limit=` (any member; `kind` is required; `filter` default `open`; `limit` 1 to 100, default 50; `before` is the `next` cursor of the last page; a bad cursor is 400 `validation`) lists one page of the organization, oldest due first (`listLoops`). `due` means open with `due_at` at or before the first instant of the next local day of the organization (`endOfLocalDay`, so the web list includes a loop due exactly at midnight, which the brief of rule 21 leaves for the next day). A day that skips or repeats midnight (Havana, Santiago) starts at the first 00:00 or at the clock change (`startOfLocalDay`). Each `LoopItem` holds `kind`, `id`, `status`, `closeReason`, `counterpart`, `delegate` (`{ id, name }` for `delegated`), `text`, `subject`, `dueAt`, `dueSource`, `sentAt` (when the wait began, `wait_from_at`), `laterLeft` (3 minus `later_count`), `followUpsSent`, `followUpWaiting` and `sendId` (a follow-up send in `awaiting_approval`, `approved` or `applying`), `matchedBySubject` (`close_reason` is `replied_subject`), `autoReplyOnly` (`auto_reply_at` set and the loop still open) and `reason` (`asked_no_answer`, `promised` or `forwarded_to_delegate`). `text`, `subject` and `counterpart` are null after the retention cleared them; no log line holds them. The write routes: `POST /api/loops/:id/follow-up`, `/drop`, `/reopen`, `/untrack` and `POST /api/emails/:id/delegate` are owner only (403 `owner_only` comes before any query, also for an unknown id); `/later` and `/done` are for any member. The body is `{}` (a field is 400); `delegate` takes `{ delegateId }`. A success is 200 with `status` = the command kind and its fields: `{ status: "planned", sendId }` or `{ status: "would_draft" }` (follow-up), `{ status: "ok", dueAt }` (later), `{ status: "ok" }` (done, drop, reopen, untrack), `{ sendId, delegationId }` (delegate). Every other command kind is a 409 with that kind as `error` (`waiting`, `closed`, `limit_reached`, `too_soon`, `suspicious`, `drafts_off`, `already`, `not_allowed`, `exists`, `delegate_inactive`, `not_delegable`); `not_found` (also a loop or mail of another organization) is 404. Settings: `PATCH /api/settings/:mailboxId/loop-wait` `{ days }` (owner; a whole number from 1 to 10, else 400 `validation`; 404 while `open_loops` is off) writes `mailbox_settings.loop_wait_days`, sets `updated_at` (the settings version: a chaser run that read the old version skips once) and writes one audit row `settings.changed` (`mailbox_id`, `field` = `loop_wait_days`, `from`, `to`, `via`); the same value changes nothing. It moves the due date of loops opened later only. The switch `auto_follow_up` (default off) is a tool switch of the schema `toolSwitchesSchema`, so a mode or switch change keeps it; `PATCH /api/settings/:mailboxId/switches/auto_follow_up` (owner) turns it on, and it is 404, and absent from the switch list of the settings view, while `open_loops` is off. `GET /api/settings/:mailboxId` also shows `loopWaitDays` and `sentTracking` (`on`, `off`, or `flag_off` while the flag `sent_sync` is off, also when the switch is still on). In the digest of rule 21, Draft, Drop, Reopen and the Delegate button are owner only: a member's keyboard has no such button, a member's digest has no ⌛ line (its one button is Reopen) and does not mark the loop shown, and the `delegable` hint of the digest rows and of the urgent notice goes to owners only. Tests: `web-loops`, `web-loop-settings`, `channels-digest-role`, `openapi-routes.test.ts`.

## Data

- `mailbox_sent_sync`: one row per mailbox: `enabled`, `enabled_at`, `path`, `uidvalidity`, `last_uid` (the cursor), `first_pass_at`, `last_pass_at`, `last_error_code` (`no_folder`, `folder_missing`, `failed`). No row means off.
- `sent_emails`: one row per mail: location (`path`, `uidvalidity`, `uid`), `message_id`, `parent_message_id`, `references_ids`, `thread_key`, addresses (`to`, `cc`; never Bcc), `subject`, `sent_at`, `internal_date`, `origin`, `action_id`, `content`, `body_text` (at most 100 000 characters) and the markers `auto_submitted`, `precedence`, `list_id`, `has_calendar`. `content` flow: `pending` → `stored` | `headers_only` | `gone`.
- Both tables have RLS on `org_id` and cascade with the mailbox. They are in the registries of the account export and the DSR address map (F106). The organization delete removes them by cascade.

## Limits

- Only a known Sent folder is read (`folder_map.sent`); the pass never guesses a folder by name (F104 plan, Q4).
- One mail that makes `fetchContent` fail on every run (a server `BAD` on one UID) holds the text step: the order is oldest first and the error ends the step. It clears when the row leaves the text window, after up to 14 days. The pass logs `sent_sync_failed` each run.
- Worst case of one run: 100 text fetches of up to 5 MB each, one after another, on the connection of the mailbox. The budget of rule 10a caps the Sent pass at 60 s, plus up to 3 s of close; a very slow server can show repeated `budget` lines, and a first pass then takes several runs.
- Mail moved into Sent by hand after it is older than 30 days is not stored (`tooOld`).
- The switch is set by `setSentSync`, at connect, by the route and by the CLI (rule 15). Run `org:dsr --erase` again after a new first pass and after its text step (rule 18).
- The notice (rule 17) never fires for a period that the pass did not observe, and it names no error: the panel card shows an error code.
- No analysis of sent mail by the LLM: E5b. No pass before a system send: E6a (F115).
- `listUserAnswers` reads a direct reply only (the parent id): a later reply elsewhere in the thread does not mark older mails; a reader that wants the thread rule builds it from `thread_key`. No caller yet: E3a, E4-B, E11a, E6 (reply drafts) and E5b (open loops) use it. F116 (open loops) note: Sent text goes after `data_retention_days` and the recipients after 90 days, so a loop that stays open longer than `data_retention_days` needs its own copy of what it needs.

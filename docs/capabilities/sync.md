# Sync

> Checked against the code at `5ba3e0bc`, 2026-11-18.

## What it does now

Sync brings mail from an IMAP mailbox into the `emails` table. An owner connects a mailbox on the web panel or with `bun run mailbox:connect`. Both paths test the IMAP and SMTP login first, and a failed login stores nothing. The password is stored only encrypted. Every `MAIL_SYNC_EVERY_MIN` minutes (default 2; 3 or 5 are allowed) the job `mail.sync` walks each `active` mailbox of every organization that is not `suspended`. It reads INBOX, then the provider sort folders, then the spam folder. Each folder has its own cursor (UIDVALIDITY and last UID). New mail becomes an `emails` row with status `pending`, and the triage worker takes it from there (`triage.md`). Sync only reads the mailbox: it never moves, flags or deletes mail. It also detects a mail that the user moves back after a system move (`emails.returned_at`). An operator can pause, resume, rescan, backfill and audit a mailbox with the CLI tools below. A login error sets the mailbox to `auth_error`; the way out is `bun run mailbox:password`.

## Rules

1. **Connect (web and CLI).** Both go through `connectMailbox`. The order is fixed:
   1. The input is validated (a bad address or port stops here).
   2. A mailbox with the same address in the organization gives `mailbox_exists` (web `409`).
   3. An organization at its mailbox limit gives `mailbox_limit` (web `409`). The check runs before any login, without a lock.
   4. The IMAP login and the SMTP login are tested (`smtpSecurity` is `tls` or `starttls`). The web route stops a check that hangs: the socket timeout is 20 s and the deadline is 25 s (`WEB_MAIL_TIMEOUTS`).
   5. One transaction takes the limit lock, checks the limit again, then inserts the `mailboxes` row, the `INBOX` row of `mailbox_folders`, the encrypted credentials, the default settings, the Sent switch row (`mailbox_sent_sync`: on when the flag `sent_sync` was on before the transaction, else off) and the audit row `mailbox.connected` (data: `mailbox_id`, `via`, `sent_sync`). `connectMailbox` returns `sentSync`; `mailbox:connect` prints `sent mail: tracked, read only` when it is true (`sent-mail.md`).

   Connect changes nothing in the mailbox: it does not create the `AI/*` folders. The committer creates them before the first move (`actions-and-undo.md`).

2. **Host guard.** Every IMAP and SMTP connection resolves its host through `resolveMailHost` and connects to the checked address, so a second DNS answer cannot redirect it. A host that is, or resolves to, a local, private, Tailscale, benchmark, multicast, reserved, NAT64, site-local or 6to4 address gives `HostNotAllowedError` (web `400 host_not_allowed`). A DNS failure is a soft error: a warning, and the next tick tries again. A refused host at a sync run or at a committer open makes an `active` mailbox `host_blocked` (`markHostBlocked`, audit row `mailbox.host_blocked`). `MAIL_ALLOW_LOCAL_HOSTS=true` (or the old `WEB_MAIL_ALLOW_LOCAL`) turns the guard off for tests and local servers. The web connect route also refuses a local host name before any network call, unless local hosts are allowed.
3. **Presets.** The web form accepts a preset (`interia`, `gmail`, `onet`, `wp`, `o2`, `icloud`) or explicit hosts. `mailbox:connect` takes the hosts as flags.
4. **Capability check.** `bun run mailbox:check` first prints `status:`, `imap-host:` and `smtp-host:`. A refused host gives exit 2 and no connection. Then it reads the server capabilities (IDLE, MOVE, UIDPLUS, CONDSTORE, SPECIAL-USE, KEYWORDS) and the folder list. With `--probe` it also adds one draft and sends one mail to the mailbox itself, to test `SEARCH HEADER` and the auto-save of sent mail. Use `--probe` only on a test account. Connect stores the capabilities in `mailboxes.capabilities`.
5. **Folder keys (ADR 0014).** The keys are `inbox`, `offers`, `social`, `bills` and `junk`. At Interia the defaults are `Oferty`, `Społeczności`, `Rachunki` (role `sort`) and `Wiadomości-śmieci` (role `junk`). At each run the job adds a row for each default name that the server lists exactly. It never adds a folder that is Drafts, Sent, Trash, an `AI/*` folder or the `AI` root. Sync reads INBOX and the enabled rows of `mailbox_folders` only; it never reads `AI/*`, Drafts, Trash or the user's own folders, so that mail is never touched. The Sent folder is read by its own pass (rule 6), not by this loop. The run goes folder by folder: INBOX, the `sort` folders, then the spam folder. An error in a folder other than INBOX gives a warning and the run goes on; the third failed run in a row for one folder gives one `error` line. A folder row that the server does not list is skipped. `bun run mailbox:settings sync-folder --key offers|social|bills|junk --value on|off` switches a folder (INBOX has no switch); switching on again clears its cursor, so the folder starts with a new 24 h first sync. The web panel does the same with `PATCH /api/settings/:mailboxId/sync-folders/:key` (owner only). Details of the folder rules: `docs/architecture.md` §6.1.
6. **The `mail.sync` job.** Cron `*/N * * * *`, where N is `MAIL_SYNC_EVERY_MIN` (2, 3 or 5; default 2; `mailSyncCron` in `platform/config-mail.ts`). The start logs `mail_sync_interval` with `minutes`. The target list is `listSyncTargets`: mailboxes with status `active` of organizations whose plan is not `suspended`. The job checks the plan before each mailbox, so a suspend during a run stops at the next mailbox. After a good run it sets `mailboxes.last_synced_at`. Then, on the same connection, the job refreshes the IMAP flags of the mailbox (`refreshFlags`, `flags.ts`): at most every 10 minutes per mailbox and process (an in-memory map, so a restart refreshes at the first run). It checks mail received in the last 30 days, at most 3,000 per run, never-checked mail first and then the oldest check. It asks the server for `\Seen`, `\Answered` and `\Flagged` per folder in chunks of 500 UIDs (`fetchFlagsIn`) and keeps them in `email_flags` with the first time each flag was seen. The write is guarded: it changes a row only while `emails.folder` and `emails.uid` still equal what the run read, and only when the fetched mail is the stored one (the same normalized Message-ID, else the same INTERNALDATE to the second), because a UID can name another mail after a UIDVALIDITY change. A UID the server no longer returns counts as `notFound`, a UID of another mail as `mismatch` (a Message-ID on one side only is also a mismatch); both write no flags. They only set `email_flags.checked_at` (`touchEmailFlags`), so such mail goes to the back of the queue and cannot fill the 3,000 of a run; a mail without a row gets one with all flags false and no first-seen time. `checked_at` means "last tried", not "flags read". The refresh only reads FLAGS, so "sync only reads the mailbox" stays true. A failure in the refresh (also a login error) is one `flags_refresh_failed` warning and never fails the sync. The mail counted in `notFound` (gone from its stored folder) goes to the move finder (`findUserMoves`, `moves.ts`): a webmail move keeps the UID at Interia, so it fetches that UID in each enabled synced folder whose cursor is at or above it (not the mail's own folder, not a folder that failed or was skipped in this run; at most 500 UIDs per fetch). A hit with the stored identity that no other identical row holds there is the mail: a row that the system had moved is `returned` (rule 11), any other row is moved to that folder with no feedback. The write runs under the folder lock and only while the row still has the folder and UID that the refresh read; a fresh move marker skips the row. A failure is one `user_moves_failed` warning and never fails the sync. The info line `user_moves_checked` gives the number of candidates (gone rows that still have the folder and UID of the read and no fresh move marker), which can be lower than the `notFound` count. The log lines hold the mailbox id and counts only. Last, on the same connection, the job runs the Sent pass (`syncSentFolder`, [sent-mail.md](sent-mail.md)): it does nothing and logs nothing while the organization flag `sent_sync` or the mailbox switch is off (the default). The pass reads the Sent folder only (it gets the provider as a `SentFolderReader`, which has no write method), takes a plain `Db` so that no row lock is held across a mail server call, and writes into `sent_emails`, never into `emails`. An error in the pass (also a login error) is one `sent_sync_failed` warning with the mailbox id and the error name and code; it never fails the sync, never sets `auth_error` (the next INBOX sync does), and sets `mailbox_sent_sync.last_error_code` to `failed`.
7. **Cursor and first sync.** The cursor of a folder is `uidvalidity` and `last_uid` in its `mailbox_folders` row. An incremental run fetches the UIDs above the cursor and drops the UIDs at or below it (`UID FETCH n:*` also returns the highest message). The mode is `initial` when the folder has no cursor (only mail of the last 24 h), `incremental` when UIDVALIDITY is unchanged, and `rescan` when it changed (mail of the last 7 days; the dedup key stops duplicates). `bun run mailbox:rescan` forces a rescan of every synced folder of one mailbox. The UIDNEXT of a folder is the largest of the STATUS value, the SELECT value and the highest UID + 1, because Interia gives a wrong STATUS value.
8. **Dedup key.** `Message-ID` plus `content_hash` (SHA-256 of the `From` address, the `Date` header, else INTERNALDATE, and RFC822.SIZE). A mail without a `Message-ID` uses the hash only. The same `Message-ID` with another hash is a new mail. A second identical copy gets the key with `#2`, `#3`, and so on. The unique index is `(mailbox_id, dedup_key)`. Exact rules: `docs/architecture.md` §6.1.
9. **Own mail is skipped.** A message whose `X-EA-Action-Id` header matches an `actions` row of the mailbox is the system's own draft or sent mail: sync does not store it (`isOwnActionId`). The same header with the id of an outbox row of this mailbox with `channel = 'mail'` marks a report mail that the system appended (F110 stage 20, `isOwnReportMail`): sync does not store it either. The two checks are composed in `isOwnMailOf` (`apps/server/src/composition.ts`), and every root that builds a sync, the history job or the operator backfill passes it (`apps/server/src/main.ts`, `apps/server/src/scripts/mailbox-backfill.ts`; `apps/server/src/composition.test.ts` scans for it). A header value that is not a uuid, or the id of a Telegram row, of another mailbox or of another organization, is no own mail: the mail is stored and triaged. `From:` with the owner's address is not a reason to skip.
10. **Known mail is never triaged again.** `update_uid` and `returned` never change `emails.status`.
11. **Returned mail.** When the user moves a mail that the system moved back to a synced folder, sync sets `emails.returned_at`, `folder` and `source_folder` (the mail is gone from the folder it was moved to). When the mail has two or more known identical copies outside the synced folder (also a first copy that sits in its own source folder), the sync checks them in copy order (at most 5) and the first one that is gone is the mail that came back; only when all are still there does it store a new identical copy (`#n`). The job `triage.returned` then writes the feedback row (`triage.md`). At the end of each incremental run, sync also looks at the mail that the system moved in the last 7 days (at most 500, newest first) in the folder it came from, for a return that kept its UID below the cursor. A mail that sits in two synced folders (a cross copy) is counted and not stored. While a system move runs (`emails.move_pending_at` younger than 24 h), sync stores no copy of the mail. A hit whose mail is still in its system folder at the row's own UID is a copy below the cursor: the end-of-run check stores it as `#n` (body, `email_headers` row, status `pending`; the triage worker takes it like any new mail), and `copiesStored` counts it. Sync stores nothing in four cases: a move of the mail is in flight; another row of the mail holds that UID; this run saw the mail in another synced folder; the row's mail was found only at another UID. A copy that a row holds is not a hit again, so the next run counts `copies 0` and a real return of the moved row is still found. A return or a move below a synced folder's cursor that the end-of-run check does not cover (another folder than the source, or a mail the system did not move) is found by the move finder of rule 6.
12. **Mailbox statuses.** `active`: synced. `paused`: not synced and not triaged; the owner sets it on the web panel (`POST /api/mailboxes/:id/pause`, `.../resume`) or with Telegram `/pause` and `/resume` (owner only). `auth_error`: set by the job when a login fails; a pause or resume on an `auth_error` mailbox answers `409 wrong_status` on the web. `host_blocked`: set by the sync job or the committer when the host guard refuses a host; the mailbox is not synced, triaged or sent; a pause or resume answers `409 wrong_status` on the web and Telegram skips it. Each change writes an audit row (`mailbox.paused`, `mailbox.resumed`).
13. **Mailbox errors** (moved from `docs/architecture.md` §8). IMAP/SMTP login error → mailbox `auth_error`, a Telegram notice to the linked owners (one per `status_changed_at`), other mailboxes continue. The way out is `bun run mailbox:password` (new password on stdin, login test, `auth_error` → `active`). Connection errors → a warning; the next 5-minute tick tries again.
    - A host that the guard refuses → mailbox `host_blocked` and one Telegram notice to the linked owners per `status_changed_at`. The notice names the mailbox address, never a host name or address. The way out is the re-check at the start of each `mail.sync` run (`recheckBlockedHosts`): it runs the guard on both hosts with no connection (two DNS lookups per blocked mailbox per run, no cap). When both pass, the mailbox becomes `active`, the audit row `mailbox.host_allowed` is written and the same run syncs it. A successful password change (`updateMailboxPassword`) also ends it.
    - A hard error is logged as an `error` line. A cursor that moved during a run (`CursorMovedError`) is a soft error like a connection error.
    - `updateMailboxPassword` tests the IMAP and SMTP login with the new password first; a failed login stores nothing. An `auth_error` or `host_blocked` mailbox becomes `active`; a `paused` one stays paused. A refused host makes the call fail with `host_not_allowed` and changes nothing. The web route is `POST /api/mailboxes/:id/password` (owner only). On an OAuth mailbox (`oauth_provider` set) it throws `MailboxOAuthError` before any login: the route answers `409 oauth_mailbox`, `bun run mailbox:password` exits 1 with `oauth mailbox: use Reconnect in the panel`, and nothing changes. `GET /api/mailboxes` shows `authMethod` (`password` or `oauth`), `oauthProvider` and `authReason` (`oauth_expired`, `oauth_revoked`, `admin_consent_required`, `protocol_disabled`; `null` for a password mailbox and outside `auth_error`).
14. **Remove.** `DELETE /api/mailboxes/:id` (owner only) needs the typed address (`confirm_mismatch` gives `400`). The mailbox is paused first; then one transaction runs `delete_mailbox`, writes the audit row `mailbox.removed` and queues the owners' notice. A deadlock is retried once. On any other error a mailbox that this call paused returns to `active`. The answer is `200` with `{ authMethod, oauthProvider, revoked, accessPage }` (a password mailbox: `password` and three nulls). An OAuth mailbox: the secret is read under the mailbox OAuth lock before the delete. After the commit the token cache of the mailbox is dropped. Google: the refresh token is revoked (10 s timeout; a failure is one `mail_oauth_revoke_failed` warn line with `provider` and `kind`, and the Remove still succeeds), and the owners' notice is queued after the revoke, in its own transaction, so its text says if the access is withdrawn (`revoked`). Microsoft: no call (a delegated token has no revoke API); `accessPage` is `microsoft_work` (My Apps) or `microsoft_personal` (tenant `9188040d-6c67-4c5b-b112-36a304b66dad`, the consent page of the account). The `mailbox_removed` notice view has an optional `access` field `{ page, revoked }`; a row without it renders the password text. An organization delete revokes nothing.
15. **Backfill (one-off).** `bun run mailbox:backfill --org-id <uuid> --mailbox-id <uuid> [--days 1-180]` (default 30) reads INBOX mail of the last days, stores the missing mail with `emails.backfilled_at` set, and never moves the cursor. It changes nothing in the mailbox. It refuses a window above 180 days, a mailbox that was never synced, a changed UIDVALIDITY (wait for the regular rescan) and a suspended organization. After the store it re-queues real mail of the window that the worker skipped as `too_old`, or that the history check stored as `history_check` (`triage.md`). The history check of the trust ladder calls the same read with the purpose `history`: it stores new mail as `skipped` / `history_check`, changes no stored row and returns each refusal as a value.
16. **Operator tools.** `bun run mailbox:seed` appends synthetic mail into INBOX or a sync folder; it refuses every mailbox that is not in `TEST_MAILBOX_ADDRESS` (one address, or a comma-separated list). The four mailbox tools (`mailbox:seed`, `mailbox:audit`, `mailbox:signals`, `mailbox:backfill`) open a stored mailbox through `openMailboxProvider`, so they work on an OAuth mailbox; a refused OAuth login prints its reason code and exits 1, and the tool never changes the mailbox status. A mailbox with a real provider takes seed mail only with `--from-owner <address>` (optional `--number-from <n>`): each `From` becomes `<local>+ea-smoke-<nn>@<domain>` of that address and `To` the mailbox, so a reply reaches only the owner; without it the seed exits 1. `bun run mailbox:audit --org-id <uuid> --mailbox-id <uuid> --since <ISO time>` is read-only: it compares the mail of each enabled synced folder on the server with the stored rows (exit 0 no difference in INBOX, exit 2 lost or duplicate INBOX mail). Run it right after a sync, because mail that came after the last sync can show as missing. `bun run mailbox:signals --org-id <uuid> --mailbox-id <uuid> [--days 30]` is read-only: it prints counts of INBOX mail of the window (`\Answered`, `\Seen`, `\Flagged`, `Authentication-Results`, `List-Unsubscribe`) and the mail server names of `Authentication-Results`; it prints no subject, address or UID and writes nothing.
17. **Mailbox limit.** `organizations.max_mailboxes` caps the mailboxes; connect checks it twice (rule 1). See [tenancy-and-plans.md](tenancy-and-plans.md).
18. **Header capture.** Each mail that sync or backfill stores gets one `email_headers` row, written in the transaction of the `emails` insert and only when that insert stored the mail (`storeCapture`, `insertEmailHeaders`). The row holds: `from_name` (200 characters), `reply_to` (at most 5 addresses), `return_path` (320), `auth_results` (the topmost value, 1000), `list_unsubscribe` (1000; null when the mail has more than one `List-Unsubscribe` or `List-Unsubscribe-Post` line, F110 stage 24 review: DKIM checks the lowest instance of a repeated header and capture reads the topmost, so a forged line on top of a signed mail would change the target), `list_unsubscribe_post` (a flag: false when either header repeats; true only when the topmost `List-Unsubscribe-Post` value, trimmed and in any case, is `List-Unsubscribe=One-Click` (RFC 8058); false when the header is absent or has another value; the header text is not stored; null on a row stored before F110 stage 22: no backfill), `dkim_signatures` (a JSON array of at most 8 `{ d, h }`: the signing domain `d=` and the signed header names `h=` of each `DKIM-Signature` header, lower case, at most 64 names of at most 40 characters each; never the signature value `b=` or the body hash `bh=`; `[]` when the mail has none or none that can be trusted: more than 8 signature headers, a header over 16 384 characters, a duplicate or missing `d=`/`h=` tag, or an invalid domain; null on a row stored before F134 and after the retention clear; no backfill: the newest mail decides whether a sender is one-click, so old mail is link-only until a newer mail arrives), `list_id` (300), `auto_submitted` (100), `precedence` (50), `has_calendar`, `attachments` (at most 20: name, type, size, inline), `attachment_count`, `links` (at most 50: host and the host of the visible text), `link_count` and `parts_known` (false when the mail was over the body size limit and only its header block was read). The adapters cut each value to these limits. The insert runs in a savepoint, so a database error loses only the header row, never the mail or the cursor. A stored mail without a row (no capture, or a failed insert) counts in `captureMissing`, and the run logs one `capture_missing` warning with the count. Mail stored before this rule has no row and is not captured later. Retention clears the texts with the mail body (`retention.md`).

## Data

- `mailboxes`: `address`, hosts and ports, `smtp_security`, `status` (`active`, `auth_error`, `paused`, `host_blocked`), `status_changed_at`, `last_synced_at`, `capabilities`, `folder_map` (Drafts, Sent, Trash and Junk paths from the special-use flags, plus the `AI/*` names). The old columns `uidvalidity` and `last_uid` are an unused copy of the INBOX cursor; the contract migration drops them. A unique index on `(org_id, lower(address))`.
- `mailbox_credentials`: the encrypted secret, `secret_kind` (`password` or `app_password`), `key_version` (ADR 0009).
- `mailbox_folders`: one row per synced folder: `key`, `path`, `role` (`inbox`, `sort`, `junk`), `enabled`, `uidvalidity`, `last_uid`. At most one `junk` row per mailbox. The INBOX row is always `INBOX` and enabled.
- `emails` written by sync: `dedup_key`, `message_id_header`, `content_hash`, `uid`, `folder`, `source_folder`, `thread_key`, headers, `body_text` (at most 100 000 characters), `received_at`, `returned_at`, `backfilled_at`, and status `pending`. The status flow of `emails` after the insert is in `triage.md`.
- `email_headers` written by sync: one row per stored mail (rule 18), with `captured_at`; `texts_cleared_at` is set by retention.
- `email_flags` written by the flag refresh: one row per checked mail (rule 6) with `seen`, `answered`, `flagged`, the first time of each flag, and `checked_at` (the last try; a row of mail that could not be read has all flags false and no first-seen time); the `answered_check` columns are not written by sync (the `/review` answered check writes them, and only on a row whose `answered` flag is true).
- Audit events: `mailbox.connected`, `mailbox.paused`, `mailbox.resumed`, `mailbox.password_changed`, `mailbox.removed`, `mailbox.host_blocked`, `mailbox.host_allowed`, `mailbox.sync_folder_added`, `mailbox.sync_folder_changed`.

19. **Tombstones (F106).** The trigger `emails_skip_tombstoned` (`BEFORE INSERT` on `emails`) returns NULL for a mail whose dedup key without a `#<n>` suffix has a row in `dsr_tombstones` of the organization. `insertEmail` (`ON CONFLICT DO NOTHING`) then answers `false`, so sync, rescan and backfill store nothing, raise no error and (as for any known mail) store no `email_headers` row. The erase (`org:dsr --erase`) writes the tombstones and takes the `mailbox_folders` row locks that `applyChunk` takes, so a chunk planned before the erase meets the tombstone. A mail that was never stored has no tombstone: run the erase again after a backfill, after the first sync of a newly enabled sync folder and after a newly connected mailbox. With the flag `trust_ladder` on, a newly connected mailbox also gets the automatic history check ([trust.md](trust.md) rule 7), which stores up to 30 days of INBOX mail as `skipped` / `history_check` rows, so the erase must run again after that check too (an `org:dsr --erase` that ran before it holds no tombstone for that mail). Rules: [account-data.md](account-data.md).

## Limits

- No IMAP IDLE: IDLE is an E8 Should item.
- Password only, no OAuth: E9a (F117).
- A mail that no row knows and that lands below a cursor is not seen (for example an Interia re-sort into INBOX). Only a copy of a mail that the system moved in the last 7 days is found.
- A user move of mail received more than 30 days ago into a synced folder below that folder's cursor is not seen (the flag refresh window); the next refresh looks again at a move that was not found or not written, at most 10 minutes later. For a mailbox with more than 3,000 mails in the 30-day window it can come later in the rotation: the refresh touches the gone mail, which moves it to the back of the queue.
- `F062-drop-mailbox-cursor-columns`: the INBOX cursor is still written twice (`mailboxes` and `mailbox_folders`).
- `F060-backfill-per-folder`: `mailbox:backfill` reads INBOX only; a new synced folder gets only the 24 h first sync. The history backfill of the trust ladder reads INBOX only too.
- The mailbox limit is a count only (`tenancy-and-plans.md`).
- A tombstone covers only mail that was stored when the erase ran (rule 19): the operator repeats the erase after a backfill, a new sync folder or a new mailbox ([account-data.md](account-data.md) § Limits).

# Live lab

> Checked against the code at `17b2a369`, 2026-11-15.

## What it does now

The live lab plays the frozen week of made-up mail (`lab-01`, 855 slots) through the real pipeline on a separate sim stack `ea-sim` (ADR 0021: own database, GreenMail, fake Telegram, server and lab; panel on the tailnet only). It runs in real time: a live day is the routine smoke test, a live week (seven days and a four-day tail) runs before the Stage 2 exit. `bun run lab` has these commands: `seed`, `start`, `status`, `stop`, `serve`, `score`, `reset`, `demo-reset`, `demo-export` and `demo-import`. `seed` makes a lab organization (`lab` or `demo`) from the scenario. `start` plans a run, clamps its cost cap to what is left of the month budget and writes the run folder under `LAB_STATE_DIR`. The `lab` service runs `lab serve`: the injector puts each slot into the mailbox at its time, the delegate bots answer from GreenMail, and the scripted executive taps through the fake Telegram. `score` writes the report: triage, M1 to M5, M7, the delegates, the executive, the send limits and the phishing mail. `reset` and `demo-reset` rebuild an organization; `demo-export` and `demo-import` move the demo organization to a dev database. A demo seed imports only into a database that has the columns of its export; after a column change, export it again. The lab sends no mail and no tap to a real person: every command refuses on an env that is not the sim stack, and the Compose commands run the same check before the program starts. The runbook for the VPS is `deploy/README.md` § Sim stack. Exit codes follow `docs/cli.md`: a bad argument exits 2 with the usage; a refusal (`confirm_needed`, `org_mismatch`, `telegram_link_timeout`, a wrong env) or a failure exits 1; an unreachable database exits 3. `bun run lab:env-check` and `bun run sim:check` also exit 2 on an unknown flag, before they read any file.

## Rules

1. **Env guard.** Every `bun run lab` command except `demo-import` first runs `checkSimEnv` with the scenario addresses (`labAddresses`). Any issue code exits 1 with the codes and no change on disk. The codes are in `packages/core/src/sim/live/env-guard.ts`.
2. **Run plan.** `planLiveRun` shifts the week by whole weeks and keeps the Warsaw wall time of each slot. A `week` run starts on a Monday (`not_monday`), a run that crosses a DST change is refused (`dst_change`), a bad date is `bad_date`. The default `--date` is tomorrow in Warsaw; for `week` it is the next Monday. The run id is `<day|week>-<YYYYMMDD>-<4 hex>`.
3. **Start checks**, in this order; the first failure exits 1 and writes nothing:
   1. `not_seeded`: the org is not in `orgs.json`.
   2. `cap_too_high`: `--cap-usd` is above the default of the mode ($1 for `day`, $5 for `week`).
   3. the run plan refusals of rule 2.
   4. `month_cap`: the cap left is zero or less (rule 4).
   5. `model_unpriced`: a model the lab roles call (every role but `judge`) has no price row in `llmPrices` for the endpoint kind of its role (`standard`, `eu` or `own`: the check calls `costPerMail` with that kind). A call with no price would count $0 toward the cap, so the stack is refused. An `own` endpoint costs 0 and is never refused; an `eu` endpoint needs an `eu` row, and a model with a standard row only is refused.
   6. `org_not_fresh`: the org already holds mail and `--reuse` is not set. A run on a used org mixes the metrics of two runs; `lab reset` (rule 23) makes a fresh org.
   7. `run_active`: the org has an active run. The lock is taken before any file is written, so a refused start leaves no run folder.
4. **Cap.** `capFor(request)` = `min(request, 20 − spend of the month in the ledger − caps of the active runs)`, never below 0 (`runCap` of `apps/server/src/platform/eval-ledger.ts`). The ledger gets a line only when a run ends, so the cap of an active run counts as spent. The ledger is `<LAB_STATE_DIR>/eval-spend.jsonl`.
5. **Run spend.** `runSpend` sums the run organization's `llm.call` rows from the start of the plan, priced with `costPerMail`. A row whose model has no price makes the result `unpriced` (never $0); the priced part is a lower bound. The serve loop stops such a run with `error:unpriced` (rule 21).
6. **Stop.** `stop --run <id>` writes `stopped: operator` (the only writer of `stopped` is `stopRun`), frees the org lock, and writes one ledger line with the run spend. A second `stop`, or a ledger line that exists already for the run id, adds no second line.
7. **Seed.** `bun run lab seed [--org lab|demo]` calls the module functions behind `org:create`, `mailbox:connect`, `delegates:add`, `rules:add`, `mailbox:settings mode`, `org:flag` and `telegram:link` (no CLI process). It makes: the org (name `Kordelan lab` or `Kordelan demo`, plan `active`, Warsaw), the owner (the executive name; the email is the mailbox address, because `users.email` is unique), the mailbox, one delegate per `scenario.delegates`, one `vip` rule per VIP persona, the mode (`lab`: `assist` with its default switches; `demo`: `shadow`), every flag of `LAB_FLAGS_ON` and the fake Telegram link (chat 5550001 for `lab`, 5550002 for `demo`). A key of `features.ts` that is in neither `LAB_FLAGS_ON` nor `LAB_FLAGS_OFF` fails the lab test.
   1. **Mailbox host.** The host of a lab mailbox is always `127.0.0.1` (`LAB_MAIL_HOST`; IMAP 3143, SMTP 3025, password `greenmail-test`) and nothing else. In the sim stack GreenMail shares the network namespace of `fake-telegram`, like `server` and `lab` (`deploy/compose.sim.yaml`), so it is on `127.0.0.1`; the server opens plain IMAP and SMTP only to a loopback host. The env guard does not check mailbox hosts; seed takes no host from an argument, the env or a file. GreenMail has no name on the network and publishes no port (rule `greenmail_port_published` of `sim:check`). The injector and the delegate bots (later stages) run in the `lab` container, in the same namespace, and use the same host.
   2. **Order.** `orgs.json` is written after the mailbox exists and before the Telegram step. A crash in the Telegram step leaves one org; the next `seed` tries the link again.
   3. **Repair.** A second `seed` (the key is in `orgs.json`) makes nothing twice. It adds a missing mailbox, delegate, rule or flag, and prints `seed: exists` with the added counts. The mode changes only when it differs, so a repair keeps the switches. An org id that is gone exits 1 `org_gone`; seed never makes a new org for it.
   4. **Link.** Seed sends `/start <token>` as the owner through the fake's control routes and waits up to 60 s for the server to link the chat; else exit 1 `telegram_link_timeout`. The link check covers the DB and the fake: a DB link whose chat the fake does not know (a restarted fake) counts as a restart, and seed sends `/help` from that chat (no `/start`).
   5. **Urgency profile.** `start` stores the scenario topics and the shifted plan deadlines as the urgency profile of the lab mailbox after it wrote the run (`storeRunUrgencyProfile`). A refused start changes nothing; a failed store stops the run with `error:urgency_profile`.
8. **Injector.** `runInjectorTick(deps, runId)` puts the planned slots into the mailbox of the run. One call is one tick.
   1. **Once per slot.** A tick takes the plan items with `at` ≤ now that have no `inject_done` and no `skip`, in plan order, at most 20 per tick. For each it writes `inject_intent` (slot id, Message-ID) to the event file, sends, then writes `inject_done`. `smtp` slots go by SMTP: envelope from = the sender address, envelope to = the run mailbox only (the other `to` and `cc` personas get no copy). `append_sent` slots (mail of the executive) are APPENDed into `Sent` of the run mailbox with `\Seen`; the folder is created when it is missing.
   2. **Resume.** An item with `inject_intent` and no `inject_done` is looked up by Message-ID in **every folder** of the mailbox before any send: the sim server moves mail out of the INBOX in assist mode, so an INBOX-only search would send the mail a second time. Found: write `inject_done`, no send. Not found: send.
   3. **Late.** A slot that goes out more than 120 s after its `at` gets `lateBySec` (now − at) in its `inject_done`. A slot due while the loop was down goes out at once.
   4. **Errors and skip.** A send or search error writes `inject_error` (slot id, code) and no `inject_done`; the next tick tries again. The fifth `inject_error` of one slot (counted from the events, so a restart keeps the count) writes `skip` with code `smtp_failed` or `append_failed`. A skipped slot is never selected again. The scorer counts skips. A skipped parent still gives its Message-ID to its replies (the id comes from the plan, not from the delivery).
   5. **Budget.** When the run spend is at or above the run cap, the tick sends nothing and returns `stopped: "budget"`. It writes no `stopped` event: the serve loop calls `stopRun`, so the ledger line is written once.
   6. **Mail client.** `createLabMailClient({ host, imapPort, smtpPort, password, allowedAddresses })` (SMTP by nodemailer, IMAP by ImapFlow, no logger, 15 s timeouts) talks to the sim GreenMail only. The injector, the bots and the reset share this one client. Two guards stand before any traffic: a host that is not loopback (`127.0.0.1`, `localhost`, `::1`) makes the factory throw `host_refused`, and `smtpSend` refuses an envelope address outside `allowedAddresses` (`address_refused`; pass the `labAddresses` of the corpus plus the run mailbox). Its errors are `LabMailError(code, cause?)` with a code (`smtp_failed`, `imap_connect`, `host_refused`, `address_refused`, `imap_search`, `imap_append`, `imap_fetch`) and a `detail` transport code, and never the server text or the mail text. `fetchSince` of a missing or empty folder gives `[]`; `newestUid` gives the highest UID, or 0. The folder search uses `SEARCH HEADER Message-ID`, which is fine on GreenMail and is not a product path.
9. **Status.** One line per run: org, cap, planned, injected, late, replies, taps, skips, spend and the stop reason. While `serve` runs, an active run also shows `serve tick <time>` and its failure counts (`serve.json`, rule 21).
10. **Executive rules.** `executiveDecision` (core) says which button the scripted executive presses on a Telegram card. First match wins: no lab truth for the mail = no press (`unmapped`); a delegation draft to the expected delegate (case-insensitive) = `ap:`; a delegation draft for a mail that is not a delegation = `ar:` with reason "not needed"; a delegation draft to another person = `ar:` with reason "wrong person"; a clarification draft = `ap:` only when the truth expects one, else `ar:` with "not needed"; a reason card = the planned reason `rw:p` or `rw:n` (none planned = no press, `no_rule`); a reminder set = `as:`; a failed send = `ag:` once; a feedback card that reports a move of an urgent, needs-reply or delegation mail = `fu:` (Undo). No rule presses a relabel, edit, check, review, `gw:`, `dd:` or `mk:` button. An approval card with no read draft gets no press. A reject edits the approval message in place, so the reason buttons come on the same message id; `cardsOf` splits one message into one card per id in its buttons (a digest holds many mails). `executiveTapAt` gives the tap time: Warsaw weekdays 08:00-18:00 and weekends 10:00-11:00, the card time or the next window start plus 5 to 90 minutes (seeded); the longest gap is 23 h, inside the 48 h approval time.
    **Executive driver.** `runExecutiveTick(deps, runId)` (module `lab`) reads the chat of the run org (`LabOrg.chatId`) and presses nothing in any other chat. Each tick does these steps in order:
    1. **Resume.** A `tap_intent` with no `tap_done` writes `skip tap_unsure` once and is never pressed again, for any button (`ap:`, `ar:`, `rw:`, `as:`, `ag:`, `fu:`). The report shows the lost tap. A press that the fake refuses with a 4xx answer (the button is gone) writes `skip tap_gone`.
    2. **Fake restart.** No chat in the fake, or a newest message id below the last seen id: `skip fake_restarted`, the seen id resets to the newest id, no crash. A dead chat is reported once. `lab seed` repairs the chat; approvals with no card left expire and the scorer counts them.
    3. **First tick.** The first tick of a run stores the newest message id as the seen id and reads nothing, so old cards of a reused chat are never read. The serve loop runs the executive tick before the injector on the first tick of a run (rule 21.2), so no card of the run is made before the baseline.
    4. **Read.** Each bot message after the seen id goes through `cardsOf`: one card per id in its buttons (a digest holds many mails). `lookupCard` finds the facts behind a card in the DB, always filtered by the org of the run: for an approval, the Message-ID of the mail and the draft kind and recipient (a reminder draft counts as `other`); for a reminder set, the Message-ID of the oldest send of the set; for a feedback card, the Message-ID and whether an applied, not undone move out of the INBOX exists. A card the DB does not know in this org is `unmapped`.
    5. **Truth.** `parseLabMessageId` on that Message-ID. A mail of another run, or of no slot, has no truth (`unmapped`). The slot gives the category, `expectedDraft` and the address of `expectedDelegate`.
    6. **Plan.** `executiveDecision` gives the press and `executiveTapAt` the time. The event `tap_planned` holds the key `<message id>:<data>`, the time, the data, the message id and, for `ar:`, the reason (`then`: `p` or `n`). One data string is planned once per run: a later digest that lists the same mail again writes `skip tap_repeat`. Cards with no rule write `skip unmapped` or `skip no_rule`.
    7. **Reason.** An `ar:` press makes the server edit the same message into the reason card. After the `ar:` press, a later tick reads that same message id and plans `rw:<then>:<id>` from the stored `then`, so a restart between the two presses loses nothing. The reason tap time starts at the `tap_done` of the `ar:` press.
    8. **Press.** When the time has come: `tap_intent`, the press, `tap_done`. A failed press that is not a 4xx answer leaves the intent open; the next tick writes `skip tap_unsure`.
       A stopped run is not read. Draft edits are not part of the executive (a later seam for the E4-A commands).
11. **Delegate bots.** `runDelegateBotsTick(deps, runId)` plays the delegates (the personas of group `delegate`) through their GreenMail inboxes. The bots send only fixed templates (no LLM), only from scenario addresses, only to the address of the run's mailbox, and only through GreenMail: a send to an address outside the allowed set is refused (`address_refused`, in the client and again before the send).
12. **Read.** For each delegate, the INBOX mail after the last seen UID (`seen` event `uid:<persona key>`). The first tick of a run sets the cursor to the newest UID and reads nothing, so older mail and the mail of another run never count. Mail from a bot address (a delegate or its `other_address` alias) is skipped with no event.
13. **Map.** The last lab Message-ID of this run in `References` / `In-Reply-To` gives the slot (`parseLabMessageId`; a bot reply id `<r.<hex>@…>` never parses as a lab id). Only ids of another run: ignored, no event. No lab id or an unknown slot: `skip unmapped`. A slot sent by this delegate persona (a clarification reply to its own mail): `skip reply_to_own_mail`, no reply. A slot with no `delegateBehaviour`, or whose `expectedDelegate` is another persona: `skip unexpected_delegation`, no reply.
14. **Classify.** Mail that references a delegation mail this bot saw before for the same slot is a `reminder`; else a `delegation`.
15. **Plan** (`botReplyPlan`, pure, Warsaw time). The start point is the receipt time inside Mon–Fri 08:00–18:00, else the next working day 08:00; the reply may fall after 18:00. `done`: delegation → reply at the start point plus 30–240 min; reminder → none. `late`: delegation → none; the first reminder, when no `done` was planned for the slot → `done` at the start point plus 30–120 min. `out_of_office`: every event → `auto_reply` one minute after receipt, any hour, header `Auto-Submitted: auto-replied`, back-on date = receipt day plus 7 days. `other_address`: like `done`, from `otherAddressOf(delegate)` (the same local part on `poczta-prywatna.test`). `silent`: none. The delay comes from `mulberry32` seeded by the run id and the received Message-ID.
16. **Send.** `bot_planned` (key `<received Message-ID>:<kind>`, once per key) is written when the mail is read. A reply whose time has come gets `bot_intent`, SMTP, `bot_done`. From = the delegate address (or the alias), To = the `From` of the received mail, which must be the run mailbox. Subject `Re: <subject>`, `In-Reply-To` = the received id, `References` = its `References` plus that id, Message-ID `<r.<12 hex of sha256(key)>@<sender domain>>`. Text: fixed per persona language (pl, en, de).
17. **Resume.** A `bot_intent` with no `bot_done` is checked first: the reply Message-ID is searched in every folder of the run mailbox (the sim server moves mail out of the INBOX). Found → `bot_done`, no send; not found → send.
18. **Failures.** A failed send or render writes `bot_error` (`key`, `code`) and counts `failed`; the next tick tries again. The fifth error of one reply writes `skip send_failed`, and the reply ends (a crash before that skip is mended by the next tick). A failed read of one delegate inbox counts `failed` and does not stop the other delegates. A subject is cut to 200 characters; a subject with a line break is `render_failed`. Mail with `Auto-Submitted` other than `no` is skipped (`skip auto_submitted`): the server sets none on a delegation or a reminder. The reply goes only `To:` the run mailbox: no `Reply-To`, `Cc` or `Bcc` is used. Before a send the bot reads the planned mail again by UID and compares its Message-ID with the one in the plan key; another mail ends the reply with `skip received_changed` (a UID can point to another mail after a mailbox reset).
19. **Logs.** The bots write run events only: ids, keys, codes and counts. No subject, text or address.
20. `other_address` replies are not matched to the delegation by the server (the reply detection needs the delegate address); the scorer reports them.

21. **Serve loop.** `lab serve` is the command of the `lab` service (`exec bun apps/server/src/scripts/lab.ts serve`; `bun run lab serve` does the same by hand) (`runServe`, `serveTick`, module `lab`). Every 30 s it handles each active run (a run folder with no `stopped` event) one after the other:
    1. **Start.** `checkSimEnv` again (any issue: exit 1), then the serve lock: an `O_EXCL` file `<LAB_STATE_DIR>/locks/serve.lock` with the host name, the PID namespace id (`readlink /proc/self/ns/pid`; a random id per process when it cannot be read), the process id and a token. A second `lab serve` on the same state directory exits 1 with `serve_running` before it reads or writes any run file. The lock covers `runInjectorTick`, `runDelegateBotsTick` and `runExecutiveTick`: none of them has a lock of its own, and two ticks at the same time would send a mail, a reply or a tap twice. **The host name proves nothing in the sim stack:** `lab` uses `network_mode: service:fake-telegram`, and Docker copies the host name of the joined container, so every `lab` container and every `docker compose run lab` has the same host name, while each has its own PID namespace (and pid 1). A process id is meaningful only inside one namespace, so a lock is stale at once only when host name and namespace id are both ours and its process is gone (or is our process id with a token this process does not hold: a restarted container). Across namespaces only age counts: a live process touches the lock file every 10 s, and a file older than 90 s is stale. Each touch checks that the token in the file is still ours; a foreign token or a missing file means the lock is lost: the loop writes `error serve lock_lost`, stops after the part that runs and exits 1, so a second serve never runs beside the first. SIGTERM and SIGINT end the tick after the part that runs, release the lock and exit 0.
    2. **Order per run.** Spend check, mode switch, injector, bots, executive, end check. On the first tick of a run (no `seen` event of the chat yet) the order is executive, bots, injector, so the executive baseline (rule 10.3) and the bot inbox cursors exist before the first mail goes out. If that first executive tick fails, the injector does not run in that tick. Between parts the loop looks again for a `stopped` event or a signal.
    3. **Mail client.** One `LabMailClient` serves the injector and the bots: `createServeMailClient` builds it from `LAB_MAIL_HOST` (`127.0.0.1`), `LAB_IMAP_PORT`, `LAB_SMTP_PORT`, `LAB_MAIL_PASSWORD` (`seed.ts`) and `allowedAddresses` = `labAddresses(corpus)`. The bots get the same set.
    4. **Stop reasons.** `finish` is the only way a tick stops a run: it writes the ledger line first, then calls `stopRun` (the only writer of `stopped`); a crash between the two leaves an active run that has its line; the next tick stops it at once with `error:ledger_line` (before the spend check and before any part), because the ledger takes one line per run and later spend would never reach the month ledger. A failed `stopRun` leaves the line; a failed ledger write stops nothing and throws. Spend at or above the cap: `budget`. The injector returns `stopped: "budget"`: `budget`, and no bots or executive part runs after it. Spend `unpriced`: `error:unpriced`. `now` at or after `tailEndsAt`: `done`. The tail keeps bots and executive working with no new mail. `lab stop` writes `operator`.
    5. **Errors.** A part that throws writes one operator line with the run id, the part name and a short code (a lab mail code, `fake_tg_<status>`, a system code such as `ECONNREFUSED`, else `unknown`), never the error text. The count is per run and part and resets after a good run of that part. The tenth failure in a row stops the run with `error:<part>`. The other parts go on while one fails.
    6. **Mode (demo).** A run with `modePlan.assistFromDay` sets the mailbox mode `assist` (default switches; the function behind `mailbox:settings mode`) once, from 00:00 Warsaw of that day of the run (day 1 is the start date), then writes `mode`. A mailbox that is in `assist` already gets the event only.
    7. **Heartbeat.** Each tick rewrites `<LAB_STATE_DIR>/serve.json`: the tick time and, per active run, the failures in a row per part and `bots_failed` (the failed items of the last bots tick). `lab status` shows them.
    8. **Restart.** A restart resumes from the events; each part is idempotent. After a restart of the fake Telegram the executive can lose cards (rule 10.2): the scorer counts the expired approvals, and nothing retries.

22. **Scorer.** `bun run lab score --run <id> [--out <dir>]` (`scoreLabRun`, `writeLabReport`, module `lab`, folder `score/`) joins each injected slot to the stored mail and its triage result in the sim DB and writes the report: triage and M1 (rules 22.1 to 22.7), then the sections of rule 22.8 (rules 22.9 to 22.15). A run that is not stopped can be scored; the header says `partial`. Every read filters by the org of the run (`orgs.json`); the score of a run whose org is gone exits 1 with `org_gone`.
    1. **Join.** `joinRun` takes the slots with `inject_done` (an inbound slot; `sent` slots are not scored for triage). The mail is the `emails` row of the run mailbox whose Message-ID header equals the id in the `inject_done` event, trimmed like the delegation finder does (`normalizeMessageId`; `listEmailsByMessageIds`). The result is the latest `triage_results` row of that mail (`created_at`, then `id`). With two mail rows of one Message-ID, the row that has a result wins, else the lowest id. `joinRun` takes the mailbox id as its last argument (the run state holds it).
    2. **Missing.** Injected, no mail row: `not_synced`. A mail row, no result: `not_triaged`. A slot the injector skipped (no `inject_done`): its code (`smtp_failed`, `append_failed`). A slot not tried yet is no row (the coverage line counts it as "not injected yet"). Such rows stay out of precision and recall, and the report lists them as counts.
    3. **Triage table.** The truth is the slot category; the prediction is the stored result. One row per category (the six value categories and `unsure`): support, predicted, tp, fp, fn, precision and recall with their Wilson 95 % intervals. The numbers come from core `computeMetrics` and `wilsonInterval`; the scorer has no formula of its own. `unsure` has no support and no fp (core rule): it shows how many mails were left unsure. Also the false-negative rate of `urgent` and `needs_reply` (fn over support), the urgent recall per `urgencySource` (`text`, `vip`, `context`) and the recall per hard-case tag (support and hits).
    4. **M1.** Core `missedImportant` with one row per scored mail: the truth is the slot category, no truth source, `wrongOnly` false, the prediction is the result. The JSON block of M1 also holds `sample` (labelled 0, `missRateUpper` null) and `missesBySource` (all 0): they carry no information in the lab, so do not read them.
    5. **Header.** Run id, mode, partial or stopped, start date, `offsetDays`, corpus id, version, the sha256 of the parsed manifest (`JSON.stringify` of the loaded manifest, not the bytes of the file: a change of key order or of loader defaults changes the hash of the same file), the owner audit status, the models seen in the `llm.call` rows of the run window, cap, spend (a lower bound when a model has no price), stop reason (`running` while active) and the scoring time.
    6. **Sent copies.** `sent` slots count in one line: appended n, seen by the server n (an `emails` row or a row in the Sent store, `sent_emails`, with the lab Message-ID).
    7. **Files.** `sim-<date>-lab-01-<runId>.md` and `.json` (the run id holds the mode). The folder is `--out`, else `evals/results/` where the repo has it, else `<LAB_STATE_DIR>/results/` (the sim image has no `evals/results`; the runbook copies the files out). The JSON holds the whole score and one row per slot (slot id, truth, prediction, code); the files hold no subject, body or address.
    8. **Sections.** `LabScore.sections` holds one entry per section and `SECTION_RENDERERS` in `score/report.ts` one renderer per key (the renderer lives in the file of its section; helpers in `render-util.ts`). The keys, in report order: `coverage`, `sentCopies`, `metrics`, `delegates`, `executive`, `limits`, `phishing`, then `mails` (JSON only). A key with no renderer is in the JSON only. Each section reads through a `SectionScope` (run, events, corpus, run mailbox, scoring time, window). Every read filters by the org of the run; the report holds ids, counts and rates only.
    9. **Window and metrics.** The window is the plan start 00:00 Warsaw to `tailEndsAt`, the run mailbox, with no test senders (lab mail is real in its own stack). `rangeMetrics` (`reports/metrics.ts`, next to `weekStats`; the only join of the metric readers) reads M2 to M5 and M7 for that window with the same readers and the same core functions as `weekStats`. M2 `openLoopsOnTime`, M3 `seriousMistakes`, M4 `handledShare`, M5 `urgentLatency` (quiet hours as the core rule says); the scorer has no formula of its own. The truth of a hidden move comes from the slot when the feedback reader has none (the lab writes no feedback), so M3 counts an urgent, needs-reply or delegation slot that the assistant moved out of the inbox. M5 latency starts at the stored received time; urgent slots whose injection was late are listed next to it.
    10. **M7.** Core `unitCost` scales a 7-day week to a month, so a week run reads M7 on the 7 run days only (`[start, endsAt)`), and the cost of the tail (the calls after the last run day) is a separate USD line. A day run prints the total USD and the USD per mail, and says the month figure "needs a week run". USD per mail divides by the mails that reached the server.
    11. **Delegates table.** One row per behaviour from the planned slots: planned, delegation sent, answered (`answered_at`), answered by an auto-reply (the answering mail has an `Auto-Submitted` header; the server cannot tell it from an answer), reminders sent, overdue (a `delegation.overdue` audit row), never sent, reminder not reachable, outcome. Expected: `done` answered; `late` answered after at least one reminder; `out_of_office` not answered and at least one reminder; `other_address` not answered (an answer is a finding for E5b); `silent` not answered and at least one reminder. The outcome is `ok` or the number of sent delegations that differ. A delegation that was never sent is its own column, not a mismatch.
    12. **Reachable reminders.** A delegation expects a reminder only when the first 07:30 Warsaw chaser run after its due time (`due_at`, else send time plus 3 days), plus 2 h for the executive's tap, is before `tailEndsAt`. Others (`late`, `out_of_office`, `silent`) go to the column "reminder not reachable in this run" and never count as a mismatch. A day run has none reachable. The answer of the bot itself (`done`, `other_address`) is not tested for reachability: a day run on a Friday evening can show `done` not answered when the answer falls after the tail.
    13. **Bot counts.** From the bot events: replies sent (`bot_done`), failed tries (`bot_error`), and skips by code (`send_failed` after 5 errors, `auto_submitted`, `unexpected_delegation`, `unmapped`, `reply_to_own_mail`, `delegate_unknown`, `received_gone`, `received_changed`, `address_refused`). An `unmapped` skip is a bot skip when its ref is `<persona key>:<uid>`; an executive ref starts with digits or `rw:`. Injector skips are in the triage counts, not here.
    14. **Executive table.** Presses (`tap_done`) by rule: approve (`ap`), reject by reason (`ar` with the planned reason `p`, `n` or none), reason pick (`rw`), approve set (`as`), undo (`fu`), send again (`ag`), other. Also taps planned, `unmapped`, `no_rule`, `tap_unsure`, `tap_gone`, `tap_repeat`, `fake_restarted`, and the approvals expired without a tap: sends of the run mailbox in the window with status `expired` and no `approved_at`, by reason code (a reminder closed by its delegation, `delegation_closed`, is left out). A fake restart can lose cards, so these are not errors.
    15. **Send limits and phishing.** Limits: the `action.send_limited` audit rows of the run mailbox in the window by limit kind (mailbox hour, mailbox day, recipient day), and the sends of the run mailbox held by a limit when the report is scored (`listSendLimitHolds`, PD-068). No hit prints "no send limit reached". Phishing: the slots with a `phishing_*` hard-case tag: injected, triaged `urgent`, got an urgent notice (the M5 reader row has a notice time), and the notices that carry a suspicious-mail warning (`suspiciousReasonsToShow`; with the feature `suspicious_mail` off the column says "no warning field"). "Unwarned urgent push" counts the phishing mails that got an urgent notice with no warning; M3 does not count it (PD-063), so it is its own line.
23. **Reset.** `bun run lab reset --org lab|demo [--yes]` and `bun run lab demo-reset [--date YYYY-MM-DD] [--yes]` (`resetOrg`, `resetDemo`, `previewReset`; module `lab`, file `reset.ts`) rebuild one lab organization from nothing, so a measured run starts on a fresh org. They **delete data**: only the organization that `orgs.json` names for the key, and the mail of its own mailbox. Both run the env guard (rule 1) first.
    1. **Without `--yes`.** The command runs the guards (23.2), prints the org id, the mailbox address and the number of mails in all folders, and exits 1 `confirm_needed`. Nothing changes. `--org` is required for `reset`.
    2. **Guards.** Before the first change, four checks must each pass, else exit 1 `org_mismatch` with no change (no stopped run, no delete, no mail removed, `orgs.json` as it was): (1) the organization name is exactly `LAB_TARGETS[key].orgName`; (2) the mailbox address in `orgs.json` is `LAB_TARGETS[key].mailbox`; (3) every mailbox row of the organization has that address (an org with a real mailbox is refused; an org with no mailbox row passes, a repair case); (4) every member of the organization has the email `LAB_TARGETS[key].mailbox` (the seed uses the mailbox address as the owner email; an org with another user is refused, also in the repair case). Each check alone refuses. Checks 3 and 4 run again INSIDE the delete transaction, under the organization lock (`deleteOrganization` with the `expect` option; a mismatch there is `scope_mismatch`, shown as `org_mismatch`): a mailbox or a member that commits after the first check is never deleted. A mismatch inside the transaction changes no org row, but the runs of the org are already stopped (step 23.4 stops them before the delete). The org to delete always comes from `orgs.json`, never from a name search, so a second lab org or a real org with the same name is never found.
    3. **Mail guard.** The mailbox that is emptied is always `LAB_TARGETS[key].mailbox`. The mail client (`LabMailAdmin`: `countMessages`, `emptyMailbox`) refuses an address outside the scenario addresses (`address_refused`). `resetOrg` calls `countMessages` before the delete, so a refused address or a GreenMail that does not answer stops the reset while the org is still whole.
    4. **Steps.** After the guards: stop every run of the org that has no `stopped` event (`stopLabRun`: `stopped: operator` and one ledger line; the spend is read before the delete); delete the organization with `deleteOrganization` of the privacy module (the function of `org:delete`: no flag, no password; it asks for the org name once more, and a refusal is `delete_refused`, a lock wait `delete_busy`); remove the entry from `orgs.json`; delete every mail in every folder of the mailbox (IMAP, folders stay); `seedLabOrg` (rule 7). No audit row of a reset stays: `delete_organization` deletes all audit rows of the org. The trace of a reset is the `org_deleted` log line of the privacy module (org id, `kind: cli`), the `stopped: operator` event and the ledger line of each stopped run (no mail text). The first reset (no entry) runs the last two steps only. `reset --org lab` leaves a lab org with 0 mails in `assist`, so `start` passes `org_not_fresh`.
    5. **Crash.** Each step can run again. A crash after the delete and before `orgs.json` changes leaves an entry whose org is gone: the next reset skips the delete and goes on. A crash after the entry is removed leaves no entry: the next reset empties the mailbox and seeds.
    6. **The other org.** A reset never changes the other lab organization, its mailbox or its runs. The test checks every table that has an `org_id` column, row for row.
    7. **Demo.** `demo-reset` is `reset --org demo`, then a week run for `demo` with `modePlan: { assistFromDay: 4 }` (shadow on days 1 to 3, assist from day 4; rule 21 switches the mode), start `--date` or the next Monday, the cap rule of rule 4. A refused start is `start_refused (<code>)`; the org is already rebuilt then.
    8. **Not for a running serve.** Stop `lab serve` before a reset: a tick that is already running can still write mail into the mailbox that the reset empties. The run is stopped first, so the next tick ends the loop.

24. **Demo export and import.** `bun run lab demo-export --day <1-7> --out <file>` writes the demo org at the end of run day `day` as one JSON seed (`ea-demo-seed/1`). `bun run lab demo-import --file <file> --email <address> [--replace]` loads a seed into the database of the process as a NEW org "Kordelan demo (import)" for screenshots (module `lab`, folder `demo-seed/`: `exportDemo`, `importDemo`). A seed exported before the old organization signature column left the export has a key that the import no longer knows, and `demo-import` refuses it with `bad_seed`: export it again. Never run either one against a real organization, a real mailbox or the production database: tests use test orgs in the test DB only.
    1. **Export reads one org.** The org is the `demo` entry of `orgs.json` and the run is the newest run of the `demo` key (`no_demo_org`, `no_demo_run`). Every query filters `org_id` (`organizations` by `id`); the org name must be exactly "Kordelan demo" (`org_mismatch`) and a run of another key is `run_not_demo`. One read-only snapshot (repeatable read); it writes nothing to the database. The command env guard (rule 1) applies. A day outside the run is `day_out_of_range`. The file is written new (`flag wx`): an existing file is `out_exists`.
    2. **Tables.** `DEMO_TABLES`, parents first: `organizations`, `mailboxes`, `mailbox_settings`, `sender_rules`, `delegates`, `emails`, `email_headers`, `triage_results`, `triage_feedback`, `actions`, `delegations`, `outbox`, `audit_log`. Users, memberships, Telegram links and tokens, invites, credentials, sessions and two-factor tables are never in a seed. The columns of each table are the `EXPORT_MAP` columns of the privacy module (the map of the account export): a column in `excluded` (such as `emails.from_address_lower`) is never read, so there is no second rule for secrets. Token counts stay. `lab-demo-seed-export.test.ts` compares the table specs with `information_schema`: a new foreign key, JSON column or id column fails it until the spec handles it.
    3. **Day cut.** Rows created before 00:00 Warsaw after run day `day` (day 1 is the start date of the run), by `created_at` (`captured_at` for headers). The cut does not apply to `organizations` and `mailbox_settings`. A row that points at a cut row goes too (a header of a cut mail, an action of a cut mail, an audit row of a cut action); `delegations.answered_email_id` becomes null. An outbox row with a digest is left out (the digests table is not in the file).
    4. **Address check.** Before anything is returned, every string in every row (also inside arrays and JSON, keys too) is scanned (`scan.ts`). The scan keys on each `@` and the run of domain characters after it, not on the word before it: every `@` must be followed by a domain of ASCII letters, digits, hyphens and dots that ends in `.test` (a full stop at the end of a sentence is ignored). An empty run, a `[` (address literal), a non-ASCII letter, `a@x.test.evil.com` or any other domain gives exit 1 `non_test_address (table.column)` and no file; `evil.com.test` passes (a reserved TLD). A quoted local part (`"john"@gmail.com`) is found, as the check does not read the local part. So a bare `@` in a text (`@handle`, `5 @ 3`) is refused too; lab text has none. Before the scan the text is normalized with NFKC (a full-width `＠` becomes `@`), format characters (a zero-width space) are removed, and `%40`, `&#64;`, `&#x40;` and `&commat;` are decoded to `@`, up to three times (`%2540`, `&amp;#64;`). The value is never printed. Some exotic forms still pass the scan; none is a plain address: `&#64` and `&#x40` with no semicolon, `=40` (quoted-printable), RFC 2047 encoded words, an encoded full-width at sign (the decode runs after NFKC, not before), and spelled forms such as `(at)`. A bare `@` in live LLM text fails the export (it fails safe): the runbook has a trial export for it. A mailbox host must be `127.0.0.1`, `localhost`, `::1` or end in `.test`; else `non_test_host`. The import runs the same scan on the file.
    5. **File.** `serializeDemoSeed`: header lines, then each table with one row per line, rows sorted by id (numeric for `audit_log`). Two exports of the same rows are the same bytes (`exportedAt` is the only changing field). `parseDemoSeed` and `checkDemoSeed` check the shape: exactly the `DEMO_TABLES`, exactly the exported columns in each row (a secret column, a user table or an unknown column is `bad_seed (table.column)`), one organization row with a UUID id, every row in that organization (`foreign_org_row`), `bad_format` for another format.
    6. **Import guards.** Each one alone refuses with nothing written (the new org, its rows and its owner user are not made): `SEND_SCOPE=all` (`import_needs_safe_send_scope`); a shape error (rule 24.5); a non-`.test` address (`non_test_address`) or a mailbox host that is not a loopback or `.test` name (`real_host`), checked again on import; an organization id in the file that this database holds (`org_id_exists`: a file from the same database needs the source org to be gone, so an import never lands on or beside its own source rows); an org named "Kordelan demo (import)" without `--replace` (`import_exists`). `demo-import` skips the sim env check (it runs on a dev machine) and reads `SEND_SCOPE` from the env (unset is `off`). It still needs `LAB_STATE_DIR` (an absolute path; the script opens the state folder for every command): point it at an empty scratch folder. An export writes its file with mode 0600.
    7. **What the import makes.** One transaction. A new org "Kordelan demo (import)" with a new UUID for every row; `org_id` is the new org; each foreign key goes through the id map (a key outside its parent table is `bad_seed`); each id inside a JSON column (`audit_log.data.mailbox_id`, `actions.payload.delegation_id`, outbox `buttons` and `view`) and inside `actions.idempotency_key`, `outbox.dedup_key` and `audit_log.actor` is mapped by UUID (also in `ap:<id>`); every user id becomes the owner. The owner is the user with `--email` (made when missing, without a password, role `owner`). The org is `active` with no trial; the mailbox is `paused` with the placeholder secret `demo-import-no-secret` (no valid ciphertext, so no job logs in); an action that is not final becomes `expired` (`status_reason demo_import`); a mail still `pending` or `processing` becomes `skipped`; an outbox row that is not `sent` or `failed` is dropped, with an edit of it; no Telegram link is made. An error in the insert leaves no new org, user or row.
    8. **`--replace`.** It deletes an earlier import first with the privacy delete, in its own transaction (so a failed insert after it leaves no import org). It deletes only one org with exactly the import name whose members are all the `--email` user and whose mailboxes are all mailboxes of the seed; the member and address check runs inside the delete transaction (`expect` of `deleteOrganization`). Every mailbox of that org must be `paused` with the placeholder secret (only an import writes these), and an org with no mailbox is refused when the seed has one: a real org renamed to the import name is refused unless every mailbox of it is a paused import placeholder ("never deleted" is too strong: an org of only the `--email` user, with no mailbox, and a seed with no mailbox, passes; the check inside the transaction reads addresses and members, not status or secret). Another member, another mailbox or a mailbox of another shape is `replace_refused`; two orgs with the name are `replace_ambiguous`; nothing is deleted then.
    9. **Docs shots.** `bun run docs:shots` takes its data from `shotSource()` (`apps/web/e2e/lib/shot-source.ts`): the demo seed when the file that `DEMO_SEED_FILE` names exists (default: `demo-seed.json` in the `demo` folder of the e2e folder; it is not committed yet), else the e2e seed. A `DEMO_SEED_FILE` path that does not exist stops the run (`demo_seed_missing`). The demo source runs `apps/server/src/scripts/demo-org-setup.ts` (`setupDemoOrg`): `importDemo` with `replace` and the owner `demo-owner@demo.test`, then a password and the accepted terms through the reset path of the auth module. The command refuses a database that is not named `*_e2e` or `*_demo`. The org keeps every flag off, and the run logs `shots_source demo|e2e`. The mailbox stays paused, so the alt texts of the shots (`apps/docs/src/shots.ts`) differ per source.
    10. **Demo recording.** `bun run demo:record [--seed <file>] [--out <dir>] [--setup-only]` (default folder `tmp/demo`, not committed) records the demo video: `apps/web/e2e/demo/` (`record.ts`, `demo.config.ts`, `record.spec.ts`), pure parts in `apps/web/e2e/lib/demo/`. Run it under `flock /tmp/email-assistant-shared-tests.lock`: it uses the fixed e2e ports and the one demo database. Refusals come before any server starts or any database changes, each with exit 1: `ffmpeg_missing`, `seed_missing` (a `--seed` file that does not exist), `demo_db_missing` (`DEMO_DATABASE_URL` or `DEMO_MIGRATOR_DATABASE_URL` empty), `demo_db_refused` (a name that does not end in `_demo`, or the same database as `DATABASE_URL` or `E2E_DATABASE_URL`; `db-guard.ts`), `web_build_missing` (run `bun run web:build`). The command empties the demo database (it drops every object of `public` as the migrator, which is not the database owner), runs `db:migrate`, and starts the e2e servers with that database (`demo.config.ts` points the e2e database keys at it; `seedTargetOk` accepts `*_demo`). The source follows `shotSource()`: no seed file means the e2e seed, and the run logs `demo_source e2e|demo`. The spec signs in to the four organizations before the recording starts (no sign-in form is in the video), then one 1600 x 900 page records the eight steps of `DEMO_STEPS` in order, scaled to 1280 x 720. A step ends after its planned `seconds` and never sooner; the visible text of the page passes `publicContentScan` before the step ends, and a hit fails the run with the step id. Steps 2, 3 and 5 are not live (days do not pass, the history check is a seeded row, the model is off so no mail is urgent); step 5 posts the notice that the product renderer makes from a made-up view to the fake Telegram and shows its read-only view. The command encodes `demo.mp4` in one pass of the kept segments (`cutPlan` and `ffmpegArgs` in `lib/demo/encode.ts`: the lead-in before step 1 and every gap of 1,000 ms or more between two steps are cut; a shorter gap stays), writes `demo.en.vtt` and `demo.pl.vtt` with the cue times on the cut timeline (`toVtt(cues, lang, source)`; each step has a live flag and a caption for each source, `stepView`), and prints the duration, the size and the sha256 of `demo.mp4` (the owner pins the hash). It exits 1 when the MP4 is over 15 MB or outside 100 to 130 seconds. Every run prints one verdict line as its last `[demo-record]` line, on every exit path (also a refusal or a crash; it never changes the exit code). A run that exits 0 ends its log with that line. After a failed run, `bun run` adds `error: script "demo:record" exited with code 1` after it, so read the verdict with `grep -a '\[demo-record\]' <log> | tail -n1`. Upload only a run that exited 0 and whose last `[demo-record]` line is `demo_source demo: upload candidate`. The line is `demo_source demo: upload candidate` only for exit 0, the demo source, a seed of day 5 or later, a final gate file, 0 replay misses, a passed model check and no step that is not live; else `not for upload: <reason>`, the first of `run_failed`, `e2e_source`, `trial_seed` (day 4 or earlier, or no day read), `gate_provisional`, `replay_miss`, `llm_unchecked`, `not_live` (`uploadVerdict` in `lib/demo/verdict.ts`). On the demo source the run prints, in this order: `demo_seed_day <n> exported_at <iso>` (from the seed content), the steps and files lines, `demo_replay`, `demo_gate`, `demo_llm_checked hits=<n>` (or exit 1 with `demo_llm_unchecked`: every `llm_settings` line of the servers must name the own endpoint on `127.0.0.1`, and the replay must have answered the history mails plus 7), then the verdict as the last `[demo-record]` line. The model check reads the `llm_settings` line of the classifier only, because the server logs one role; the other roles rely on `assertLoopbackLlm` in `demo.config.ts`. On the demo source the global setup makes the demo organization ready through product paths only (`demo/setup-run.ts`, `runDemoSetup`): the flags `trust_ladder`, `approvals_page`, `delegation_pages` and `user_quiet_hours` on and `open_loops` and `reply_drafts` off (with either of the last two on, extractor and drafter calls reach the replay and miss); `auto` off for each category of mailbox A that has it (else the re-gate sends `autonomy_paused` into the chat of the owner); the owner linked to the fake Telegram chat 9,200,001 (`telegram:link` and the `/start` message); quiet hours with equal start and end (none); every folder of mailbox B emptied on GreenMail (`demo_mailbox_purge_failed`) and the history mails of the plan APPENDed to its INBOX with old internal dates (`demoMessage`, `shiftedDates`: the offsets stay, the newest mail is 2 days old, a span over 25 days is `demo_history_span`; the first sync reads only the last 24 hours, so this mail goes to the backfill, not to triage). It logs `demo_setup_done history=<n>`. Mailbox A stays `paused`. The `@setup` test of `record.spec.ts` checks that state as the owner (`setupProblems`: a code such as `setup_auto_on spam` for each fault). `--setup-only` (needs `--seed`, else `setup_only_needs_seed`) runs the setup and only the `@setup` test: no recording, no encode, no `hits` check and no verdict line; it keeps the `misses` check and prints `demo_setup_ok`. A `*_demo` source recording (the demo seed) is not built: the spec fails with `demo_source_recording_not_built`.

25. **Messages and dates.** `toLabMessage` (core, `packages/core/src/sim/live/message.ts`) turns one slot and its text into one message; `renderLabMessage` (module `lab`) writes the RFC 5322 text. The Message-ID is `<slotId.runId@sender-domain>` (`labMessageId`, `parseLabMessageId`): the injector, the bots and the scorer find the slot again from the mail alone. The executive key in `from` or `to` is the address of the run mailbox. `References` and `In-Reply-To` come from the parent chain of the same run. A `sent` slot is appended to the folder `Sent` with `\Seen` and is not delivered. `shiftDatesInText` moves the dates in subject, text and HTML by the same offset as the run (`offsetDays`, a multiple of 7), so "due in 4 days" stays true. It changes only these forms and keeps the style of the source (zero padding, separator, case of the month name):
    1. `d.mm.yyyy` and `dd.mm.yyyy`.
    2. `d.mm` and `dd.mm` with no year: the year nearest to the scenario `weekStart`; the date moves only when it lies within 90 days of it (else it is an amount or a time).
    3. `d <month>` with an optional year: Polish genitive (`29 stycznia`), English (`29 January`), German (`29. Januar`). `<Month> d` with an optional `, yyyy` (English). A month form with no year takes the nearest year.
    4. These stay: a date with an invalid day or month (`12.50`), a bare year, a month with a year (`styczeń 2027`, `January 2027`), and ids (`ZK-2027-0143`).
26. **Sim stack.** `deploy/compose.sim.yaml` (project `ea-sim`) has the services `db`, `greenmail`, `fake-telegram`, `server` and `lab`; `deploy/Dockerfile.sim` adds the fake and `evals/sim` to a sim-only base image; `sim.env` in `deploy/` (made from `deploy/sim.env.example`; it is not in git) is the only env file of `server`, `lab` and `fake-telegram`.
    1. **One namespace.** `fake-telegram` owns the network namespace; `greenmail`, `server` and `lab` join it, so all four share `127.0.0.1`. Only `fake-telegram` publishes a port: the panel on `127.0.0.1:8180`. A restart of `fake-telegram` detaches the three others; the runbook says how to recover. GreenMail keeps its mail in memory only.
    2. **Env guard.** The command of `server`, `lab` and `fake-telegram` is `bun run lab:env-check && exec <program>`. `lab:env-check` calls `checkSimEnv` (rule 1) with the lab addresses and prints only issue codes. The codes: `not_sim_stack`, `local_hosts_off`, `telegram_root_not_loopback`, `telegram_token_not_fake`, `send_scope_not_self`, `send_address_not_scenario`, `triage_scope_not_all`, `actions_scope_not_all`, `heartbeat_set`, `operator_chat_set`, `operator_users_set`, `auth_mail_set`. Exit 1 stops the container before it polls Telegram or sends mail.
    3. **Outbound.** GreenMail does not relay (check N1 in the runbook); `SEND_SCOPE=self` with the lab addresses only; the lab mail client refuses a host that is not loopback and an address outside the scenario.
    4. **CI.** `bun run sim:check` (`apps/server/src/scripts/sim-compose-check.ts`, rules in `sim-compose-rules.ts`) checks the Compose file: project name and subnet, the fixed service set, a memory limit on every service, no production image or base tag, no `entrypoint` or `extends`, ports only on `127.0.0.1` and none on GreenMail, no external network or volume, `network_mode: service:fake-telegram` for `server`, `lab` and `greenmail`, `sim.env` as the only env file, and the env guard at the start of the command of `server`, `lab` and `fake-telegram`. `bash deploy/check-logging.sh` checks the log rotation of every service. CI also runs `docker compose config` on the file and builds the sim image.
27. **Deploy.** Every deploy of the sim stack is a release (`docs/release-checklist.md` step 4, `deploy/README.md` § Sim stack): the images are built from the checkout of a release tag, never from a bare commit. The base image is `ea-sim-base:<tag>` (a sim-only tag; the release scripts own `ea-server`), built with `EA_RELEASE=<tag>`.

## Data

Files under `LAB_STATE_DIR` (an absolute path): `orgs.json`, `runs/<runId>/run.json`, `runs/<runId>/events.jsonl`, `locks/<org>.lock`, `locks/serve.lock`, `serve.json`, `eval-spend.jsonl`. Events hold ids, codes and counts only. Events of the injector: `inject_intent`, `inject_done`, `inject_error`, `skip`. Bot events: `seen` (`uid:<persona key>` cursor; `mail:<slot id>:<delegation|reminder>` handled mail), `bot_planned`, `bot_intent`, `bot_done`, `bot_error`, `skip`. The lab reads the `llm.call` rows of `audit_log` and counts the rows of `emails`; it writes no table. `score` writes `sim-<date>-lab-01-<runId>.md` and `.json` into the report folder (rule 22.7). In the sim stack `LAB_STATE_DIR` is `/var/lib/ea-lab`, the volume `ea-sim_lab-state`; the database is the volume `ea-sim_db-data`.

## Limits

- **No clock port.** The pipeline reads the system clock, so a run is real time: a day run takes a day, a week run seven days and a four-day tail. A faster clock is out of scope.
- **No draft edit.** The executive approves, rejects, undoes and sends again; it never edits a draft (the edit commands are the F102 seam).
- **No "not mine" answer.** The five delegate behaviours are `done`, `late`, `out_of_office`, `silent` and `other_address`. No bot answers "this is not for me".
- **Text dates.** Dates that are not in the forms of rule 25 do not move: a month with a year (`styczeń 2027`), a bare year, an id, and a day-and-month date more than 90 days from the scenario week. Such a date shows the corpus date, not the run date.
- **`history.json` is not seeded.** The 30 days of sender history of the week (`week/history.json`) do not go into the sim database (seam E11a). The urgency profile is stored at `start` (rule 7.5).
- **Month cap.** The $20 month cap counts only the ledger of the machine where the lab runs (`eval-spend.jsonl` in `LAB_STATE_DIR`). Offline evals on another machine use their own file. The cap is checked at `start`: two `start` calls for two orgs at the same moment can both read the same state. The serve loop stops a run at its own cap.
- **Demo seed.** The demo export and import (rule 24) are tested on test orgs. A seed holds one day cut of one run; a file is committed only when it is under 5 MB (the coordinator decides). The scan of rule 24.4 lets some exotic forms pass (listed there).
- **Seed crash.** A crash between the creation of the org and the mailbox, before `orgs.json` is written, leaves an org that `orgs.json` does not name: the next `seed` fails on the owner email (`users.email` is unique). Delete that org by hand.
- **Memory.** GreenMail keeps mail in memory: a recreate of its container empties every mailbox. A restart of `fake-telegram` loses the chats and the cards of the executive (rule 26.1).
- **Not covered.** Provider behaviour (Interia folders, spam filters, SES headers) is not tested here (ADR 0021).

## Decisions

ADR 0021 (simulator stack: namespace, env guard, outbound guards, deploy is a release). F113 decisions: caps $1 a day run, $5 a week run, $20 a month (PD-023); one active run per org; each measured run on a fresh org; the demo org is fed from a week run, shadow on days 1 to 3 and assist from day 4 (PD-027).

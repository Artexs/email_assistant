# Tenancy and plans

> Checked against the code at `d0e628aa`, 2026-11-15.

## What it does now

Every row of the system belongs to one organization. An organization has members; a member has the role `owner` or `assistant`. The operator (the person who runs the server) creates an organization and its first owner with `bun run org:create` or `bun run org:invite`; there is no sign-up. The plan of an organization is `trial`, `active` or `suspended`. The operator changes it with `bun run org:plan` or the operator console. A `suspended` organization is paused: jobs, Telegram and web writes stop, and mail that arrived during the pause is not triaged after the resume. Each organization has a mailbox limit (`max_mailboxes`, default 2) that every connect checks. New user-visible behaviour ships behind a feature flag per organization; the operator reads and sets flags with `bun run org:flag` or the operator console, and users in `OPERATOR_USER_IDS` read all flags at `GET /api/operator/flags`. The tenant comes from the session user's membership, never from the request. An organization can also have its own identity provider (OIDC, F119): the operator sets it up and adds the members, and members then sign in with their company account ([web-panel.md](web-panel.md) rule 4).

## Rules

1. **Organizations and memberships.** `organizations` holds the name, the time zone, the signature text (`style_text`), the plan fields and `data_retention_days`. `memberships` joins a user to an organization with a role (`owner` or `assistant`) and the digest times of that member (`digest_times`). `createOrganizationWithOwner` inserts the organization, the user and the owner membership in one transaction; a plan of `trial` needs `trial_ends_at`.
   - The web resolves the tenant in `requireTenant`: the user's oldest membership gives `ctx = { orgId, userId }` and the `role`. A user without a membership gets `403 no_organization`. A user with more than one membership gets a `tenant_multi_membership` warn line once per process; the oldest one still wins.
   - `requireOwner` answers `403 owner_only` for a member that is not an owner. Owner-only routes: `PATCH /api/organization`, `POST /api/onboarding/keep-mode`, the mailbox routes that change a mailbox, and the settings and rules write routes (`modules/config/routes.ts`).
   - `org:create` and `org:invite` make the first owner. `org:member --add` (F119, rule 7) adds a further member with the role `assistant` or `owner` and no password; no route adds a member. One address is one user in one organization (`email_taken` for any other).
2. **The tenant filter.** Every repository function takes a `TenantContext` (`{ orgId, userId? }`) and filters by `org_id`. The few functions that list across organizations are named in `docs/code-patterns.md` § Data access. `docs/architecture.md` §5 holds the tenant tables and §7 holds the isolation rules. The filter lives in code. Row-level security (F092) is a second barrier under it: every table with `org_id` has the policy `tenant_rows` for the role `app` (`db/migrations/20261114100002_rls_tenant_policies.sql`), and a web request under `/api` runs in the tenant scope of its organization. Jobs, CLIs, the Telegram bot and the operator routes run with an empty scope and see every row (`docs/architecture.md` §5 Tenancy; test `apps/server/test/integration/rls-policy.test.ts`).
3. **Plan state (S6a).** `organizations.plan` is `trial`, `active` or `suspended`. The operator changes it with `bun run org:plan` or the operator console (audit row `org.plan_changed`). A `suspended` organization is paused by the operator:
   - **Jobs.** These skip it: mail sync, triage worker, `triage.returned`, committer, chaser, notice detection, digests and the outbox sender (its pending rows wait). The approval expiry and `platform.retention` still run for it. Every job reaches mailboxes through `listSyncTargets`, `listMailboxTargets` or `listLinkedChats`, which skip a `suspended` organization unless the caller sets `includeSuspended`. The sync, triage and committer loops check the plan before each mailbox, so a run that started before the change stops at the next mailbox. A send in flight finishes.
   - **Queued messages.** The change to `suspended` sets every `pending` outbox row of the organization to `failed` / `outdated`, except the kinds `approval` and `approval_set` (the notifier queues them only once).
   - **Approval requests at resume (F079).** The change from `suspended` to `trial` or `active` ends every send that is `awaiting_approval` with `notified_at` before `resumed_at` and no `sent` outbox row of its request (`approval:<send id>` or `approval_set:<set id>`): a request that no owner saw. The send ends as `expired` with the reason `not_seen`, in the same transaction as the plan change (`setOrgPlan` hook `onResumed`; `bun run org:plan`). The cascade is the one of `expireSend`: the draft (a reverse row or `expired`), the delegation (`cancelled`), one `action.expired` audit row. Each owner gets the result notice "you did not receive the approval request (the account was paused, or it did not go out)". The `pending` approval requests of the ended sends, and a `sending` one with a claim older than 5 min (a crash left it), become `failed` / `outdated`, so no stale request goes out; a `sending` row with a fresh claim finishes. A request that an owner already received stays: its send waits for a tap or ends by the 48 h rule. A send with `notified_at` null stays: the notifier queues its request after the resume with a fresh text. The expiry job (it also runs for a suspended organization) ends a send as `timeout` only when a `sent` outbox row of its request exists. An old request with no `sent` row ends as `not_seen` when the organization is not suspended; while it is suspended, the send waits for the resume hook. So no send ends as `timeout` without a delivered request.
   - **Telegram.** Every command except `/help`, and every tap, answers "account paused" and changes nothing. `/start` linking still works.
   - **Web.** Every write under `/api` answers `403 org_suspended`, except the paths in `SUSPENDED_WRITE_ALLOW` (see the check below). Sign-out and the password routes are Better Auth paths outside `/api`, so they work. Reads work. The panel shows a paused banner with `OPERATOR_CONTACT`.
     - Check against the code: `SUSPENDED_WRITE_ALLOW` has four entries now: `POST /api/me/terms` and `PATCH /api/me/locale` (a paused account can still accept the terms and choose its language; they change no mail and no organization data), `DELETE /api/organization` (a paused account can still delete itself, F106) and every `POST /api/operator/…` (the operator acts on other organizations). The guard is `refuseSuspendedWrites`.
   - **Resume.** The change from `suspended` to `trial` or `active` sets `resumed_at`. Mail with `received_at` more than 24 h before `resumed_at`, stored before `resumed_at` + 24 h and not backfilled, becomes `skipped` with `suspended_backlog` (no LLM call; the digest counts it on its own line). The sync-late notice and its 30 min grace count from `resumed_at`, and the urgent look-back starts at `resumed_at`. Stale `ready` actions expire at the first committer run (24 h rule).
   - **48 h rule.** For every plan, the committer claims an `approved` send only when the tap is less than 48 h old. A send approved before a pause ends as `held_timeout` after it.
   - **Mailbox limit.** `connectMailbox` (web and CLI) refuses a mailbox above `max_mailboxes` with `mailbox_limit` (web: `409`). The count runs under an advisory lock after the IMAP check, so two connects at once give one success.
     - Check against the code: the check runs twice. A first check without a lock runs before any login, so an organization at its limit never opens a connection. The second check runs inside the transaction under the advisory lock `mailbox_limit:<org id>`, after the IMAP and SMTP checks. Every mailbox status counts (a paused or `auth_error` mailbox holds credentials). `org:plan --max-mailboxes N` sets the limit (0 to 100); the default is 2.
4. **Plan changes.** `setOrgPlan` runs in one transaction: it locks the organization row, writes the new state and one audit row `org.plan_changed` (`from`, `to`, `max_from`, `max_to`, `trial_ends_at`), then runs the suspend or resume hook. A throw in a hook rolls back everything. A change that leaves every field the same is `unchanged` and writes nothing. A change to `trial` needs `--trial-days N` (1 to 365), or an organization that is already in `trial`. `--trial-days` with a plan other than `trial` is refused. `resumed_at` is set only when the plan leaves `suspended`.
5. **Feature flags (F087):** `bun run org:flag --org-id <uuid> [--flag <key> --on|--off]` lists or changes the flags of one organization (audit row `org.flag_changed`). Turning `sso_sign_in` off in an organization that requires SSO still applies, and the CLI prints `warning: sso_required is on; only the break-glass owner can sign in` (the operator route answers `warning: "sso_required_on"`). `FEATURES_OFF` turns flags off for every organization at the next restart (kill switch); an unknown key stops the start. The start log line `features off by FEATURES_OFF: <keys|none>` shows it.
   - Check against the code: the start writes two JSON log events: `features_off` with `count`, and one `feature_killed` with `flag` for each killed key (`apps/server/src/main.ts`). The text form `features off by FEATURES_OFF: …` does not exist.
   - The read order of `isFeatureOn` is: `FEATURES_OFF` (off, no query) → the row of `org_features` for the organization → the `default` of the registry (`packages/core/src/features.ts`). The registry holds each flag with `default`, `description`, `epic` and `removeBy`. Every flag of the registry is off by default. `setOrgFeature` locks the organization row, writes the row and the audit row in one transaction; a write with the same value is `unchanged` (no row change, no audit row).
   - These places in the server read a flag with `isFeatureOn`: `security_log` in `modules/tenancy/routes.ts` (`GET /api/security-log`); `stats_page` in `modules/reports/routes.ts` (`GET /api/stats`); `review_command` and `answered_check` in `modules/channels/commands.ts` (`reviewMessage`, the `/review` command); `answered_check` in `modules/channels/answered-taps.ts` (the Yes and No taps); `mistake_capture` in `modules/actions/routes.ts` (the two action routes), `modules/channels/action-feedback-taps.ts` (the reason and mistake taps), `modules/channels/approval-taps.ts` (the reason buttons after a reject) and `modules/channels/notices/send-result.ts` (the mistake button); `weekly_report` in `modules/channels/notices/weekly-report.ts` (the Monday message); `handled_share` in `modules/reports/digest.ts` (the handled-share line of the digest); and `llm_pause_line` in `modules/reports/llm-pause.ts` (the LLM pause line of `/status` and the digest). `sso_sign_in` (F119, E7-T7, `removeBy` 2027-06-01) in `modules/tenancy/sso-resolve.ts` (the callback refuses `sso_off`), `modules/tenancy/sso-sign-in.ts` (`GET /api/sign-in-options`) and `modules/tenancy/sso-require.ts` (a prerequisite of `--require on`). `GET /api/me` lists the enabled flags of the organization in `features`, and the operator console reads and sets flags (rule 6). `approvals_page` (F102, epic E4-A, remove-by 2027-03-01) has three readers: the five routes `GET /api/approvals`, `GET /api/approvals/:id` and the three POST routes (`modules/channels/approval-routes.ts`: each answers `404 not_found` while it is off, before the role check); the panel line on the approval card (`modules/channels/notices/approval.ts`, with `WEB_BASE_URL`); and the badge count `approvalsWaiting` of `GET /api/me` (`approvalsWaiting` in `apps/server/src/web-route-deps.ts`: 0 while it is off); the web nav shows the Approvals item from `features`. `delegation_pages` (F102, epic E4-A, remove-by 2027-03-01) has two readers: the three `/api/delegates` routes and the four `/api/delegations` routes (`modules/delegation/routes.ts`: `404 not_found` while it is off, before the role check; [delegation.md](delegation.md) rules 11 to 14); the web shows the Delegations nav item from `features`. The live lab turns both flags on (`modules/lab/seed.ts`). `sent_sync` is read in `modules/mail/` and in `modules/channels/notices/sent-missing.ts` ([sent-mail.md](sent-mail.md)). The registry (`packages/core/src/features.ts`) lists every flag.
6. **The operator role.** An operator is a user whose id is in `OPERATOR_USER_IDS` (a comma list of user ids; each must be a UUID, or the start fails). `requireOperator` guards the whole `/api/operator` prefix: any other user gets `404 not_found`, like a path that does not exist, and a `operator_route_refused` warn line with the user id. The operator routes are `GET /api/operator/flags` (the effective value of every registry flag for every organization; its only path to `listOrgFeatureRowsOfAll` is `featureStatesOfAll`), `GET /api/operator/orgs`, `GET /api/operator/orgs/:orgId`, `GET /api/operator/notices?days=` and two writes, `POST /api/operator/orgs/:orgId/plan` and `POST /api/operator/orgs/:orgId/flags` (the console, F099; details in `web-panel.md`). A write uses the same function and writes the same audit row as `org:plan` or `org:flag`, with the operator's user id as actor. The operator also works through the CLIs (rule 7) and gets notices in a Telegram chat (`digest-and-notices.md`). An operator without TOTP gets `403 two_factor_required` on every `/api/operator/*` route (F105), and an operator with an SSO session gets `403 password_sign_in_required` (F119; `web-panel.md` rule 8).
7. **Operator CLIs.** They read `DATABASE_URL` and print ids, codes, dates and counts only.
   - `bun run org:create --org-name <name> --email <email> --display-name <name> [--timezone <tz>] [--plan trial|active] [--trial-days N]` creates an organization with its owner. Defaults: `Europe/Warsaw`, `trial`, 30 days. `--trial-days` with `--plan active` is refused. An email that exists gives "user with this email already exists".
   - `bun run org:invite --org-name <name> --email <email> --display-name <name> [--lang pl|en] [--timezone <tz>] [--trial-days N] [--print]` creates a trial organization like `org:create`, then makes a 24 h setup link for the owner. The link goes by mail when the mail sender is on, and is printed to stdout when it is off or with `--print`. It needs `WEB_BASE_URL` and `WEB_AUTH_SECRET`.
   - `bun run org:plan --org-id <uuid> [--plan trial|active|suspended] [--trial-days N] [--max-mailboxes N]` (rule 4).
   - `bun run org:status [--org-id <uuid>]` prints three lines per organization: plan, trial end, mailbox limit, `resumed_at`; mailbox counts by status and the last sync; LLM calls today and linked Telegram chats.
   - `bun run org:flag --org-id <uuid> [--flag <key> --on|--off]` (rule 5).
   - `bun run org:break-glass --org-id <uuid> [--user-id <uuid> | --clear] [--confirm <organization name>]` (F105) lists the owners of an organization with their two-factor state and break-glass mark, sets the one break-glass owner, or clears it. The user must be an owner and must have TOTP on; a new owner replaces the old one. The set and the clear need `--confirm` with the organization name (compared like the web delete: trimmed, case-insensitive): missing exits 2, wrong exits 1 and changes nothing; the list needs none. Audit rows `org.break_glass_set` and `org.break_glass_cleared`. The mark stops the owner from turning TOTP off, and it is the one exception to "SSO required": that owner keeps the password and TOTP sign-in (`org:sso --require`, below).
   - `bun run org:sso --org-id <uuid> [command]` (F119) sets up and switches company sign-in for one organization. With no command it shows the state. One command at a time. The client secret never comes as an argument, and the real secret path is in [deploy/README.md](../../deploy/README.md) § Company sign-in. Each write is one transaction that locks the organization row (`FOR NO KEY UPDATE`) and the provider row; DNS and discovery run before it; a repeat with the same data writes nothing. It prints ids, hosts, domains, counts and codes only, and a database error prints its name and code, never its text (the text can hold the client secret). Commands:
     - (none) prints `provider <id>`, `issuer <host>`, `domain <domain> proof|unproved`, `txt <name> <value>` while unproved, `required yes|no`, `flag sso_sign_in on|off`, `break-glass ready|missing`, `linked <n>` and `redirect <WEB_BASE_URL>/api/auth/sso/callback/<providerId>`. It prints `no provider` when there is none, and `error organization_not_found` (exit 1) for a wrong id.
     - `--set --issuer <https-url> --domain <domain> --client-id <id> --client-secret-stdin` reads the secret from the first line of stdin. It fetches the discovery document of the issuer (10 s limit) and stores the endpoints with the client (PKCE, scopes `openid email profile`, no IdP-initiated sign-in). It refuses an issuer that is not `https:`, an IP literal, `localhost`, a name with the suffix `.local`, `.internal` or `.localhost`, a single-label name, and any host (issuer or endpoint) that resolves to an address outside global unicast (`error discovery_failed <code>`, for example `discovery_private_host`, `discovery_dns_failed` or `discovery_untrusted_origin`). It also refuses a bad domain (`bad_domain`), an empty secret (`client_secret_missing`) and a domain that another organization holds (`domain_taken`). Result: `set new`; `set secret` (only the secret changed: the proof, the links and the sessions stay); `set unchanged`; or `set boundary links_removed=<n> sessions_ended=<n>` (a new issuer, domain or client id: it drops the proof, `sso_required`, every link and the SSO sessions of the linked users). The provider id is the organization id. Audit row `sso.provider_set` (`change` is `new`, `secret` or `boundary`; the issuer host, the domain, counts).
     - `--verify` reads the DNS TXT record `_ea-sso.<domain>` and compares each record (its chunks joined) with `ea-sso=<token>`. The token is the first 32 hex characters of HMAC-SHA256 over `<org id>:<domain>`, with a key derived from `CREDENTIALS_KEY` (HKDF-SHA256, info `ea/sso-domain/v1`); `org:sso` prints the record while the domain is unproved. A match sets the proof `dns` and writes `sso.domain_verified`. It prints `verified`, `already` or `none` (no provider), and `error not_found_in_dns` (exit 1; any DNS error and a 10 s timeout count as not found). The token goes into a public record and is not a secret.
     - `--attest --confirm <domain>` sets the proof `attested` for a test organization with no DNS control (audit row `sso.domain_attested`). `--confirm` must equal the provider domain (`error confirm_mismatch`). It prints `attested`, `already` or `none`.
     - `--require on|off` switches "SSO required" (audit row `sso.required_changed`, with `sessions_ended`). `off` always works: it is the operator's way to reopen passwords. `on` needs all of these and prints every failure at once as `refused <reason>` (exit 1): `no_provider`; `unproved` (the domain has no proof); `flag_off` (the flag `sso_sign_in` is off, also by `FEATURES_OFF`); `no_break_glass` (no break-glass owner with TOTP on, or that owner is refused by the rule of another organization, or this switch would refuse the break-glass owner of another organization); `off_domain_members` (a member other than the break-glass owner has an e-mail off the provider domain; one `member <user id>` line each). When it goes on, it ends every password session of the members that the rule now refuses, and their pending two-factor challenges, trusted-device rows and open reset links. An SSO session stays.
     - `--remove --confirm <domain>` removes the provider: every link, the SSO sessions of the linked users, the provider row and `sso_required` go (audit row `sso.provider_removed`). It prints `removed links_removed=<n> sessions_ended=<n>`, `none`, or `error confirm_mismatch`.
   - `bun run org:member --org-id <uuid> …` (F119) manages SSO members. Every command needs `--org-id`, also `--end-sessions` and `--unlink-sso`. Output holds ids, counts and codes, never an address or a name.
     - `--add --email <e> --display-name <n> [--role assistant|owner] [--lang pl|en]` makes a user with a verified address, no password and a membership (default role `assistant`, default language `pl`). It prints `added <user id>`, or `error email_taken` (any user with that address, in any organization), `error off_domain` (the organization requires SSO and the address is off the provider domain) or `error not_found`. Audit row `org.member_added` (`user_id`, `role`). No mail goes out: the member signs in through the IdP.
     - `--user-id <uuid> --end-sessions [--only-sso]` checks that the user is a member of `--org-id` (`error not_member`, exit 1), then ends every session of the user, or with `--only-sso` only the SSO sessions. Sessions belong to the user, not to the organization: a user with a membership in two organizations loses the sessions in both. The audit row `web.member_sessions_ended` (`user_id`, `count`, `only_sso`) goes to the organization of `--org-id`. It prints `ended <n>`. This is how the operator ends access at once when the owner asks (ADR 0026 point 7).
     - `--user-id <uuid> --unlink-sso` removes the link of the user to the provider of `--org-id` and ends every SSO session of the user, also one from another provider. The next SSO sign-in links again by e-mail. It prints `unlinked, sessions <n>` or `none` (no link). Audit row `sso.unlinked`.
   - A callback in flight and these writes take turns. The SSO plugin locks the provider row with an `UPDATE` in the same transaction that makes the link and the session (`lockSSOProviderForAccountLink`, `@better-auth/sso` 1.7.18). `--set`, `--verify`, `--attest`, `--require on`, `--remove` and `--unlink-sso` lock the same row `FOR UPDATE`, so they wait for a callback in flight and then act on its result. Our callback code takes no lock of its own; it relies on the plugin's lock, which a plugin upgrade must keep (`deploy/README.md` § Company sign-in). The test `sso-provider-service.test.ts` holds the row with the same `UPDATE`; `web-sso-callback-lock.test.ts` runs a real callback against a waiting `unlinkSso` and `removeSsoProvider`, and a callback against a held removal.
   - `bun run org:delete --org-id <uuid> --confirm <organization name>`, `bun run org:export --org-id <uuid> --recipient <age1…> --out <path>` and `bun run org:dsr --org-id <uuid> --address <address> (--find | --erase --confirm <address>)` (F106) delete an organization, export its data to an `age` file and find or erase the data of one sender. Rules: [account-data.md](account-data.md). The flag `org_delete` (rule 5) is off by default and gates only the delete dialog and route.
   - `bun run web:two-factor-reset --org-id <uuid> --user-id <uuid> --confirm <organization name>` (F105) resets the second factor of a member who lost the phone and the codes. In one transaction it deletes the second-factor row, trusted devices and every session of the user, and clears the break-glass mark in each organization of the user. Audit rows `web.two_factor_reset` and `org.break_glass_cleared`. A repeat run changes nothing more. `--confirm` works as for `org:break-glass`. The operator first checks who asks, outside the system.
8. **Organization settings.** `PATCH /api/organization` (owner) changes the time zone (it must be a supported IANA name: `timezone_invalid`) and the signature text. Each changed field writes one audit row (`org.timezone_changed`, `org.style_changed`); the style audit row holds no text. Every member can change their own digest times (`PATCH /api/me/digest-times`) and accept the current terms (`POST /api/me/terms`; an old version gives `409 terms_outdated`).

## Data

`organizations`: `id`, `name`, `timezone`, `style_text`, `plan` (`trial`, `active` or `suspended`), `trial_ends_at` (required when the plan is `trial`), `max_mailboxes` (default 2, at least 0), `resumed_at`, `data_retention_days` (default 30, at least 1), `created_at`.

`users`: `id`, `email`, `display_name`, `locale`, `terms_version`, `terms_accepted_at` (and the Better Auth columns). `memberships`: `org_id`, `user_id`, `role` (`owner` or `assistant`), `digest_times`, `created_at`.

`org_features`: `org_id`, `flag`, `enabled`, `set_by` (`cli` or a user id), `set_at`; one row per organization and flag. No row means the registry default.

`organizations.sso_required` (boolean, default false). `sso_providers` (F119, migration `db/migrations/20261114170001_sso.sql`): `provider_id` (the organization id as text), `org_id`, `issuer`, `domain`, `domain_verified`, `domain_proof` (`dns` or `attested`), `oidc_config` (the plugin JSON, with the client secret in clear), `saml_config` (always null); one row per organization and one per domain; it goes with the organization by cascade ([account-data.md](account-data.md)). The IdP links are `auth_accounts` rows with the provider id.

Audit events: `org.plan_changed`, `org.flag_changed`, `org.timezone_changed`, `org.style_changed`, and the F119 events `sso.provider_set`, `sso.provider_removed`, `sso.domain_verified`, `sso.domain_attested`, `sso.required_changed`, `sso.unlinked`, `org.member_added` and `web.member_sessions_ended` (from the CLIs of rule 7), and `sso.login` and `sso.refused` (from the sign-in, [web-panel.md](web-panel.md) rule 4). All of them show in the security log with their own kinds.

Plan states:

```
trial     → active | suspended     (org:plan; trial_ends_at is kept only in trial)
active    → trial | suspended      (org:plan --plan trial needs --trial-days)
suspended → trial | active         (org:plan; sets resumed_at and runs the resume hook)
```

## Limits

- No sign-up and no billing: the operator creates every organization (PD-001, PD-047). A trial that ends does not change the plan by itself; only the operator notice `trial_ending` goes out (`digest-and-notices.md`).
- Account data (F106, [account-data.md](account-data.md)): the owner deletes the organization in the Account card (flag `org_delete`, off by default; `DELETE /api/organization`), and the operator runs `org:delete`, `org:export` and `org:dsr`. The delete also works for a `suspended` organization. There is no grace period and no panel page for data requests (PD-038).
- Platform controls (F099): send limits, the operator console (`/operator`, `/api/operator/*`) and the security log (`GET /api/security-log`, flag `security_log`; F106 adds the kinds `data_exported`, `delete_refused`, `dsr_find` and `dsr_erase`). The console shows ids, codes, counts and dates only. The CLIs stay.
- A route cannot add a member. Only `org:member --add` does, and it makes a member with no password, for company sign-in (F119). The panel has no members page. Company sign-in has no SAML, no SCIM and no just-in-time accounts, and one provider with one domain per organization (a subdomain e-mail is refused). The operator ends member sessions on the owner's request (`org:member --end-sessions`). Sessions belong to the user: a user in two organizations loses both. The public reset request refuses an SSO-only member (no password account, a membership in an organization with a provider) with the generic answer, no mail and no token; only the operator's `web:invite --user-id` gives such a member a password. The first `--set` of a provider deletes the open reset links of the members with no password, in the same transaction. The operator console has a read-only SSO block; the operator changes everything with the CLIs.
- `sent_sync` has no reader in the server yet (rule 5). The readers of the other flags are listed in rule 5.

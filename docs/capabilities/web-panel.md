# Web panel

> Checked against the code at `522100d2`, 2026-11-14.

## What it does now

The web panel is a static Astro build with one React island per page (`apps/web`). The server serves it from `WEB_DIST` and answers the JSON API under `/api` from the same process (`apps/server/src/web.ts`, `apps/server/src/platform/http.ts`). A user signs in with an e-mail and a password (Better Auth, 12 to 128 characters), gets a session cookie, and reaches ten pages: Onboarding, Activity, Mailboxes, Settings and Rules after sign-in, Stats (only while the flag `stats_page` is on) and Operator (only for an operator), and Login, Setup and Forgot before it, plus the legal stubs. The panel connects and manages mailboxes, shows what the system did to each mail with Undo and feedback buttons, sets the mode, the switches, the category policy, the sync folders, the digest times, the time zone and the signature, manages the sender rules, links Telegram, and lists the live sessions. The panel is reachable only through Tailscale Serve on the tailnet of the owner. It is off while `WEB_BASE_URL` is empty. An operator (a user in `OPERATOR_USER_IDS`) has one route that reads across organizations. The panel has no approvals, delegates or delegations page: those stay in Telegram.

## Rules

1. **The web is on only with `WEB_BASE_URL`.** An empty value logs "web is off" and the server serves `/health` only. The config check needs `WEB_AUTH_SECRET` (at least 32 characters) when `WEB_BASE_URL` is set. The server listens on `127.0.0.1:8080`; Tailscale Serve adds HTTPS (`deploy/README.md` § Web panel, ADR 0017). The panel is never reached by another path.
2. **Pages and the session.** Every page except `/login`, `/setup`, `/forgot`, `/legal/<pl|en>/<privacy|terms|dpa>`, `/404.html` and the static assets (`PUBLIC_PAGE_PATHS`) redirects to `/login?next=<path>` without a session. `/` redirects to `/activity` when the onboarding checklist is done and to `/onboarding` when it is not (`homePathOf`). A page that is not in the build answers the `404.html` page. When `WEB_DIST` has no build, every page answers `503` "The web build is missing. Run bun run web:build.".
3. **Sign-in.** The client calls Better Auth under `/api/auth/*`, and only these paths reach it (`AUTH_ALLOWED_PATHS`): `sign-in/email`, `sign-out`, `get-session`, `reset-password` (POST, and GET `reset-password/<token>`), `change-password`, `revoke-other-sessions`, `revoke-sessions`, the five two-factor paths `two-factor/enable`, `two-factor/disable`, `two-factor/verify-totp`, `two-factor/verify-backup-code` and `two-factor/generate-backup-codes`, and `request-password-reset` (POST) when the auth-mail sender is on. Every other path answers `404`, also `two-factor/get-totp-uri`, `two-factor/send-otp` and `two-factor/verify-otp`. The session lasts 30 days and renews after one day of use; the cookie has the prefix `ea`. The tenant is the oldest membership of the session user; the request never names it (`requireTenant`). A `401` from `/api` sends the browser to `/login`.
4. **Login hardening** (the rules and their numbers are in `docs/architecture.md` §7 "Web security"; each one is in the code at the checked commit):
   - Lockout: 10 failed sign-ins in 15 minutes lock the user for 15 minutes (`auth-lockout.ts`); one lock mail per lock, at most 3 per UTC day; the audit row `web.login_locked`.
   - Leaked-password check: a password set or change asks the Have I Been Pwned range API (`pwned.ts`); it fails closed (`400 PASSWORD_COMPROMISED`, `503` when the API is down). `AUTH_PWNED_CHECK=off` turns it off (tests only).
   - Terms: a password set through a link needs `termsVersion` (`400 TERMS_REQUIRED`); every member sees the terms dialog once at the next sign-in; `POST /api/me/terms` records the acceptance (`409 terms_outdated` for an old version).
   - Session list: `GET /api/me/sessions` lists the live sessions of the member (device, address, last use), never the token; the Account card ends all sessions or all other sessions.
   - Reset by e-mail: open only when the four `AUTH_SMTP_*` keys and `AUTH_MAIL_FROM` are set (`resetRequestOpen`); otherwise `/forgot` says "Reset by e-mail is off" and the CLI prints the links. Reset requests are limited per client address by Better Auth (3 per 15 minutes) and per e-mail address by our own limit (3 per hour), and the `reset-password` and `change-password` routes by Better Auth (5 per 60 s).
   - Two-factor sign-in (F105, `platform/auth-two-factor.ts`): a member turns on TOTP in Settings → Account (password, QR code or key, first code) and gets 10 single-use backup codes once. Later sign-ins ask for a code after the password; the member can tick "Trust this device for 30 days". Turning TOTP on ends every older trusted device and every other session of the user. Turning it off needs a live session and the password. A new set of backup codes needs the password and makes the old ones useless. Limits: 5 wrong codes end one sign-in step, 10 failed codes lock the code step for 15 minutes (audit `web.two_factor_locked`), and 3 calls per 10 s per client address on `/two-factor/*`. A password reset does not skip the code. An operator needs TOTP (rule 8). The break-glass owner of an organization (one owner, set with `bun run org:break-glass`) cannot turn TOTP off (`403 BREAK_GLASS_NEEDS_TWO_FACTOR`). `bun run web:two-factor-reset --org-id <uuid> --user-id <uuid>` is the reset for a member who lost the phone and the codes: it ends the second factor, every session and trusted device of the user, and the break-glass mark.
5. **Invite.** `bun run org:invite --org-name <name> --email <email> --display-name <name> [--lang pl|en] [--timezone <tz>] [--trial-days N] [--print]` makes an organization with a `trial` plan (30 days by default) and its owner, then makes a 24 h setup link. `bun run web:invite --org-id <uuid> [--user-id <uuid>] [--print]` makes a setup or reset link for an existing member. With the auth-mail sender on and no `--print`, the link goes by mail; otherwise the command prints it. The link works once. The owner opens it on a device in the tailnet, accepts the terms and sets a password (`/setup`). The link never goes to a log.
6. **The `/api` guards** (`createApp`): every `/api` route needs a session (`401 unauthorized`) and a tenant (`403 no_organization`). A write method needs an allowed `Origin` (`403 bad_origin`); the body limit is 64 KB (`413`). A route marked "owner" answers `403 owner_only` to a member (`requireOwner`). A write in an organization with the plan `suspended` answers `403 org_suspended`, except `POST /api/me/terms`, `PATCH /api/me/locale`, `DELETE /api/organization` (a paused account can still delete itself) and every `POST /api/operator/…` (`refuseSuspendedWrites`, `SUSPENDED_WRITE_ALLOW`); reads work. An unknown `/api` path answers `404 not_found`. A body that fails its schema answers `400 validation` with the details.

   `GET /health` (DB reachable) is outside `/api`. The behaviour behind each group is in its capability page: mailboxes in [sync.md](sync.md), settings in [actions-and-undo.md](actions-and-undo.md), feedback in [triage.md](triage.md), reject reasons and the mistake mark in [drafts-and-send.md](drafts-and-send.md), Telegram link and digest times in [digest-and-notices.md](digest-and-notices.md).

8. **The operator route.** Every path under `/api/operator` answers a user who is not in `OPERATOR_USER_IDS` with `404 not_found` and a log line with the user id (`requireOperator`). `OPERATOR_USER_IDS` is an env list of user ids; a DB write cannot make an operator (ADR 0027). The routes are `GET /api/operator/flags` (the feature flags of every organization), `GET /api/operator/orgs` (the organization list), `GET /api/operator/orgs/:orgId` (one organization), `GET /api/operator/notices?days=` (the operator notices) and two writes, `POST /api/operator/orgs/:orgId/plan` and `POST /api/operator/orgs/:orgId/flags`. A write calls the same function as `org:plan` or `org:flag`, writes the same audit row into that organization with the operator's user id as actor, and works while the operator's own organization is `suspended`. A path id that is not a UUID answers `404`. An operator without TOTP gets `403 two_factor_required` on every `/api/operator/*` route, reads and writes, and a `operator_two_factor_required` warn line with the user id; `/operator` redirects them to `/settings?two_factor=required`. The data holds ids, codes, counts and dates only. `docs/architecture.md` §7 "Operator" has the rule.
9. **The pages** (rule 2 lists the public ones): Onboarding is a checklist (connect a mailbox, link Telegram, choose the mode or keep shadow mode, add sender rules; optional); Activity lists what happened to each mail and why, with filters (mailbox, category, "needs my action", range, "only not rated"), a detail panel, the ✅ / ✏️ feedback buttons and Undo, and reloads every 30 s while the tab is visible; Mailboxes shows the badge "Server not allowed" and an owner hint for a `host_blocked` mailbox (no pause, resume or password button); it connects (address and password), pauses, resumes, changes the password and removes a mailbox, and links Telegram (after the consent text and a tick: `tg_consent_*`); Settings holds the mode, the switches, the category policy with the go/no-go gate, the sync folders, the digest times, the time zone, the signature and the Account card (language, change password, the two-factor section, sessions, sign out everywhere, and for an owner with the flag `org_delete` the delete block with its dialog; the section reads `GET /api/me/two-factor`, and `?two_factor=required` scrolls to it); Rules holds the VIP, whitelist and blocklist; Stats (`/stats`, island `StatsPage.tsx`, read-only) is a nav item that shows only while `/api/me` `features` holds `stats_page`: one table with the metrics as rows and the last 8 finished weeks as columns (newest first), each rate with its count, and a mailbox select when there are two or more mailboxes; it loads once per choice and does not poll, and with the flag off the page shows `stats_off`; an evidence row shows its precision only from 30 labels (`EVIDENCE_MIN_LABELS`), below that the label count (`stats_evidence_few`, with the `auto` mark as `stats_evidence_few_auto`), and `–` for a category without labels; when the chosen mailbox is gone (the API answers 404 for its id) the page shows all mailboxes and the text `stats_mailbox_gone`; Operator (`/operator`, island `OperatorPage.tsx`) is a nav item that only an operator sees (`/api/me` field `operator`); any other user gets the 404 page for `/operator` (`OPERATOR_PAGE`) and shows the organization list (the mailbox count has three numbers: all, with a login error, with a server not allowed), one organization, the operator notices and the plan and flag changes of rule 8; the Settings page also has a security log card for owners when the flag `security_log` is on (`GET /api/security-log`); Login, Setup and Forgot are the sign-in pages (Login shows the code step after the password when the user has TOTP: a 6-digit code or a backup code, and the switch to trust the device); the legal pages are draft stubs until E7-T4 (F107). The pages without an island follow their own language: a legal page prints its `<pl|en>` language in its text and in `<html lang>`, the 404 page shows Polish and then English, and the start page link reads "Dalej / Continue". A banner shows a paused account (with `OPERATOR_CONTACT`), a mailbox in `auth_error`, and the trial end. `/api/me` is read every 30 s.
10. **The static build.** `bun run web:build` writes the folder `dist` in `apps/web` (Astro `output: "static"`, a meta CSP on every page). The server serves it with `serveStatic` from `WEB_DIST` (default `WEB_DIST=apps/web/dist`): files under `/_astro/` are cached for a year, every other file has `private, no-store`. `bun run web:dev` runs the dev server and proxies `/api` to `127.0.0.1:8080`. The container image runs `bun run web:build` and sets `WEB_DIST=/app/apps/web/dist` (`deploy/Dockerfile`; `deploy/README.md` § Web panel).
11. **Texts.** Every visible text is a key in `apps/web/src/i18n/en.ts` (English) and in `apps/web/src/i18n/pl.ts` (Polish; a missing or extra key fails `bun run typecheck`). Plural texts are in `enPlurals` and `plPlurals` (Polish has one, few and many). The panel language is `users.locale` (`pl` or `en`) once `/api/me` answers, else the stored browser choice, else the browser language (`apps/web/src/i18n/index.ts`). The Account card writes it with `PATCH /api/me/locale` (any member; also allowed for a paused organization; no audit row) and the panel switches at once, keeping typed form state; every sign-in on any device takes the stored choice. The choice has no "browser language" option, so a null value cannot be set again. `apps/web/src/i18n/i18n.test.ts` checks the placeholders and the plural forms; `en.test.ts` checks the keys of the core schemas. The browser calls the API through `api()` in `apps/web/src/lib/api.ts`, which parses each answer with a Zod schema from `@ea/core/web`.
12. **The language of the panel.** The panel language is `users.locale`, else the browser language. The Account card sets `users.locale` (`PATCH /api/me/locale`). `GET /api/activity` renders the AI line and the action phrases in the same language: `users.locale`, else the first tag of the `Accept-Language` header, else English (`resolveLocale`, `firstLanguageTag`). No other route returns phrases of ours. Every island is `client:only="react"` and calls `useLocale()` on its first line (`docs/code-patterns.md` § Texts carry a locale).
13. **Telegram consent.** A Telegram link needs the consent of version `TELEGRAM_CONSENT_VERSION`: the link block shows the consent text and a tick, and `POST /api/channels/telegram/link` refuses an old or missing version (rule 7). Change the content that goes to Telegram: bump the version.

## Data

- Better Auth tables: `users` (with `locale`, `terms_version`, `terms_accepted_at`), `auth_sessions`, `auth_accounts`, `auth_verifications` (reset and invite tokens; deleted 1 day after `expires_at`), `auth_lockouts` (`failed_count`, `locked_until`, the lock mails of the day), `auth_two_factors` (the TOTP secret and the backup codes, encrypted by Better Auth with `WEB_AUTH_SECRET`; `verified`, `failed_verification_count`, `locked_until`) and `users.two_factor_enabled`. The full list is in `docs/architecture.md` §5.
- `memberships` (the role, `digest_times` and `break_glass`) give the tenant and the role of a session; `break_glass` marks at most one owner per organization (F105); `organizations` hold `plan`, `trial_ends_at`, `timezone` and `style_text` (the signature).
- Audit events of the web: `web.login`, `web.password_set`, `web.password_changed`, `web.login_locked`, `web.terms_accepted`, `web.telegram_consent`, `web.sessions_revoked`, `web.other_sessions_revoked`, `web.two_factor_enabled`, `web.two_factor_disabled`, `web.two_factor_reset`, `web.backup_codes_generated`, `web.backup_code_used`, `web.two_factor_locked`, `org.break_glass_set`, `org.break_glass_cleared` (`web.login` has the field `second_factor`), `org.exported`, `org.delete_refused`, `dsr.find`, `dsr.erase` (F106; the last four show in the security log, [account-data.md](account-data.md) rule 16), `onboarding.mode_kept`; each write route of the groups of rule 7 writes the audit rows of its capability.

## Limits

- No approvals, delegates or delegations page: E4-A (F102).
- The panel has Polish texts for every key, and the activity phrases and AI lines follow the request language. The delete dialog and its login notice (`del_*` keys, F106) are in [account-data.md](account-data.md) rule 5. Operator pages and legal texts have their own tickets (E7-T4).
- No live updates: Activity and `/api/me` poll every 30 s while the tab is visible, the Telegram card every 5 s while a link waits (F055-web-live-updates).
- The build uses Astro 5 (`apps/web/package.json`); the move to Astro 7 is F101.
- Two-factor sign-in has TOTP and backup codes only: no e-mail or SMS codes, no passkeys (ADR 0026). The panel has no page to choose the break-glass owner (only `org:break-glass`). A TOTP code works again inside its window (no replay guard, accepted). No single sign-on: OIDC is E7-T7 (F119).
- The API has no OpenAPI description yet (ADR 0023 proposed, E4-A F102).
- The legal pages are draft stubs until the papers of E7-T4 (F107). The panel can delete the organization (flag `org_delete`) but has no export and no page for data requests: the operator runs `org:export` and `org:dsr` (F106, PD-038).
- The operator console shows ids, codes, counts and dates only and has no billing (PD-047). The operator needs TOTP (rule 8).
- A user belongs to the oldest of their memberships; the panel has no organization switcher.

## Decisions

- ADR 0016 (Astro static build with React islands, login with Better Auth), ADR 0017 (web access only through Tailscale Serve), ADR 0027 (operator role and feature flags).
- ADR 0023 (proposed: every user action is a typed HTTP command described in OpenAPI) and ADR 0026 (identity tier 1, OIDC, TOTP, break-glass owner: TOTP, backup codes and the break-glass mark landed by F105; OIDC stays proposed, F119).
- `docs/architecture.md` §7 holds the auth and web security rules and §10 the deployment; `docs/modules.md` §4 lists the pages by slice.

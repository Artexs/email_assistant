# Web panel

> Checked against the code at `05702e0c`, 2026-11-19.

## What it does now

The web panel is a static Astro build with one React island per page (`apps/web`). The server serves it from `WEB_DIST` and answers the JSON API under `/api` from the same process (`apps/server/src/web.ts`, `apps/server/src/platform/http.ts`). A user signs in with an e-mail and a password (Better Auth, 12 to 128 characters), or with the company account of the organization when the operator set up company sign-in (OIDC, rule 4), gets a session cookie, and reaches fifteen pages: Onboarding, Activity, Mailboxes, Settings and Rules after sign-in, Report and Review (no nav tab; both need the flag `trust_ladder` or `panel_review`, rule 9), Approvals (nav item only while the flag `approvals_page` is on), Delegations and Delegates (nav item only while the flag `delegation_pages` is on), Stats (only while the flag `stats_page` is on) and Operator (only for an operator), and Login, Setup and Forgot before it, plus the legal pages. The panel connects and manages mailboxes, shows what the system did to each mail with Undo and feedback buttons, sets the mode, the switches, the category policy, the sync folders, the card "Sent mail" (the switch "Track my sent mail", a status line and the off note; it shows only while the flag `sent_sync` is on, or the switch is on and the flag is off: then it says "paused" and the switch can only go off; [sent-mail.md](sent-mail.md) rule 16), the digest times, the time zone and the signature, manages the sender rules, links Telegram, and lists the live sessions. The panel is reachable only through Tailscale Serve on the tailnet of the owner. It is off while `WEB_BASE_URL` is empty. An operator (a user in `OPERATOR_USER_IDS`) has one route that reads across organizations. The owner approves, rejects and edits a waiting draft on the Approvals page, and adds delegates, reminds, cancels and closes delegations on the two delegation pages (rule 9). Every `/api` route is described in one OpenAPI file, `GET /api/openapi.json` (rule 6).

**Look.** The panel follows one design system (ADR 0037): a teal brand colour, large rounded corners, soft card shadows and 16 px text. All colour, radius, shadow and font values are tokens in `apps/web/src/styles/global.css`; a component uses token classes only. The panel follows the system setting for light or dark; there is no manual switch. The font is Nunito, served from the panel's own files (`apps/web/src/assets/fonts/`, Latin and Latin Extended, so Polish letters render), and no page loads a font from another host. Buttons are pills, 48 px high (`lg` 52, `sm` 44, `xs` 36 px) with a soft teal shadow on the main one; fields (input, textarea, select) are 48 px high with 16 px text and a 2 px edge in the `--input` colour (the compact size is 36 px); a switch is 52 × 30 px; a card has a shadow and no border, except in forced-colors mode. Every focused control shows a 3 px ring in the ring colour with a 2 px gap (`apps/web/e2e/tests/base-controls.spec.ts` reads these sizes). Tabs are a pill group that scrolls sideways inside itself when the tabs do not fit; dialogs, sheets and menus use the card colour and shadow, menu items are 44 px high, a dialog scrolls inside when it is taller than the screen, and overlay animations stop under `prefers-reduced-motion`. The toast follows the system colour scheme. The pattern page of the dev build (`/dev/patterns`) shows each of these. The legal pages read as one card in a column of at most 768 px, under a brand line that links to sign-in; the 404 and offline pages are one card with a teal icon tile and a full-width teal button for each language, and the offline page needs no script. A test (`apps/web/src/lib/tokens.test.ts`) checks every token value and the contrast of each text pair. A scan test (`apps/web/src/lib/token-classes.test.ts`) fails on a palette class, a white or black class, a hex or `rgb(`, `hsl(` or `oklch(` colour, an inline `style=`, a focus colour with an opacity and an `accent` class outside the warm box and the warning banner; its allow list names each exception (the dialog and sheet scrim, the QR code, the toast variables, `theme-color`).

## Rules

1. **The web is on only with `WEB_BASE_URL`.** An empty value logs the event `web_off` and the server serves `/health` only. The config check needs `WEB_AUTH_SECRET` (at least 32 characters) when `WEB_BASE_URL` is set. The server listens on `127.0.0.1:8080`; Tailscale Serve adds HTTPS (`deploy/README.md` § Web panel, ADR 0017). The panel is never reached by another path.
2. **Pages and the session.** Every page except `/login`, `/setup`, `/forgot`, `/legal/<pl|en>/<privacy|terms|dpa>`, `/404.html` and the static assets (`PUBLIC_PAGE_PATHS`; since the phone channel this includes the installable shell: `/manifest.webmanifest`, `/sw.js`, `/offline.html` and `/icons/`) redirects to `/login?next=<path>` without a session. `/` redirects to `/activity` when the onboarding checklist is done and to `/onboarding` when it is not (`homePathOf`). A page that is not in the build answers the `404.html` page. When `WEB_DIST` has no build, every page answers `503` "The web build is missing. Run bun run web:build.". **The installable shell (phone channel).** Every page links `/manifest.webmanifest` (`start_url` `/activity`, `display` `standalone`, icons 192, 512 and 512 maskable in `/icons/`), and the panel layout registers the service worker `/sw.js` (scope `/`; `web:build` bundles `apps/web/src/sw/sw.ts` after `astro build`; `/sw.js` answers `Cache-Control: no-cache`, every other file except `/_astro/` answers `private, no-store`). The worker caches `/offline.html` and the hashed files of `/_astro/` only. `web:build` reads `dist/offline.html` after `astro build` and lists each `/_astro/` file the page links (its style sheet) and each `/_astro/` file that style sheet names in `url(...)` (the font files); the build fails when the page links no style sheet or a listed file is missing. The install stores `/offline.html` and that list in the cache `ea-shell-v2-<8 hex characters>`; the hex part is a hash over the bytes of `/offline.html` and of each listed file, so a new offline text or a new file makes a new worker and a new cache. It never handles an `/api` request and never stores a page: a page load goes to the network, and only a network error shows `/offline.html`, with its own look because its files are precached (`activate` deletes the other `ea-shell-` caches; a file that fails at install fails the install and the old worker stays). The CSP names `worker-src 'self'` and `manifest-src 'self'` (`apps/web/astro.config.mjs`). A push (`pushPayloadSchema`: `v`, `id`, `kind`, `count`, `itemId`, `lang`; anything else shows nothing) becomes a notification from `pushTexts`; a tap opens `noticePath(kind, itemId)` in the open panel window or a new one. Code: `apps/web/src/lib/service-worker.ts`, `apps/web/src/lib/shell-precache.ts`, `apps/web/scripts/build-sw.ts`, `packages/core/src/notices/push.ts`, `packages/core/src/texts/push.ts`. Tests: `service-worker.test.ts`, `shell-precache.test.ts`, `integrations/pwa-shell.test.ts`, `web-http-pages.test.ts` (served headers) and the e2e spec `pwa.spec.ts`.
3. **Sign-in.** The client calls Better Auth under `/api/auth/*`, and only these paths reach it (`AUTH_ALLOWED_PATHS`): `sign-in/email`, `sign-out`, `get-session`, `reset-password` (POST, and GET `reset-password/<token>`), `change-password`, `revoke-other-sessions`, `revoke-sessions`, the five two-factor paths `two-factor/enable`, `two-factor/disable`, `two-factor/verify-totp`, `two-factor/verify-backup-code` and `two-factor/generate-backup-codes`, `request-password-reset` (POST) when the auth-mail sender is on, and the two paths of the SSO plugin (F119, `isAllowedSsoPath`): `sign-in/sso` (POST) and `sso/callback/<providerId>` (GET; one id, no `/`). Every other path answers `404`: also `two-factor/get-totp-uri`, `two-factor/send-otp` and `two-factor/verify-otp`, and every other plugin path (`sso/register`, `sso/providers`, `sso/get-provider`, `sso/update-provider`, `sso/delete-provider`, the domain-proof paths, `sso/callback` without a provider id and the SAML paths). So no user makes, reads or changes a provider: only the operator CLI does (rule 4). `sign-in/sso` takes only the body keys `email`, `providerId`, `callbackURL`, `errorCallbackURL` and `requestSignUp` (another key gives `400 BAD_BODY`) and allows 10 calls per 60 s per client address. The session lasts 30 days and renews after one day of use; the cookie has the prefix `ea`. The tenant is the oldest membership of the session user; the request never names it (`requireTenant`). A `401` from `/api` sends the browser to `/login`. The login and setup pages show a brand panel from `lg` (1024 px) up (the mark, the name, one line and one sentence, with keys `login_panel_title` and `login_panel_text`) and only the form below it, with the mark and the name above the title; the code step of the login keeps the panel. The forgot page is one card. The pages use the `split` and `card` frames of `Public.astro`.
4. **Login hardening** (the rules and their numbers are in `docs/architecture.md` §7 "Web security"; each one is in the code at the checked commit):
   - Lockout: 10 failed sign-ins in 15 minutes lock the user for 15 minutes (`auth-lockout.ts`); one lock mail per lock, at most 3 per UTC day; the audit row `web.login_locked`.
   - Leaked-password check: a password set or change asks the Have I Been Pwned range API (`pwned.ts`); it fails closed (`400 PASSWORD_COMPROMISED`, `503` when the API is down). `AUTH_PWNED_CHECK=off` turns it off (tests only).
   - Terms: a password set through a link needs `termsVersion` (`400 TERMS_REQUIRED`); every member sees the terms dialog once at the next sign-in; `POST /api/me/terms` records the acceptance (`409 terms_outdated` for an old version).
   - Session list: `GET /api/me/sessions` lists the live sessions of the member (device, address, last use), never the token; the Account card ends all sessions or all other sessions.
   - Reset by e-mail: open only when the four `AUTH_SMTP_*` keys and `AUTH_MAIL_FROM` are set (`resetRequestOpen`); otherwise `/forgot` says "Reset by e-mail is off" and the CLI prints the links. Reset requests are limited per client address by Better Auth (3 per 15 minutes) and per e-mail address by our own limit (3 per hour), and the `reset-password` and `change-password` routes by Better Auth (5 per 60 s).
   - Two-factor sign-in (F105, `platform/auth-two-factor.ts`): a member turns on TOTP in Settings → Account (password, QR code or key, first code) and gets 10 single-use backup codes once. Later sign-ins ask for a code after the password; the member can tick "Trust this device for 30 days". Turning TOTP on ends every older trusted device and every other session of the user. Turning it off needs a live session, the password and a code (F128): a current code from the app, or one unused backup code, which the request uses up. A new set of backup codes needs the same and makes the old ones useless. The body field is `code`; a missing code answers `400 TWO_FACTOR_CODE_REQUIRED`, a wrong one the plugin's `401 INVALID_CODE` or `INVALID_BACKUP_CODE`. The hook (`requireSecondFactorCode`) checks the password first, then the lock, then the code, through the plugin's own verify; each wrong code counts toward the same 10-code lock as the sign-in (`429 ACCOUNT_TEMPORARILY_LOCKED`). Every refusal writes `web.two_factor_refused` (`action`, `reason`; never the code). A user with TOTP off is not asked for a code. Limits: 5 wrong codes end one sign-in step, 10 failed codes lock the code step for 15 minutes (audit `web.two_factor_locked`), and 3 calls per 10 s per client address on `/two-factor/*`. A password reset does not skip the code. An operator needs TOTP (rule 8). The break-glass owner of an organization (one owner, set with `bun run org:break-glass`) cannot turn TOTP off (`403 BREAK_GLASS_NEEDS_TWO_FACTOR`). `bun run web:two-factor-reset --org-id <uuid> --user-id <uuid>` is the reset for a member who lost the phone and the codes: it ends the second factor, every session and trusted device of the user, and the break-glass mark.
   - Company sign-in (F119, ADR 0026 points 2–5 and 7; code in `platform/auth-sso.ts`, `modules/tenancy/sso-*.ts`). The login page sends `POST /api/auth/sign-in/sso` with the work e-mail; the plugin finds the provider by the e-mail domain and answers `{ url }` of the IdP (OIDC with PKCE, scopes `openid email profile`, no IdP-initiated sign-in). The IdP returns to `GET /api/auth/sso/callback/<providerId>`. The provider id is the organization id. Only the operator makes a provider (`bun run org:sso`, [tenancy-and-plans.md](tenancy-and-plans.md) rule 7). A provider signs nobody in until its domain is proved (a DNS TXT record, or the operator's attestation for a test organization) and the flag `sso_sign_in` is on for its organization (off by default).
   - Who gets in (`resolveSsoMember`). The callback never makes a user and never answers the plugin's `continue`, so `requestSignUp: true` makes no user either. It links an existing user whose oldest membership is the provider's organization. A first sign-in needs: `email_verified` not `false`; an IdP e-mail that ends with exactly the provider domain (a subdomain does not match); for Google (`https://accounts.google.com`) the claim `hd` equal to the domain; a user with that e-mail; and no other IdP subject already linked to that user for this provider. The link is a row in `auth_accounts` (provider id, IdP subject). Later sign-ins match the subject, so a changed IdP e-mail still works; the membership rule still holds. One user has one SSO identity. A refusal sends the browser to `/login?sso=failed&error=<code>` with no user, link or session; the codes are `no_provider`, `sso_off`, `domain_mismatch`, `email_unverified`, `not_a_member` and `identity_mismatch`. The plan of the organization is not read: a member of a `suspended` organization signs in like with a password, and the panel then refuses writes (rule 6).
   - Audit and logs. A sign-in writes `sso.login` (`provider_id`, `first_link`) after the plugin transaction committed, and the info line `sso_sign_in`. A refusal that names an organization writes `sso.refused` (`provider_id`, `code`; actor `system`) and the warn line `sso_refused`; a refusal with no provider writes no row. A failed audit write logs `sso_audit_failed` and does not stop the sign-in. A crash between the commit and the row can lose one `sso.login` row (accepted). No row, line, error or stdout holds the client secret, an IdP token, a code or the IdP e-mail. The plugin's own failures (a bad `state`) reach the log as `better_auth_log` with a fixed `reason`, for example `oauth_state_failed`.
   - The SSO session (`ssoSessionData`). A callback session has `auth_sessions.sign_in_method = 'sso'` and `sso_started_at` (the IdP sign-in time). It ends 12 hours after `sso_started_at`, also after a refresh: the trigger `auth_sessions_sso_cap` sets `expires_at` to at most `sso_started_at + 12 h` on every insert and update. The cookie keeps its 30-day `Max-Age`; the session row decides. A session made from an SSO session (turning TOTP on, `/change-password`) stays `sso` with the same start, so it ends at the same time. No IdP token is stored (the account hooks null `idToken`, `accessToken` and `refreshToken`). So an account that the IdP disables loses access within 12 hours at most; at once, the operator runs `org:member --end-sessions` ([tenancy-and-plans.md](tenancy-and-plans.md) rule 7).
   - No TOTP code after SSO (a default that the owner can still change, `docs/owner-decisions.md`). The IdP owns the second factor of an SSO user, so an SSO callback asks no code and writes no `web.login`. The operator console needs a password session (rule 8).
   - "SSO required" (ADR 0026 point 6; `organizations.sso_required`; only the operator sets it, `org:sso --require on`). A member of that organization who is not its break-glass owner with TOTP on gets the answer of a wrong password: `401 INVALID_EMAIL_OR_PASSWORD`, after the real password check, with no lockout count, no lock mail and no audit row, so a refused member cannot be told from a wrong password (`password_sign_in_refused_sso` info line, user id only). A user is refused when any of their organizations requires SSO and the user is not its break-glass owner with TOTP. A reset request of a refused member gets the generic answer, no mail and no token (`reset_request_refused_sso`). The session hook also refuses to make a password session for such a user (`password_session_refused_sso`), for `/sign-in/email` and `/two-factor/verify-totp`, so a sign-in or a two-factor challenge that passed the first check just before the operator's switch gets no session. `/reset-password` with a token still works; the sign-in stays refused. The flag `sso_sign_in` does not change this rule: with the flag off, SSO refuses (`sso_off`) and passwords stay refused, so only the break-glass owner gets in. Only `org:sso --require off`, a provider removal or a changed issuer, domain or client id reopens passwords. `org:flag … --flag sso_sign_in --off` and the operator flag route warn about it (`warning: "sso_required_on"`), and a start with `FEATURES_OFF=sso_sign_in` and at least one such organization logs `sso_flag_killed_with_sso_required` (`count`).
   - An SSO member has no password. `org:member --add` makes a user with no `credential` row in `auth_accounts`. A password comes only from the operator's `web:invite --user-id` link; Better Auth then creates the credential account (the public reset mail is refused, see below). In an organization that does not require SSO, that member can then sign in with the password (and TOTP, if they turn it on). The reset request refuses such a member: with no `credential` row and a membership in an organization that has an SSO provider row (`isSsoOnlyMember`, wired as `ssoOnlyMember` in `web.ts`), it gets the generic answer, no mail and no token (log line `reset_request_refused_sso`). Reason: a password from a public request would put the access outside the company's IdP, so a person who left the company would keep it. A member of an organization with no provider keeps the reset mail (an invite that was not used yet). The first `org:sso --set` of an organization (a new provider) deletes, in the same transaction, the open reset links of its members with no password account (`deleteResetLinksOfPasswordlessMembers`; an unused `web:invite` link goes too, so the operator makes a new one). The `web:invite --user-id` link still works, because the CLI handle has no such check. In an organization that requires SSO, the sign-in stays refused after such a reset.
5. **Invite.** `bun run org:invite --org-name <name> --email <email> --display-name <name> [--lang pl|en] [--timezone <tz>] [--trial-days N] [--print]` makes an organization with a `trial` plan (30 days by default) and its owner, then makes a 24 h setup link. `bun run web:invite --org-id <uuid> [--user-id <uuid>] [--print]` makes a setup or reset link for an existing member. With the auth-mail sender on and no `--print`, the link goes by mail; otherwise the command prints it. The link works once. The owner opens it on a device in the tailnet, accepts the terms and sets a password (`/setup`). The link never goes to a log.
6. **The `/api` guards** (`createApp`): one route is public, `GET /api/sign-in-options` (F119): it takes no input, answers `{ "sso": true | false }` with `Cache-Control: no-store`, and `true` means that some organization has a provider with a proved domain and the flag `sso_sign_in` on. The answer is the same for every caller and names no organization, domain or count; a failed read answers `false` and logs `sign_in_options_failed`. A suspended organization still counts. Every other `/api` route needs a session (`401 unauthorized`) and a tenant (`403 no_organization`). A write method needs an allowed `Origin` (`403 bad_origin`); the body limit is 64 KB (`413`). A route marked "owner" answers `403 owner_only` to a member (`requireOwner`). A write in an organization with the plan `suspended` answers `403 org_suspended`, except `POST /api/me/terms`, `PATCH /api/me/locale`, `DELETE /api/organization` (a paused account can still delete itself) and every `POST /api/operator/…` (`refuseSuspendedWrites`, `SUSPENDED_WRITE_ALLOW`); reads work. An unknown `/api` path answers `404 not_found`. A body that fails its schema answers `400 validation` with the details. `GET /api/openapi.json` (any member, behind the same session and tenant guards) answers the OpenAPI 3.1 file of the API (`openApiSpec` in `platform/openapi.ts`; the library is `hono-openapi`, which builds it from the `apiDoc` of each route; the file is built at the first request and kept). Every `/api` route is in it, or is hidden with a reason: the `/api/operator/*` routes and `/api/auth/*` (E10 publishes the file), the OAuth callback redirect and the file itself. The test `apps/server/src/openapi-routes.test.ts` builds the real app and fails for a route that is neither described nor hidden, so a new route needs its `apiDoc` in the same change (`docs/code-patterns.md` § HTTP routes, ADR 0023). The docs site publishes the file as `docs/api/openapi.json` (F121 stage 06; `bun run api:spec` writes it from the same app built with fakes in `apps/server/src/openapi-app.ts`, `bun run api:spec --check` exits 1 `openapi_drift` when it differs, and the unit test `apps/server/src/scripts/api-spec.test.ts` fails on a route change until the file is written again). The file holds no operator, auth or file path. The page `reference/api` of the docs site renders it; it stays held by `OWNER_REVIEW_PENDING` until the owner reads it.

Each pattern has a section in `src/dev/sections/` and a render test in `src/lib/`.

## Limits

- The one-click Unsubscribe button posts to the link of the newest trusted mail of the sender. One-click needs a verified DKIM signature of the sender domain that covers the `List-Unsubscribe` and `List-Unsubscribe-Post` headers; mail stored before that check is link-only until a newer mail arrives. See `trust.md` rule 21 and § Limits.
- The new pages (F102) are behind flags that are off by default (`approvals_page`, `delegation_pages`; remove-by 2027-03-01). A page shows its flag-off text when the API answers 404. The focus after a row moves was checked in Chromium only; no Playwright project runs Firefox or WebKit, and the phone project is Chromium emulation. The phone tab bar with five Polish labels is tight (not measured on a real phone).
- The urgency editor (F110, flag `urgency_editor`) is a card on the Rules page, and production triage does not read the profile yet ([trust.md](trust.md) rule 20 and § Limits). The Activity API item has the field `suspicious` (reason codes; `[]` while the flag `suspicious_mail` is off), but no page shows it ([triage.md](triage.md) rule 17).
- The sender line (F120, flag `sender_context`; [sender-context.md](sender-context.md) rule 11) is one line under the From line of the Activity detail and the Approvals summary. The Activity item and the approval answer have the key `sender` (a `SenderLine`: relation, counts, no address); the key is absent while the flag is off, and `null` when the sender has no profile, retention cleared the address, or the send is a follow-up. One profile read serves a whole page. The line is not in Telegram.
- The suggestions card (F120 stage 07, flag `sender_suggestions`; remove-by 2027-06-01) is on the Rules page above the newsletters card. Its Polish reasons use the impersonal past ("Odpowiedziano", "Oznaczono") like the rest of the panel. The card cannot know that the flag is off before it asks: with the flag off and N mailboxes it sends N list requests (one for each mailbox, one after the other as each 404 comes) and then no more; a 404 leaves only that mailbox out. Its e2e spec (`suggestions.spec.ts`) uses its own seeded organizations (`E2E Suggestions mobile|desktop`, with Sent coverage so the blocklist row survives the hourly profile pass); each test resets the rows first (`e2e-suggestions.ts`), so the order does not matter.
- The F110 pages and cards are behind flags that are off by default (`trust_ladder`, `panel_review`, `user_quiet_hours`, `report_mail`, `urgency_editor`, `bulk_unsubscribe`; remove-by 2027-03-01). The one-click button is tested at the API and in a unit test; the e2e spec shows the button but never taps it (a tap would make the e2e server resolve a seeded host). The e2e specs of the F110 pages check values, reload and axe in Chromium; review 18 notes that the quiet-hours and channel cards were not judged visually. The plan asked for an Opus review of the Polish text of stages 13, 14, 16, 18, 21 and 23; the ticket folder holds review files for 16, 18 and 21 (and 10 for the notices) only, so the Polish text of the autonomy card, the report page, the panel review and the Newsletters card has no review file.
- The block "New Telegram terms" (`NewTerms.tsx`) is in `TelegramLink`, so it shows on `/mailboxes` and in onboarding, not on the settings page. The Playwright specs of the page (`open-loops.spec.ts`) and of the Delegate action, the settings card and the terms (`loops-panel.spec.ts`) use their own seeded organizations (`E2E Loops mobile|desktop`).
- The panel has Polish texts for every key, and the activity phrases and AI lines follow the request language. The delete dialog and its login notice (`del_*` keys, F106) are in [account-data.md](account-data.md) rule 5. Operator pages and legal texts have their own tickets (E7-T4).
- No live updates: Activity and `/api/me` poll every 30 s while the tab is visible, the Telegram card every 5 s while a link waits (F055-web-live-updates).
- Two-factor sign-in has TOTP and backup codes only: no e-mail or SMS codes, no passkeys (ADR 0026). The panel has no page to choose the break-glass owner (only `org:break-glass`). A TOTP code works again inside its window (no replay guard, accepted).
- Company sign-in (F119) is OIDC only: no SAML, no SCIM, no just-in-time accounts (a person must be a member first, `org:member --add`), one provider and one domain per organization (a subdomain e-mail is refused), no panel page for providers or members (the console block is read-only; the operator uses the CLIs). The operator ends member sessions on the owner's request (`org:member --end-sessions`); the panel has no such button. The SSO session cap is 12 hours, and an account that the IdP disables loses access when that time ends. An SSO sign-in asks no TOTP code, and the operator console refuses an SSO session (rule 4, rule 8). The public reset request refuses an SSO-only member with the generic answer; only the operator's `web:invite --user-id` gives such a member a password (rule 4). The client secret is stored in clear (`docs/owner-decisions.md`). A DNS change between the discovery check and the fetch is accepted. Google Workspace runs on the same code but has no real check yet; the real end-to-end check is one Microsoft Entra test tenant (owner step, F119 stage 16).
- No Playwright spec covers company sign-in (a decision of the plan; the integration tests drive the callback against a fake IdP, `apps/server/test/fake-oidc.ts`). The e2e seed makes no provider, so `/api/sign-in-options` answers `{ "sso": false }` there: the axe check of `/login` (`apps/web/e2e/tests/auth.spec.ts`) and of `/settings` (`apps/web/e2e/tests/account.spec.ts`) never sees the company sign-in block or the Account card of a member with no password. No e2e spec opens `/operator`, so the console block has no axe check either. The unit tests of `apps/web/src/lib` check the label, `autocomplete`, `role=alert` and the focus request of the company sign-in form on rendered markup and form state; no test runs the focus effect in a browser, and nobody reviewed browser frames of the new blocks.
- The OpenAPI file has no API version (`info.version` is `"0"`, ADR 0023 point 5) and no client is generated from it. It lists no operator route and no `/api/auth/*` path (E10 publishes the file). The route test checks that every route is described or hidden with a reason, that each operation has its own `operationId` and a 2xx JSON schema (or 204); it does not compare a schema with what the route really answers.
- The legal pages, the registries behind them and the cost model are in [papers.md](papers.md).
- The legal pages have a fixed frame and draft texts for the privacy policy, the terms and the DPA (F107 stages 03 and 04). Open facts are visible placeholders (`legalPlaceholders` in `apps/web/src/lib/legal.ts`, or `<to confirm: …>`). `TERMS_VERSION` stays until the bump of stage 06. The panel can delete the organization (flag `org_delete`) but has no export and no page for data requests: the operator runs `org:export` and `org:dsr` (F106, PD-038).
- The operator console shows ids, codes, counts and dates only and has no billing (PD-047). The operator needs TOTP (rule 8).
- A user belongs to the oldest of their memberships; the panel has no organization switcher.
- The phone channel (F118) is behind two flags that are off by default: `web_push` (the phone notices card, the routes card, the device API) and `telegram_minimal` (the Telegram detail choice and the lock card). With a flag off, the cards are absent, the panel sends no request to the routes of that flag, and the routes answer 404 ([digest-and-notices.md](digest-and-notices.md) rules 3c to 3f). The service worker and the manifest do not depend on a flag: every page registers the worker.
- The "(default)" mark of a route select (rule 17) cannot tell a stored value from the default, and a member cannot pin the value that is the default now: Save drops it, so the select keeps following the default. This is kept as designed (D7 of F118); say so in the help text if the owner wants a pin.
- A push needs the browser to reach its push service (FCM for Chrome); the phone needs Tailscale to open the panel, but the push arrives without it. iOS shows a push only for a panel on the Home Screen (iOS 16.4 or later) and is not tested. A session that ends stops the notices of its device until the next panel load re-binds it.

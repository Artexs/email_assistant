# Web panel

> Checked against the code at `d331192b`, 2026-11-15.

## What it does now

The web panel is a static Astro build with one React island per page (`apps/web`). The server serves it from `WEB_DIST` and answers the JSON API under `/api` from the same process (`apps/server/src/web.ts`, `apps/server/src/platform/http.ts`). A user signs in with an e-mail and a password (Better Auth, 12 to 128 characters), or with the company account of the organization when the operator set up company sign-in (OIDC, rule 4), gets a session cookie, and reaches ten pages: Onboarding, Activity, Mailboxes, Settings and Rules after sign-in, Stats (only while the flag `stats_page` is on) and Operator (only for an operator), and Login, Setup and Forgot before it, plus the legal stubs. The panel connects and manages mailboxes, shows what the system did to each mail with Undo and feedback buttons, sets the mode, the switches, the category policy, the sync folders, the card "Sent mail" (the switch "Track my sent mail", a status line and the off note; it shows only while the flag `sent_sync` is on, or the switch is on and the flag is off: then it says "paused" and the switch can only go off; [sent-mail.md](sent-mail.md) rule 16), the digest times, the time zone and the signature, manages the sender rules, links Telegram, and lists the live sessions. The panel is reachable only through Tailscale Serve on the tailnet of the owner. It is off while `WEB_BASE_URL` is empty. An operator (a user in `OPERATOR_USER_IDS`) has one route that reads across organizations. The panel has no approvals, delegates or delegations page: those stay in Telegram.

## Rules

1. **The web is on only with `WEB_BASE_URL`.** An empty value logs the event `web_off` and the server serves `/health` only. The config check needs `WEB_AUTH_SECRET` (at least 32 characters) when `WEB_BASE_URL` is set. The server listens on `127.0.0.1:8080`; Tailscale Serve adds HTTPS (`deploy/README.md` § Web panel, ADR 0017). The panel is never reached by another path.
2. **Pages and the session.** Every page except `/login`, `/setup`, `/forgot`, `/legal/<pl|en>/<privacy|terms|dpa>`, `/404.html` and the static assets (`PUBLIC_PAGE_PATHS`) redirects to `/login?next=<path>` without a session. `/` redirects to `/activity` when the onboarding checklist is done and to `/onboarding` when it is not (`homePathOf`). A page that is not in the build answers the `404.html` page. When `WEB_DIST` has no build, every page answers `503` "The web build is missing. Run bun run web:build.".
3. **Sign-in.** The client calls Better Auth under `/api/auth/*`, and only these paths reach it (`AUTH_ALLOWED_PATHS`): `sign-in/email`, `sign-out`, `get-session`, `reset-password` (POST, and GET `reset-password/<token>`), `change-password`, `revoke-other-sessions`, `revoke-sessions`, the five two-factor paths `two-factor/enable`, `two-factor/disable`, `two-factor/verify-totp`, `two-factor/verify-backup-code` and `two-factor/generate-backup-codes`, `request-password-reset` (POST) when the auth-mail sender is on, and the two paths of the SSO plugin (F119, `isAllowedSsoPath`): `sign-in/sso` (POST) and `sso/callback/<providerId>` (GET; one id, no `/`). Every other path answers `404`: also `two-factor/get-totp-uri`, `two-factor/send-otp` and `two-factor/verify-otp`, and every other plugin path (`sso/register`, `sso/providers`, `sso/get-provider`, `sso/update-provider`, `sso/delete-provider`, the domain-proof paths, `sso/callback` without a provider id and the SAML paths). So no user makes, reads or changes a provider: only the operator CLI does (rule 4). `sign-in/sso` takes only the body keys `email`, `providerId`, `callbackURL`, `errorCallbackURL` and `requestSignUp` (another key gives `400 BAD_BODY`) and allows 10 calls per 60 s per client address. The session lasts 30 days and renews after one day of use; the cookie has the prefix `ea`. The tenant is the oldest membership of the session user; the request never names it (`requireTenant`). A `401` from `/api` sends the browser to `/login`.
4. **Login hardening** (the rules and their numbers are in `docs/architecture.md` §7 "Web security"; each one is in the code at the checked commit):
   - Lockout: 10 failed sign-ins in 15 minutes lock the user for 15 minutes (`auth-lockout.ts`); one lock mail per lock, at most 3 per UTC day; the audit row `web.login_locked`.
   - Leaked-password check: a password set or change asks the Have I Been Pwned range API (`pwned.ts`); it fails closed (`400 PASSWORD_COMPROMISED`, `503` when the API is down). `AUTH_PWNED_CHECK=off` turns it off (tests only).
   - Terms: a password set through a link needs `termsVersion` (`400 TERMS_REQUIRED`); every member sees the terms dialog once at the next sign-in; `POST /api/me/terms` records the acceptance (`409 terms_outdated` for an old version).
   - Session list: `GET /api/me/sessions` lists the live sessions of the member (device, address, last use), never the token; the Account card ends all sessions or all other sessions.
   - Reset by e-mail: open only when the four `AUTH_SMTP_*` keys and `AUTH_MAIL_FROM` are set (`resetRequestOpen`); otherwise `/forgot` says "Reset by e-mail is off" and the CLI prints the links. Reset requests are limited per client address by Better Auth (3 per 15 minutes) and per e-mail address by our own limit (3 per hour), and the `reset-password` and `change-password` routes by Better Auth (5 per 60 s).
   - Two-factor sign-in (F105, `platform/auth-two-factor.ts`): a member turns on TOTP in Settings → Account (password, QR code or key, first code) and gets 10 single-use backup codes once. Later sign-ins ask for a code after the password; the member can tick "Trust this device for 30 days". Turning TOTP on ends every older trusted device and every other session of the user. Turning it off needs a live session, the password and a code (F128): a current code from the app, or one unused backup code, which the request uses up. A new set of backup codes needs the same and makes the old ones useless. The body field is `code`; a missing code answers `400 TWO_FACTOR_CODE_REQUIRED`, a wrong one the plugin's `401 INVALID_CODE` or `INVALID_BACKUP_CODE`. The hook (`requireSecondFactorCode`) checks the password first, then the lock, then the code, through the plugin's own verify; each wrong code counts toward the same 10-code lock as the sign-in (`429 ACCOUNT_TEMPORARILY_LOCKED`). Every refusal writes `web.two_factor_refused` (`action`, `reason`; never the code). A user with TOTP off is not asked for a code. Limits: 5 wrong codes end one sign-in step, 10 failed codes lock the code step for 15 minutes (audit `web.two_factor_locked`), and 3 calls per 10 s per client address on `/two-factor/*`. A password reset does not skip the code. An operator needs TOTP (rule 8). The break-glass owner of an organization (one owner, set with `bun run org:break-glass`) cannot turn TOTP off (`403 BREAK_GLASS_NEEDS_TWO_FACTOR`). `bun run web:two-factor-reset --org-id <uuid> --user-id <uuid>` is the reset for a member who lost the phone and the codes: it ends the second factor, every session and trusted device of the user, and the break-glass mark.
   - Company sign-in (F119, ADR 0026 points 2–5 and 7; code in `platform/auth-sso.ts`, `modules/tenancy/sso-*.ts`). The login page sends `POST /api/auth/sign-in/sso` with the work e-mail; the plugin finds the provider by the e-mail domain and answers `{ url }` of the IdP (OIDC with PKCE, scopes `openid email profile`, no IdP-initiated sign-in). The IdP returns to `GET /api/auth/sso/callback/<providerId>`. The provider id is the organization id. Only the operator makes a provider (`bun run org:sso`, [tenancy-and-plans.md](tenancy-and-plans.md) rule 7). A provider signs nobody in until its domain is proved (a DNS TXT record, or the operator's attestation for a test organization) and the flag `sso_sign_in` is on for its organization (off by default).
   - Who gets in (`resolveSsoMember`). The callback never makes a user and never answers the plugin's `continue`, so `requestSignUp: true` makes no user either. It links an existing user whose oldest membership is the provider's organization. A first sign-in needs: `email_verified` not `false`; an IdP e-mail that ends with exactly the provider domain (a subdomain does not match); for Google (`https://accounts.google.com`) the claim `hd` equal to the domain; a user with that e-mail; and no other IdP subject already linked to that user for this provider. The link is a row in `auth_accounts` (provider id, IdP subject). Later sign-ins match the subject, so a changed IdP e-mail still works; the membership rule still holds. One user has one SSO identity. A refusal sends the browser to `/login?sso=failed&error=<code>` with no user, link or session; the codes are `no_provider`, `sso_off`, `domain_mismatch`, `email_unverified`, `not_a_member` and `identity_mismatch`. The plan of the organization is not read: a member of a `suspended` organization signs in like with a password, and the panel then refuses writes (rule 6).
   - Audit and logs. A sign-in writes `sso.login` (`provider_id`, `first_link`) after the plugin transaction committed, and the info line `sso_sign_in`. A refusal that names an organization writes `sso.refused` (`provider_id`, `code`; actor `system`) and the warn line `sso_refused`; a refusal with no provider writes no row. A failed audit write logs `sso_audit_failed` and does not stop the sign-in. A crash between the commit and the row can lose one `sso.login` row (accepted). No row, line, error or stdout holds the client secret, an IdP token, a code or the IdP e-mail. The plugin's own failures (a bad `state`) reach the log as `better_auth_log` with a fixed `reason`, for example `oauth_state_failed`.
   - The SSO session (`ssoSessionData`). A callback session has `auth_sessions.sign_in_method = 'sso'` and `sso_started_at` (the IdP sign-in time). It ends 12 hours after `sso_started_at`, also after a refresh: the trigger `auth_sessions_sso_cap` sets `expires_at` to at most `sso_started_at + 12 h` on every insert and update. The cookie keeps its 30-day `Max-Age`; the session row decides. A session made from an SSO session (turning TOTP on, `/change-password`) stays `sso` with the same start, so it ends at the same time. No IdP token is stored (the account hooks null `idToken`, `accessToken` and `refreshToken`). So an account that the IdP disables loses access within 12 hours at most; at once, the operator runs `org:member --end-sessions` ([tenancy-and-plans.md](tenancy-and-plans.md) rule 7).
   - No TOTP code after SSO (a default that the owner can still change, `docs/owner-decisions.md`). The IdP owns the second factor of an SSO user, so an SSO callback asks no code and writes no `web.login`. The operator console needs a password session (rule 8).
   - "SSO required" (ADR 0026 point 6; `organizations.sso_required`; only the operator sets it, `org:sso --require on`). A member of that organization who is not its break-glass owner with TOTP on gets the answer of a wrong password: `401 INVALID_EMAIL_OR_PASSWORD`, after the real password check, with no lockout count, no lock mail and no audit row, so a refused member cannot be told from a wrong password (`password_sign_in_refused_sso` info line, user id only). A user is refused when any of their organizations requires SSO and the user is not its break-glass owner with TOTP. A reset request of a refused member gets the generic answer, no mail and no token (`reset_request_refused_sso`). The session hook also refuses to make a password session for such a user (`password_session_refused_sso`), for `/sign-in/email` and `/two-factor/verify-totp`, so a sign-in or a two-factor challenge that passed the first check just before the operator's switch gets no session. `/reset-password` with a token still works; the sign-in stays refused. The flag `sso_sign_in` does not change this rule: with the flag off, SSO refuses (`sso_off`) and passwords stay refused, so only the break-glass owner gets in. Only `org:sso --require off`, a provider removal or a changed issuer, domain or client id reopens passwords. `org:flag … --flag sso_sign_in --off` and the operator flag route warn about it (`warning: "sso_required_on"`), and a start with `FEATURES_OFF=sso_sign_in` and at least one such organization logs `sso_flag_killed_with_sso_required` (`count`).
   - An SSO member has no password. `org:member --add` makes a user with no `credential` row in `auth_accounts`. A password can still come from a reset link: the reset mail (when `request-password-reset` is open, rule 3) or `web:invite --user-id`; Better Auth then creates the credential account. In an organization that does not require SSO, that member can then sign in with the password (and TOTP, if they turn it on). No code refuses such a reset (a default that the owner can still change). In an organization that requires SSO, the sign-in stays refused.
5. **Invite.** `bun run org:invite --org-name <name> --email <email> --display-name <name> [--lang pl|en] [--timezone <tz>] [--trial-days N] [--print]` makes an organization with a `trial` plan (30 days by default) and its owner, then makes a 24 h setup link. `bun run web:invite --org-id <uuid> [--user-id <uuid>] [--print]` makes a setup or reset link for an existing member. With the auth-mail sender on and no `--print`, the link goes by mail; otherwise the command prints it. The link works once. The owner opens it on a device in the tailnet, accepts the terms and sets a password (`/setup`). The link never goes to a log.
6. **The `/api` guards** (`createApp`): one route is public, `GET /api/sign-in-options` (F119): it takes no input, answers `{ "sso": true | false }` with `Cache-Control: no-store`, and `true` means that some organization has a provider with a proved domain and the flag `sso_sign_in` on. The answer is the same for every caller and names no organization, domain or count; a failed read answers `false` and logs `sign_in_options_failed`. A suspended organization still counts. Every other `/api` route needs a session (`401 unauthorized`) and a tenant (`403 no_organization`). A write method needs an allowed `Origin` (`403 bad_origin`); the body limit is 64 KB (`413`). A route marked "owner" answers `403 owner_only` to a member (`requireOwner`). A write in an organization with the plan `suspended` answers `403 org_suspended`, except `POST /api/me/terms`, `PATCH /api/me/locale`, `DELETE /api/organization` (a paused account can still delete itself) and every `POST /api/operator/…` (`refuseSuspendedWrites`, `SUSPENDED_WRITE_ALLOW`); reads work. An unknown `/api` path answers `404 not_found`. A body that fails its schema answers `400 validation` with the details.

8. **The operator route.** Every path under `/api/operator` answers a user who is not in `OPERATOR_USER_IDS` with `404 not_found` and a log line with the user id (`requireOperator`). `OPERATOR_USER_IDS` is an env list of user ids; a DB write cannot make an operator (ADR 0027). The routes are `GET /api/operator/flags` (the feature flags of every organization), `GET /api/operator/orgs` (the organization list), `GET /api/operator/orgs/:orgId` (one organization), `GET /api/operator/notices?days=` (the operator notices) and two writes, `POST /api/operator/orgs/:orgId/plan` and `POST /api/operator/orgs/:orgId/flags`. A write calls the same function as `org:plan` or `org:flag`, writes the same audit row into that organization with the operator's user id as actor, and works while the operator's own organization is `suspended`. A path id that is not a UUID answers `404`. An operator with an SSO session gets `403 password_sign_in_required` on every `/api/operator/*` route and an `operator_sso_session_refused` warn line with the user id (F119; the check comes after the operator check and before the TOTP check); the `/operator` page answers them the 404 page. An operator without TOTP gets `403 two_factor_required` on every `/api/operator/*` route, reads and writes, and a `operator_two_factor_required` warn line with the user id; `/operator` redirects them to `/settings?two_factor=required`. `GET /api/operator/orgs/:orgId` holds `sso`: `null`, or `{ domain, proof, required, linkedMembers, breakGlassReady }` (`proof` is `dns`, `attested` or `null`); it holds no issuer, client id, secret or member id. `POST /api/operator/orgs/:orgId/flags` adds `warning: "sso_required_on"` to its answer when it turns `sso_sign_in` off in an organization that requires SSO. The data holds ids, codes, counts and dates only. `docs/architecture.md` §7 "Operator" has the rule.

10. **The static build.** `bun run web:build` writes the folder `dist` in `apps/web` (Astro 7.4 static build with React islands, `output: "static"`, a meta CSP on every page). The server serves it with `serveStatic` from `WEB_DIST` (default `WEB_DIST=apps/web/dist`): files under `/_astro/` are cached for a year, every other file has `private, no-store`. `bun run web:dev` runs the dev server and proxies `/api` to `127.0.0.1:8080`. The container image runs `bun run web:build` and sets `WEB_DIST=/app/apps/web/dist` (`deploy/Dockerfile`; `deploy/README.md` § Web panel).
11. **Texts.** Every visible text is a key in `apps/web/src/i18n/en.ts` (English) and in `apps/web/src/i18n/pl.ts` (Polish; a missing or extra key fails `bun run typecheck`). Plural texts are in `enPlurals` and `plPlurals` (Polish has one, few and many). The panel language is `users.locale` (`pl` or `en`) once `/api/me` answers, else the stored browser choice, else the browser language (`apps/web/src/i18n/index.ts`). The Account card writes it with `PATCH /api/me/locale` (any member; also allowed for a paused organization; no audit row) and the panel switches at once, keeping typed form state; every sign-in on any device takes the stored choice. The choice has no "browser language" option, so a null value cannot be set again. `apps/web/src/i18n/i18n.test.ts` checks the placeholders and the plural forms; `en.test.ts` checks the keys of the core schemas. The browser calls the API through `api()` in `apps/web/src/lib/api.ts`, which parses each answer with a Zod schema from `@ea/core/web`.
12. **The language of the panel.** The panel language is `users.locale`, else the browser language. The Account card sets `users.locale` (`PATCH /api/me/locale`). `GET /api/activity` renders the AI line and the action phrases in the same language: `users.locale`, else the first tag of the `Accept-Language` header, else English (`resolveLocale`, `firstLanguageTag`). No other route returns phrases of ours. Each activity item has `suspicious`, the codes of the suspicious-mail rules of the newest result (`[]` while the flag `suspicious_mail` is off); the panel row that shows it comes with E4. Every island is `client:only="react"` and calls `useLocale()` on its first line (`docs/code-patterns.md` § Texts carry a locale).
13. **Telegram consent.** A Telegram link needs the consent of version `TELEGRAM_CONSENT_VERSION`: the link block shows the consent text and a tick, and `POST /api/channels/telegram/link` refuses an old or missing version (rule 7). Change the content that goes to Telegram: bump the version. A linked user confirms a new version with `POST /api/telegram/consent`; the loop senders read it (`consentCovers`, [digest-and-notices.md](digest-and-notices.md) rule 1).

## Data

- Better Auth tables: `users` (with `locale`, `terms_version`, `terms_accepted_at`), `auth_sessions`, `auth_accounts`, `auth_verifications` (reset and invite tokens; deleted 1 day after `expires_at`), `auth_lockouts` (`failed_count`, `locked_until`, the lock mails of the day), `auth_two_factors` (the TOTP secret and the backup codes, encrypted by Better Auth with `WEB_AUTH_SECRET`; `verified`, `failed_verification_count`, `locked_until`) and `users.two_factor_enabled`. The full list is in `docs/architecture.md` §5.
- Company sign-in (F119, migration `db/migrations/20261114170001_sso.sql`): `sso_providers` (one row per organization and one per domain: `provider_id` = the organization id, `issuer`, `domain`, `domain_verified` and `domain_proof` `dns` or `attested`, `oidc_config`; RLS `tenant_rows`); `organizations.sso_required`; `auth_sessions.sign_in_method` (`password` or `sso`) and `sso_started_at`, with the pair CHECK and the trigger `auth_sessions_sso_cap`; the SSO links are `auth_accounts` rows whose `provider_id` is the organization id. `oidc_config` is the plugin JSON and holds the client secret in clear (a default that the owner can still change, `docs/owner-decisions.md`); the export leaves it out ([account-data.md](account-data.md) rule 6) and no read path returns it.
- `memberships` (the role, `digest_times` and `break_glass`) give the tenant and the role of a session; `break_glass` marks at most one owner per organization (F105); `organizations` hold `plan`, `trial_ends_at`, `timezone` and `style_text` (the signature).
- Audit events of the web: `web.login`, `web.password_set`, `web.password_changed`, `web.login_locked`, `web.terms_accepted`, `web.telegram_consent`, `web.sessions_revoked`, `web.other_sessions_revoked`, `web.two_factor_enabled`, `web.two_factor_disabled`, `web.two_factor_reset`, `web.backup_codes_generated`, `web.backup_code_used`, `web.two_factor_locked`, `web.two_factor_refused`, `org.break_glass_set`, `org.break_glass_cleared` (`web.login` has the field `second_factor`), the SSO events `sso.login`, `sso.refused`, `sso.provider_set`, `sso.provider_removed`, `sso.domain_verified`, `sso.domain_attested`, `sso.required_changed`, `sso.unlinked`, `org.member_added` and `web.member_sessions_ended` (F119; each shows in the security log, `securityEvents` in `packages/core/src/security-log.ts`), `org.exported`, `org.delete_refused`, `dsr.find`, `dsr.erase` (F106; the last four show in the security log, [account-data.md](account-data.md) rule 16), `onboarding.mode_kept`; each write route of the groups of rule 7 writes the audit rows of its capability.

## Limits

- No approvals, delegates or delegations page: E4-A (F102).
- No urgency editor: the route `PUT /api/settings/:mailboxId/urgency` and `bun run mailbox:settings urgency` exist (F109) and E4-B (F110) builds the editor. The Activity API item has the field `suspicious` (reason codes; `[]` while the flag `suspicious_mail` is off), but no page shows it ([triage.md](triage.md) rule 17).
- The panel has Polish texts for every key, and the activity phrases and AI lines follow the request language. The delete dialog and its login notice (`del_*` keys, F106) are in [account-data.md](account-data.md) rule 5. Operator pages and legal texts have their own tickets (E7-T4).
- No live updates: Activity and `/api/me` poll every 30 s while the tab is visible, the Telegram card every 5 s while a link waits (F055-web-live-updates).
- Two-factor sign-in has TOTP and backup codes only: no e-mail or SMS codes, no passkeys (ADR 0026). The panel has no page to choose the break-glass owner (only `org:break-glass`). A TOTP code works again inside its window (no replay guard, accepted).
- Company sign-in (F119) is OIDC only: no SAML, no SCIM, no just-in-time accounts (a person must be a member first, `org:member --add`), one provider and one domain per organization (a subdomain e-mail is refused), no panel page for providers or members (the console block is read-only; the operator uses the CLIs). The operator ends member sessions on the owner's request (`org:member --end-sessions`); the panel has no such button. The SSO session cap is 12 hours, and an account that the IdP disables loses access when that time ends. An SSO sign-in asks no TOTP code, and the operator console refuses an SSO session (rule 4, rule 8). No password reset is refused for an SSO member (rule 4). The client secret is stored in clear (`docs/owner-decisions.md`). A DNS change between the discovery check and the fetch is accepted. Google Workspace runs on the same code but has no real check yet; the real end-to-end check is one Microsoft Entra test tenant (owner step, F119 stage 16).
- No Playwright spec covers company sign-in (a decision of the plan; the integration tests drive the callback against a fake IdP, `apps/server/test/fake-oidc.ts`). The e2e seed makes no provider, so `/api/sign-in-options` answers `{ "sso": false }` there: the axe check of `/login` (`apps/web/e2e/tests/auth.spec.ts`) and of `/settings` (`apps/web/e2e/tests/account.spec.ts`) never sees the company sign-in block or the Account card of a member with no password. No e2e spec opens `/operator`, so the console block has no axe check either. The unit tests of `apps/web/src/lib` check the label, `autocomplete`, `role=alert` and the focus request of the company sign-in form on rendered markup and form state; no test runs the focus effect in a browser, and nobody reviewed browser frames of the new blocks.
- The API has no OpenAPI description yet (ADR 0023 proposed, E4-A F102).
- The legal pages are draft stubs until the papers of E7-T4 (F107). The panel can delete the organization (flag `org_delete`) but has no export and no page for data requests: the operator runs `org:export` and `org:dsr` (F106, PD-038).
- The operator console shows ids, codes, counts and dates only and has no billing (PD-047). The operator needs TOTP (rule 8).
- A user belongs to the oldest of their memberships; the panel has no organization switcher.

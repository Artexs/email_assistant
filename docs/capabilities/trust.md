# Trust ladder

> Checked against the code at `5ba3e0bc`, 2026-11-18.

## What it does now

The trust ladder lets a mailbox earn automatic moves (`auto`) per category without labelling mail (ADR 0028). Four sources decide. The global holdout evidence (the gate files in the image) says whether a category is proven for the running model, prompt and endpoint. A history check of the last 30 days of INBOX, which starts at connect with no user step, can only block. A tripwire pauses a category that the user corrects. A re-gate keeps every `auto` tied to the model setup that earned it. The panel shows the result as a report page with one "Turn on recommended" tap, an autonomy card with three evidence lines, and an optional "Check 10 decisions" page. The same ticket adds the digest and the trust reports as mail in the member's own INBOX (ADR 0022), quiet hours per member, why lines in the digest, the urgent notice and Activity, a spam review line, an urgency card, and a Newsletters list with one-click unsubscribe. Eight feature flags (epic `E4-B`, default off, remove-by 2027-03-01) gate everything except the grant and the re-gate (rules 5, 9 and 22). The product rules are in `spec/features/active/F110-e4-b-earn-trust/plan.md` (P1 to P9, D1 to D17); this page states what the code does at the checked commit.

## Rules

1. **Evidence for `auto` (flag `trust_ladder`).** `autoEvidence` (`packages/core/src/trust/evidence.ts`) turns the three sources and the trip state into `{ eligible, recommended, blocks }`. A block is one of `no_global`, `global_no_go`, `global_provisional`, `history_fail`, `tripped`, `real_labels_no_go`. The rules: no gate file for the running key is `no_global`; a final `no-go` or `too-few` file is `global_no_go`; a `provisional` file (the owner audit is pending) is `global_provisional`, so it shows on the card but proves nothing; a history result `fail` is `history_fail`; an active trip is `tripped`; real labels block only at 30 or more labels with a `no-go` decision (`EVIDENCE_MIN_LABELS`). `eligible` means no block except `tripped` (a deliberate manual switch may clear a trip). `recommended` means no block at all and a moving category (`movingCategories`: `info`, `notification`, `spam`; `urgent` and `needs_reply` keep the Settings switch because their `auto` only rescues junk-folder mail). Test: `packages/core/src/trust/evidence.test.ts`.
2. **The global evidence is a file, matched by key.** `loadGateEvidence` reads the gate files of `evals/results/gate` once at start; `runningEvidenceKey` builds the key of the running classifier (provider, model, reasoning effort, prompt version and parts, endpoint, host for `own`); `globalEvidenceFor` picks per category the non-provisional file first, then the newest date, then the name (`apps/server/src/modules/triage/evidence.ts`; `sameKey` in `packages/core/src/trust/key.ts`). The image holds the gate files (`GATE_EVIDENCE_DIR` overrides the folder, used by the e2e fixture). At the checked commit the only file of the running key (`evals/results/gate/classifier-classifier-v2-gpt-6-luna-none-lab-01-v1.json`) has `provisional: true` and `audit: pending`; it says `go` for `info` and `no-go` for `notification`, `spam`, `urgent` and `needs_reply`. So no category is eligible or recommended until the owner audit is applied and a better file lands (owner decision 2026-11-15). Tests: `apps/server/src/modules/triage/evidence.test.ts`, `apps/server/src/modules/triage/gate-evidence.test.ts`.
3. **History outcome (D4).** `historyOutcome` (`packages/core/src/trust/history.ts`) takes `acted` (mails of the sample that the user acted on) and `moved` (those the category would have moved). Under `HISTORY_MIN_ACTED` (50) it is `no_result`; a Wilson 95 % upper bound of at most `HISTORY_PASS_UPPER` (2 %) is `pass`; an observed share above `HISTORY_FAIL_SHARE` (2 %) is `fail`; the rest is `inconclusive`. Only `fail` blocks. Reason (owner decision 2026-11-15, `spec/features/active/F110-e4-b-earn-trust/questions.md` Q2): with zero hidden mails the bound needs 189 acted-on mails, so a strict pass would block most mailboxes, against the owner rule that user signals only block.
4. **Acted-on mail (D6).** A mail counts as acted on when `email_flags` has `\Answered` or `\Flagged`, or when feedback gives the true category `urgent` or `needs_reply` (`historyActedOn`, `apps/server/src/modules/trust/acted-on.ts`; the Sent folder joins here when E5a lands).
5. **The grant ties `auto` to the running key (F110 stage 04).** Every `auto` on stores `category_policy[category].grant = { key, by, at }`: the `EvidenceKey` of the running classifier (model, provider, effort, prompt version and parts, endpoint, host for `own`), who granted it (`evidence`, `forced`, `real_labels`, `recommended`, `regate` or `legacy`) and when. `auto: false` removes the grant. The triage worker gets the running key from the composition root (`createTriageJob({ runningKey })`) and reads `effectiveAutoFor`: `auto` counts only when the grant key equals the running key (a different `endpoint` alone is a mismatch). A mismatch is `auto` off at once: the `move` and `mark_read` rows are `logged`, with no job in between. A row with no grant (set before F110) counts as matching. The settings view still shows `auto` as stored; the re-gate (rule 9) stamps or pauses the old rows.
6. **The evidence gate (flag `trust_ladder`, epic `E4-B`).** With the flag on for the organization, `PATCH /api/settings/:mailboxId/auto/:category` and `bun run mailbox:settings auto` call `setCategoryAutoWithEvidence` (`trust/gate.ts`, chosen by `autoSetter` in the composition root). It reads the global evidence of the running key (`globalEvidenceFor`), the last history result, the active trips and the real labels, and calls `autoEvidence`. Eligible → `auto` on, grant `evidence`, threshold from the gate file when it has one. Not eligible → 409 `no_go` with `gate` and `blocks`; `force` sets it anyway with grant `forced`, and the audit row keeps `forced: true` and the block list. An active trip never refuses. Turning `auto` on clears the active trips of the category in the same transaction as the policy row and its audit row. `auto: false` reads no evidence. With the flag off the real-label gate stays; it also writes the grant (`real_labels`, or `forced` with force) and clears the trips. The CLI and the web build the gate files and the running key in one place (`gateEvidenceOf`), so neither is stricter.
7. **The history check starts at connect and runs as a job (flag `trust_ladder`).** The connect paths (`mailbox:connect`, the web connect and the OAuth connect) pass `queueHistoryCheckOnConnect` (`apps/server/src/modules/trust/connect-hook.ts`) as `onConnected`; after the commit it queues a check with the reason `connect` only when the flag is on and the organization is not suspended, and a failure logs `connect_hook_failed` and never fails the connect. The job `trust.history` (`createHistoryJob`, `apps/server/src/modules/trust/history-job.ts`) runs every 15 s, only when `TRIAGE_LLM_SCOPE` is not `off`, and the shutdown waits for it; it also queues a `flag_on` check for each active mailbox of a flag-on organization that never had a check (`queueFlagOnCheck`; a mailbox that had one gets no second by this path). `bun run trust:history-check --org-id <uuid> --mailbox-id <uuid>` queues a `cli` check (it ignores the flag, refuses a suspended organization and an unknown mailbox); `POST /api/trust/:mailboxId/history-check` queues a `web` check (rule 11). One check per mailbox is open at a time (the partial unique index `history_checks_open_key`). A check goes `queued` → `backfilling` → `waiting_flags` → `classifying` → `done` or `no_result`; `done` and `no_result` are written together with `finished_at`. **Gates** before every step: a suspended organization waits 5 min with no attempt; `trust_ladder` off waits (the `cli` reason ignores it); a `paused` or `host_blocked` mailbox waits 5 min (it keeps its check open until it is active again); an `auth_error` mailbox ends `no_result` / `auth_refused`. **Backfill:** `backfillMailbox` with the purpose `history` (`apps/server/src/modules/mail/tools.ts`, `backfillInbox` in `apps/server/src/modules/mail/sync-backfill.ts`) reads INBOX of the last 30 days (`HISTORY_WINDOW_DAYS`) and stores the mail as `skipped` / `history_check`: inserts only (no `update_uid`, `returned` or `relocated` write), only mail with `uid <= folder.last_uid` (newer mail belongs to the normal sync, review 5 B1), no digest line, no action, no requeue, and no row for the system's own mail (`isOwnMailOf`). A refusal is a value: `never_synced` waits 5 min, `uidvalidity_changed` ends `no_result` / `uidvalidity`, `auth_refused` ends `auth_refused`, an empty window ends `no_history`. `key`, `backfill_done_at` and `window_start` are written when the backfill ends. **Flags:** `refreshFlagsOfMailbox` reads `\Seen`, `\Answered` and `\Flagged` of the window (`touchGone: false`); the wait ends when every INBOX mail of the window has a fresh `email_flags` row, or 20 min after the backfill (`HISTORY_FLAGS_WAIT_MS`), and a mail with no fresh row counts as not acted on. **Errors:** a cursor race (`CursorMovedError`) retries in 1 min and costs no attempt, except that the 20th retry of one check counts one (`HISTORY_CURSOR_RETRIES`); any other step error costs one attempt and waits 5 min; the third attempt, also by a stale-lock take-back after 10 min (`HISTORY_LOCK_STALE_MS`), ends `no_result` / `stopped`. One run visits the organizations that wait longest first and starts none after 12 s. History mail is ordinary `emails` rows with the normal retention, so the Telegram, panel and onboarding text must not suggest a 30-day age limit: retention counts from `created_at`, so mail that arrived 29 days before the connect keeps its body about 30 more days (review 5 N3); [account-data.md](account-data.md) § Limits and [sync.md](sync.md) rule 19 name the automatic history check. Tests: `apps/server/test/integration/trust-history-job.test.ts`, `trust-history-job-race.test.ts`, `trust-history-greenmail.test.ts`, `mail-history-backfill.test.ts`, `mail-history-backfill-race.test.ts`, `mail-history-connect.test.ts`.
8. **The history check classifies a sample (F110 stage 07, flag `trust_ladder`).** The job `trust.history` (every 15 s, one check per organization per run) moves a check from `classifying` to `done`. The sample is INBOX mail of the last 30 days with its body, not written by the mailbox itself, in the scope of `TRIAGE_LLM_SCOPE` (`synthetic`: test mail only; a check that classified nothing under it ends `no_result` / `no_history` and queues no notice): mail the user acted on (`\Answered`, `\Flagged`, or feedback with the true category `urgent` or `needs_reply`) first, then a fill ordered by `md5(check id || mail id)`, at most 500. The check reuses the newest `triage_results` row only when its model and prompt version equal the key of the check and the check is not a `model_switch` check; a blocklist result is always reused. Any other mail goes through `classifyStored` (`triage/classify-stored.ts`): hard rules, thread context, `classifyEmail`, `decideCategory` with the mailbox thresholds, and the plan of `assist` mode with the default switches and `auto` on. It writes no `triage_results` row, no action and no status change. A run classifies up to 20 mails one after another and stops after 12 s; a run starts no new organization after 12 s. Each item (`history_check_items`) commits alone with its cost, and `history_checks.cost_usd` is their sum. The check stops at $0.25 (`capped`) and evaluates what it has; a model with no price row ends the check `no_result` / `cost_unknown` before any call. Each call writes an `llm.call` row with `data.historyCheckId`: `countLlmCallsSince` (the daily cap) leaves those rows out, the cost reports count them. A pause of the model client waits for its end with no attempt. A mail that the model cannot judge is an `unsure` item that is not acted on; its failed call counts at the cost of its tokens when known, else at 0.002 USD, so the cap sees it, and five failed calls in a row end the check `no_result` / `model_failing`. A run whose running key differs from the key of the check ends it `no_result` / `key_changed` and queues a `model_switch` check. The result per moving category holds `acted`, `moved`, `upper`, `total`, `wouldMove` and the outcome of `historyOutcome`; `done` and `finished_at` are written together. The first check of a mailbox that ends `done` or `no_result` (not `key_changed`) queues `trust_report_ready` in the same transaction when `trust_ladder` is on. One `history_check_result` log line holds counts, the outcome per category and the share of `\Answered` mail.
9. **The re-gate keeps `auto` honest after a switch (F110 stage 08, always on, no flag).** `regateAll` (`trust/regate.ts`) runs once at start in `main.ts`, before the triage worker and the committer are registered, and then as the job `trust.regate` every 5 minutes. It reads every mailbox of every organization that is not `suspended`, with the settings row locked, one transaction per mailbox. For each category with `auto: true`: no grant → a `legacy` grant on the running key (one audit row per mailbox; the deploy changes no behaviour). Grant key equal to the running key and grant `evidence`, `recommended` or `regate`, and the gate files now pick a final `no-go` (or `too-few`) file for that key → `auto` off with the trip reason `evidence_changed`; `legacy`, `forced` and `real_labels` grants skip this check, and a provisional file never withdraws a grant. Grant key different from the running key: when the grant is not `forced` and `autoEvidence` under the running key is eligible (final global `go`, last history result not `fail`, real labels not `no-go` at 30 or more labels), the grant moves to the running key with `by: regate` and the audit row names the old key; otherwise `auto` is off (`setCategoryAuto`, audit `reason: model_switch`), the `ready` `move` and `mark_read` rows of the category expire as `policy_changed`, one `autonomy_paused` trip (`granted_at` = the old grant's `at`) and one notice per linked owner are written in the same transaction. A re-grant keeps the `ready` rows: both keys had evidence when they were granted. After a pause or a re-grant, a `model_switch` history check is queued when `trust_ladder` is on. The settings write moves the settings version, so a triage batch that read the old settings writes nothing. A second run at once waits for the lock and finds the work done; the unique key of the trip stops a second notice. The run logs one `trust_regate_done` line with `stamped`, `regranted`, `paused`, `failed` and `run` (`start` or `job`); a mailbox that fails is logged and left for the next run (the other mailboxes still run), and in the start run its `ready` `move` and `mark_read` rows are expired in a transaction of their own, because the committer has no policy check; a failure of the whole run at start stops the server. A history end hook that throws every time costs the check one attempt per run; the third attempt ends it `no_result` / `stopped` with no notice (the hook alone is rolled back and logged as `history_ended_hook_failed`).
10. **The tripwire pauses a category that the user corrects (F110 stage 09, flag `trust_ladder`).** The job `trust.tripwire` runs every 60 s, also with `TRIAGE_LLM_SCOPE` off (it calls no model). It watches every moving category (`info`, `notification`, `spam`) with `auto` on and a grant (`category_policy[cat].grant`) in an `assist` mailbox of an organization that is not suspended; `auto` with no grant (set before F110) is not watched until the re-gate stamps it. A correction is a mail whose newest `triage_feedback` row has the verdict `wrong` (any source; several rows of one mail count once), and whose original `move` action took effect (`applied`, or `undone` later) for this category (the category of the newest `triage_results` row not newer than the action). Both times are after the grant `at`. Real mail only. The job reads the corrections of one organization with one query. Two corrections in 7 days trip the category `corrections`; one correction whose true category is `urgent` or `needs_reply` trips it `important_hidden` (an Undo row names no category, so the newest category named in a `wrong` row of the mail counts). A category with a non-`forced` grant whose newest `done` history check has `fail` for it and finished after the grant trips `history_fail`. A trip is one transaction under the settings row lock: it re-reads the policy and writes nothing when `auto` is off or the grant `at` changed meanwhile, then inserts the `autonomy_trips` row (unique per `(mailbox, category, granted_at)`), sets `auto` off through `setCategoryAuto` (audit `mailbox.policy_changed` with `reason: tripwire`, `trip_reason` and the counts; the `ready` moves of the category expire) and queues `autonomy_paused` to each linked owner. The trip stays active until the user turns `auto` on again (the evidence gate clears it); corrections of the earlier grant never count again. One `autonomy_tripped` info line per trip holds the organization, the mailbox, the category and the reason. `autonomy_paused` names a moving category only; `CategoryGrant.at` is an ISO instant. The lock is `FOR UPDATE` (`lockMailboxSettings`), not `FOR SHARE`: a share lock deadlocks with the setters (40P01 with four concurrent runs, review 9 N2); the same lock serves "Turn on recommended" (rule 11).
11. **The trust view and "Turn on recommended" (F110 stage 11, flag `trust_ladder`).** `GET /api/trust/:mailboxId` (any member) returns `trustViewFor` (`trust/view.ts`), the one read model of the autonomy card, the report page and M8: the mode, the running evidence key, the newest check of any status (`status`, `reason`, `noResultReason`, `startedAt`, `finishedAt`, `checked`, `capped`; null when there is none), and per bar category `auto` (as triage reads it: `effectiveAutoFor`, so a category on under another model setup shows off), `grantBy`, the global evidence, the history result of the newest `done` check (moving categories only), the active trip, the real-label numbers and the verdict of `autoEvidence` (`eligible`, `recommended`, `blocks`; `judgeCategory` in `trust/gate.ts` is the one rule that the gate, the notice, the write and the view call). `examples` holds up to 3 mails per moving category, newest first: acted-on mail of the newest `done` check that the category would have moved, with `receivedAt`, the sender's display name and the subject (both null after retention cleared them; the address is never read). The panel is behind login; the view never goes to Telegram. `POST /api/trust/:mailboxId/recommended` (owner only) runs `turnOnRecommended` (`trust/recommended.ts`) in one transaction under the `FOR UPDATE` lock of the settings row: it reads the evidence after the lock (a second tap reads the first commit), moves a `shadow` mailbox to `assist` with the default switches (as `setMode`), and for each moving category that is recommended and not on under the running key turns `auto` on with the grant `recommended` and the threshold of the gate file. A tripped category is never recommended, so no trip is cleared. One audit row per change, with `via: "web"`. Nothing to turn on answers 409 `nothing_recommended` and changes nothing (the mode stays); the answer is `{ turnedOn, mode, view }`. `POST /api/trust/:mailboxId/history-check` (owner only) queues a check with the reason `web` and answers 202 with the check, or 409 `check_running` while one is open. With the flag off every route is 404 `not_found` for every role. A mailbox of another organization is the same 404 as an unknown id; a member of the own organization gets 403 `owner_only` on the two writes. The operator line `bun run org:status` shows `history_calls_today` next to `llm_calls_today`: the daily count leaves the history calls out.
12. **The two trust notices.** `queueTrustNotice` (`apps/server/src/modules/channels/notices/trust.ts`) queues `trust_report_ready` and `autonomy_paused` in the transaction of the event that causes them. `trust_report_ready` (dedup `trust_report:<mailbox id>`; the view holds counts, the recommended and blocked categories and the report link) is queued once per mailbox, after its first check that ends `done` or `no_result` (not `key_changed`), only while `trust_ladder` is on (`history-ended.ts`); under `TRIAGE_LLM_SCOPE=synthetic` a check that classified nothing queues none, so the notice stays free for a real check. `autonomy_paused` (dedup `autonomy_paused:<trip id>`; the view holds a moving category and the `TripReason`) is queued by a trip (rule 10) and by a re-gate pause of a moving category (rule 9); a pause of `urgent` or `needs_reply` writes a trip and no notice (owner decision 2026-11-17). Both go to each linked owner in the language of the user (`users.locale`), and to owners with the report channel `mail` or `both` also as a mail row (rule 19). The views are strict (no sender, subject, domain or address); the texts hold counts, categories, fixed phrases and the link, so the Telegram consent version does not change (D15). Quiet hours apply (rule 18). Tests: `apps/server/test/integration/trust-notices.test.ts`, `apps/server/src/modules/channels/notices/registry.test.ts`, `packages/core/src/notices/registry-render.test.ts`.
13. **The report page `/report` (flag `trust_ladder`).** `apps/web/src/pages/report.astro` mounts `apps/web/src/islands/ReportPage.tsx`; `apps/web/src/lib/report-view.ts` holds the pure state rules. Address `/report?mailbox=<id>`; no or an unlisted id shows the newest connected mailbox, and a selector shows with two mailboxes or more. With the flag off the page shows the text `rep_off` and asks for nothing. One state per `GET /api/trust/:mailboxId` (rule 11): no check (`rep_starting`), an open check (progress, polled every 30 s), `no_result` (one sentence per `noResultReason`, then the categories) and `done` (the summary and the categories). Each moving category shows counts (`history.total` checked, `history.wouldMove` would move), the global proof line, the history line, the pause line and one status phrase. The page never shows an example mail, a subject, a sender name or an address: counts and fixed phrases only (owner question of stage 14; `view.examples` stays in the API for the panel review). An owner sees `Turn on recommended (<categories>)` while at least one category is recommended and not on, and `Check again` in an end state (`check_running` 409 is a toast); a member sees `rep_owner_only` and no button. The onboarding checklist changes with the flag on: mailbox, channel (Telegram linked, or the member's report channel is `mail` or `both`; a server with no bot never blocks), report (any mailbox of the organization has a `done` or `no_result` check, `hasEndedCheck`) and rules; the mode step is gone, and the mode stays `shadow` until the user taps the button (`homePathOf` follows the same rule). The nav has no new tab: the entries are the card link and the onboarding step. Tests: `apps/web/src/lib/report-view.test.tsx`, `apps/web/e2e/tests/report.spec.ts`.
14. **The autonomy card (flag `trust_ladder`).** `apps/web/src/components/settings/CategoriesCard.tsx` asks for `GET /api/trust/:mailboxId` only when `me.features` holds `trust_ladder` (flag off: no request, the card is as before; a failed load gives the old card). The switch shows `auto` as triage reads it (`effectiveAutoFor`), not the stored value, so a category earned under another model reads off. Per category three lines show (`apps/web/src/lib/trust-card.ts`): Proof (global), Your mail (history, moving categories only; `inconclusive` has its own phrase) and Paused (only while tripped). The old ratings line shows from `minKept` rated mails. A refused switch (409 `no_go`) opens `SetAnywayDialog.tsx`: one fixed phrase per `EvidenceBlock` from the 409 body (the view blocks are the fallback), no gate text; confirm sends `force: true` (grant `forced`). `too-few` and `no-go` both read "Not proven". "See the report" links to `/report?mailbox=<id>` once a check exists. Tests: `apps/web/src/lib/trust-card.test.tsx`, `apps/web/e2e/tests/settings.spec.ts`.
15. **The panel review "Check 10 decisions" (flag `panel_review`).** A page `/review?mailbox=<id>` (`apps/web/src/pages/review.astro`; no nav tab, no required step, no onboarding item; the report page links to it only with the flag on and a shown category list). `GET /api/review/sample?mailboxId=<uuid>` gives up to 10 items (`PANEL_REVIEW_SIZE`) of one mailbox with the sample rules of Telegram `/review` (`listReviewSample`: real mail of 30 days, no feedback row, no test mail, random order seeded by the user id and the request time); each item holds `emailId`, `receivedAt`, the sender's display name (never the address), the subject, the category, the confidence, the stored AI summary and `delegation` (an active delegate exists). `POST /api/review/label` takes `{ emailId, verdict: "right" }` or `{ emailId, category }` and writes through `recordFeedback` with the source `review` and `skipIfSame`; `right` on an `unsure` mail is 409 `needs_category`, `delegation` without an active delegate is 409 `no_delegates`. The flag is the first middleware (404 for every role); a mailbox or mail of another organization, an unknown id and a bad id all answer the same 404 `not_found`. Any member may read and label: a mailbox has no single user owner (owner decision 2026-11-18). A label unlocks nothing: it only feeds the tripwire (a `wrong` after a grant) and the real-label block, and metrics read it as unbiased (the same random sample). The code opens no logger and writes no audit row. Code: `apps/server/src/modules/triage/review-panel.ts`, `review-routes.ts`, `apps/web/src/lib/review-view.ts`. Tests: `apps/server/test/integration/web-review.test.ts`, `apps/web/src/lib/review-view.test.tsx`, `apps/web/e2e/tests/review.spec.ts`.
16. **M8 shows the evidence.** With `trust_ladder` on, each M8 row carries `global`, `history` and `trip`, read through `trustViewFor` by the `trustEvidence` dependency (`apps/server/src/modules/reports/metrics.ts`); `bun run stats:week` prints one `m8_trust` line per category, and the Monday message adds one line per bar category (`measurement.md` rules 9 and 12). The cost of the history calls is in M7 (the `llm.call` rows carry `data.historyCheckId`) and not in the daily cap (`measurement.md` rule 8).
17. **Why lines and the spam review line (flags `why_lines`, `spam_review_line`).** **Why lines:** `whySuffix` (`packages/core/src/digest/why-line.ts`) adds ` · <suffix>` to the `💬` line of a digest item and of the urgent notice, and the Activity API item gets `rule`. The suffix is the confidence in percent rounded down to a multiple of 5 (`confidencePercent`; 0 shows nothing), or the sender rule (`rule: VIP sender`, `rule: whitelisted sender`, `rule: blocked sender`; Polish in `packages/core/src/texts/why.ts`), which replaces the percent. An `unsure` item gets no second percent. A result with the reason `blocklist`, `triage_error` or `llm_blocked` has no model mark (`hasModelMark`). The rule comes from `triage_results.fields.rule`, written by `saveTriage` for every result whatever the flag; the flag gates only the readers (digest, urgent view, Activity). The would-do phrase of a delegation draft names the competence tags next to the delegate (`skills: finance, legal`; at most 3 tags of 30 characters). With the flag off every text is byte for byte as before; with it on, a digest of 15 items with the longest fields lists up to 3 items fewer (accepted, review 16 N2). The urgent view has the optional keys `confidence` and `rule`, so rolling the flag back needs the pending urgent rows to drain first (the earlier code has a strict view schema). **Spam review line:** `loadSpamReview` (`apps/server/src/modules/reports/digest-brief.ts`) counts mails whose original `move` to `ai_spam` was `applied` in the digest window (after the member's last slot, at most 24 h back, `SPAM_REVIEW_MAX_PERIOD_MS`) and, in a `shadow` mailbox, `logged` moves (`countSpamMoves`, `apps/server/src/modules/actions/repo/reads.ts`); a mail that the user undid and a mail that sat in the spam folder before the system do not count. The footer line reads `🗑 <n> went to spam · review: <WEB_BASE_URL>/activity?category=spam` (shadow: `would have gone to spam`; with no `WEB_BASE_URL`: `check them in the panel`); it is a count and a fixed link, so no consent bump. No line when `n` is 0. A crash after the request leaves `requested` (shown as "Requested"; no automatic retry; the owner may open the page). The URL, the host, the address and the answer of the other server are in no row, no audit field and no log line; the panel shows `senderLower` as the identity, never the display name. The guarded client is `postOneClick` in `platform/public-http.ts`: only `https`, port 443, no user name; no IP literal in any spelling (the URL parser turns decimal, octal, hex and short forms into dotted form first) and no single-label, `.local`, `.internal` or similar host; one DNS lookup, and every answer must be a global unicast address (`isLocalAddress` plus documentation and Azure wire server ranges, and the IANA protocol block 2001::/23 except its globally reachable entries; an IPv4-mapped IPv6 address and an address with a zone id are always refused; NAT64 `64:ff9b::/96` is refused too, so a DNS64 host cannot reach IPv4-only targets); the connection goes to the first checked address as a literal, with the host name as TLS server name and `Host`, so there is no second lookup; no redirect is followed (3xx is `failed` / `redirect`); 10 s for everything; at most 4 KiB of the answer is read and dropped; the body is exactly `List-Unsubscribe=One-Click` with `Content-Type: application/x-www-form-urlencoded`, `User-Agent: email-assistant-unsubscribe/1` and no cookie, credential or referrer. Codes: `refused` (nothing sent): `scheme`, `userinfo`, `port`, `host`, `private_host`; `failed`: `dns`, `redirect`, `timeout`, `tls`, `connect`, `network`, `http_<status>`; `ok`: `http_<2xx>`. Tests reach a loopback server only through the `dial` argument of `postOneClick`, which the guard does not skip (the test lookup gives a public address) and which no production file passes (a source scan in `public-http.test.ts`); the integration tests use a fake client through `WebExtras.postOneClick`. The request goes to a host that the newsletter names, not to a sub-processor: `OUTSIDE_CALL_CLASSES` in `apps/server/src/platform/outside-services.ts` records why. The limits of the proof (newest mail, trusted ids, NAT64, the domain limit) are in § Limits.

## Limits

- **The gate file is provisional.** The only file of the running key has `audit: pending`, so no category is eligible or recommended today (rule 2). The F109 holdout work and the owner audit decide when this changes.
- **INBOX only.** The history reads INBOX of the last 30 days (`F060` reads other folders); Sent signals wait for E5a (`F104`; the seam is `historyActedOn`); sample reply drafts on the report wait for E6a (`F115`); Telegram `/review` is `F028`.
- **History mail is stored mail.** A history mail keeps its body by the normal retention counted from `created_at` (about 30 days after the connect for old mail), and history bodies reach the model as thread context for later mail (`listThreadContext` has no status filter). The user text must not suggest a 30-day age limit (review 5 N3).
- **History cost.** At most $0.25 and 500 mails per check; a model with no price for its endpoint runs no check (`cost_unknown`); history calls are in M7 and in `org:status` (`history_calls_today`) and not in `LLM_DAILY_CAP` or Telegram `/status`; on a provider with a small free quota 500 extra calls can reach the quota and pause triage.
- **The tripwire reads corrections only.** A `wrong` feedback after the grant on a move of that category that applied after the grant. It does not read flags on moved mail (sync does not read `AI/*` folders). `auto` with no grant (set before F110) is not watched until the re-gate stamps it, which happens at the first start.
- **Re-gate.** Two server processes with different running keys would flip grants every 5 min (a misconfiguration; review 8 N2); every run takes one `FOR UPDATE` transaction per mailbox with `auto` on, also when nothing changes (review 8 N7); the stored reason of a check that a failing end hook stopped says `stopped`, and its result is lost (review 8 N6); a pause of `urgent` or `needs_reply` has a trip and no notice.
- **Smaller gaps (accepted, each with its review).** No database CHECK ties `finished_at` to the status `done` or `no_result` (the five writers do it together and a test asserts it, review 3). No CHECK ties `mailbox_id` to the two trust notice kinds (review 10). The sample of a check is rebuilt on every run, and one batch can end up to 19 items over 500 (review 7 N4). A deploy kill leaves a stale lock that costs the check one attempt, and one long backfill holds up the other organizations inside a tick (review 6 N7). The audit rows `grant_*` omit `promptParts` and `host` (the policy row keeps the full key; review 4 N5), and the running key comes from `productionClassifierChoice()`, not from the prompt of the triage job, so a caller that injects another prompt could drift (review 4 N6). A paused mailbox keeps its history check open until it is active again (review 5 N5; decision of stage 06).
- **Report mail.** A shared mailbox shows the report to everyone who reads it (ADR 0022). Someone who sees the Message-ID of a report mail could mark a mail to that same mailbox as own (low: the id is a random uuid of that mailbox; review 20 N5). The job runs two index-backed queries every 15 s while the flag is off. Report mails stay in INBOX after a rollback (rule 23).
- **Quiet hours.** The SLO alert `slo_urgent_latency` takes the largest wait over the pending urgent rows, each without that user's own quiet hours; M5 keeps the default hours on purpose (question 18).
- **Urgency card.** Production triage does not read the urgency profile (owner decision 42 is open), so the card changes no triage today. Switching the mailbox select drops an unsaved draft without a warning (review 21 N7).
- **Panel review.** The item shows the stored AI summary only (no stored plain-text reason exists), samples one mailbox (Telegram samples the organization), and shows sender name and subject to every member (owner decision 2026-11-18).
- **One-click unsubscribe, what the proof is.** The proof has two parts: `dkim=pass` for the From domain (or a parent) in the topmost `Authentication-Results` of a trusted authserv-id, and a signature that covers the list headers. The trusted server verified a signature but does not say which `DKIM-Signature` header it was, and a replayer can add headers of the same domain. So `hasCoveredDkimPass` needs EVERY stored signature of the passing `header.d` to name both `list-unsubscribe` and `list-unsubscribe-post` in `h=` (case-insensitive; one name signs one instance, and capture already refuses a mail with a repeated list header). Capture stores only `d=` and `h=` (`dkimSignaturesOf`, [sync.md](sync.md) rule 18); it fails closed: more than 8 signature headers, a header over 16 384 characters, a duplicate or missing `d=`/`h=` tag or an invalid domain store no signature at all. Mail stored before the column existed has no proof and is link-only until a newer mail arrives (the newest mail decides). A mail whose retention cleared the texts has no link either. Limits that stay: the newest mail decides, the trusted ids must be providers that write their own `Authentication-Results` on top, NAT64 is refused, and the domain limit. The request is still a fixed body to a public `https` host on port 443, only after an owner tap.
- **One-click, other limits.** The target comes from the NEWEST mail of the sender with a result: a newer mail with a bad authentication result turns one-click off until a newer good mail arrives. `MAIL_TRUSTED_AUTHSERV_IDS` may name only providers that write their own `Authentication-Results` on top (the IMAP host is not used for one-click). NAT64 `64:ff9b::/96` is refused for every embedded address, so on an IPv6-only host behind DNS64 every IPv4-only target ends `refused` / `private_host` (fail closed). The domain limit (3 per sender domain per hour) counts a domain that the sender chooses, so only the organization cap (20 per hour) binds; every request needs an owner tap. A single-label name such as `.test` or `.invalid` passes the name check, and the address check refuses its private answers. A sender address with no `@` ends 500 and sends nothing (review 24 N7). No `mailto:` method, no retry, no redirect; a crash leaves "Requested". `listNewsletterSenders` applies its 200 cap in code after a full read (a LIMIT would change which senders show after the spam filter) and ignores corrections and VIP rules.
- **Privacy text.** The legal pages are NOT changed by F110, and none of these changes bumps `TERMS_VERSION` here. What needs a bump: (1) the privacy page must say that after an owner tap the server sends one request from its own address to the server that the newsletter names (the sender learns that the subscription asked to leave, that the mailbox is active and when; owner decision 2026-11-18); (2) the 7-day sentence of the privacy page: done by F153 (the privacy text, the registries and the DPIA name the context mails and the history check; a new legal version); (3) the data category `unsubscribe-data` names the subject `others` only; review 22 NOTE 7 asks for `members` too (`packages/core/src/legal/data-categories.ts`); (4) a line that the product appends report mail into the member's INBOX is optional (ADR 0022: no new sub-processor). Points (1), (3) and (4) stay open. The bump is batched with the next legal change (F115 stage 17).

# Triage

> Checked against the code at `cb3f73dd`, 2026-11-18.

## What it does now

Triage turns a stored mail with status `pending` into a category, a short reason, a summary for `info` mail and a plan of actions. The job `triage.worker` runs every 15 seconds. It claims a batch of 5 mails per mailbox, oldest first. First it applies the age rules and the hard rules (the sender rules of the mailbox). If a mail needs the LLM, one call with the role `classifier` returns a category, a confidence, a reason code and extracted fields. The service then decides the final category by the thresholds. It writes the `triage_results` row, the planned actions and the audit rows in one transaction. The policy decides if each action is `ready`, `awaiting_approval` or `logged` (`docs/architecture.md` §4.3). Users give feedback with Telegram buttons, the web panel, the Undo button, or by moving a mail back; a CLI labels mail for the eval. Without `TRIAGE_LLM_SCOPE` the worker does not run.

## Rules

1. **Hard rules before the LLM.** A blocklisted sender (and not whitelisted) gives `spam` with reason `blocklist` and confidence 1, with no LLM call. A whitelisted or VIP sender gets the category list without `spam`. A VIP is also whitelisted. The category `delegation` is allowed only when the organization has at least one active delegate. The rules are in `packages/core/src/triage/rules.ts`; the sender rules are per mailbox or per organization (`apps/server/src/modules/config/rules.ts`).
2. **Age rules.** Mail older than 7 days is `skipped` with `too_old`, unless `emails.backfilled_at` is set. Mail received more than 24 h before `organizations.resumed_at`, and stored before `resumed_at` + 24 h, is `skipped` with `suspended_backlog` (no LLM call). A backfilled mail that lost its body while it waited (older than 7 days in `pending`) is `skipped` with `body_expired`. A skipped mail still closes an open delegation when it is a reply of the delegate.
3. **The classifier call.** `classifyEmail` makes one call with the role `classifier` and the production prompt from the prompt registry (`apps/server/src/modules/triage/prompts/index.ts`): `classifier-v2`. `triageOne` reads no `ClassifierExtras` for it (rule 18). The input is the mail, the sender context (whitelisted, VIP, no-reply), the allowed categories, the delegates list and the last 3 mails of the same `thread_key` as context. Mail text is marked as untrusted (`markUntrustedText`), with a random nonce for each call. For a test mail (a synthetic `Message-ID` or a sender in `TEST_SENDER_ADDRESSES`), the thread context comes from test mail only. The output must match a Zod schema built for the allowed categories and the delegate ids. A category outside the allowed list is an `LlmOutputError`. A delegate id that is not in the list becomes null. The LLM returns data only: it never names a free-form recipient.
4. **Categories and thresholds.** The final category is the model category, or `unsure` when the confidence is below the threshold of that category (`decideCategory`; reason code in the audit row: `below_threshold`). The start threshold is 0.7 per category (`mailbox_settings.category_policy`). The categories and their plans: `docs/architecture.md` §4.2.
5. **The policy table.** `decidePolicy` (pure, `packages/core/src/triage/policy.ts`) returns `apply`, `await_approval` or `log_only` for each planned action. The table and the modes: `docs/architecture.md` §4.3. Mail from the spam folder uses another plan (`fromJunk` in `planActions`).
6. **`TRIAGE_LLM_SCOPE`.** `off` (default): no worker. `synthetic`: the worker claims only test mail: a synthetic `Message-ID` or a sender in `TEST_SENDER_ADDRESSES`. `all`: all mail of every active mailbox of an organization that is not `suspended`. The key of the provider must be set when the scope is not `off`. `LLM_PROVIDER` (`gemini` or `openai`) picks the provider of the classifier. Own-model server path (Ollama `/v1/responses`): see `notes/2026-11-15-ollama-responses-path.md`; the endpoint setting is rule 16.
7. **Retries live on the row that failed** (rule 7 of `docs/architecture.md` §4.1, first paragraph, stays there). The triage worker (S1b; `triage/service.ts`, `triage/jobs.ts`, `triage/pause.ts`) applies this rule to the email as follows:
   - **Soft error** (timeout, a lost network connection, HTTP 429, 500, 502, 503, 504): the LLM client of the process pauses. The pause is 5 min.
     Each next soft or config error without a good LLM answer in between doubles it, up to 60 min. The pause is in memory and covers all mailboxes.
     The mail goes back to `pending` with `next_attempt_at` = the pause end. It gets no count. The job claims no mail during the pause.
     Claimed mail that the worker did not try keeps its old `next_attempt_at`. One `warn` line per pause.
   - **Config error** (HTTP 401, 402, 403, 404; HTTP 400 with `FAILED_PRECONDITION` or `API_KEY_INVALID`): the same pause, no count.
     One `error` line names the keys to check.
   - **Safety block** (`llm_blocked`): the mail becomes `unsure` at once. The worker writes one `llm.call` row and does not retry.
   - **Hard error** (an HTTP 400 without the two config signs, an unreadable answer, an error without an HTTP status and without a network code, or any other HTTP status that is not listed):
     the mail waits a fixed 5 min and `attempts` goes up by 1. At 3 attempts the mail becomes `unsure` (`triage_error`).
     A stale claim (`locked_at` older than 5 min) that a later run takes back also counts one attempt.
     A mail that reaches 3 attempts this way becomes `unsure` (`triage_error`) without an LLM call.
   - **Error outside the LLM call** (thread read, save, DB): the mail in work counts one try, with a 5-min wait, like a hard error.
     At 3 tries it becomes `unsure` (`triage_error`). If that save fails, the mail goes back with a count.
     Mail that the worker claimed later in the same batch goes back with no count. The error stops this mailbox only; the next mailbox runs.
   - **Shutdown:** the server waits up to 30 s for a running batch. A batch that is cut off leaves claimed mail in `processing`;
     the next start takes it back and counts one attempt for each mail.
8. **Cost limits** (moved from `docs/architecture.md` §4.1 rule 8; the headline stays there). The daily cap (default 300, `LLM_DAILY_CAP`) counts every LLM call attempt (`audit_log` event `llm.call`)
   per mailbox per `America/Los_Angeles` day (the quota day of the free tier). At the cap the mail goes back to `pending`
   with `next_attempt_at` = the start of the next quota day, with no count. Mail older than 7 days is not sent to the LLM: status `skipped` (reason `too_old`);
   the digest lists it as "not processed" (ADR 0012). Mail with `emails.backfilled_at` set skips the 7-day rule (one-off backfill, `docs/architecture.md` §6.1).
   - Check against the code: the cap holds LLM calls only, so a blocklist mail or a too-old mail after a capped mail is still handled. The job writes one `warn` line for each mailbox and quota day, and calls the operator notice `llm_cap` ([digest-and-notices.md](digest-and-notices.md)).
9. **One transaction per mail.** `saveTriage` share-locks the settings row and compares the settings version. If the settings changed after the batch read them, nothing is written and the mail goes back without a count; the next run uses the new settings. The same transaction writes the `emails` status `triaged`, the `triage_results` row, the actions (`ready`, `awaiting_approval` or `logged`), the delegation row for a `delegation` mail, and the audit rows `email.triaged` and `action.planned`. A reply of a delegate closes the open delegation in this transaction.
10. **Feedback sources** (moved from `docs/architecture.md` §4.4): labeling CLI (S1b); ✅ / ✏️ buttons under each digest line (S2); the `/review` page (✅ / ✏️ per item, flag `review_command`, source `review`; [digest-and-notices.md](digest-and-notices.md) rule 9); the Undo button (S3);
    a mail that the user moves back to a synced folder after a system move (`docs/architecture.md` §6.1); the web panel (S5).
    Every source writes a `triage_feedback` row through `triage.recordFeedback()`. A known mail is never triaged again (no loop).
    - The source `review` is for the labels of the Telegram `/review` page (a random sample of unlabelled real mail, `listReviewSample` in `triage/review-repo.ts`); its buttons are `vr`, `vc`, `ve`, `vx` (see [digest-and-notices.md](digest-and-notices.md) rule 10), so metrics can tell them from digest taps.
    - The panel review "Check 10 decisions" (flag `panel_review`, F110 stage 15) writes the same source `review` from the page `/review`: `GET /api/review/sample?mailboxId=` gives up to 10 items of the same sample (`listReviewSample`; the seed is the user id and the request time), each with category, confidence, the stored AI summary, the sender's display name, the subject and the date; `POST /api/review/label` takes `{ emailId, verdict: "right" }` or `{ emailId, category }` and writes through `recordFeedback` with `skipIfSame`. Any member may use both. A label unlocks nothing: it feeds the tripwire and the real-label block only. The report page links to it as an optional step; it is never a required one.
    - The source `answered_check` is written only by a "yes" in the answered check of `/review` ([digest-and-notices.md](digest-and-notices.md) rule 9): `answerAnsweredCheck` sets `email_flags.answered_check` and writes one row (`true_category` `needs_reply`, verdict `wrong`, `skipIfSame`) in one transaction. A "no" writes the answer only. The first answer wins. A mail that already has any feedback row (for example a ✅ on the random `/review` page) keeps that first label: a "yes" then saves the answer, so the block does not show the mail again, but writes no `answered_check` row. The check acts only on mail whose flag read said "answered" (`email_flags.answered`); a row of mail that sync could not read (all flags false) is never a candidate and a tap on it answers "not found". Candidates (`listAnsweredCandidates`): real mail of the chat's mailboxes of the last 14 days, answered, latest category `info`, `notification` or `spam`, no feedback row, no answer yet, oldest first, at most 5. `countAnsweredWaiting` counts the same over the organization.
    - Check against the code: `triage.returned` (every 15 s) and the Undo path also call `recordFeedback`; the Telegram handler and `POST /api/feedback` set `skipIfSame`, so the same answer twice writes no row.
11. **Buttons under a digest line (S2)** (moved from `docs/architecture.md` §4.4): ✅ means "the shown category is right": it writes `true_category` = the shown category (verdict `right`).
    ✏️ opens a picker with five categories (Urgent, Reply, Info, Notification, Spam) and Cancel; a pick writes `true_category` = the pick
    (verdict `right` or `wrong`). The latest row of a mail wins (as in `listLabeledResults`). The same answer twice writes nothing
    (the bot answers "Already saved"). An `unsure` line has only ✏️, because a verdict without a category is not valid for `unsure`.
12. **Feedback rows** (moved from `docs/architecture.md` §4.4): `verdict` (`right` / `wrong`) and an optional `true_category`. A row with a `true_category` counts for precision and recall.
    A row with only `wrong` counts only against the precision of the predicted category.
    Rows with the source `review` come from a random sample of recent real mail, not from the mail the user chose to label: they are the unbiased base for the metrics of E3a.
13. **Eval on real mail** (moved from `docs/architecture.md` §4.4): the eval runner reads the labels from `triage_feedback` in the DB. Real labels never go to git. Real labels leave out test mail: mail with a synthetic `Message-ID` and mail from a sender in `TEST_SENDER_ADDRESSES` (the check is case-insensitive and also drops old feedback on such mail). `--real --json <file>` also writes the counts per category (tp, fp, fn, support; no id, no address, no text). `bun run eval --gap --sim-json <gate file> --real-json <file> [--out <file.md>]` compares sim and real precision and recall for `notification` and `spam` (final category, no threshold, Wilson intervals): `gap`, `no gap` or `too few real labels` (real tp + fp under 30). It needs no DB and no LLM key. A prompt or model change of any role runs the sim gate (`bun run eval --sim lab-01 --part holdout`, `--judge` for a drafter change) and commits the report and the gate file in `evals/results/gate/` before the merge (PD-025, ADR 0028); the CI test checks that a gate file exists for the classifier prompt version.
    Real-mail evals use mail younger than 30 days (the body is cleared after that, `docs/architecture.md` §7). Pilot exception: backfilled mail up to 180 days (`docs/architecture.md` §6.1).
    - `bun run eval` runs the cases of `evals/cases` (80 synthetic, 16 injection, 12 delegation) against one provider and model, and prints precision and recall per category with a bar (default 0.98) and a minimum support (`--min-kept`, default 30). `bun run eval --real --org-id <uuid> --mailbox-id <uuid>` reads the labels from the DB and makes no LLM call. The gate for `auto` per category uses the same report (`goNoGoFor`: precision at least 98% on at least 30 labelled rows of the mailbox).
    - `bun run eval --sim <scenario> --part dev|holdout|week` runs a synthetic corpus part (`evals/sim/<scenario>/`) through a worker pool (8 calls in flight, 240 requests per minute by default). A run stops at its cap: $1 per run, and the $20 month cap counted from a spend ledger outside git (`$XDG_STATE_HOME/email-assistant/eval-spend.jsonl`). A stopped run is not complete (exit 2) and resumes from its state file; a lock file keeps two runs off one state file. A model without a price in `llmPrices`does not start. The`holdout` part needs a frozen corpus, and its report prints counts, not case ids.
    - Flags of F109: `--suspicious` (with `--sim <scenario> --part dev|holdout|week [--out <file.md>]`: runs the suspicious-mail rules on a sim part; no LLM call, no config read, no spend; rule 17); `--prompt-version classifier-v2|classifier-v3` and `--prompt-parts urgency,history,list|none` (parts only with `classifier-v3`; `none` means `attachments` only; without the flags the run uses the production prompt, and its parts when v3 is in production; rule 18); `--escalate [--escalation-model <id>] [--escalation-reasoning-effort <value>]` (a second call by the role `escalation` for a person's mail that the first answer called `info`, `notification`, `spam` or `unsure`; the report shows the cascade; a usage error with `--prompt-version classifier-v3` or `--prompt-parts`, and refused on an own endpoint; rule 19).
    - With `--judge` (and the optional `--judge-provider`, `--judge-model` and `--judge-rpm`; the first two override the `judge` role row) every planned delegation or clarification draft is checked by code (`draftCodeChecks`: recipient, clean text, language, length, planted strings) and graded by the `judge` role (`judge-v1`); the report gets a `## Draft judge` section that names the judge provider and model and says that the scores are LLM-scored. `--rpm` is the classifier provider's rate only: the judge provider keeps the rate of the config (`GEMINI_RPM` or `OPENAI_RPM`, or `LLM_JUDGE_RPM` for the role) and `--judge-rpm` replaces it. The judge refuses to start when its provider is the classifier's provider, when its API key is missing (the message names the key) or when its model has no price; a judge call counts in the cap, and judge errors stop the run like classifier errors.
    - Synthetic corpora (a made-up company, mail written by agents, labels fixed before the text) are planned and checked with `bun run sim`; the runbook is `evals/sim/README.md`. A complete corpus freezes into a version with `manifest.json` (counts and hashes); the owner audit (30 random and up to 20 contested cases) is made and applied with `sim audit-list` and `sim audit-apply`.
14. **Success metric** (moved from `docs/architecture.md` §4.4; not built) ("share of mail handled without the user", target 80–90%):
    handled = mail in `spam`, `notification`, `info`, or `delegation` sent after one tap, with an applied plan
    that the user did not undo or correct within 7 days. Share = handled ÷ all triaged mail. One line in the weekly digest.
    The line is built (F100): M4 in `measurement.md` rule 6 (the weekly report and the stats page) and the line `🤖 Handled in the last 7 days` of the digest behind the flag `handled_share` (`digest-and-notices.md` rule 4).
15. **Labels and cost tools.** `bun run triage:label --org-id <uuid> --mailbox-id <uuid>` shows unlabeled triaged mail one by one (`--synthetic` for test mail, also from a sender in `TEST_SENDER_ADDRESSES`); `--email-id <uuid>` with `--category`, `--right` or `--wrong` labels one mail. `bun run triage:cost --org-id <uuid> --mailbox-id <uuid> [--days 7] [--mail real|synthetic]` (test-sender mail counts as `synthetic`) prints per model and endpoint the result count, the average tokens, the latency p50 and p95, the average cost per mail and the monthly cost, priced at the rate of that endpoint (an `eu` result at the EU row, an `own` result at 0). It takes the endpoint of a result from the `ok` `llm.call` row of the same mail; no row reads `standard`. `bun run llm:check` sends the real triage schema to one provider.
16. **The LLM endpoint (F111).** One endpoint per server, set by `OPENAI_BASE_URL` for the `openai` provider (default `https://api.openai.com/v1`; empty means the default). Gemini has one fixed endpoint. There is no endpoint per organization.
    - **Always explicit.** The adapter always passes the checked URL to the SDK. The SDK would read `OPENAI_BASE_URL` from the process env on its own, so a stray variable never redirects a call around the check.
    - **The check runs at every start,** also with `TRIAGE_LLM_SCOPE=off`, and in `eval --sim`, `eval` and `eval --real`. The URL must be `https`, or `http` only to loopback (`127.0.0.0/8`, `::1`, `localhost`) or a one-label host (a container on the same machine). No user name, password, query or fragment. A bad value stops the start with an error that names `OPENAI_BASE_URL` and never the value; the eval commands print `config error: <keys>` and exit 1. `eval --suspicious` and `eval --gap` read no config and still run.
    - **Endpoint kind.** `standard` (`api.openai.com`), `eu` (`eu.api.openai.com`) or `own`. Another `*.openai.com` host is refused. A loopback or one-label host is `own`. Any other host is `own` only with `OPENAI_ENDPOINT_KIND=own` ("a server I run", https only); the kind cannot relabel an OpenAI host.
    - **A hosted OpenAI-compatible API is not supported** (Azure OpenAI, OpenRouter and the like): its cost and its sub-processor are unknown. Without `OPENAI_ENDPOINT_KIND=own` the start refuses it.
    - **An own server gets no `reasoning` field.** Every `openai` role row has no effort there, whatever `OPENAI_REASONING_EFFORT` or `LLM_<ROLE>_REASONING` says. `store: false` stays.
    - **Logs show the kind and the host only.** `llm_settings` has `endpoint` and `host` (the hostname: no path, no port, no user info, no key); `bun run llm:check` prints `endpoint=<kind> host=<host>`. `LlmUsage.endpoint` and `LlmClient.endpointOf(role)` carry the kind of every call.
    - **Every `llm.call` row has `endpoint`** (`standard`, `eu`, `own`). A success takes it from `LlmUsage.endpoint`; the error branch has no usage and takes `LlmClient.endpointOf("classifier")`. A row written before F111 has no key and reads `standard`; any other value reads `standard` too (the dearest rate). There is no migration: the key is in the JSON `data`.
    - **Prices follow the endpoint** (`costPerMail(..., endpoint)`). `standard` takes the price rows without `endpoint`; `eu` takes only rows with `endpoint: "eu"` (a model with no EU row is unpriced there, never priced at the standard rate); `own` costs 0, also for a model with no price row. `own` is set only by the start check (`OPENAI_ENDPOINT_KIND=own` or a loopback or one-label host, never an `openai.com` host), so a paid API cannot be priced at 0. The EU row of `gpt-6-luna` (0.11 / 0.55) is **unverified**: its source is a secondary one (E11 discovery notes §6), and each report and `triage:cost` line says so. F111 stage 07 replaces it with the OpenAI price.
    - **A gate file proves one model and prompt on one endpoint and host.** It holds `endpoint` and `host` (the host name only). A file without the keys is `standard` with host `null`. `-eu` or `-own` goes before `.json` in its name and before `.jsonl` in the eval state name, so a resume never takes the results of another endpoint. An explicit `--state` path gets no suffix: the caller keeps one endpoint per file. The CI evidence test (`gate-evidence.test.ts`) parses every gate file of the prompt version but counts only a `standard` file (no suffix, `endpoint` `standard`) as evidence.
    - **The grant ties `auto` to the running key (F110 stage 04).** Every `auto` on stores `category_policy[category].grant = { key, by, at }`: the `EvidenceKey` of the running classifier (model, provider, effort, prompt version and parts, endpoint, host for `own`), who granted it (`evidence`, `forced`, `real_labels`; later `recommended`, `regate`, `legacy`) and when. `auto: false` removes the grant. The triage worker gets the running key from the composition root (`createTriageJob({ runningKey })`) and reads `effectiveAutoFor`: `auto` counts only when the grant key equals the running key (a different `endpoint` alone is a mismatch). A mismatch is `auto` off at once: the `move` and `mark_read` rows are `logged`, with no job in between. A row with no grant (set before F110) counts as matching. The settings view still shows `auto` as stored; the re-gate (next bullet) stamps or pauses the old rows.
    - **The evidence gate (flag `trust_ladder`, epic `E4-B`).** With the flag on for the organization, `PATCH /api/settings/:mailboxId/auto/:category` and `bun run mailbox:settings auto` call `setCategoryAutoWithEvidence` (`trust/gate.ts`, chosen by `autoSetter` in the composition root). It reads the global evidence of the running key (`globalEvidenceFor`), the last history result, the active trips and the real labels, and calls `autoEvidence`. Eligible → `auto` on, grant `evidence`, threshold from the gate file when it has one. Not eligible → 409 `no_go` with `gate` and `blocks`; `force` sets it anyway with grant `forced`, and the audit row keeps `forced: true` and the block list. An active trip never refuses. Turning `auto` on clears the active trips of the category in the same transaction as the policy row and its audit row. `auto: false` reads no evidence. With the flag off the real-label gate stays; it also writes the grant (`real_labels`, or `forced` with force) and clears the trips. The CLI and the web build the gate files and the running key in one place (`gateEvidenceOf`), so neither is stricter.
    - **The history check classifies a sample (F110 stage 07, flag `trust_ladder`).** The job `trust.history` (every 15 s, one check per organization per run) moves a check from `classifying` to `done`. The sample is INBOX mail of the last 30 days with its body, not written by the mailbox itself, in the scope of `TRIAGE_LLM_SCOPE` (`synthetic`: test mail only; a check that classified nothing under it ends `no_result` / `no_history` and queues no notice): mail the user acted on (`\Answered`, `\Flagged`, or feedback with the true category `urgent` or `needs_reply`) first, then a fill ordered by `md5(check id || mail id)`, at most 500. The check reuses the newest `triage_results` row only when its model and prompt version equal the key of the check and the check is not a `model_switch` check; a blocklist result is always reused. Any other mail goes through `classifyStored` (`triage/classify-stored.ts`): hard rules, thread context, `classifyEmail`, `decideCategory` with the mailbox thresholds, and the plan of `assist` mode with the default switches and `auto` on. It writes no `triage_results` row, no action and no status change. A run classifies up to 20 mails one after another and stops after 12 s; a run starts no new organization after 12 s. Each item (`history_check_items`) commits alone with its cost, and `history_checks.cost_usd` is their sum. The check stops at $0.25 (`capped`) and evaluates what it has; a model with no price row ends the check `no_result` / `cost_unknown` before any call. Each call writes an `llm.call` row with `data.historyCheckId`: `countLlmCallsSince` (the daily cap) leaves those rows out, the cost reports count them. A pause of the model client waits for its end with no attempt. A mail that the model cannot judge is an `unsure` item that is not acted on; its failed call counts at the cost of its tokens when known, else at 0.002 USD, so the cap sees it, and five failed calls in a row end the check `no_result` / `model_failing`. A run whose running key differs from the key of the check ends it `no_result` / `key_changed` and queues a `model_switch` check. The result per moving category holds `acted`, `moved`, `upper`, `total`, `wouldMove` and the outcome of `historyOutcome`; `done` and `finished_at` are written together. The first check of a mailbox that ends `done` or `no_result` (not `key_changed`) queues `trust_report_ready` in the same transaction when `trust_ladder` is on. One `history_check_result` log line holds counts, the outcome per category and the share of `\Answered` mail.
    - **The re-gate keeps `auto` honest after a switch (F110 stage 08, always on, no flag).** `regateAll` (`trust/regate.ts`) runs once at start in `main.ts`, before the triage worker and the committer are registered, and then as the job `trust.regate` every 5 minutes. It reads every mailbox of every organization that is not `suspended`, with the settings row locked, one transaction per mailbox. For each category with `auto: true`: no grant → a `legacy` grant on the running key (one audit row per mailbox; the deploy changes no behaviour). Grant key equal to the running key and grant `evidence`, `recommended` or `regate`, and the gate files now pick a final `no-go` (or `too-few`) file for that key → `auto` off with the trip reason `evidence_changed`; `legacy`, `forced` and `real_labels` grants skip this check, and a provisional file never withdraws a grant. Grant key different from the running key: when the grant is not `forced` and `autoEvidence` under the running key is eligible (final global `go`, last history result not `fail`, real labels not `no-go` at 30 or more labels), the grant moves to the running key with `by: regate` and the audit row names the old key; otherwise `auto` is off (`setCategoryAuto`, audit `reason: model_switch`), the `ready` `move` and `mark_read` rows of the category expire as `policy_changed`, one `autonomy_paused` trip (`granted_at` = the old grant's `at`) and one notice per linked owner are written in the same transaction. A re-grant keeps the `ready` rows: both keys had evidence when they were granted. After a pause or a re-grant, a `model_switch` history check is queued when `trust_ladder` is on. The settings write moves the settings version, so a triage batch that read the old settings writes nothing. A second run at once waits for the lock and finds the work done; the unique key of the trip stops a second notice. The run logs one `trust_regate_done` line with `stamped`, `regranted`, `paused`, `failed` and `run` (`start` or `job`); a mailbox that fails is logged and left for the next run (the other mailboxes still run), and in the start run its `ready` `move` and `mark_read` rows are expired in a transaction of their own, because the committer has no policy check; a failure of the whole run at start stops the server. A history end hook that throws every time costs the check one attempt per run; the third attempt ends it `no_result` / `stopped` with no notice (the hook alone is rolled back and logged as `history_ended_hook_failed`).
    - **The tripwire pauses a category that the user corrects (F110 stage 09, flag `trust_ladder`).** The job `trust.tripwire` runs every 60 s, also with `TRIAGE_LLM_SCOPE` off (it calls no model). It watches every moving category (`info`, `notification`, `spam`) with `auto` on and a grant (`category_policy[cat].grant`) in an `assist` mailbox of an organization that is not suspended; `auto` with no grant (set before F110) is not watched until the re-gate stamps it. A correction is a mail whose newest `triage_feedback` row has the verdict `wrong` (any source; several rows of one mail count once), and whose original `move` action took effect (`applied`, or `undone` later) for this category (the category of the newest `triage_results` row not newer than the action). Both times are after the grant `at`. Real mail only. The job reads the corrections of one organization with one query. Two corrections in 7 days trip the category `corrections`; one correction whose true category is `urgent` or `needs_reply` trips it `important_hidden` (an Undo row names no category, so the newest category named in a `wrong` row of the mail counts). A category with a non-`forced` grant whose newest `done` history check has `fail` for it and finished after the grant trips `history_fail`. A trip is one transaction under the settings row lock: it re-reads the policy and writes nothing when `auto` is off or the grant `at` changed meanwhile, then inserts the `autonomy_trips` row (unique per `(mailbox, category, granted_at)`), sets `auto` off through `setCategoryAuto` (audit `mailbox.policy_changed` with `reason: tripwire`, `trip_reason` and the counts; the `ready` moves of the category expire) and queues `autonomy_paused` to each linked owner. The trip stays active until the user turns `auto` on again (the evidence gate clears it); corrections of the earlier grant never count again. One `autonomy_tripped` info line per trip holds the organization, the mailbox, the category and the reason. `autonomy_paused` names a moving category only; `CategoryGrant.at` is an ISO instant.
    - **The trust view and "Turn on recommended" (F110 stage 11, flag `trust_ladder`).** `GET /api/trust/:mailboxId` (any member) returns `trustViewFor` (`trust/view.ts`), the one read model of the autonomy card, the report page and M8: the mode, the running evidence key, the newest check of any status (`status`, `reason`, `noResultReason`, `startedAt`, `finishedAt`, `checked`, `capped`; null when there is none), and per bar category `auto` (as triage reads it: `effectiveAutoFor`, so a category on under another model setup shows off), `grantBy`, the global evidence, the history result of the newest `done` check (moving categories only), the active trip, the real-label numbers and the verdict of `autoEvidence` (`eligible`, `recommended`, `blocks`; `judgeCategory` in `trust/gate.ts` is the one rule that the gate, the notice, the write and the view call). `examples` holds up to 3 mails per moving category, newest first: acted-on mail of the newest `done` check that the category would have moved, with `receivedAt`, the sender's display name and the subject (both null after retention cleared them; the address is never read). The panel is behind login; the view never goes to Telegram. `POST /api/trust/:mailboxId/recommended` (owner only) runs `turnOnRecommended` (`trust/recommended.ts`) in one transaction under the `FOR UPDATE` lock of the settings row: it reads the evidence after the lock (a second tap reads the first commit), moves a `shadow` mailbox to `assist` with the default switches (as `setMode`), and for each moving category that is recommended and not on under the running key turns `auto` on with the grant `recommended` and the threshold of the gate file. A tripped category is never recommended, so no trip is cleared. One audit row per change, with `via: "web"`. Nothing to turn on answers 409 `nothing_recommended` and changes nothing (the mode stays); the answer is `{ turnedOn, mode, view }`. `POST /api/trust/:mailboxId/history-check` (owner only) queues a check with the reason `web` and answers 202 with the check, or 409 `check_running` while one is open. With the flag off every route is 404 `not_found` for every role. A mailbox of another organization is the same 404 as an unknown id; a member of the own organization gets 403 `owner_only` on the two writes. The operator line `bun run org:status` shows `history_calls_today` next to `llm_calls_today`: the daily count leaves the history calls out.
    - The API key of the EU endpoint must belong to the OpenAI project of that region.
    - **An own server never gets an OpenAI credential.** Its row holds `OPENAI_OWN_API_KEY` (optional, secret) or the fixed text `own`; the start needs no `OPENAI_API_KEY` for it. The client sets `organization` and `project` to null for `own`, so `OPENAI_ORG_ID` and `OPENAI_PROJECT_ID` of the process env never reach the server. It also sets `adminAPIKey` and `webhookSecret` to null and nulls each header name of `OPENAI_CUSTOM_HEADERS` (an empty `defaultHeaders` does not stop the SDK from adding them: tested on SDK 7.53.0). A remote own server therefore never sees the key of OpenAI.
    - **Other SDK env variables are fixed in code too.** The OpenAI client sets `baseURL` and `logLevel: "off"` (so `OPENAI_LOG=debug` cannot print mail text); the Gemini client sets `httpOptions.baseUrl` and `vertexai: false` (so `GOOGLE_GEMINI_BASE_URL`, `GOOGLE_VERTEX_BASE_URL` and `GOOGLE_GENAI_USE_VERTEXAI` change nothing). Gemini has one fixed endpoint.

17. **Suspicious-mail rules (F109, PD-063).** `assessSuspicious` (pure, `packages/core/src/triage/suspicious.ts`) returns the reason codes of one mail, in this order and without duplicates. It makes no LLM call. The six codes:
    - `auth_fail`: the topmost `Authentication-Results` header has a trusted `authserv-id` and says `dmarc=fail`, or `spf=fail` and `dkim=fail`. The trusted ids are the registrable domain of the IMAP host of the mailbox (the id may be a sub-domain of it) and each entry of `MAIL_TRUSTED_AUTHSERV_IDS` (optional comma list, lower case; `.env.example`). A header with another id is ignored: a sender can write such a header.
    - `lookalike_domain`: the sender's registrable domain is not known but looks like a known one: the same skeleton after folding (Cyrillic and Greek look-alike letters, `0` and `1`, hyphens, `rn` as `m`; `xn--` labels are decoded), or one edit apart for labels of at least 5 characters. The registrable domain uses a built-in list of two-level suffixes, not a public-suffix library (D3).
    - `display_name_spoof`: the display name holds an address that is not the From address, or equals a protected full name (two words or more): the name of a delegate, the display name of a member, or the newest display name (90 days) of a VIP address in this mailbox.
    - `reply_to_mismatch`: a `Reply-To` address is on another registrable domain than the From address. Not for list mail (`List-Id` or `List-Unsubscribe`).
    - `link_mismatch`: a link whose visible text names another registrable domain than its target. Not for list mail.
    - `risky_attachment`: an attachment with a risky extension (`exe`, `scr`, `js`, `docm` and others in `RISKY_EXTENSIONS`) or a risky type. It reads the name and the type, never the content.
    - **Known sender.** A known sender gets only `auth_fail` and `risky_attachment`. Known: an own mailbox address of the organization, an active delegate, an exact whitelist or VIP address, any sender on the domain of those addresses or of an `@domain` whitelist or VIP rule (never a free-mail domain: `freeMailDomains`), and a frequent sender: 3 or more mails in this mailbox in 90 days, each with a newest `triage_results` row that is not `spam` and has no reason. The frequency is read once at the start of the batch, so mail of the same batch does not count for its siblings.
    - **Stored.** `triage_results.suspicious_reasons` (`text[]`, codes only, never text; the retention job does not clear it). The reasons are computed before the cap check and the LLM call, for the blocklist path, the classify path and the `llm_blocked` path. The error path (`finishTriageError`) stores `{}`, and a row from before F109 reads `{}`. The audit row `email.triaged` has the field `suspicious` (a comma list of codes; empty when none).
    - **Cost with the flag off.** Reasons are stored and the plan does not change. Each batch loads the context (up to 4 queries: mailbox addresses, frequent senders, members, VIP display names) and each mail reads its header row (1 query).
    - **Flag `suspicious_mail`** (default off, epic E3b, remove-by 2027-03-01). With the flag on, a mail with reasons whose final category is `delegation` plans nothing: no draft, no send, no `delegations` row, no move, also from the Junk folder (`holdDelegation` in `planActions`). The category and the place of the mail stay. The urgent notice and the digest show a warning line, and the Activity API field `suspicious` holds the codes (`[]` while the flag is off; the panel does not show it): [digest-and-notices.md](digest-and-notices.md) rule 6. The flag never changes the category and never moves mail.
    - **Readers for later tickets** (exported by `modules/triage/index.ts`): `suspiciousReasonsOf(db, ctx, emailIds)` (the newest row of each mail; a mail with no row and a clean mail are both absent) and `suspiciousThreadKeysOf(db, ctx, mailboxId, threadKeys)` (a thread is flagged when an incoming mail has a newest row with reasons). `suspiciousSendersOf(db, ctx, mailboxId, sendersLower, since)` (F110 stage 22: the senders with at least one mail since `since` whose newest row has reasons; bulk unsubscribe leaves them out). `listNewsletterSenders(db, ctx, mailboxId, now, { trustedAuthservIds })` (`newsletter-senders.ts`, F110 stage 22) lists the senders of the last 30 days whose every mail with a result is `info` or `notification` and that have no suspicious mail: at most 200, most mail first, each with `oneClick` (the newest mail has `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, an `https` link in `List-Unsubscribe`, and `dkim=pass` for the From domain in an `Authentication-Results` header of a trusted authserv-id) and `hasLink`. It reads stored headers only and never fetches a URL. All three suspicious readers ignore the flag, so a draft block holds with the flag off. `suspiciousReasonsToShow` follows the flag and serves notices and the panel.
    - **Measured on the sim** (`bun run eval --sim lab-01 --part holdout --suspicious`, `evals/results/2026-11-15-sim-lab-01-holdout-suspicious.md`): phishing recall 21 of 21 (100.0%), whitelisted cases flagged 0 of 315, non-phishing cases flagged 67 of 1392 (4.8%) against the target of at most 2%: missed. All 67 come from the one phishing persona. The owner decision of 2026-11-15 keeps the flag off.
18. **Classifier prompt versions (F109, PD-061, PD-062).** The registry holds `classifier-v2` and `classifier-v3` (`classifierVersions`); the pointer `prompts.classifier` names the production one: `classifier-v2`. `classifier-v3` runs only in `eval --prompt-version` and in tests.
    - **Parts of v3** (`classifierV3Parts`): `attachments` (always on), `urgency`, `history` and `list`. A list of optional parts is sorted by name (`classifier-v3[list]`). `CLASSIFIER_V3_PARTS` is the list of the production prompt when the pointer is v3; it is `["attachments"]` now. A later change of the text or the list is `classifier-v4` with its own gate.
    - **`ClassifierExtras`** (`classifier.ts`; v2 ignores it): `attachments` (non-inline parts, at most 10: name, type and size; the names are untrusted mail data), `isList` (a `List-Id` or `List-Unsubscribe` header), `senderHistory` (counts only: the mails of this sender in this mailbox in the 90 days before the mail, and the user's `wrong` corrections by `true_category`; `null` for a flagged mail or when there is no earlier mail; never the text of another mail) and `urgency` (the urgency profile of the mailbox with the local date of the mail; deadlines from the day before to 30 days after). `loadClassifierExtras` (`extras-reader.ts`) reads them for real and test mail. `triageOne` calls it only when the production prompt is not v2, so production triage reads no extras and does not use the stored urgency profile. The urgency profile is stored in `mailbox_settings.urgency_profile` and set by `PUT /api/settings/:mailboxId/urgency` or `bun run mailbox:settings urgency` ([actions-and-undo.md](actions-and-undo.md) rule 8).
    - **Dev result** (`evals/results/2026-11-15-f109-v3-dev-summary.md`): `Chosen parts: [list]`. `urgency` and `history` lost on the dev set.
    - **Holdout result: not shipped, decision pending.** One run of `classifier-v3[list]`: `K` 34 against 74 for v2, `spam` precision 97.6–99.9 against 80.3–88.8, but the whitelist rule shows 314 of 315 (one `bad_output` error on one whitelisted case, counted as not correct), so ship rule 4 failed. Owner decision 42 (the v3 ship question, `docs/owner-decisions.md`) is open. Production stays `classifier-v2`. The gate file `evals/results/gate/classifier-classifier-v3-gpt-6-luna-none-lab-01-v1.json` is committed.
    - **How to switch** (only after the owner says yes): in `prompts/index.ts` point `prompts.classifier` at the `classifier-v3` entry and set `CLASSIFIER_V3_PARTS` to `["list"]`. `triage_results.prompt_version` then records `classifier-v3`; old rows keep `classifier-v2`.
    - **Rollback rule after a switch.** The coordinator reads after 14 days of v3 on the pilot: if `bun run eval --gap` with the v3 gate file says `gap` for `notification` or `spam`, or the weekly M1 shows more found misses than the mean of the last two v2 weeks, point the registry back to `classifier-v2` (its gate file stays).
19. **Escalation (F109, PD-060): not built in triage.** Stage 13 said no ship: the cascade (a stronger model for about 24% of mail) costs $3.96 per mailbox per month against the limit of $3.00 (`evals/results/2026-11-15-f109-escalation-summary.md`), and it changed few answers. Owner decision "F109 escalation cascade: no ship by the cost rule". The worker never calls the role `escalation`, and no flag or setting turns it on. What is in the code: the role and its keys `LLM_ESCALATION_*` (`.env.example`), the prompt `escalation-v1` (the text of `classifier-v2`; its `base` must equal `prompts.classifier.version`), the pure trigger `shouldEscalate` (`packages/core/src/triage/escalation.ts`: a person's mail answered `info`, `notification` or `spam`, or `unsure`; never for `triage_error`, `llm_blocked` or `blocklist`) and the eval flag `--escalate` (rule 13).

## Data

`emails.status` flow (moved from `docs/architecture.md` §4.6):

```
emails.status:   pending → processing → triaged → done                (done = all its actions have an end status)
                 processing → pending                                 (soft error, config error or daily cap: no count; untried claimed mail keeps its next_attempt_at)
                 processing → pending                                 (hard error with tries left: attempts + 1, next try after 5 min)
                 processing → pending                                 (error on the mailbox, for example a DB error: untried claimed mail goes back, no count)
                 processing → triaged as `unsure`                     (after 3 hard errors, reason triage_error)
                 processing → triaged as `unsure`                     (safety block, reason llm_blocked)
                 processing → processing                              (stale claim: locked_at older than 5 min, taken again by a later run;
                                                                       the take-back counts one attempt; a mail at 3 attempts ends as unsure / triage_error without an LLM call)
                 processing → skipped                                 (older than 7 days and not backfilled, reason too_old)
                 processing → skipped                                 (received more than 24 h before resumed_at and not backfilled, reason suspended_backlog; tenancy-and-plans.md § Rules, rule 3, Resume)
                 skipped → pending                                    (one-off backfill re-queue of too_old and history_check mail in the window)
```

- `emails.status` is one of `pending`, `processing`, `triaged`, `done`, `skipped`; `skip_reason` holds `too_old`, `suspended_backlog`, `body_expired` or `history_check` (mail that the history check of the trust ladder stored: the worker never claims it, and no digest line or audit row counts it); `attempts`, `next_attempt_at` and `locked_at` drive the claim (`FOR UPDATE SKIP LOCKED`).
  - Check against the code: no code writes the status `done`. The check constraint of `emails.status` allows it, but a mail stays `triaged` when its actions end, so the flow `triaged → done` above does not happen today.
- `triage_results`: `category`, `vip`, `confidence`, `reason_code`, `reason`, `fields` (with `model_category` and, since F110 stage 16, `rule`: `blocklist` when the hard rule gave spam, `vip` for a VIP, `whitelist` for a whitelisted sender that is not VIP, else `null`; no pattern is stored; an old row has no key), `model`, `prompt_version`, `suspicious_reasons` (`text[]`, codes of rule 17, default `{}`), `tokens_in`, `tokens_out`, `latency_ms`. A mail can have several rows; the newest wins.
- `triage_feedback`: `verdict` (`right`, `wrong`), `true_category`, `source` (`cli`, `telegram`, `undo`, `imap_move`, `web`, `review`, `answered_check`), `user_id`.
- `mailbox_settings`: `mode`, `tool_switches`, `category_policy` (per category: `threshold`, `auto`), `urgency_profile` (jsonb or null: topics and deadlines of the owner; set by the route and the CLI of rule 18; a change bumps the settings version); the job compares a settings version (rule 9).
- `emails.from_address_lower`: a stored generated copy of `lower(from_address)` with the index `emails_mailbox_sender_idx (mailbox_id, from_address_lower, received_at)`. The sender queries of rules 17 and 18 use it, never `lower(from_address)` (the tenant policy blocks that expression as an index condition). It follows `from_address` when retention clears the address (`notes/2026-11-15-f109-sender-index-rls.md`).
- `sender_rules`: `pattern`, `kind` (`whitelist`, `blocklist`, `vip`); at most 1000 per organization.
- Audit events: `llm.call` (one per call attempt: role, prompt version, model, endpoint, outcome, tokens, latency), `email.triaged` (with the field `suspicious`, rule 17), `email.skipped`, `email.requeued`, `action.planned`, `settings.urgency_set` (counts and `via` only).

## Limits

- Suspicious-mail rules (rule 17), limits that stay:
  - No check of password-protected archives: `risky_attachment` reads the name and the type of an attachment, never its content.
  - `auth_fail` is silent without a trusted `Authentication-Results` header. Whether the pilot host (Interia) adds one is not known (N1 still open, `notes/2026-11-15-e3b-improve-results.md`).
  - A forged own mailbox address, a forged delegate address or any forged address on an organization domain counts as known. Only `auth_fail` can catch it, and only with a trusted header.
  - A CEO name that is not a member, a delegate or a VIP is not protected from `display_name_spoof`.
  - Old `triage_results` rows read as `{}` and count as clean for the frequent-sender rule, so a phisher with 3 old non-spam mails in the window is known. The error path also stores `{}`.
  - The lab-01 phishing mail comes from one look-alike persona with one domain. The sim has no `Authentication-Results`, no `Reply-To` and no HTML links, so the sim numbers say little about the other rules and nothing about marketing mail with tracking links.
  - The folder hint (F061) and a cold-mail reason code are not built: the sim has no truth for them (plan D14).
- The prompt (rules 18 and 19): the production prompt is `classifier-v2`, v3 is not shipped (decision pending) and escalation is not built. `urgent` stays the weak category: the false-negative rate of `urgent` on the v2 holdout is 14.1% and of `needs_reply` 6.2% (`spec/features/active/F109-e3b-improve/plan.md` P10), against the M1 target of under 2%. The urgency profile is stored but production triage does not read it.
- The first sim-vs-real gap report (`evals/results/2026-11-15-sim-vs-real-gap-lab-01.md`, holdout reports and gate file in `evals/results/`) says `no gap` for `notification` and `spam`: the sim precision intervals overlap the real ones (138 real labels, 2026-11-15). Real labels never unlock `auto` (ADR 0028).
- The gate on real labels (precision at least 98% on at least 30 labels) stays until ADR 0028 (proposed) changes it; E3 sets the numbers.
- A junk-folder wave can use the shared daily cap: `F063-junk-llm-cap`.
- The roles `classifier`, `judge` (`judge-v1`) and `escalation` (`escalation-v1`, eval only) and `extractor` (`extractor-v1`, called by `extractSent` in module `loops`, from the job `loops.analyze`: `open-loops.md` rule 2) have a prompt. `drafter` (E6a) has none (`rolesWithoutPrompt`).
- The LLM pause is in memory: a restart clears it. `/status` and the digest read the pause from the `llm.call` audit rows (`latestLlmPause`), so they show it after a restart too (flag `llm_pause_line`).

# Code patterns — rules for agents and humans

> **Accepted 2026-11-02** (user). Replaces `.ai/AGENT.md` (history: it describes the old `IntegrationFactory` and generic adapters; do not use them).
> Source: `docs/architecture.md` §3–4 and `docs/modules.md` §3. When code and this file disagree, fix one of them in the same commit.

## Layout and borders

- Packages: `@ea/server` (`apps/server`), `@ea/web` (`apps/web`), `@ea/core` (`packages/core`).
- Server code lives in `apps/server/src/modules/<module>/` and `apps/server/src/platform/`. Shared pure code lives in `packages/core/`.
- Real platform paths: `platform/config.ts` (the merged schema and `loadConfig`; the keys by concern in `config-llm.ts`, `config-mail.ts`, `config-ops.ts`, `config-push.ts`, `config-shared.ts`; `config.ts` re-exports every name, importers keep `./config`), `platform/log.ts`, `platform/http.ts`, `platform/db/`, `platform/llm/`, `platform/crypto.ts`, `platform/errors.ts`, `platform/auth.ts`, `platform/scheduler.ts`, `platform/heartbeat.ts`.
- A module exposes one `index.ts`. Other modules import only from it, never from its inner files. ESLint enforces it (§ Layers and borders).
- Module files: `index.ts` (public API), `service.ts`, `repo.ts` (DB; past about 400 lines a `repo/` folder, one file per aggregate, behind `repo/index.ts`: `actions/repo/`, `mail/repo/`), `routes.ts` (HTTP), `jobs.ts` (workers), `*.test.ts` next to the code.
- `packages/core` has no I/O: no DB, no network, no `process.env`, no imports from `apps/*`.
- Test tools live in `tools/<name>/` (workspace `tools/*`, first: `tools/fake-telegram/`). App code (`apps/*`, `packages/*`) never imports them, and the server image holds only their `package.json`.

## Layers and borders

The server modules sit in layers. `bun run lint` fails on an import that crosses a border the wrong way (`import/no-restricted-paths`, zones generated in `eslint.config.js` from `apps/server/src/modules/layers.json`). The list lives once, in that file; this table repeats it for readers.

| Layer | Modules                                                                                                                             |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------- |
| roots | the composition roots `apps/server/src/*.ts` (`main.ts`, `web.ts`, `composition.ts`, `retention.ts`), `apps/server/src/start/` (one start file per runtime) and `apps/server/src/scripts/` |
| 6     | `lab` (a leaf: `main.ts` never starts it)                                                                                           |
| 5     | `operator`, `privacy`, `trust`                                                                                                      |
| 4     | `reports`, `channels`, `testmail`                                                                                                   |
| 3     | `triage`, `actions`, `delegation`                                                                                                   |
| 2     | `config`, `mail`                                                                                                                    |
| 1     | `audit`, `tenancy`                                                                                                                  |
| base  | `apps/server/src/platform/`, then `packages/core`                                                                                   |

- A module imports only the `index.ts` of a module in a lower layer, or of a module in its own layer when `sameLayerEdges` in `layers.json` names the pair with its reason. Never an inner file (`../mail/repo`), also not for a type, a re-export or an `import()`.
- A module never imports a composition root or a script. `platform` imports no module. `packages/*` import nothing from `apps/*`.
- A reverse need (a lower module must call a higher one) is a hook interface or a parameter in the lower module, filled in a composition root: `DelegationHooks` in `actions/hooks.ts` (write side), the keep rule `PayloadKeepRule` of `clearActionPayloads` that `retention.ts` fills with `isOpenDelegationDraft` of `delegation` (read side). A shared plain shape goes to `packages/core` (`ExpireFilter`).
- A new module: add its folder name to a layer in `layers.json` (the lint stops with "Modules without a layer" until you do).
- A new or removed import between two modules (also a permitted one): run `bun run graph:modules` and commit `docs/diagrams/module-graph.{md,json}`; `layers.test.ts` fails on a stale graph. On a merge or rebase conflict in these two files, run the command again; do not merge them by hand.
- A new same-layer edge: add `{ from, to, why }` to `sameLayerEdges`. It must not close a cycle: the lint stops on a cycle in `sameLayerEdges`, and `apps/server/src/modules/layers.test.ts` fails on a cycle, on an edge that the layers do not permit, and on a stale generated graph.
- Test files (`*.test.ts`, `apps/server/test/`) are outside the borders: they assemble modules like a composition root. The e2e seed scripts in `rootDeepImportExceptions` may import a repository directly; add no other entry without a reason in its `why`.
- The generated graph: `docs/diagrams/module-graph.md`. The reasons for single edges: `docs/modules.md` §2.

## Size and shape

- A source file stays under about 400 lines and holds one aggregate (one table or one closely tied group of tables). A repository that grows past it becomes `repo/<aggregate>.ts` behind the same module `index.ts`. `bun run lint` warns over 400 lines and fails over 800 for every non-test source file (`eslint.config.js`, the `size` rule); an `eslint-disable` of the size rules is not allowed.
- Registries over if-chains: action handlers, notice detectors, notice renderers, LLM roles, prompts and jobs are entries in a typed record keyed by the enum. A test checks the record against the enum and, where one exists, the CHECK list of the migration. A new kind is a new entry, not a new `if` or `case` in a shared function.
- A CLI script that reads or writes the DB parses its arguments, loads config and calls a service function of a module index, the same function a route calls (ADR 0023). It does not query a repository directly. A dev tool that touches no DB (`scripts/module-graph.ts`) is outside this rule. Existing scripts change when they are touched.
- Split a file by moves, not rewrites. A repository becomes `repo/<aggregate>.ts` plus `repo/index.ts`, which re-exports by name every export of the old file and nothing else; importers keep `./repo` (it resolves to `repo/index.ts`), so no import path changes. A helper that two files need stays in the file of its topic with an internal export; `repo/shared.ts` holds only what has no topic (`DbOrTrx`, `actionTypeSchema`). Keep `git log --follow` for every new file with the history merge of `spec/features/*/F091-repo-split/tools.md` (`history-copies.sh`: one rename commit per new file, one merge, then the trim commit), and prove the move with its `same-bodies.ts` and `exports-of.ts`. Never rebase or squash such a branch; merge `master` into it. After its land, fix a failed push with `git pull --no-rebase`, not `git pull --rebase` (a rebase replays the copy commits and conflicts).
- A typed record keyed by the enum is the default for a per-kind choice. Where each case is a few lines inside a larger function (`decidePolicy`, `payloadOf`, `phrase`), an exhaustive `switch` with no `default` is allowed: typecheck fails on a missing case, as with a record. A `default` branch or an `if` chain that falls through to one kind is not.
- Minutes, hours and days in milliseconds come from `MINUTE_MS`, `HOUR_MS` and `DAY_MS` in `packages/core/src/time.ts`, folded to the largest whole unit (`2 * HOUR_MS`, not `120 * MINUTE_MS`). The local lint rule `ea/no-time-literals` bans the literals (`60_000`, `3_600_000`, `86_400_000`), the folded chains (`24 * 60 * 60 * 1000`) and local copies of the three names outside test code. A value that is not a time takes a disable comment with its reason. A new local rule joins the `ea` plugin in `tools/eslint-rules/index.js`.

A draft that waits for approval is never edited in place. An edit is a superseding row: `editApproval` (`actions/edit.ts`) adds a new `create_draft` and a new `send`, each with `supersedes_action_id` set to the old row, and ends the old send as `expired` / `superseded`, in one transaction. The version, the Drafts copy and the new tap all need new rows; a changed payload would need rules for each of them.

### An action on a loop

A follow-up answers the user's own Sent mail, so it has no incoming mail. An action hangs on one anchor: `email_id` or `loop_id` (open loops, ADR 0036). Use this list when a new code path reads or writes `actions` or `outbox`.

1. **The anchor rule.** The database allows exactly one of `email_id` and `loop_id`, and a `loop_id` row is a `create_draft` or a `send` only (`actions_anchor_check`; `actions-loop-anchor-schema.test.ts`). A new writer for loops uses `createPlannedForLoop` (`actions/repo/planned.ts`); it never sets `set_id` (a follow-up is never in an approval set).
2. **Read it through the anchor helpers** (`actions/anchor.ts`). A path that exists only for incoming mail (Undo, mailbox moves, triage planning, delegation, clarification, reminder, the activity of a mail) calls `emailIdOf(row)`: for a loop row it throws `ActionAnchorError("loop_anchor")`, so a missed path fails loud, not silent. A path that must handle both calls `anchorOfRow(row)` and branches.
3. **The hook.** `actions` never imports `loops`. It calls `LoopHooks` (`isOpen`, `anchorOf`, `onFollowUpSent`; `noLoopHooks` by default, `loopHooks()` from the composition root). The committer asks `isOpen` before the Drafts APPEND and before SMTP and ends a send of a closed loop `expired` / `loop_closed`; the card builder reads the text through `anchorOf`, so the card shows the text that is sent.
4. **Recipients from the loop row only.** `to` and `cc` of the draft and the send come from `open_loops`; a payload that names another address is `bad_payload` and no SMTP call. Nothing from an LLM reaches an address. The send limits and `SEND_SCOPE` count `to ∪ cc`.
5. **Lock order.** The settings row (share), the Sent state row, then the loop, then its sends. A close, a Later, a Draft tap, the chaser, the committer and `onSentOff` follow it, and each rule of the kind "exactly one" has a race test on two connections (also as the table owner).
6. **Copies.** A loop action copies subject, recipients and a quote into `actions.payload` and `outbox`. A new copy needs a delete rule in `onSentOff` (`clearLoopSentCopies`, `clearLoopCards`), in retention and in the erase, and a case in the scan test `loops-sent-off-copies.test.ts`.
7. **Consent.** A message with loop data in Telegram goes through `loopConsentOf` (`channels/consent.ts`); `consent-gate.test.ts` lists the files that may queue loop data.

### Add a user command

A user command is an HTTP route plus one service function (ADR 0023). In this order:

1. The service function in the module (`approve`, `editApproval`, `remindNow`, `cancelByUser`, `updateDelegate`). It takes `via` (`web`, `telegram` or `cli`) and writes it to the audit row (and to `approved_via` for a send). It takes no request object, runs in one transaction in the lock order of its module, and makes no outside call inside it.
2. The schemas in `packages/core/src/web/` (a strict body, the answer, the error codes). The route and the page import the same ones. The raw limits of a body are wider than the limits of the service: the service decides and answers `400 validation` with the field.
3. The route in the module's `routes.ts` with its `apiDoc` in `api-docs.ts` (§ HTTP routes). It parses with `parseBody`, checks a path id with a UUID schema (a bad id is `400 validation`), and lists every error code that it can answer.
4. The role check: `requireOwner` for an owner command, none for a read or a command of every member. While the feature is new, a flag middleware runs before the role check, so every role gets `404 not_found` while the flag is off. The flag is in `featureFlags` (`packages/core/src/features.ts`) with its epic and remove-by date, default off.
5. A command that decides a send (approve, reject, edit, a cancel that rejects a send) calls `ApprovalHooks.onDecided` in the same transaction, with the real hook `cardEditHooks` from the composition root (`web-routers.ts`), so the Telegram cards follow. The hook never changes the decision: its failure is logged and undone to a savepoint.
6. Tests: the route test (401, 403 for a role that may not, 404 for a foreign id and for the flag off, 400 for a bad body or id), a race test on two connections when the command changes state (`web-approvals-races.test.ts` is the model), `openapi-routes.test.ts`, and for a page the e2e spec with `expectNoA11yViolations`. The texts of the page go into `en.ts` and `pl.ts`; the texts of a notice go into `packages/core/src/texts/`.
7. The docs: the rules in the capability page, the router row in `docs/capabilities/web-panel.md` rule 7, and `docs/modules.md` §3.10.

## Notices are facts

A module that has something to tell a user through the outbox (digests and notices) queues facts. It never builds the text of a channel (ADR 0032 point 5). Direct replies (command answers, tap answers, the link texts, the operator notices) are not outbox rows and read their texts from `packages/core/src/texts/bot.ts` (one file for each locale: `bot-en.ts`, `bot-pl.ts`) in the chat's locale (the operator notices in `operator/notices.ts` read `OPERATOR_LOCALE`).

- A notice enters the outbox only through `queueNotice` (`apps/server/src/modules/channels/notice-queue.ts`) with `{ userId, locale, kind, view, dedupKey }`. The view is the input of the kind's renderer: ids, counts, dates, and the strings from mail data or from users that the text prints (subject, sender, names). It holds no phrase of ours: a fixed word or sentence comes from the renderer, so a new locale or a new channel changes only the renderer.
- Each kind has a strict view schema (`noticeViewSchemas`, `packages/core/src/notices/views.ts`; the shared fields are in `view-fields.ts`, the approval and send result views in `views-approvals.ts`): no field that the renderer does not print. A view holds mail-derived text: it follows the retention of `outbox.text` (`clearOutboxTexts`, `docs/architecture.md` §7) and never reaches a log line, an error text or a test name.
- `queueNotice` renders the view once as a check. A view that does not render never enters the outbox, and the event gets no row. Where the producer marks its source row (approvals, sets, send results, delegation answers, action failures, digests), the mark is in the same transaction, so it rolls back and the event is tried again. Urgent, `auth_error`, `sync_stale` and `sync_ok` have no mark: the next tick finds the event again and retries through the dedup key.
- `queueNotice` with no `channel` is the fan-out of one member and event: `planFanOut` (`channels/notice-fan-out.ts`) reads the flag `web_push`, the stored routes, the chat link and the live devices, and the call writes the Telegram row (the dedup key as it was) and one push row per device (`<key>:push:<device id>`). A kind of a push group (`noticeGroupOf`) needs `eventAt`, the time of the event: a push row goes only to a device that existed then, so a new device gets no burst of old notices. `only: "telegram"` is for the answer to a Telegram tap (it reads nothing and needs no `eventAt`); `only: "push"` is for the real kind of a follow-up that the loop-consent gate holds back from Telegram (`splitByLoopConsent`).
- The sender renders when it sends: `renderNotice(kind, view, { channel, detail, locale })` from `@ea/core`. `outbox.text` and `outbox.buttons` are the cache of the sent message (null and `[]` until the send). A row whose view does not render becomes `failed` / `bad_view`.
- A row waits up to 24 h in the outbox (the sender fails an older row with `expired`), and newer code may render it. A change of a view schema or of a view field must still accept the views of the rows queued in the last 24 h. If it cannot, the change waits until those rows drain (`deploy/README.md` § Notices as facts). Otherwise every waiting row of the kind becomes `failed` / `bad_view` and the user gets nothing.
- A clock in a view is a fact of the queue time (`now`, `timeZone`): a notice held by the quiet hours prints the same text when it goes out.
- The edit after a tap keeps the stored text of the card and adds one status line (`renderNoticeEdit`); it never renders the card again.
- Every kind has a `telegram.minimal` renderer (the type requires it): fixed phrases, numbers, the clock and one panel link, never a string of the view, no button (`notices/minimal.ts`, `texts/minimal.ts`). A new kind or a new view field that prints text needs its planted word in the canary test (`notices/minimal.test.ts`): a string that a `minimal` text can hold must be a fact (`noticeFactsOf`), not a field of the view.
- The row's `locale` comes from `users.locale` (null = `pl`, as the auth mails). A renderer takes its words from `textsFor(locale)` (`packages/core/src/texts/`): one entry per text, in `en` and `pl`.

### Add a notice kind

1. Core: add the kind to `noticeKinds` (`packages/core/src/notices/kinds.ts`), a strict view schema to `noticeViewSchemas` (`views.ts`) and an entry to `noticeRenderers` (`renderers.ts`) with a `telegram.full` function and a `telegram.minimal` function (the type requires both: a kind without `minimal` fails the typecheck, so it can never send full text to a member at the level `minimal`). The `minimal` text is fixed phrases and numbers only: add its phrase in `en` and `pl`: a kind in a push group (`noticeGroups`, `notices/push.ts`) takes the line from its push text (`packages/core/src/texts/push.ts`; the same texts build the notification), any other kind gets an own phrase in `packages/core/src/texts/minimal.ts` (`minimalOwnPhraseKinds`). Take the count and the item id from `noticeFactsOf` (`notices/facts.ts`; a string of the view is never a fact). For a kind in a push group, also add a `push` renderer (`pushOf(kind)`). Unit tests: the exact text for one fixed view, and the planted word of `notices/minimal.test.ts` for the new kind.
2. Migration: add the kind to `outbox_kind_check` (drop and add the constraint, as `db/migrations/20261111000001_delete_mailbox.sql` does); the `down` part deletes the rows of the kind first. A kind that needs `email_id`, `mailbox_id` or `digest_id` gets that check too.
3. Server: one detector file `apps/server/src/modules/channels/notices/<kind>.ts` that exports a `Detector` listed in `detectors` (`notices/index.ts`), or, for a producer outside the notifier, an entry in `queuedBy`. The producer calls `queueNotice`.
4. Tests: `channels/notices/registry.test.ts` and the `CHECK` test in `apps/server/test/integration/telegram-schema.test.ts` fail until steps 1–3 are complete. Add an integration case in `channels-notices.test.ts`: one row per member, no second row on a second run.
5. Docs: the `outbox` row of `docs/architecture.md` §5 (kind, dedup key) and the `channels` table of `docs/modules.md` §3.8.

## Texts carry a locale

Every text that a user reads has an English and a Polish version, from the first commit. Two surfaces, two dictionaries (F098).

The language of a product text is `UserLocale`; the lint rule `ea/no-locale-union` bans a copy. The language of a mail or a draft is another concept.

**The null rule.** `users.locale` is `pl`, `en` or null. A null value means a different language on each surface:

- Panel: `resolveLocale(users.locale, browserTag)` from `@ea/core`. Null → the browser language (`navigator.language` starting with `pl` → Polish), else English.
- Telegram and auth mails: null → Polish. A user with no stored language gets Polish Telegram text at once (owner decision, `docs/owner-decisions.md`).
- The Account card writes only `pl` or `en` (`PATCH /api/me/locale`). A null value cannot be set again.

**Panel texts** (`apps/web/src/i18n/`):

- `en.ts` holds the keys and `TextKey`. `pl.ts` is `Record<TextKey, string>`: a missing or extra key fails `bun run typecheck`. `i18n.test.ts` checks that each key has the same `{placeholders}` in both files.
- A count text is a plural pair: `enPlurals` (`one`, `other`) and `plPlurals` (`one`, `few`, `many`). Read it with `tp(key, count, vars)`. A single text reads with `t(key, vars)`.
- The default export of every island calls `useLocale()` on its first line, so a language change re-renders the island (`islands.test.ts` checks every file in `src/islands/`).
- Every island is `client:only="react"`. The static build cannot know the user's language, and a server-rendered English island hydrated with Polish text gives a hydration mismatch.
- A date uses `dateLocale()` (`pl-PL` or `en-GB`), never a fixed locale.

**Core texts** (`packages/core/src/texts/`):

- One file per section (`clock.ts`, `categories.ts`, `answers.ts`, `would-do.ts`, `ai-text.ts`, `notices.ts`, `approvals.ts`, `digest.ts`, `bot.ts`, …). Each file has `{ en: {…}, pl: {…} } satisfies Record<UserLocale, Section>`: both languages sit side by side and TypeScript enforces the parity.
- `index.ts` holds `CoreTexts`, `textTables` and `textsFor(locale)`. A render function takes `texts: CoreTexts` as its last, required parameter. A function never reads a global locale.
- Where each Telegram path takes its locale: an outbox row, from `outbox.locale` (set by `queueNotice` from `chat_links` → `users.locale ?? "pl"`); a command or a tap, from the chat link (`LinkedChat.locale`); `/start` with a used or expired token, from the token owner (`users.locale ?? "pl"` through `getUserAuthProfile`). The command menu follows the app language of Telegram, not `users.locale`.
- A route that returns our phrases to the panel (today only `GET /api/activity`) reads the request locale: `resolveLocale(profile?.locale ?? null, firstLanguageTag(c.req.header("accept-language")))`, then `textsFor(locale)`.

**Polish text rules.**

- Informal second person ("ty"), imperative for actions ("Wpisz", "Zapisz"). One word per idea, from the glossary (`spec/features/active/F098-e7-t1-polish-ui-i18n-frame-first/plan.md` § Glossary, until a docs page takes it).
- A Polish text is a whole sentence. It never reuses English word order or English fragments.
- Every count goes through `pluralCategory(locale, count)`. Polish has `one`, `few` and `many`; `other` (a fraction) reads as `many`.
- A line holds at most one colon. A message uses one separator style (`·`, as the English texts do).
- A name or an address (sender, delegate, mailbox, folder) never takes a Polish case ending. Put it after a fixed word, as in "zostaje w INBOX".
- A placeholder for an unknown value that is stored in a view (`"(unknown sender)"`) maps to a text of the locale at render time (`texts.common.unknownSender`): the stored English value is a key, not a text.

**The consent version.** `TELEGRAM_CONSENT_VERSION` (`packages/core/src/web/telegram.ts`) names the consent text of the Telegram link step. When a new kind of mail-derived data reaches Telegram (addresses, names, domains, subject, body, attachment names or types, link hosts), change the consent text and bump the version in one commit. Fixed phrases that our own code picks from our own codes (the suspicious warning line, category tags, would-do phrases) do not bump: they hold no mail-derived data. A new field of a notice bumps only when it carries a new kind of mail-derived data. An old version gets 409 `telegram_consent_outdated`. The gate blocks only NEW links (`POST /channels/telegram/link`). Chats that are already linked are not asked again by the link route. Loop data (F116) is the first kind that checks the version at send time: `consentVersionsOf` and `consentCovers(version, OPEN_LOOPS_CONSENT_SINCE)` decide per user, and a linked user confirms through `POST /api/telegram/consent`. Both legal stamps (this one and `TERMS_VERSION`) use `YYYY-MM-DD` and `.N` from 2 (`packages/core/src/web/legal-version.ts`); `nextLegalVersion` gives the next one, and the two old hyphen terms entries stay as stored. A bump after the first one on the same day needs the new version: the gate compares versions, so a kept version would mark an old consent as covered. So a feature flag that adds a new kind of mail data to Telegram stays OFF for every org with linked chats until a re-ask exists or the owner accepts the gap (owner decision of 2026-11-15 in `docs/owner-decisions.md`).

**Old cards.** A Telegram card keeps the text that was sent. The edit after a tap adds one status line in the row's locale and never renders the card again. A card that was queued before a language switch keeps its old text, and the status line follows the new one. The buttons Gotowe, Wysłano and "To był błąd" work for 7 days, and the approval buttons for 48 h, so a mixed card can show for up to 7 days. A new text change must plan for this.

## Migrations

- **Forward only.** A live database never gets `db:rollback`. The `-- migrate:down` part is for the dev database. A release rolls back by code (`deploy/rollback.sh`), not by schema.
- **Expand, then contract.** Release N adds (a table, a nullable column, a column with a default, an index, a wider CHECK list) and its code writes the new shape. A later release removes what the code no longer uses (a drop, a rename, a type change, `SET NOT NULL`, a narrower CHECK list), after the release that stopped the use is deployed.
- **A release's migration works with the code of the previous release.** The rollback target runs on the new schema. Check it: the previous code must still read and write every table and column that it knew.
- **A contract statement carries `-- contract: v<x.y.z>`** on its own line in the file: the release that stopped the use. `bun run db:check-migrations` (CI, `ci` job, before `db:migrate`) fails a migration newer than `CONTRACT_CHECK_AFTER` that holds `DROP TABLE|COLUMN|TYPE|VIEW|SCHEMA|SEQUENCE|EXTENSION`, `RENAME`, `ALTER COLUMN … TYPE`, `SET NOT NULL`, `TRUNCATE`, `REVOKE`, `ADD CONSTRAINT` on a table that the file does not create, or `DROP CONSTRAINT|INDEX|FUNCTION|TRIGGER|POLICY x` that the file does not create again. A replace (drop `x`, create `x`) passes. Only the `-- migrate:up` part is read, comments and quoted strings excluded.
- **A narrowed CHECK is a contract.** A replace that makes a CHECK list shorter (for example a `kind IN (...)` list) passes the script, because the script does not read the list. The reviewer checks the lists of every replaced constraint and adds the `-- contract:` line by hand. The same holds for a new `NOT NULL` column with no default and a new unique index on data that already exists.
- **A broken migration gets a forward fix or a restore.** Do not edit an applied migration. Ship a new migration in a patch release, or restore from the backup taken by `deploy/release.sh` (`deploy/README.md` § Release).
- The cutoff is the newest migration at the base of the check. Do not move it to hide a finding.

## HTTP routes (S5)

A route file (`routes.ts`) is thin: it parses the body with `parseBody` and a `@ea/core` schema, calls one service or repository function, and maps the result to JSON. No SQL, no business rule, no `org_id` from the request: `requireTenant` sets `ctx` from the session. Every route test covers 401 (no session), 403 (an assistant on an owner route, when the route is owner-only), 404 (another organization's id, when the route takes an id) and 400 (a bad body, `details` without the input). The platform (`platform/http.ts`) imports no module; the composition root (`apps/server/src/web.ts` and its parts `web-routers.ts`, `web-route-deps.ts`) wires the module routers. A service that needs another module's write inside its own transaction gets it as an injected hook from the composition root (`removeMailbox.onRemoved`, which queues the owner notice of `channels`), and the onboarding state is injected into `tenancyRoutes` (S5b). A route that needs another module's service gets it as an injected dependency from the composition root: `settingsRoutes` gets the gate (`triage`) and the folder setter (`mail`) through `settingsRouteDeps` in `web-route-deps.ts` (S5c). `config` reads `mailboxes` for `mailboxInOrg`, as it does for `getMovesSupported`, because it cannot import `mail`.

Every `/api` write (any method except GET, HEAD, OPTIONS) of a `suspended` organization answers `403 org_suspended` through `refuseSuspendedWrites` (`platform/http.ts`). A write that must work in `suspended` goes into `SUSPENDED_WRITE_ALLOW` with a test.

Routes under `/api/operator` are the only web code that reads across organizations (ADR 0027). `createApp` guards the whole prefix with `requireOperator`: only users in `OPERATOR_USER_IDS` pass; every other user, also an owner, gets the same `404 { error: "not_found" }` as an unknown path. The guard runs after `requireTenant`, so the operator is a member of an organization. Mount an operator router at `/operator`. A router never calls `use("*")` when it is mounted at `/`: Hono then runs it for every `/api` path. Every operator route test covers 401 (no session), 404 for an owner who is not an operator, and the operator's answer. `requireTenant` runs the rest of each `/api` request in the tenant scope; `requireOperator` runs operator routes without it. Only `platform/http.ts` and `platform/scheduler.ts` call `withTenantScope` and `withoutTenantScope` (`tenant-scope-sites.test.ts`). Work that a request starts and that outlives it (a timer, a loop, a promise chain), and an object made in a request whose callbacks outlive it (an `EventEmitter`, an IMAP IDLE client, a stream: its callbacks run in the scope of the request), is made in `withoutTenantScope`, or it stays limited to that organization. The `operator` module (layer 5) owns every `/api/operator/*` route. It reads other organizations only through tenant-scoped functions, one organization at a time. The one exception is the SLO job (F114), which uses the readers listed in § Data access (`listLaggingMailboxes`, `listUrgentCandidates`, `countLlmCallOutcomesSince`) and runs with no tenant scope. Its answers hold ids, codes, counts and dates (ADR 0027 point 3); a route test asserts the key set and that the body holds no name or address. A write calls the CLI's service function with the operator's user id as actor. `POST /api/operator/*` is in `SUSPENDED_WRITE_ALLOW`. The page `/operator` answers non-operators the 404 page (`OPERATOR_PAGE` in `platform/http.ts`); its JS chunk under `/_astro/` stays public, so a page never holds data in its build.

Every `/api` route, also one before the session guard, has `apiDoc` (`platform/openapi.ts`); `openapi-routes.test.ts` fails otherwise (ADR 0023). A route has no list of gaps: it is described, or hidden with a reason in `HIDDEN_ROUTES`. A module keeps its `apiDoc` calls in `api-docs.ts`; they use the same body and answer schemas as the route and the web (never a second copy). `ok: { status: 204 }` describes an empty answer; `params` types a path parameter (a UUID); the shared guard codes (401, 403, 413 and 400 `validation` for a body) are added for every route.

An id in a body or a query that fails the schema is 400. An unknown or foreign id that passes the schema is 404 `{ error: "not_found" }`, with no row written (S5d, B8). The service decides the 404 (`recordWebFeedback`, `undoWithFeedback` return `not_found`), not the route. Telegram and the web call the same service for Undo, so both channels answer alike.

## Config and secrets

- All config comes from env, checked with a Zod schema at start (`platform/config`). A missing key stops the start.
- `.env.example` lists every key with a placeholder. Never commit `.env`, keys, passwords or tokens. Never log them.
- Mailbox secrets are encrypted with `platform/crypto` (AES-256-GCM, key version) before they reach the DB.
- LLM keys: `LLM_PROVIDER` picks the provider for every role (its tiers pick the models); each row has `<P>_API_KEY`, `<P>_TIMEOUT_MS` and `<P>_RPM`; `LLM_<ROLE>_TIMEOUT_MS` and `_RPM` set one role. The model and effort keys of older releases are removed (`removedEnvKeys` in `platform/config-llm.ts`): a non-empty value stops config. The openai row also reads `OPENAI_BASE_URL`, `OPENAI_ENDPOINT_KIND` and `OPENAI_OWN_*` for an own server (`docs/own-model.md`).

## Logs (ADR 0024)

- A log line is an event: `log.<level>("<event_code>", { <fields> })`. The code is a snake_case literal of at most 64 characters, constant, and names what happened (`auth_mail_failed`): the thing, then what happened. `msg` equals the code. One code for one kind of line. A number or an id is a field, never part of the code.
- Fields come only from the three kind lists in `apps/server/src/platform/log-fields.ts`; `logFieldNames` joins them, and `LogFields` types each name by its kind.
  - `uuidFieldNames`: a lower-case UUID or `null` (`org_id`, `mailbox_id`, `run_id`). The writer drops any other string, so a non-UUID id vanishes.
  - `numberFieldNames`: a finite number or `null` (counts, times, durations). A new number name is free.
  - `codeFieldNames`: a number, a boolean, `null`, or a code of at most 64 characters from `A–Z a–z 0–9 _ . : / * -` without `://`. A code value comes from a closed set: a union, a constant, a config value, a route pattern, an error name or code. Never mail text, a user value or any text from outside the server. A new UUID or code name needs a reason in the change that adds it.
    The writer drops a wrong name or a wrong kind and counts it in `dropped_fields`. A line with `dropped_fields` is a bug to fix. `log.info("x", { count: "a" })` and a name that is on no list fail the typecheck. Never widen a kind to make a call compile.
    The value rule does not stop a secret that looks like a code: never add a field for a token, a password or a key value, and never pass one in a code field.
- Errors: `...errorFields(error)` (`error` = the error name, `error_code`). In Telegram code: `...telegramErrorFields(error)` (`error`, `error_code`, `method`). Never `error.message`, `payload` or `description`, a mail text, an address, a URL or a token. The lint fails on `.message` inside a log call.
- Context: the scheduler gives every line of a job tick `job` and `run_id` (`runJobTick`). Every Telegram update runs in `withLogContext({ job: "telegram.update", run_id })` (the first bot middleware), so its lines carry a `run_id` too. The HTTP layer gives every line of a request `request_id` and sets the `x-request-id` header.
  Per-item ids come from a child logger: `const mailboxLog = log.with({ org_id, mailbox_id })`. Name a child logger `<thing>Log` (the lint finds it by that name). A call on a chain (`log.with({ … }).info(…)`) and a call on a member logger (`this.log.info(…)`) are checked too.
  Inside a run or a request, never pass `job`, `run_id` or `request_id` by hand (the context value wins and the call value is dropped).
  Only a line outside any context names a job with `job` (`job_scheduled`, `job_skipped`).
  Create a long-lived timer, interval, socket or pool at start, outside any context: it keeps the context it was created in.
- Format: the server prints `json` by default (its config) and the VPS pins `LOG_FORMAT: json` (`deploy/compose.yaml`). `text` prints `[module] event key=value …` (dev, `.env.example`).
  A process that does not load the config (a CLI, a test) prints `text` unless `LOG_FORMAT=json`. Tests run in `text` (the test preload).
- `Log` has only the event signature. A call of another shape (a free text, a second argument that is not an object, three arguments) writes one `log_call_invalid` line with the context fields only and `dropped_fields: 1`, and never prints the argument.
- Lint: in `apps/server/src` (tests excepted) `no-restricted-syntax` and `no-console` are at `error` (`eslint.config.js`, `logEventSelectors`). It fails on a first argument that is not a snake_case literal, a call with no or more than two arguments, a second argument that is not an object literal or a call of `errorFields` / `telegramErrorFields`, a `.message` in the fields, and a call on a chain with any of these. A new log line in any file is an event.
- CLI scripts (`apps/server/src/scripts/`): the standard for arguments, exit codes, output and risk is `docs/cli.md`. They print to the operator's terminal through `createCliOutput(name)` (`platform/cli.ts`): `print` to stdout, `fail` to stderr, `[name] text`, always text; `raw` writes a bare line to stdout for machine output that a person or a test reads line by line (`stats:week` prints its `key value …` lines with it). It is not a log line and never enters the log store. Only scripts import it (a lint border). A script that must stay silent on its machine output uses `process.stdout.write`, and may log a failure as an event line (`org_delete_refused`); free text goes through `createCliOutput`. An existing `error.message` print in a script stays; a new one only in a mail-connection script, never for a Telegram error.
- Guards (server process, `main.ts`): in JSON format `installConsoleGuard()` turns a call of `console.log`, `info`, `debug`, `warn`, `error` or `trace` that does not come from `platform/log.ts` into one text-free `console_output` event. Other console methods (`dir`, `table`, `assert`) stay out of scope and still print. `installProcessGuard(log)` turns an uncaught exception and an unhandled rejection into `process_uncaught_exception` / `process_unhandled_rejection` with `errorFields`, then exits 1. Scripts install neither. Text format (dev) keeps the normal console. Bun's own output before `main.ts` runs is out of scope.
- `docs/known-alerts.md` keys the entries of event lines by the event code.
- What each part does and where it lives: `docs/capabilities/logs.md`.

## Style

- TypeScript strict. `const` / `let` only, never `var`.
- Template literals for strings with variables, never `+` concatenation.
- Use the `log` util (`platform/log`), never `console.log` (`no-console` is at error in `apps/server/src`). The rules are in § Logs.
- Folder keys in logs and audit rows, never paths from mail data or user input.
- Telegram errors: `...telegramErrorFields(error)` (`error`, `error_code`, `method`). Never log `error.message` of an inner error, `payload` or `description` (they can hold the bot token or message text). Other errors: `...errorFields(error)`. `describeError(error)` only in CLI output and in DB error texts (a label in a row), never in a log line.
- Errors: throw typed errors (`SoftError` for timeout / 429 / 503 / lost connection, `HardError` for the rest); the job runner decides the retry.
- A comment states the rule in one sentence. If it needs a source, it names an ADR (`ADR 0014`) or a ticket folder path (`spec/features/done/2026-11/F083-…/`). No bare stage or decision codes (`S3`, `D29`, `U11`, `A23`, `F079`): their plan files move, and no reader can resolve them. Fix the codes of a comment when you change its code; no mass edit. The same ban covers strings outside tests, JSON files, the docs site pages and `docs/modules.md`; letter codes inside a string are data and pass. `apps/server/src/bare-codes.test.ts` scans them, and `bun run check:job` runs it.

## Web app (`apps/web`)

- Every user-visible string is a key in `apps/web/src/i18n/en.ts` and in `pl.ts` (the keys sit in the group files of `apps/web/src/i18n/texts/`) and reaches a component through `t()` or `tp()` (`## Texts carry a locale`). A component never holds a literal text (`react/jsx-no-literals` on the islands and the shell and auth components).
- No inline `<script>` and no hand-written `<style>`: the build hashes the scripts (D5), and styles come from Tailwind classes.
- shadcn components come from the shadcn CLI, never by hand.
- One island per page. The shell is a React component inside the island.
- Data comes from `/api/*` through `lib/api.ts`; only the auth paths (`/api/auth/*`) go through `lib/auth-client.ts`. The request and response shapes are the `@ea/core/web` schemas. The web imports core only through that subpath.
- A form that sits under polling (`useResource` reloads every 30 s) keeps the user's typing with `lib/draft.ts` (`nextDraft`) and the hook `lib/use-draft.ts`: a new server value moves in only while the form has no change.
- The Telegram answer words live in `packages/core/src/digest/answers.ts`. The web keeps its own keys in `en.ts` (every string stays there for S6), and `lib/activity-text.test.ts` ties each key to the core function (S5d, B2). Change a Telegram answer: the test fails until `en.ts` follows.
- A web feature behind a flag reads `me.features` (`/api/me`); the server route checks `isFeatureOn` too and answers 404 when it is off.

## Docs site

- The public site is `apps/docs` (ADR 0030). A user page goes to `apps/docs/src/content/docs/<section>/` with the sections `start`, `how-to`, `reference`, `explanation` and `faq`; its Polish twin is `pl/<same path>`. The operator pages are the sources named in `apps/docs/src/in-place.ts`: edit the source, never a copy.

- PD-009 extension (PD-100): a landed user-visible feature updates its user page (en) in the same change. A page describes only what the code does now; a feature behind a default-off flag gets no page until its flag defaults on.
- The browser check of the built site is `bun run docs:test` (`apps/docs/e2e/`, Chromium, port 8093; build first with `bun run docs:build`; run it under `flock /tmp/email-assistant-shared-tests.lock`). It checks every built page for CSP violations and page errors and for axe WCAG 2.2 AA violations, the search, the page language and the 404 page. A new page needs no entry: the page list comes from `dist`. A violation in Starlight's own markup that config or CSS cannot fix is a question to the owner; never turn an axe rule off.
- A page shows a screenshot of the panel with `<Shot page="settings" />` on its own line (`apps/docs/src/shots.ts` holds the list `SHOTS`: 5 pages, 2 languages, 2 viewports). The PNG files are made by `bun run docs:shots` from the e2e seed (`apps/web/e2e/docs-shots/`, run under `flock /tmp/email-assistant-shared-tests.lock` with an own e2e DB), written to `apps/docs/public/shots/` and never committed or added by hand. A claim without proof is not published; if the fact matters to a buyer, it goes into "What this product does not promise" with its source and date.

## Tests

- `bun run test:unit` and `bun run test:int` run on the local Bun. `bun run test:unit:ci` and `bun run test:int:ci` run on the Bun in `.bun-version`, the version of CI and the server image (`scripts/ci-bun.sh`). A stage proof uses the `:ci` scripts. A test that passes only on the local Bun is a failing test.
- `test:unit` and `test:int` run their files in 4 worker processes (`--parallel=4`, each file isolated; `--timeout=30000` so that a loaded machine does not fail a case on the 5 s default). `test:int` gives each worker its own database (`<database>_w<n>`, made and migrated by `apps/server/test/worker-db.ts`, kept for the next run), so a file sees the same data as in a serial run. A test must still not depend on rows another file of its worker left: filter by the ids of the test. A test that spawns a script passes `env: process.env`, or the child uses the database of `.env`, not the worker database.
- Unit tests stay next to the code. Pure logic in `packages/core`: unit tests without mocks.
- Integration tests live in `apps/server/test/integration/`. Repositories: tests against Postgres in a container (each test in a transaction that rolls back).
- Adapters: contract tests; the fake and the real adapter pass the same suite.
- A prompt or model change runs the sim gate (§ Side effects) and commits the gate file; the CI test `gate-evidence.test.ts` fails when the classifier prompt version has none.
- A test that waits for time-driven code waits for its condition: `waitFor(condition, what)` from `apps/server/test/wait-for.ts` (polls every 25 ms, fails after 5 s). No fixed sleep over 100 ms. A fake that holds a response releases it in its `stop()`.
- A test that makes a folder in the temp dir (`mkdtempSync`) removes it in `afterEach` or `afterAll`; /tmp is a tmpfs, and leaked folders used up its inodes (`EDQUOT`). The sim corpus helpers (`createMiniCorpus`, `completeCorpus` and the sent twins) track their folders: each test file that uses them calls `afterAll(removeAllCorpora)` (`removeAllSentCorpora` for the sent helper). `scripts/tmp-leak.test.ts` fails when a file forgets it or a helper run leaves a folder.
- No retry in CI, no re-run as a fix, no longer test timeout as a fix for a test that hangs. A retry hides a real race.
- Quarantine: a test that fails twice in CI on `master` without a code change (the test file and the code it tests did not change between the two runs) is quarantined the same day. The coordinator creates a ticket (`limen ticket new "<test> passes on the pinned Bun" --lane planned`) and, in one commit, marks the test `test.skip(…)` with the comment `// Quarantined YYYY-MM-DD: fails in CI without a code change. Fix: spec/features/planned/FNNN-slug/`. A worker never quarantines by itself; it reports the test in its final message.
- A test checks one behaviour named in its title, with an exact expected value (`toBe`, `toEqual`, a full error code). `toBeDefined`, `toBeTruthy` or a bare `toHaveBeenCalled()` alone is not a check.
- A case that only shows that a call does not throw (`not.toThrow`, no `expect`) also asserts the value or the effect (the test audit of 2026-11-20 found 25 of 28 weak cases of this kind).
- Before you add a test, search the test file and the tests next to the code for the same behaviour. Add a row to an existing `test.each` table or extend the case instead of a near copy.
- Three or more cases with the same body and other values are one `test.each` table, with one readable label per row.
- Pure logic gets a unit test (in `packages/core` when it is core logic). An integration test is for what needs the DB, IMAP, SMTP or a process, and a CLI test proves the wiring once.
- A test that cannot fail when the code under it breaks tests nothing: before the commit, break the code once and see the test fail.
- Never wait for a production timeout in a test: pass a short one as a parameter.
- Registry, enum and completeness tests are wanted: they fail when the next change misses a place.
- A test that reads the source text of a production file is a guard with a reason in its name, not a way to check wiring that a call can check (the test audit found 3 of 28 weak cases of this kind).
- A test that fixes the clock builds all its data from that clock, never from `new Date()` or `Date.now()`; a mix passes until the real time leaves the fixed window (a CI failure on 2026-11-20; 73 integration files call `new Date()`).

# F110 stage 24: one-click unsubscribe POST (notes for stages 25 and 26)

- Step 0 probe (Bun 1.4.4, `node:https.request`, local TLS server with a self-signed certificate): Bun calls a custom `lookup` and connects to the address it returns, and TLS still uses the host name for SNI. It also connects to an IP literal in `host` with `servername` set and makes no lookup (a throwing `lookup` was never called). A wrong `servername` gives `ERR_TLS_CERT_ALTNAME_INVALID`. The design uses the second form: the guard resolves once, then `sendPinned` connects to the checked literal with `servername` = host name. Mutation M17 (remove `servername`) is killed. Probe scripts: `/tmp/f110-s24-probe-saved/` (outside the repo; they held a throw-away key, which was deleted).
- Client: `apps/server/src/platform/public-http.ts` (`postOneClick`, `readTarget`, `isPublicAddress`, `sendPinned`). `dial` in `OneClickDeps` is the only test seam; it replaces the connection, never the guard. A source scan (`public-http.test.ts` test 22) fails when any production file passes `dial` or names `sendPinned`, or calls `postOneClick` with anything but `{ lookup: dnsLookupAll }` outside `web.ts`.
- The integration tests use a fake client through `WebExtras.postOneClick` (`web.ts`) and the kit field `post` of `web-newsletters-kit.ts`. No test resolves or calls a real host. The e2e test shows the button but does not tap it: a tap would make the e2e server resolve the seeded link host.
- Command: `modules/triage/newsletter-unsubscribe.ts` (`unsubscribeSender`), route `POST /api/newsletters/:mailboxId/unsubscribe` in `newsletter-routes.ts`. Limits: 20 per organization and 3 per sender domain per hour (`UNSUBSCRIBE_ORG_LIMIT`, `UNSUBSCRIBE_DOMAIN_LIMIT`), counted in `unsubscribe_requests.created_at` under an advisory lock per organization. There is no limit per target host: the target host is not stored (the URL is never stored), so the domain limit counts the sender domain, which the sender chooses. A per-target-host limit would need an in-memory map; not built.
- Deviation from the stage text (type 2): the list item `request` gains `code` (nullable) so the owner sees the result code after a reload. The 409 `already_requested` body has `request: { status, at }` only.
- Registry: no config key and no sub-processor row. The call goes to the host that the newsletter names and holds only the fixed one-click body, so it is no sub-processor. `OUTSIDE_CALL_CLASSES` (`platform/outside-services.ts`) records this with a reason and a test. No legal text changed, so `TERMS_VERSION` is not bumped. Owner decision: if the privacy page should name this request (the server sends one request to the sender's server after an owner tap), that is a legal text change and a `TERMS_VERSION` bump.
- Stage 25 (docs) must say: the target comes only from a sender whose topmost `Authentication-Results` has a trusted authserv-id (`MAIL_TRUSTED_AUTHSERV_IDS` only names providers that write their own A-R on top); `dkim=pass` is not checked to cover `List-Unsubscribe` (question 16); no retry; a crash leaves "Requested".
- Equivalent by design: the numeric-TLD check in `readTarget` (the URL parser already refuses such a host); the per-organization advisory lock is killed by the parallel-tap test 11d.

## Pre-mortem: the retention job

Assume the job shipped and failed. These are the likely causes, in falling order of harm.

- **It cleared live text.** A wrong cutoff or a missing organization filter deletes mail text that triage still needs. Fix: test rows at the limit, with one organization per `data_retention_days`. Log counts in a dry run before the first real run.
- **A big delete blocked the database.** The first run touches every old row at once. Fix: batches with a limit, one tick that never overlaps the next, and the two outbox indexes that the task already plans.
- **The outbox constraint stopped the migration.** `outbox.text` is `NOT NULL` with a length check from 1. Fix: decide in the plan between deleting old rows and allowing an empty text. Never edit an applied migration.
- **The docs still say it is missing.** `architecture.md` §7 keeps the old note. Fix: put the doc update in the done-checklist.
- **It ran on mail the pilot week needs.** The S3 and S4 week results read old rows. Fix: start after 2026-11-14, or keep the 30-day limit longer than the week. The week data is under 30 days old, so the risk is low.

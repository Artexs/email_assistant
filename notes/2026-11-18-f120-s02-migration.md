## Decisions taken in the migration (type 2, each on the safe side)

- `sender_profiles.first_seen_at` and `last_seen_at` are nullable and hold INCOMING mail only (`SenderHistory.firstSeenDaysAgo` and `lastSeenDaysAgo` keep their meaning). A contact that the user only wrote to has both null and `last_user_mail_at` set. CHECK: at least one of `last_seen_at`, `last_user_mail_at` is set. **Stage 04 retention must use `GREATEST(last_seen_at, last_user_mail_at) < before`** (GREATEST skips NULL); `last_seen_at` alone would never delete a Sent-only row.
- `sender_suggestions`: an open row has `ended_at` null and a pattern; every other status has `ended_at` and `pattern IS NULL` (CHECK, so the end of a suggestion must clear the pattern in the same UPDATE). Scope and pattern agree (a domain pattern starts with `@`). `reason` keys are limited to `received, answered, flagged, corrected, rescued, senders` (CHECK).
- `by_category` and `corrections` keys are limited to the seven category names (CHECK); `bulk_signals` to the four `bulkSignals`. A new category or signal needs a migration.
- The medians are `real` with CHECK 0 to 100000: the pass must drop delays of 0 or less before it takes the median (D5).
- `sender_profiles` has no `reply_samples_user`: only `reply_samples_theirs` (D12 needs it).
- `usual_reply_days` has no CHECK that ties it to `due_source = 'contact'`. A tie would make the plain rollback `UPDATE ... SET due_source = 'default'` fail. The writer (stage 09) sets both together.
- Indexes: unique `(mailbox_id, key_hash)` and `(org_id, key_hash)` on profiles (the DSR erase finds the person by hash in every mailbox); open-unique, `(mailbox_id, created_at)` and `org_id` on suggestions.

## Rollback (for stage 12 and the deploy notes)

The old release parses `open_loops.due_source` as the enum `('stated', 'default')` (`apps/server/src/modules/loops/repo.ts` `toLoopRow`, `packages/core/src/web/loops.ts`). It throws on a `contact` row. A rollback of the CODE (no schema down, as `deploy/rollback.sh` does) must run this first, with the new server stopped (plan review M3):

```sql
UPDATE open_loops SET due_source = 'default', usual_reply_days = NULL WHERE due_source = 'contact';
```

The due date of the loop stays as it was. The old release ignores the two new tables and the new column. The `down` part of the migration runs the same statement before it narrows the CHECK list and drops the column and the tables (a dev DB or a restored DB only). `contacts-schema.test.ts` tests 20 to 23 cover both.

Stage 12 must write this statement into `docs/capabilities/open-loops.md` (rollback) and `deploy/README.md` (a rollback step 0 of F120), next to the three F110 migrations.

# F115 stage 03: what the migration built and what stage 03b must know

Migration: `db/migrations/20261115200001_reply_drafts.sql` (expand only; no `-- contract:` line; `db:check-migrations` finds nothing).
Apply it on the shared dev DB after the land: `bun run db:migrate` (coordinator).

## Schema choices that the plan did not fix

- `reply_requests.next_attempt_at` is `NOT NULL DEFAULT now()`: a new request is due at once. `status` defaults to `pending`, `attempts` to 0.
- `reply_requests.reason_code`: free text of at most 40 characters (no CHECK list; the drafter and the eligibility reasons grow in later stages). `sample_body` ≤ 2000 (the limit of `checkReplyBody`).
- No CHECK that ties `sample_body` to `trigger = 'sample'` or `requested_by` to the trigger: `requested_by` is `SET NULL` when a user goes, so such a CHECK could fail a user delete.
- Indexes for the foreign keys: `(org_id, email_id)`, `(mailbox_id)`, and partial ones on `previous_send_id` and `send_action_id`. The unique index of the auto trigger is `reply_requests_auto_key`; the claim index is `reply_requests_queue_idx (org_id, status, next_attempt_at)`.
- `mailbox_profiles` has an `org_id` index. The copy of `organizations.style_text` uses `left(NULLIF(style_text, ''), 1000)`: the form allows 500 characters, but the column has no CHECK.
- A mailbox that is created after the migration has NO profile row. Stage 03b `mailboxProfileOf` must treat a missing row as all-null (fallbacks: signature → `style_text` → owner name), and `upsertMailboxProfile` must insert-or-update.

## For stage 03b and later

- Retention: the legal registry (`packages/core/src/legal/data-categories.ts`, category `reply-texts`) says `days: 90` (the same cut-off as the action payloads, `RETENTION_TEXT_DAYS` in `apps/server/src/retention.ts`). The stage 03b text says "(data_retention_days)": use the 90-day `textsBefore` of the action payloads, or change the category in the same commit (`data-categories.test.ts` does not read the period).
- The privacy maps already hold the five text columns (`address-map.ts`, `erase.ts` `TEXT_LIMITS`, `export-map.ts`). A new text column in these tables needs entries in all three.
- `dsr-match.ts` `ROW_SHAPE`: `mailbox_profiles` has no `id`; its key is `mailbox_id`. The no-mail filter now reads `shape.id` (it read `t.id`).
- Notice kinds `replies_ready`, `reply_prompt`, `reply_result` have minimal views and one fixed en and pl line (`digest/notices.ts`, `texts/notices.ts` `replyDrafts`). `reply_result.reason` is a lower-case code (`/^[a-z_]{1,40}$/`); stage 13 may narrow it to the block reasons and statuses. `queuedBy` names `replies/notices.ts` and `replies/telegram.ts`: the files do not exist yet.
- Sub-processors: no new row. The drafter sends mail text, the instruction, the signature and the style to the existing LLM provider rows ("drafts"). Stage 07 should check the `dataReceived` text of those rows.
- Only one column classification is not enforced by a test: `reply_requests.thread_key` in the legal category `mail-ids` (the tests need the table, not each column).
- Rollback note (stages 17 and 18): a release without the three kinds fails the whole outbox claim batch on one such row. The Down section of the migration deletes those rows first.

### 2.3 Flow of one ticket

1. Ticket written (`limen ticket new` or by hand). The owner or a planning session adds `## Sequenced` (Plan after, Build after, Gate).
2. Planner job: scouts, `plan.md`, `stages/`, `questions.md`, cold review, fixes. The coordinator lands the plan and copies `[important]` questions to `docs/owner-decisions.md`.
3. Before stage 01: `scripts/plan-drift.sh <folder> <plan base>`. Exit 1 → a refresh planner job first.
4. The coordinator moves the ticket to `active/` and spawns each stage whose `Needs` line holds.
5. Review (risky stages Opus). Land check in the job worktree: `git merge --no-edit master && bun run typecheck && bun run test:unit:ci`. `limen land <job> --keep-open` until the last stage. After each land: `gh run list --branch master --workflow CI --limit 3`.
6. Last stage: `limen land` without `--keep-open`, or `limen ticket done`. NOW/PROVEN regenerate.

### 2.4 Where order and parallelism come from

- Ticket level: `05-execution-plan.md` §2.1 "Needs" column and the ticket `## Sequenced` section. Limen has no dependency field.
- Stage level: the `Needs` line in each stage file (first lines). `scripts/coord-scan.sh` prints it for OPEN stages of active tickets.
- Hard limits (TRACK and CLAUDE.md): one DB migration in build at a time; one `bun.lock` change at a time; one VPS deploy at a time (every deploy is a release: `deploy/release.sh <tag>`); `test:e2e` and `docs:test` only under `flock /tmp/email-assistant-shared-tests.lock` (fixed ports 8081, 8092, 8093); planner cap 3; no worker cap. Limen itself only holds a job when CPU idle < 25 % or free memory < 20 %.

# F117 stage 10: facts for stages 11 to 20

Code: `apps/server/src/modules/mail/oauth/tokens.ts` (token store), `oauth/login.ts` (login refusal rules), `open.ts` (retry), `repo/mailboxes.ts` (`setMailboxStatus`, `changeMailboxStatus`).
Tests: `apps/server/test/integration/mail-oauth-refresh.test.ts` (46), plus tests in `mail-oauth-connect.test.ts` (9b, 17d), `actions-committer.test.ts`, `actions-send.test.ts` (8b, 12), `src/composition.test.ts`.

## What later stages call

- `createOAuthTokens({ pool, secrets, clients, now })` → `OAuthTokens`. `main.ts` builds one through `mailOAuthRuntime(config, db, secrets)` (`composition.ts`) and gives it to the sync job, `committerDeps({ oauthTokens })` (now required) and `WebExtras.mailOAuthLogin.oauthTokens`. `scripts/job-run.ts` builds its own for the committer. `composition.test.ts` fails when a root loses it.
- Stage 12 (Remove) calls `oauthTokens.drop(id)`. Stage 12 must take `withMailboxOAuthLock` FIRST, then the row, like Reconnect and the refresh. A writer that takes the row first can deadlock with them.
- Stage 13 (Graph): `GraphSenderOptions.freshToken` is `accessToken(ctx, id, "graph", { fresh: true })`. A refused Graph login must throw `MailAuthError` with a reason (the SMTP guard of `oauth/login.ts` does not cover Graph).
- Stage 11 (texts): reasons reach `mailboxes.auth_reason` from three places: the sync job (`jobs.ts`), `openFor` and the batch loop of the committer. All pass `error.reason ?? null`.
- `ApplyOutcome` and `SendOutcome` `{ kind: "auth_error" }` carry an optional `reason` (`authErrorOutcome` in `actions/apply-shared.ts`). The key is absent when there is none, so older `toEqual({ kind: "auth_error" })` tests hold.

## Rules as built

- Cache key `<mailboxId>:<resource>`. An entry also holds `orgId`: a hit for another organization is a miss (the refresh then finds no secret for that organization and throws `HardError`). A hit needs `expiresAt - now >= 5 min` and no `fresh`. The cache is set after the lock transaction commits.
- Refresh = `withMailboxOAuthLock(pool, id)` (advisory lock first) → `readOAuthSecret` → `client.refresh` → if the refresh token changed: `lockMailbox` (row, FOR UPDATE) → `saveOAuthSecret` → commit. The row lock comes after the HTTP call on purpose: a row lock held across a 10 s HTTP call would stall every status writer (the sync job, pause, Remove). Test 32 proves a held row lock does not stop the HTTP call; test 31 proves a Reconnect that holds advisory lock and row blocks the refresh at the advisory lock with no deadlock.
- A second concurrent refresh does not reuse the cache after the lock (the stage text says it refreshes again with the saved token). Test 9.
- `OAuthGrantError` → `drop(id)` + `MailAuthError("oauth grant refused", { reason })` (no `cause`). `OAuthSoftError` passes through unchanged (it is a `SoftError`). `client_invalid` adds one `error` line `mail_oauth_client_invalid { provider }` each time. `server` and `timeout` add no line of their own: the token client already logs one `warn` `oauth_token_failed` with the kind (test 13, 14).
- No client: `SoftError` and one `error` line `mail_oauth_not_configured { provider }` per provider and per `createOAuthTokens` instance (one per process). The check comes after the secret read, because the provider is in the secret.
- `open.ts` (OAuth mailboxes only): a refused IMAP login (`MailAuthError` without reason, or imapflow `Unsupported authentication mechanism`, see `isUnsupportedAuthMechanism` in `imap/client.ts`) → `drop`, `accessToken(..., { fresh: true })`, open again; refused again → `MailAuthError` reason `protocol_disabled` (no `cause`). The `drop` and `fresh` are each enough alone (mutant o1 survived alone, equivalent; both removed is killed). A soft error at the login is not retried and changes no status. The new token also goes to the SMTP sender.
- The SMTP sender of an OAuth mailbox is wrapped (`guardOAuthSender`): `MailAuthError` without reason → `protocol_disabled`, unless `cause.responseCode` is 4xx: then a soft `SmtpSendError` (stage `login`, code `EAUTH`) so the send retries. nodemailer puts the reply number in `error.responseCode` for EAUTH. A password sender is not wrapped.
- `setMailboxStatus(db, ctx, id, status, at?, reason?)` writes `auth_reason` in the same UPDATE: `reason` only for `auth_error`, else NULL; and NULL for a mailbox without `oauth_provider` (so a stray reason never hits the table CHECK). `changeMailboxStatus` and `finishMailboxReconnect` also write `auth_reason = NULL`. Test 25 counts the UPDATEs (one).
- Writers of `mailboxes.status`: `setMailboxStatus` (sync job, committer, `updateMailboxPassword`), `changeMailboxStatus` (pause, resume, host blocked, host allowed, Remove pause), `finishMailboxReconnect`. All clear the reason; tests 24 to 28b and the Reconnect tests of stage 09.

## Decision: Reconnect keeps the stored hosts

Reconnect tests the login at the hosts stored on the mailbox row, not at the `client.spec` hosts (test 17d). Why: the jobs connect to the stored hosts with the new token, so the check must too; a refusal when they differ would strand a mailbox after a registry change, with Remove as the only way out. No code path changes the stored hosts, and the insert took them from the registry. Undo: add the equality check in `reconnect()` (`apply.ts`) and refuse with `oauth_failed`.

Written by the stage 07 worker (2026-11-19).

## Carry-over (first commit)

- N1: `acceptSuggestion` (`apps/server/src/modules/contacts/suggestion-commands.ts`) asks `suggestionBlockedNow` (`suggest.ts`) before it
  makes a rule. That function judges the row with `isWithdrawn`, the same function that the profile pass uses for an open row: a sender
  rule of the kind covers the row, or a "never" condition holds. A blocked row ends as `withdrawn` (no `ended_by`, no audit row) and Accept
  answers `not_available`; the route answers 409 `{ error: "not_available" }`. The check covers every kind, not only blocklist.
- Review fix (B1): a row lives 30 days, but its counts need mails of the last 90 days at creation time, so at Accept the 90-day activity can
  be empty for the sender. The first version looked the address up in the activity only, so a delegate, a rule or a lost Sent coverage was
  not seen. Now an address (or domain) that the activity does not show is judged from a bare input (`standingOf(...).bare`): no counts, but
  the rules, the active delegates and the own domains apply. Counter-examples pinned in `contacts-suggestion-commands.test.ts` tests 18 to
  22b (P1 delegate, P2 no coverage, P2b VIP rule, a domain row, a domain nothing names). The pass uses the same function, so a row that
  outlives its activity is now also withdrawn by the pass when a rule, a delegate or the coverage protects it.
- Review fix (N2): a covering rule of the SAME kind blocks the row with or without activity: Accept answers `not_available` and the row ends as
  `withdrawn`, like the pass (it withdraws such a row). The earlier text said `exists`; that path is now reachable only by a race. Test 2 and
  test 21 pin it.
- Review fix (N3), cost of the re-check: `readSenderActivity` has an `only` option (one address, or one registrable domain with its
  subdomains). The read takes only the mails of that sender (window 90 days) and the Sent mails to it, and leaves out the reply-delay and
  delegation reads, which the suggestion rules do not use. The statement that read all Sent rows (`theirDelays`, `own_sent`: 52.7 ms with
  20,000 Sent mails older than a year) is no longer part of the re-check. The two reply reads also got the bound `s.sent_at >= since` (implied
  by `sent_at > received_at`). The read runs before the row lock (`protectedNow`), so the lock is held only for the writes; a sender that turns
  protected between the read and the lock is caught by the next profile pass. EXPLAIN (`ANALYZE`; 20,000 Sent mails 400 days old, 2,000 incoming
  mails, tables analyzed; probe `explain-after.log`, worktree `.f120s07/logs/`): before 91 ms for 16 statements, after 37 ms for 13
  statements. The largest remaining statement is the Sent-reply check `replied` (13 ms): on this data the planner scans `sent_emails_org_idx`
  for each of the 4 mails of the window and discards the rows by date (`Index Scan using sent_emails_org_idx ... rows=0 loops=4`). The other
  statements take 2 to 3 ms each (the aliases of the mailbox, the window, the Sent recipients). No migration, no new index.
- TG-1: test 8 of `web-suggestions.test.ts` runs the dismiss calls inside `captureLogs()` too.
- N2 (carry-over): `dismissSuggestion` answers `not_found` for a mailbox that is not `active`, as Accept does; the row stays open.
- N3 (carry-over, decision, no code): the weekly suggestion line goes to every report member, not only owners; the count is organization-wide
  like the other week stats.
- `SuggestionDeps` and `SuggestionRouteDeps` have a new required `testMail` (the activity read needs the test-mail rule); `web.ts`
  passes `testMailRule(config)`.
- Mutation logs: `.f120s07/logs/mut-*.log` (untracked, in the job worktree).

## The card

- `apps/web/src/components/rules/SuggestionsCard.tsx` (card + `SuggestionRows`), pure rules in `apps/web/src/lib/suggestions-view.ts`
  (`reasonLines`, `suggestionsGone`, `acceptOutcome`, `dismissOutcome`). The card sits on `RulesPage.tsx` above the newsletters card.
- The card renders nothing until the first list answer is in (no flash for an organization with the flag off). A 404 marks that mailbox as gone,
  which unmounts its list loader, so its 30 second poll stops.
- After Accept (`rulesChanged`) `RulesPage` raises a version that makes the rule list load again (no remount) and reloads `useMe()`.
- `409 not_available` shows `sg_not_available` and reloads the list (the row is gone). `already` is silent. `rule_limit` shows
  `err_rule_limit` (the text of `AddRuleForm`) and keeps the row.
- Texts: own group `texts/en-suggestions.ts` and `pl-suggestions.ts` (key prefix `sg_`). The Polish reasons use the impersonal past
  ("Odpowiedziano", "Oznaczono"): the panel uses that form and it needs no gender form. Domain rows have their own full sentences
  (`sg_reason_*_domain`), not a suffix, because the blocklist sentence needs a different ending.
- The toast of Accept reuses `rule_added_toast`.
- Review fixes (web): the Polish and English texts of seven keys changed (review wording); after Accept or Dismiss the focus moves to the card
  heading; an Accept no longer remounts the rule list (the add form keeps its text; a version counter makes the list load again); a 404 on
  one mailbox list leaves that mailbox out (`pickMailbox`), the card is gone only when no mailbox is left.
- E2E: own seeded organization per project (`E2E Suggestions mobile|desktop`; `e2e-suggestion-rows.ts`, `E2E_SUGGESTIONS` in
  `e2e-seed-args.ts`), spec `apps/web/e2e/tests/suggestions.spec.ts` (T1 accept, T2 dismiss and reload, T3 member, T4 axe, T5 flag off with a fake clock, T6 the poll runs).
  Each test resets the three rows, the rules and the Sent coverage first (`e2e-suggestions.ts`, called in `beforeEach`), so the order does not
  matter; the seed gives the mailbox Sent coverage (`sent_sync` on, a fresh `mailbox_sent_sync` row) because the profile pass of the e2e
  server (minute :07 each hour) withdraws a blocklist row without coverage. The mail sync job of the e2e server can still set a Sent error
  code on that mailbox; the reset before each test makes the window for it a few seconds.
- No `TERMS_VERSION` change: the texts are product UI, not legal text or a registry.

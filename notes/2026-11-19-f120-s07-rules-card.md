## Carry-over (first commit)

- N1: `acceptSuggestion` (`apps/server/src/modules/contacts/suggestion-commands.ts`) now asks `suggestionBlockedNow` (`suggest.ts`) before it
  makes a rule. That function reads the sender activity again (`readSenderActivity`, as the profile pass does) and judges the row with
  `blockedNow`, the "never" check that `isWithdrawn` of the pass also uses. A blocked row ends as `withdrawn` (no `ended_by`, no audit row) and
  Accept answers `not_available`; the route answers 409 `{ error: "not_available" }`. The check covers every kind, not only blocklist:
  the pass withdraws every kind by the same function, so one path keeps the two equal. A covering rule of the same kind is no block
  (`addSenderRule` answers `exists`, so Accept still ends the row as `accepted`). A row that the activity does not show is not blocked.
  Cost: one activity read of the mailbox (90 days) per Accept tap, not per list view.
- `SuggestionDeps` and `SuggestionRouteDeps` have a new required `testMail` (the activity read needs the test-mail rule); `web.ts`
  passes `testMailRule(config)`.
- TG-1: test 8 of `web-suggestions.test.ts` runs the dismiss calls inside `captureLogs()` too.
- N2: `dismissSuggestion` answers `not_found` for a mailbox that is not `active`, as Accept does; the row stays open.
- N3 (decision, no code): the weekly suggestion line goes to every report member, not only owners; the count is organization-wide like the
  other week stats.
- Mutation logs: `.f120s07/logs/mut-n1-*.log`, `mut-n2-*.log`, `mut-tg1-*.log` (untracked, in the job worktree).

## The card

- `apps/web/src/components/rules/SuggestionsCard.tsx` (card + `SuggestionRows`), pure rules in `apps/web/src/lib/suggestions-view.ts`
  (`reasonLines`, `suggestionsGone`, `acceptOutcome`, `dismissOutcome`). The card sits on `RulesPage.tsx` above the newsletters card.
- The card renders nothing until the first list answer is in (no flash for an organization with the flag off). A 404 sets a card state
  that unmounts the list loader, so its 30 second poll stops.
- After Accept (`rulesChanged`) `RulesPage` remounts its rule list through a version in the `key` and reloads `useMe()`.
- `409 not_available` shows `sg_not_available` and reloads the list (the row is gone). `already` is silent. `rule_limit` shows
  `err_rule_limit` (the text of `AddRuleForm`) and keeps the row.
- Texts: own group `texts/en-suggestions.ts` and `pl-suggestions.ts` (key prefix `sg_`). The Polish reasons use the impersonal past
  ("Odpowiedziano", "Oznaczono"): the panel uses that form and it needs no gender form. Domain rows have their own full sentences
  (`sg_reason_*_domain`), not a suffix, because the blocklist sentence needs a different ending.
- The toast of Accept reuses `rule_added_toast`.
- E2E: own seeded organization per project (`E2E Suggestions mobile|desktop`; `e2e-suggestion-rows.ts`, `E2E_SUGGESTIONS` in
  `e2e-seed-args.ts`), spec `apps/web/e2e/tests/suggestions.spec.ts` (T1 accept, T2 dismiss and reload, T3 member, T4 axe, T5 flag off).
  The tests run in order and change the seed: T1 accepts the VIP row, T2 dismisses the blocklist row, T3 sees what is left. Do not
  run T2 to T4 alone on a seed that has run T1 to T3 before (the global setup seeds again on each run).
- No `TERMS_VERSION` change: the texts are product UI, not legal text or a registry.

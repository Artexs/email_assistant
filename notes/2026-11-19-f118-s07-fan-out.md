## What was built

- `channels/notice-fan-out.ts`: `NoticeRecipient` (`{ userId, role, locale, since, hasChat }`), `MissingEventAtError`, `planFanOut(db, ctx, { userId, kind, eventAt, now, only? })` → `{ telegram: boolean; deviceIds: string[] }`. It is the one place that reads the flag `web_push`, the stored routes, the chat link and the live devices.
  - A kind with no push group: one Telegram row (`only: "push"` → none). No read.
  - `only: "telegram"`: Telegram row, no read, no `eventAt` needed (the answer to a Telegram tap: the review card of a reply).
  - A kind with a group needs `eventAt` (else throws, even with the flag off, so a producer that forgets it fails in tests, not in production).
  - Flag off → Telegram row as before. Flag on → `effectiveRoute` with `hasChat` and `hasDevice` = "has a live device" (any live device, not only the ones that existed at `eventAt`). Push rows go to the live devices with `createdAt <= eventAt`. A member with neither a chat nor a device keeps the Telegram row of before (it ends `no_chat`).
- `queueNotice`: no explicit `channel` → fan-out in one transaction (own transaction when the caller has none): the Telegram row (key as before) and one push row per device (`pushDedupKey`, `channel: "push"`, `push_subscription_id`). Returns the Telegram row id, else the first push row id, else null. New inputs `eventAt`, `only`. `insertOutbox` takes `pushSubscriptionId`.
- Push-only recipients: `listPushOnlyMembers` (`channels/push/repo.ts`): live device, no Telegram chat link, organization not suspended; `since` = oldest live device. `detectNotices` adds them per organization when `web_push` is on for it. `detectForOrg`: the org runs all detectors when it has a chat member; with only push-only members it runs the weekly report and the detectors that `servesPushOnly` (all kinds in `pushKinds`, at least one kind). Such a detector gets chat and push-only recipients; the other detectors get chat recipients only (digest job, weekly report, report members unchanged).
- Loop-consent gate (`notices/loop-consent.ts`): `splitByLoopConsent(db, ctx, owners, { kind, eventAt, now })` returns `{ covered, withheld, pushWithheld }`. `withheld` = not covered owners WITH a chat (they get the `loop_consent` line, `only: "telegram"`; a no-op today because `loop_consent` has no group). `pushWithheld` = not covered owners that `planFanOut(only: "push")` says have a push row; they get the real kind with `only: "push"`. The approval detector builds the view when `covered` or `pushWithheld` is not empty. Same split in the send-result detector.
- `queueMailboxRemovedNotices` also reaches push-only owners (flag on).
- `eventAt` per producer: urgent = `triaged_at`; not_triaged = later of the pause start and the mail's `receivedAt`; approval, send_result = `actions.updated_at` of the send; approval_set = newest `updated_at` of the set; replies_ready = newest `updated_at` of the counted sends; action_failed = `actions.updated_at` (follow-up: new `FailedFollowUp.updatedAt`); delegation_answered = `answered_at ?? now`; auth_error, host_blocked = `status_changed_at`; sent_missing = quiet start + 7 days; sync_stale = last sync (or the later of status change and creation) + 30 min; sync_ok = `last_synced_at`; send_held = the run time (a hold has no stable start: every retry moves the row; worst case one push per mailbox and UTC day for a new device); mailbox_removed = the removal time.
- Review cards of a reply (`queueReviewCard`, kind `approval`) pass `only: "telegram"`: they answer a Telegram tap.

## Choices to know

- The default route of an `updates` kind is Telegram, so a member with a chat and a device gets no push for `send_result` and the like until they pick `push` or `both` (stage 06 rule). A withheld owner (follow-up result) with the default route gets the consent line only.
- Cost: every `queueNotice` of a push-group kind reads the flag (one query); with the flag on it reads also the live devices, the chat link and the routes. The urgent detector calls it per mail and member each tick (the dedup key stops the insert, not the reads). If that shows in the DB load, cache the per-member plan per detector run.
- Approval `eventAt` is the send row's `updated_at`, not the time the draft was applied. A device added between the two gets no push for that one approval (the safe direction).
- `since` of a recipient with a chat is the chat link time (as before); the device filter is per row (`eventAt`), not in `since`.

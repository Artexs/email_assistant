## Decisions (the carry-over of review 13; each tested)

1. **Reply all and a different Reply-To.** Reply all goes to the stored `From` (To) and never uses the Reply-To. Why: the Reply-To is an unsigned header that a forger can point anywhere; a mail client may use it, but this system moves a draft there only on an explicit tap (`reply_to`, "Use Reply-To"). The panel shows the choice before Send with `view.to`, `view.cc`, `view.replyTo` and the new item field `recipientsMode`. Tests: `web-reply-recipients.test.ts` 5, `recipients.test.ts`. To undo: change `replyRecipients` (`all` branch); the capability page and the tests name it.
2. **A `+tag` variant of an own mailbox.** `ownAddressKey` (lower case, no `+tag` in the local part) decides "own". Reply all, Use Reply-To and `replyRecipientsProblem` use it. A `+tag` address of another person stays a different address. A real alias (a second address that delivers to the same box) is not stored anywhere in the system, so it is not removed; stage 17 may note it as a limit. Tests: `recipients.test.ts` ("an own mailbox with a +tag"), `web-reply-recipients.test.ts` 6.
3. **A stored address with a display name.** `bareAddress` takes the address in `<…>` (never reads the name); an entry with no valid address is not a recipient and does not make a button show. `replyRecipients`, `otherParticipants` and `otherReplyTo` are the one rule, so the card (`approvalViewFor`), the service and the panel agree: no button without a working call. A stored sender that is no address answers `bad_recipient`. Tests: `recipients.test.ts` ("a stored address with a display name"), `web-reply-recipients.test.ts` 7.

## Decisions for the routes

- **Flags.** `approvals_page` AND `reply_drafts` are checked before the role, the id and the body: a flag off is `404 not_found` for owner and member, also for a bad id (`web-reply-guards.test.ts` 1). The interface text said `409 feature_off` for `POST /api/replies`; the job instruction says 404 and that wins (a 409 would show that the feature exists).
- **Order for writes:** flags, `requireOwner`, strict body, service. A member with a bad body gets 403, not 400 (test 3).
- **Status read:** only requests of the trigger `tap` or `redraft` (an `auto` or `sample` id is 404). `superseded` reads one more table: the newest open reply send of the thread in the same mailbox. The interface text said "reads only the request row"; the stage asks for the open `sendId` of the thread, so one more read.
- **`instruction` in the read model.** Stage 14 step 2 and the interface list `instruction` in `ApprovalItem` and `ApprovalDetail`, so the panel can show it. It is in no write answer, no error answer, no log line and no audit row (tests 5 in `web-reply-routes.test.ts` and 5 in `web-reply-read.test.ts`). It is read by members of the organization who already read the draft text. Undo: drop the field from `approvalReplyFields` and `replyFieldsOf`.
- **Read-model fields not new:** `gaps`, `cc`, `replyTo`, `sentVisible` were already in `view` (stages 12 and 13); `gaps` comes from `body_text ?? body`, so an edit updates them (`web-reply-read.test.ts` 4).
- **Layers of the guards:** the route runs in the tenant scope (database policy), so a removed `org_id` filter on `getUserRequest` or `replyVersionFacts` shows only in a call with no scope: `web-reply-read.test.ts` 8.

## What stages 12, 13 and 14 must know

- `trustViewFor(deps, ctx, mailboxId)` is the one reader. It returns null for an unknown or foreign mailbox. It does not read the flag to refuse: `view.flag` says whether `trust_ladder` is on, and the route answers 404 with it off. Dates in the view are ISO strings.
- `auto` in the view is `effectiveAutoFor` (what triage reads under the running key), not the stored `auto`: a category on under an older model setup shows off, `grantBy` null. This is review 4 N3 for the new card; the card must still show `evidence.blocks` next to a refused 409 (stage 13).
- `judgeCategory(inputs, category)` and `readEvidenceInputs` (`trust/gate.ts`) are the one rule behind the gate, the report notice, "Turn on recommended" and the view. M8 (stage 12) should read the view, not recompute.
- `history` is the result of the newest `done` check (as the gate reads it) and the examples come from the same check. `check` is the newest check of any status; `checked` counts the items so far (`countItems`).
- Examples: up to 3 acted-on items per moving category that the category would move, newest by `emails.received_at`, then id. Sender = `email_headers.from_name` (never the address), subject = `emails.subject`; both null after retention (`listMailExamples` in `mail/repo/history.ts`). The view never goes to Telegram.
- The answer of `POST /recommended` is `{ turnedOn, mode, view }` (the stage text said "plus the new TrustView"; the view is nested under `view`).

## Decisions taken (defaults)

- Order of the guards: the flag first (404 for every role, with a bad id too), then `requireOwner` (403 `owner_only` before any mailbox read), then the mailbox (404, the same answer for a foreign and an unknown id). This follows the loop routes.
- Lock: `FOR UPDATE` on the settings row, not the share lock of the stage text (review 9 N2: the share lock deadlocks with the setters). The evidence is read after the lock, so a tap that waits reads the commit of the writer. `setMode` and `setCategoryAuto` run in the same transaction through `SettingsDeps.db = trx` (their `inTransaction` helper reuses a transaction).
- "On" for the recommended filter = `effectiveAutoFor`: a category that is on under another model setup is turned on again with a new grant `recommended`. A category on under the running key (any grant, also `forced`) is never touched, so the first tap's grants stay and a second tap gives 409 `nothing_recommended`.
- The mode changes only when it is `shadow`; a mailbox in `assist` keeps its switches. When nothing is due, nothing is written (the mode stays `shadow`).
- Audit rows: `setMode` takes a new optional `auditData`; both setters get `via: "web"`.
- `history-check` answers 202 with `{ check }` (the `OpenAPI` helper `apiDoc` accepts status 202 now) or 409 `check_running`. The suspended-org guard of every write route applies.
- Review 7 N2: `bun run org:status` (`orgStatusLines`) prints `history_calls_today` next to `llm_calls_today` (new `countHistoryLlmCallsSince` in `audit`). Telegram `/status` still shows the daily count only: its number is the one the daily cap holds.

## What stage 07 must know

- The job moves `queued` → `backfilling` → `waiting_flags` → `classifying` and then leaves the check alone: `HISTORY_STEP_STATUSES` holds the three statuses it claims. Stage 07 adds `classifying` to that list (the test "a classifying check is not claimed" must change then) and writes the classify step in the same file layout (`StepEnd` kinds `advance`, `wait`, `end`).
- A step ends through `finish`: `advance` (status and next time), `wait` (no attempt), `end` (`no_result` with a reason, `finished_at` in the same write). Stage 07 must write `done` with `finished_at` too (stage 03 carry-over). Every write after the claim goes through `guardedUpdate`, which needs `locked_at` equal to the value of the claim and a step status; use it (or `releaseCheck` / `endCheck` / `failStep`), never a plain update by id.
- `check.key` (the running `EvidenceKey`) and `backfill_done_at` are set when the backfill ends. `window_start` = the read time of the backfill − 30 days, written with `backfill_done_at` and `key` when the backfill ends (review 6 N1: a check that waited, for example for a paused mailbox, gets the window of its read, the same as the backfill and the flag refresh). It is null until then; stage 07 reads it only from `waiting_flags` on. A crashed read leaves it null, and the repeat sets its own.
- The flags wait passes to `classifying` when every INBOX mail of the window has an `email_flags` row with `checked_at >= backfill_done_at`, or 20 minutes after `backfill_done_at`. The count covers INBOX mail of this mailbox received from `window_start` to `backfill_done_at`; live mail after the backfill is the sync's and does not hold the wait (review 6 N5). After the limit a mail with no fresh row counts as not acted on.
- N1 (`refreshFlags` and `skipped` mail) is verified: `listFlagTargets` has no status filter; test 8 reads `\Answered` and `\Flagged` of history mail.
- The job passes no model client. `TRIAGE_LLM_SCOPE=synthetic` also starts the job (as the stage text says): stage 07 must decide whether the classify step runs under `synthetic`.
- A history mail never gets a `triage_results` row in this stage (test 5 counts them; a source scan forbids the table name in the job files).

## Decisions taken here

- Gate before every step, in this order: suspended org → wait 5 min, no attempt; `trust_ladder` off → wait (the operator reason `cli` ignores the flag, as the CLI note of stage 05 says); mailbox `paused` or `host_blocked` → wait 5 min (both end by themselves); mailbox `auth_error` → `no_result` / `auth_refused` (a refused login does not end by itself). Decision for the owner list: the stage 05 carry-over default says "stop with a distinct `no_result_reason`". The `history_checks` CHECK has no reason for a paused or blocked mailbox and the stage adds no migration, so `paused` and `host_blocked` wait instead of ending the check, and `auth_error` uses `auth_refused`. A paused mailbox keeps its check open (no second check can be queued) until the user resumes it.
- `CursorMovedError` is a retry in 1 minute that costs no attempt (a regular sync moved the cursor between the plan and the apply of one chunk). The 20th retry of one check (counted in the process; a restart counts again) counts one attempt, so a check cannot stay open for ever (review 6 N2). `HISTORY_CURSOR_RETRIES` is 20.
- Review 6 added: the GreenMail test `trust-history-greenmail.test.ts` (history backfill and `refreshFlagsOfMailbox` against the real IMAP server), tests of the `main.ts` wiring (`composition.test.ts`), and a test that the job files reach no `modules/triage` file and no model call through their imports. Carry-over from that review: N6 (the history refresh touches `checked_at` of gone mail), N7 (one long backfill holds up the other orgs inside a tick; a deploy kill leaves a stale lock that costs one attempt), N8 (stage 07: should `synthetic` run the backfill at all).
- `refreshFlags` fails inside the backfill step: logged as `history_flags_refresh_failed`, not a step failure (the wait step has its own limit). A refused login there ends the check as `auth_refused`.
- The step error rule: any thrown error except `CursorMovedError` adds one attempt and waits 5 minutes; the third attempt, also by a stale-lock take-back, ends the check as `stopped`.
- `flag_on` queue: each run lists active mailboxes of flag-on orgs with no `history_checks` row (a read), and queues `flag_on` for each one under a row lock on the mailbox, so a mailbox that had a check once never gets a second one by this path.

## Every place a value is copied (stage 06 adds no table, no column and no delete rule)

| Value | Source | Copy | Removed by |
| --- | --- | --- | --- |
| evidence key of the running classifier (model, provider, effort, prompt version, endpoint, host) | `gateEvidenceOf(...).runningKey` | `history_checks.key` (jsonb) | mailbox or org delete (cascade of `history_checks`); no personal data |
| window start, backfill time, attempts, status, no_result_reason, lock and retry times | the job clock | `history_checks` columns | same |
| mail of the last 30 days | the INBOX | `emails` / `email_headers` rows from stage 05 (unchanged); flag rows of that mail in `email_flags` (written by the existing `refreshFlags`) | the normal retention of `emails`, DSR erase, mailbox and org delete (`email_flags` cascades with the mail) |

The job logs the check id, the mailbox id, a status and a code: no mail value, address or token. `check_id` is a new UUID log field (`platform/log-fields.ts`): the logger drops an id that is not a UUID.

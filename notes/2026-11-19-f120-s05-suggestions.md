# F120 stage 05: suggestion engine, what later stages must know

Written by the stage 05 worker (2026-11-19). Code: `apps/server/src/modules/contacts/suggest.ts` (the pass step),
`suggestion-commands.ts` (Accept, Dismiss, readers), `flags.ts` (`sentCoverage`), `packages/core/src/contacts/suggestions.ts`.

## Decisions taken in this stage

1. **Sent coverage is now "current" (review 3b carry-over).** `sentCoverage(db, ctx, mailboxId, now)` takes the clock. It is
   true only when the flag `sent_sync` is on, the mailbox switch is on, `first_pass_at` is set, `last_error_code` is null and
   `last_pass_at` is not older than 24 hours (`SENT_COVERAGE_FRESH_MS`). Reason: a pass that ends `folder_missing`, `no_folder`
   or `failed` still sets `last_pass_at` but reads no Sent mail, so "the user never wrote to this sender" cannot be known; a
   mailbox that stops syncing keeps an old `last_pass_at`. Effect: no new blocklist suggestion and an open one is withdrawn.
   A short outage of more than a day withdraws open blocklist rows; they come back through the weekly cap when coverage returns.
   This is the safe direction (a wrong blocklist hides mail). The plan text of the coverage rule (first pass only) is widened.
2. **Frozen mailboxes (review 3b carry-over).** The job runs only for `active` mailboxes, so a mailbox in `paused`,
   `auth_error` or `host_blocked` keeps a frozen profile. The suggestion step does nothing for a mailbox that is not
   `active` (also when the pass is called directly). `listOpenSuggestions` and `countOpenSuggestions` return nothing for it.
   `acceptSuggestion` answers `not_found`; `dismissSuggestion` still works. The open rows stay and expire after 30 days
   (retention ends them as well).
3. **Both commands and both readers read `senderFlags().suggestions`.** Flag off: `not_found`, empty list, count 0. Stage 06
   still answers 404 first for every role, as the plan says.
4. **Domain rows use the registrable domain** (`registrableDomain`, core). A free-mail domain, an own mailbox domain and a
   shared hosting domain (`github.io`, `herokuapp.com`: `isSharedHostingDomain`, new in core `dkim-pass.ts`) never get a domain row.
   A domain rule has no `@`: Accept turns the stored `@acme.pl` into the rule pattern `acme.pl` (`rulePatternOf`).
5. **Only patterns that can become a sender rule are suggested** (`eligible` in `SuggestionContext`, new optional field): an
   address or domain with letters outside ASCII (an internationalized domain) is dropped before the weekly cap, so it takes no
   slot and cannot starve the others. Accept of a row whose pattern is invalid (cannot happen from the generator) ends it as
   `withdrawn` and answers `not_found`.
6. **Withdrawal** (D11) runs in this order inside the pass: expire rows older than 30 days; withdraw rows that a rule of the
   same kind covers (`matchSender`: a VIP rule also covers a whitelist) or whose "never" condition is true now
   (`addressSuggestionBlocked`, `domainSuggestionBlocked`, core; a ratio below its rule is never a reason); then generate and
   insert; then withdraw open address rows that an open domain row of the same kind covers. A whitelist row and a blocklist
   row of one address both end when both signals are true (the signals disagree). A row whose sender has no activity in the
   window is judged by the rules and by Sent coverage only. An `expired` row can be suggested again at once (only
   `dismissed` blocks; the weekly cap still counts it).
7. **Races.** Accept and Dismiss lock the row `FOR UPDATE`. The pass ends rows with `WHERE status = 'open'`, so a tap that
   holds the row wins (test 5d). `ended_by` is set only when the actor is a user id (the FK); `cli` or `system` leaves it null.
8. **The pass is one transaction.** An error in the suggestion step undoes the profile writes of that pass; the job logs the
   mailbox error by code and goes on. `RefreshResult` has no suggestion counts (many tests pin its shape); the step writes
   no log line and no audit row (a withdrawal or expiry is not a user act).
9. **Audit.** `suggestion.accepted` and `suggestion.dismissed`, data `mailbox_id`, `kind`, `scope`, `via` (`web` or `cli`).
   Accept also writes the normal `rule.added` row of `addSenderRule`.
10. No migration. `TERMS_VERSION` not changed (no legal text or registry change; two comments in `data-categories.ts` and
    `address-map.ts` and one in `export-map.ts` changed).

## For stage 06 (routes) and 07 (card)

- `acceptSuggestion(deps, ctx, { id, actor, via })` and `dismissSuggestion` take `deps = { db, now }`; results `accepted |
  already | rule_limit | not_found` and `dismissed | already | not_found`. Map `not_found` to 404, `already` to 409 or a
  harmless 200 (the stage decides), `rule_limit` to the rule-limit answer of the rules routes.
- `listOpenSuggestions(db, ctx, mailboxId)` returns `{ id, kind, scope, pattern, reason, createdAt }` oldest first.
- A member sees the card read-only; the role check belongs to the route.

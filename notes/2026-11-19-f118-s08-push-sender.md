## What was built

- `packages/core/src/notices/facts.ts`: `noticeFactsOf(kind, view)` → `{ count, itemId }`. `itemId`: approval and send_result → action id; approval_set → set id; delegation_answered → delegation id; every other kind null (urgent and not_triaged: the mail id never leaves the server). `count`: approval_set items, replies_ready count, else 1; cut to 99,999. Stage 09 reuses it for the `minimal` render of every kind.
- `renderers.ts`: `pushOf(kind)` gives the `push` renderer of each of the 15 push kinds: `JSON.stringify({ v: 1, kind, count, itemId, lang })`, checked by the strict payload schema without `id` (an item id over 64 characters makes the render fail → `bad_view`).
- `queueNotice`: when the plan has push rows, it renders the push payload once more; a failure throws `NoticeViewError` and no row is written. Unreachable with real views today (every kind that carries an id long enough to fail puts the id in a Telegram button that already fails the Telegram check); the test replaces a push renderer to reach it.
- `channels/push-sender.ts`: `createPushSender`, `pushTopicOf`, `PUSH_FLAG_WAIT_MS`, `PUSH_TTL_SECONDS`. Job `channels.push` in `main.ts` (every 15 s, only with the three `VAPID_*` keys, no bot needed, the shutdown waits for its run). Order per claimed row: stale reclaim counts an attempt (`too_many_errors` at 5); older than 24 h → `expired`; flag `web_push` off → wait 15 min; quiet hours; 3 per user per run (counted at the POST); the device must be live (`listLiveDeviceIds`), else `removeDevice` and `no_device`; `loadDeviceSecret`; render (`bad_view`); POST with `ttl` 86,400, `urgency` high for urgent and approvals and normal for updates, `topic` = base64url(sha256(row id)) cut to 32. `sent` → row `sent` (`text` = the body with `id`, `buttons` `[]`) and `markPushSuccess` in one transaction. `gone` (404, 410) → `removeDevice` (ends this row and every open row of the device as `no_device`), log `push_device_gone` (code `endpoint_gone`). `retry` → `Retry-After` or the 30 s doubling, an attempt counted, `too_many_errors` at 5, device `last_error_code` `push_retry`. `refused` → `failed` / `push_refused`, device `last_error_code` `http_<status>` (`push_not_sent` for a refusal before any request).
- `claimDueOutbox` returns `pushSubscriptionId`, `emailId`, `loopId` too. `push_refused` joined `outboxFailCodes` (the DB has a pattern check only, no list: no migration). Log field `http_status` added to the number allow-list.

## Decisions (stage 01 and stage 02 review carry-over)

- N2 of stage 01 (`HTTPS_PROXY`): keep. Bun's global `fetch` honours the proxy variables; a host that needs an egress proxy needs it. A proxy sees the push host, the VAPID token (12 h, one push service) and the encrypted body, never the payload in clear. The endpoint host check runs in `sendWebPush` before any request. Written in `PushSenderDeps` and the capability doc.
- N5 of stage 01: 400, 401, 403, 413 map to `refused`; a rejected VAPID key never deletes a device (kept, test 11).
- N6 of stage 01: the comment of `sendWebPush` now says what it does not throw for.
- N3 of stage 02 (`keyVersion` mismatch): a new `CryptoKeyVersionError` (subclass of `CryptoError`) is thrown for another key VERSION. `loadDeviceSecret` rethrows it and removes nothing; the sender releases the row and the rest of the run for 10 min and logs `push_key_version_mismatch` (error; `docs/known-alerts.md`). An auth-tag or JSON failure still removes the device. `deploy/README.md` says that a new `CREDENTIALS_KEY` drops the push devices. Push secrets are NOT added to `credentials:check` (a follow-up if the owner wants a restore drill to prove them).
- N4 of stage 02 (`endpoint_hash` plain SHA-256): keep (plan D3). Nothing reads the hash outside one user's rows; a keyed HMAC would only matter for a database dump, and the dump holds the encrypted secret anyway.

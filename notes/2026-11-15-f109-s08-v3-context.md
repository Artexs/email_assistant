# F109 stage 08: `classifier-v3` context, parts and eval flags (no LLM call, no spend)

Production still uses `classifier-v2` (`prompts.classifier` in `apps/server/src/modules/triage/prompts/index.ts`). Stage 11 moves the pointer.

## Where things are

- `ClassifierExtras`, `EMPTY_EXTRAS`: `triage/classifier.ts`. `classifyEmail` takes optional `extras` and `prompt` (a `ClassifierPromptChoice`: `{ version, parts }`). No `prompt` = the production choice (`productionClassifierChoice()`).
- `prompts/classifier-v3.ts`: `buildSystemPrompt(allowed, parts)`, `buildUserPrompt(email, sender, delegates, nonce, extras, parts)`, `classifierV3Parts`, `optionalParts`. v3 reuses the v2 helpers (`dataBlock`, `neutralize`, `oneLine`, `delegateLine`), which v2 now exports. The v2 text did not change (pinned hash in `classifier-v3.test.ts`).
- `prompts/index.ts`: `classifierVersions` (every version that can run, one builder signature), `CLASSIFIER_V3_PARTS` (now `["attachments"]`; stage 11 sets it), `productionClassifierChoice(pointer?, v3Parts?)`, `promptLabel`.
- `triage/classifier-extras.ts`: `deadlinesInWindow(today, deadlines)` (today−1 … today+30). Stage 10 uses it for the real-mail reader.
- `scripts/eval-extras.ts`: `classifierExtrasOfCase(evalCase, scenario, html)` is the sim mapping. `scripts/eval-args.ts`: `resolvePrompt`, flags, `EvalOptions.prompt`.

## Decisions taken

- The canonical part list is sorted by name (`history,list,urgency`), without `attachments` (always on). It names the run (`classifier-v3[history,urgency]`), the state file (brackets and commas become `_`) and the gate file field `promptParts`. The order of the sections in the prompt text is the type's order (`attachments, urgency, history, list`), whatever the order of the list.
- Prompt layout: `urgency` and `history` are sections before the Delegates block. The `list headers: yes|no` line and the attachment lines are inside the nonce block of the mail to classify (they are mail data). No attachments = `Attachments: none`. At most 10 attachments; names are cut to 120 characters.
- The `urgency` rule lines are added only when `urgent` is an allowed category.
- The gate file keeps its old name (`classifier-<version>-<model>-<effort>-<scenario>-v<n>.json`). A v3 file holds `promptParts`; a v2 file has no such field (schema: optional), so the v2 gate file is valid unchanged. Two v3 variants would overwrite one gate file: stage 11 runs only the chosen list.
- `--prompt-version` and `--prompt-parts` exist only for `--sim` runs. Without `--prompt-parts`: v3 as the production pointer uses `CLASSIFIER_V3_PARTS`; v3 while v2 is the pointer uses `none` (attachments only) (review N5). `--prompt-parts none` is the way to pass an empty list (review N20). `attachments` is accepted and means nothing.
- Review N2: the sim `senderHistory` is the persona group's ideal mix. Only `days`, `received` and `corrections` reach the model; `byCategory` never does. The eval usage text and the report header of a run with the `history` part say that a gain may not carry to real mail.
- A flagged sim mail (`assessSuspicious(suspiciousInputOfCase(...))` not empty) gets `senderHistory: null`.

# F109 stage 10: real-mail readers for `classifier-v3`

- `loadClassifierExtras(db, ctx, input)` is in `apps/server/src/modules/triage/extras-reader.ts` (stage 14 calls it too). `input` also needs `testMail` (the test-mail rule), because the history of a test mail counts test mail only.
- `triageOne` loads extras only when the prompt is not `classifier-v2`. The prompt is `deps.prompt ?? productionClassifierChoice()`. `TriageDeps.prompt` is for tests; the registry pointer stays `classifier-v2` until stage 11. Stage 11 changes only the pointer and `CLASSIFIER_V3_PARTS`: the service then reads the parts through `productionClassifierChoice()`.
- `TriageMailbox.urgencyProfile` comes from the batch read of `mailbox_settings` in `jobs.ts` (`parseUrgencyProfile`, now exported from the config module). A profile change mid-batch follows triage rule 9.
- `senderHistory`: window 90 days before the mail, `from_address_lower = lower(sender)`, `mailKindFilter` split, counts per `true_category` of the newest `wrong` feedback row. Flagged mail and no earlier mail give `null`.
- Limit of the guard proof: `emails` has the composite foreign key `(mailbox_id, org_id)`, so no data can make the `org_id` condition alone fail a test (the `mailbox_id` condition covers it). Removing `org_id` together with `mailbox_id` fails test 5.
- Error paths (`llm.call` row, `llm_blocked` result) now record the version of the prompt that ran (`choice.version`), not the registry pointer. With v2 in production nothing changes.

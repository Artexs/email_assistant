API:
- Core schemas (`packages/core/src/web/telegram.ts`): `telegramDetailSchema`, link body `detail?`, state keys `detail`, `effectiveDetail`, `locked` (absent while the flag is off), `telegramDetailBodySchema`, `telegramDetailAnswerSchema`, `telegramLockBodySchema`, `telegramLockAnswerSchema`; `organizationSettingsSchema.telegramMinimalLocked?` (absent while the flag is off).
- `channels/telegram-detail.ts`: `telegramDetailOfMember`, `linkDetailOf`, `storeTelegramDetail`, `recordTelegramConsent`, `changeTelegramDetail`, `changeTelegramLock`. Routes in `channels/routes.ts`: `PATCH /api/me/telegram-detail` (flag, then session user), `PATCH /api/organization/telegram-lock` (flag, then `requireOwner`), link route takes `detail`. Tenancy repo: `setMemberTelegramDetail`, `setTelegramMinimalLocked` (both `SELECT ... FOR UPDATE` the row, return the value stored before). Audit events `member.telegram_detail_changed` `{ detail }` and `org.telegram_lock_changed` `{ locked }`, written only when the value changes.
- Order of the checks: flag (404) → role (403 `owner_only`) → body (400) → lock (409 `telegram_detail_locked`) → consent (409 `telegram_consent_outdated`). The lock is checked before the consent on purpose: a locked organization cannot take `full`, whatever the consent.

## Decisions (not fixed by the stage file)
1. The link route with the flag on and no `detail` stores `minimal`, also for a member who has `full` (a pilot member who re-links through the panel with the old panel code is lowered to `minimal`; the panel card of stage 12 sends `detail`). The stage file says "default minimal".
2. The link route stores the level when the token is made, not when the chat is linked in Telegram.
3. No audit row when the value does not change. `full` writes the consent row every time (a confirmation).
4. `GET /api/organization` shows `telegramMinimalLocked` only while the flag is on (the other keys of a feature that is off are absent too).
5. The sender and `queueNotice` read the lock through the existing readers; the lock changes no member value (D14), tested through the sender.

## Rollback hazard
The `approval_edit` view has the new optional key `sendId`: the code before this stage refuses it (strict view), so pending `approval_edit` rows end `failed` / `bad_view`. They are cosmetic card edits. Rule 3e of `digest-and-notices.md` says: drain pending rows first.

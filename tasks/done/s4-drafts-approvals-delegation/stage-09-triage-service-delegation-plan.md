## Stage 9 — Triage service: the reply rule, the delegation plan, the delegations row, `send` depends on the draft [risky]

Why risky: this is where a mail turns into rows that lead to a send. A wrong status here (a `send` as `ready`, a missing `depends_on`) is caught by the database checks of stage 2, but a missing delegation row, a missing `delegation_id` in a payload or a wrong due date is not.

  - Decisions:
    - `createPlanned`: inserts the items in the given order, one statement per item (not one multi-row insert: the send needs the draft's id). For an item with `dependsOn`, `depends_on_action_id` = the id of the `create_draft` item of the same call; when that insert was a no-op (the key exists), the id is read by `idempotency_key` (`SELECT id FROM actions WHERE org_id = … AND idempotency_key = …`). A `send` item without a draft in the call finds its draft by the idempotency key, derived from the send key: the `:send` segment right after the email id becomes `:create_draft` (`<email>:send` ↔ `<email>:create_draft`, `<email>:send:reminder:<day>` ↔ `<email>:create_draft:reminder:<day>`; one mail can hold several drafts, so never "the newest draft"). No row with that key in the org (or a send key not of that form) throws a `HardError("send needs its draft")` (a programming error). The returned `CreatedAction[]` holds only inserted rows (as today).
    - `jobs.ts`: per mailbox `delegates = (await listDelegates(deps.db, ctx, { activeOnly: true })).map(…)` (the `delegation` index; edge `triage → delegation`, modules §2) and `timezone` from `getOrganization` (once per organization per run; cached in the run), both into `TriageMailbox` (built at `jobs.ts:73-81`, next to the S3 `settingsVersion: settings.version`). S3 has no log line per mailbox run (only the info line per mail, `service.ts:188`, and the cap warning in `jobs.ts`), so add one debug line after the `TriageMailbox` is built: `triage <mailboxId>: delegates <n>` (a count only; M22).

- [x] **9.2 The delegations row and the reply rule in `saveTriage` and `skipTooOld` (D6, D7)**
  - Goal: a `delegation` mail with a `ready` draft gets its `delegations` row and its `delegation_id` in both payloads in the triage transaction; a delegate's reply marks the delegation `answered` in the same transaction as its triage, on every triage path; the audit rows say so.
  - Files: change `apps/server/src/modules/triage/service.ts`, `apps/server/test/integration/triage-service.test.ts`, `apps/server/src/modules/audit/repo.ts` (no new event: `email.triaged` data grows).
  - Decisions:
    - **The reply rule runs inside `saveTriage`'s transaction, after the S3 settings version check and right after `finishEmail` returns true** (M23: `saveTriage` first runs `lockSettingsForShare` and compares it with `mailbox.settingsVersion`, and on a change it releases the mail with `settings_changed` before `finishEmail`, `service.ts:130-137`; review round 2 N5: a lost claim returns `{ kind: "lost" }` without a throw, so the transaction commits; a write before `finishEmail` would commit with it), on every path that reaches `saveTriage` (the classify path, the blocklist path `service.ts:305-309`, `finishTriageError` `service.ts:196`, `handleClassifyError` with `llm_blocked` `service.ts:220-244`): `answered = await detectReply(trx, ctx, mailbox.id, { fromAddress: email.from_address, inReplyTo: email.in_reply_to, referencesHeader: email.references_header })` (the `delegation` index; a DB read, no LLM); found → `markAnswered(trx, ctx, delegationId, { emailId: email.id, at: now })` (false when the delegation closed in between: no error). `skipTooOld` runs the same two calls in its transaction, also right after its `finishEmail` (a late reply still closes the loop). `TriageDecision` carries no reply field: the rule needs only the claimed mail.
    - **`now`:** `saveTriage(db, ctx, mailbox, email, decision, now: Date)` gets a new last parameter; every caller passes `deps.now()` (`triageOne`, `finishTriageError`; `skipTooOld` reads `deps.now()` itself). `markAnswered` and `createDelegation` use it; tests pass a fixed date.
    - After `createPlanned`: when `decision.finalCategory === "delegation"`, the created rows include a `create_draft` with `payload.kind === "delegation"` and status `ready`, and a `send` → `delegationId = await createDelegation(trx, ctx, { mailboxId, emailId, delegateId: payload.delegate_id, draftActionId, sendActionId, task: payload.task, dueDate: payload.due_date || null, timezone: mailbox.timezone, now })`, then `mergeActionPayload(trx, ctx, [draftId, sendId], { delegation_id: delegationId })` (D2: the hooks, the chaser and the notices read it from the payload; `sendAgain` copies it). A `logged` draft (shadow, switch off) and a clarification create no row and no merge. The `email.triaged` audit data gets `delegation_id` and `answered_delegation_id` when set.
    - A lost claim (`finishEmail` false) writes nothing, as today: the reply detection result is dropped with it (the run that holds the claim detects it again).
    - **`settings_changed` (S3 features 1 and 2, `958d749`):** a mail released with `settings_changed` (`service.ts:79`) gets no delegations row, no reply mark and no actions in that run; the job releases the rest of the batch without a count (`jobs.ts:110-113`) and drops its snapshot. The next run reloads the settings, triages the mail again, and then creates the delegation row or marks the reply. `createDelegation` and `mergeActionPayload` run after the settings check too (they come after `createPlanned`, which comes after `finishEmail`).

## Stage 22 — VPS deploy, `SEND_SCOPE=self`, the first real send to the user's own address, a reply [risky]

Preconditions (user checkpoint 4): stages 1–21 are committed and pushed; S3 stages 19 and 20 are done on the VPS, so the committer runs there with `ACTIONS_SCOPE=all` (a draft of real mail needs it, D16; checked in 22.1 step 1); the stage 20 gate holds; the pilot bot is linked (S2 stage 23); the user has a second address they own and can read; the user says go. Shell on the VPS: `ssh home_vm`, `cd ~/email_assistant`, bash, `C="docker compose -f deploy/compose.yaml --env-file .env"`. Pilot ids: org `<ORG>` = `ac6ed6a2-ee37-461f-9632-cc08cf549e40`, mailbox `<MB>` = `8bc7f572-a7f5-4fa5-aaab-db16dc663e96`. SQL read-only through `$C exec -T db psql -U postgres -d email_assistant -c "<SQL>"`. The agent never prints or edits `.env`; the user edits it.

**Risk (name it to the user before the go):** the deploy restarts the server (about one minute of triage stops). After this stage the pilot mailbox can create drafts in the user's real `Wersje robocze` folder and send mail from the user's real address, but only to the addresses in `SEND_TEST_ADDRESSES` (`SEND_SCOPE=self`): the pilot address and the user's second address. No mail can reach another person in this stage (the claim query refuses it in SQL, D16; `/status` shows held sends). A send that you approve but the scope holds (for example a clarification to a real sender) never goes out later by itself: it expires 48 h after your tap (`held_timeout`, D22), and stage 23.1 checks for held sends before `SEND_SCOPE=all`. Rollback: `git rev-parse --short HEAD` before the update gives `<OLD>`; if the server does not start or restarts again and again: first `update outbox set status = 'failed', error_code = 'outdated' where kind in ('approval', 'approval_set', 'send_result', 'delegation_answered') and status = 'pending';` (the S3 code's `claimDueOutbox` fails on the new kinds, S3 stage 19 m17), then close the S4 rows that the old code must not see, with the user's go, in one `psql` transaction: `update actions set status = 'expired', status_reason = 'policy_changed', result_notified_at = now(), locked_at = null, updated_at = now() where type in ('create_draft', 'send') and status in ('ready', 'awaiting_approval', 'approved');`, `update actions set status = 'failed', status_reason = 'outcome_unknown', result_notified_at = now(), locked_at = null, updated_at = now() where type = 'send' and status = 'applying';` (the user checks `Wysłane` by hand for these), `update actions set status = 'expired', status_reason = 'send_closed', result_notified_at = now(), locked_at = null, updated_at = now() where type = 'create_draft' and status = 'applying';`, `update delegations set status = 'cancelled', status_reason = 'expired', updated_at = now() where status = 'drafted';` (the S3 claim has no type filter for `ready` rows and would claim `create_draft` rows; an `approved` send must not go out after a later roll forward without a new tap; the reasons are ones the S4 notices know, and `result_notified_at` is set, so a roll forward sends no stale notice; drafts already in `Wersje robocze` stay: the user deletes them by hand), then `git checkout <OLD> && $C up -d --build --wait`, tell the user, later `git checkout master`. The S4 migration adds tables, columns and checks; the old code reads none of the new tables, and the `actions_type_check` with the new types does not block it. To stop every send at once: the user sets `SEND_SCOPE=off` and restarts, or `/pause`.

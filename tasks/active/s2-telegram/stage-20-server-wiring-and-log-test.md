## Stage 20 — Server wiring, shutdown and the log test [risky]

- [x] **20.1 `createTelegramRuntime`, `main.ts` jobs and shutdown, scheduler log line, end-to-end log test**
  - Goal: the server runs the bot, the notifier (detection + sender) every 15 s and the digest job every minute when `TELEGRAM_BOT_TOKEN` is set, and nothing of it when it is empty; the shutdown stays inside the 45-second `stop_grace_period`; one test runs the whole path against a fake Bot API and proves that no log line holds a secret or mail data.
  - Files: create `apps/server/src/modules/channels/telegram/runtime.ts`, `apps/server/test/integration/telegram-logs.test.ts`; change `apps/server/src/modules/channels/index.ts`, `apps/server/src/main.ts`, `apps/server/src/main.test.ts`, `apps/server/src/platform/scheduler.ts`, `apps/server/src/platform/scheduler.test.ts`.
  - Interfaces:
    - `interface TelegramRuntimeDeps { db: Db | Transaction<DB>; token: string; now(): Date; startedAt: Date; llmDailyCap: number; triageScope: "off" | "synthetic" | "all"; apiRoot?: string; botInfo?: UserFromGetMe }` (`apiRoot` and `botInfo` only for tests).
    - `interface TelegramRuntime { notify(): Promise<void>; scheduleDigests(): Promise<void>; startPolling(): void; stop(): Promise<void> }`
    - `createTelegramRuntime(deps: TelegramRuntimeDeps): TelegramRuntime` — builds `createTelegramBot(token, { db, now, handlers: createUpdateHandlers({ db, now, llmDailyCap, triageScope }) }, { botInfo, apiRoot })`, the channel `createTelegramChannel(bot.api)` and `createOutboxSender({ db, channel, now })`. `notify()` = `await detectNotices({ db, now, startedAt })`, then `await sender.run()`. `scheduleDigests()` = `scheduleDigests({ db, now })`. `startPolling()` = `startPolling(bot)` (stage 15), once. `stop()` = the polling `stop()`.
  - Decisions:
    - `main.ts`:
      - `const startedAt = new Date()` at the top.
      - `TELEGRAM_BOT_TOKEN` empty → `log.info("telegram is off (TELEGRAM_BOT_TOKEN is empty)")` and no Telegram job, no bot.
      - Else `createTelegramRuntime({ db, token, now: () => new Date(), startedAt, llmDailyCap: config.LLM_DAILY_CAP, triageScope: config.TRIAGE_LLM_SCOPE })`; `scheduler.add("channels.notifier", "*/15 * * * * *", …)` and `scheduler.add("channels.digest", "5 * * * * *", …)`, each keeps its running promise (as `triageRun` does); then `telegram.startPolling()`.
      - Shutdown order: `scheduler.stop()`; `await Promise.race([telegram.stop(), sleep(10 s)])` (`bot.stop()` can wait for the network); then wait for `triageRun`, `channelRun` and `digestRun` together with the existing 30-second limit; then `server.stop()`, `db.destroy()`, `process.exit(0)`. The sum (≤ 40 s) stays under `stop_grace_period: 45s` (`deploy/compose.yaml`).
      - The jobs and the polling never throw (stages 11–15). A promise of `startPolling` that rejects would print the error with its stack: `startPolling` catches everything (stage 15), so no unhandled rejection can print a token.
    - `platform/scheduler.ts`: the `catch` option logs `` `${name} failed: ${describeError(error)}` `` instead of `error.message` (D8: the scheduler cannot know which errors carry secrets).
    - The notifier and the digest job may run at the same time as the triage worker and the mail sync: the DB guards (unique keys, claim tokens) make this safe; croner never runs one job twice at the same time.
  - Test:
    - `scheduler.test.ts`: a job that throws `new Error("MARKER-SCHED")` → the `console.error` line contains `throws failed: Error` and not `MARKER-SCHED`.
    - `main.test.ts`: spawn `main.ts` with `DATABASE_URL` (any valid URL), a valid `CREDENTIALS_KEY` and `TELEGRAM_BOT_TOKEN=abc` → exit code 1; stderr contains `TELEGRAM_BOT_TOKEN` and not `abc`.
    - `telegram-logs.test.ts` (`withRollback` + `isolateChannels(trx)`; a fake Bot API on `Bun.serve({ port: 0 })` that answers `deleteWebhook`, `setMyCommands`, `answerCallbackQuery`, `editMessageText` with `true` or a message, `sendMessage` with a message (ids count up), and `getUpdates` with the queued updates whose `update_id` ≥ the offset, else `[]` after 100 ms; it records every method and payload; a spy on `console.log` and `console.error` with `setLogLevel("debug")`):
      - Markers: token `123456:MARKERTOKENaaaaaaaaaaaaaaaaaaaaaaaaaa`; subject `MARKER-SUBJECT`; from `marker-from@x.test`; reason `MARKER-REASON`; summary `MARKER-SUMMARY`; the plain link token; the chat id `987654321012`; the button data string `fr:u:<email id>`.
      - Steps (`clock` starts at `T0` = `2026-11-06T10:00:00Z`, 11:00 local, outside the quiet hours): org A with a mailbox (synced at `T0 − 5 min`), its owner, `setDigestTimes(["08:00"])`, a link token from `createLinkToken(trx, ctx, owner, T0)`; `createTelegramRuntime({ db: trx, token, now: () => clock, startedAt: T0 − 1 h, apiRoot, botInfo: testBotInfo, … })`; `startPolling()`; queue `/start <link token>` from chat `987654321012` and wait until the fake saw the reply. Then insert an `urgent` result with the markers and an `info` result with a `save_summary` action, both with `createdAt` `T0 + 1 min`; `clock = T0 + 2 min`; queue `/status` and `/digest`; `notify()` (the urgent notice is sent); queue a tap on `fr:u:<email id>` and wait for `answerCallbackQuery`. Insert a second `urgent` result (`T0 + 3 min`), `clock = T0 + 4 min`, make the fake answer the next `sendMessage` with 403 once, `notify()` (a `failed` / `blocked` row). Set `clock` to `2026-11-07T07:00:00Z` (08:00 local on the next day; the 08:00 slot of the link day is before the link), `scheduleDigests()`, then `notify()` (the digest is sent; its period starts at the link time − 24 h, so it has `MARKER-SUBJECT`); `stop()`.
      - Checks: the fake saw `sendMessage` with `MARKER-SUBJECT` (the notice and the digest really went out), `answerCallbackQuery`, and one `triage_feedback` row with source `telegram`; the collected log output contains none of the markers.
  - Check: `bun run dev:up && bun run db:migrate && bun run lint && bun run typecheck && bun run test:unit && bun run test:int`. Manual on the Mac with the dev token in `.env`: `bun run dev` → the log has `telegram: polling as @<dev bot>`; Ctrl+C → the process ends within 15 s. With `TELEGRAM_BOT_TOKEN` commented out → `telegram is off`.
  - Done when: the tests pass and the two manual runs show these lines.
  - Out of scope: the live run with the phone (stage 21). **User checkpoint 3 after this stage** (group review of stages 11–20).

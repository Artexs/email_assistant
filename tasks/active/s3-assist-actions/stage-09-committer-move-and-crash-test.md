## Stage 9 — Committer: move as an ensure, folders, the crash test [risky]

Checkpoint 1 input: stage 1 settled whether `COPYUID` comes back at Interia and whether the UID is kept. The ensure below does not depend on it (it locates the mail in the target in every case); the main session adds a note here with the Interia facts so the reviewer can check the hint rule.

- [ ] **9.1 `ensureMoved` and the `move` branch of `applyAction` (D5, D9)**
  - Goal: a `move` action (original or reverse) ends with the mail in exactly one folder, the target, whatever happened before (a crash after the COPY, a crash before the DB commit, a user who moved it already), with one audit row per applied action.
  - Files: create `apps/server/src/modules/actions/move.ts`, `apps/server/test/integration/actions-move.test.ts`; change `apps/server/src/modules/actions/apply.ts`, `apps/server/src/modules/actions/committer.ts`, `apps/server/src/modules/actions/index.ts`.
  - Interfaces:

    ```ts
    // move.ts
    export interface EnsureResult { uid: number; movedNow: boolean; leftoverDeleted: boolean }
    export async function ensureMoved(provider: MailProvider, email: ClaimedAction["email"], from: string, to: string, hints: { fromUid: number; toUid: number | null }): Promise<EnsureResult | null>; // null = nowhere
    // apply.ts
    export interface ApplyDeps { db; now(): Date; mailboxId: string; folders: FolderResolver; beforeCommit?: () => void /* test hook: runs after the IMAP change, before the DB transaction */ }
    export interface FolderResolver { resolve(key: FolderKey): Promise<string> } // ensureFolder once per key per run; writes the real path into folder_map when it differs
    export type ApplyOutcome = … | { kind: "failed"; reason: "mail_not_found" | "hard_error" | "no_provider" | "bad_payload" };
    // committer.ts
    export function createFolderResolver(deps: { db; now(): Date; provider: MailProvider; mailboxId: string; folderMap: Record<string, string> }, ctx): FolderResolver;
    ```

  - Decisions:
    - `ensureMoved`: `target = locateMessage(provider, to, { …key, hintUid: hints.toUid })`; `source = locateMessage(provider, from, { …key, hintUid: hints.fromUid })`. Cases: target and source → `deleteMessage(from, source.uid)` (a leftover of a COPY before a crash; `false` is fine: it went away in between) → `{ uid: target.uid, movedNow: false, leftoverDeleted: true }`; target only → `{ uid: target.uid, movedNow: false, leftoverDeleted: false }`; source only → `r = moveMessage(from, source.uid, to)`; `uid = r.newUid ?? (await locateMessage(provider, to, { …key, hintUid: source.uid }))?.uid ?? source.uid` (the last fallback keeps the source UID as a hint for the next locate; Interia keeps it, D2) → `{ uid, movedNow: true, leftoverDeleted: false }`; neither → null. `moveMessage` throwing `MailNotFoundError` (the mail left the source between the locate and the move) → one retry of the whole ensure inside `ensureMoved` (a user move in that second is rare); a second miss → null.
    - Hints: original move: `fromUid = email.uid`, `toUid = email.uid` (Interia keeps the UID: a hit is free; on an RFC server the miss costs one FETCH and the search runs). Reverse move: `from = email.folder`, `to = INBOX`, `fromUid = email.uid`, `toUid = email.inbox_uid`.
    - Folders: the original target is `folders.resolve(payload.folder)` (a `FolderKey`; an unknown key → `failed` / `bad_payload`, audit `action.failed`, and the stage 12 notice (every failure except `mail_not_found` notifies): the planner never writes one, so this is a guard). `FolderResolver.resolve`: cache per run; `path = provider.ensureFolder(folderMap[key] ?? AI_FOLDER_NAMES[key])`; when `path !== folderMap[key]` → own transaction `setFolderMapEntry` + audit `mailbox.folder_created` (`data: { mailbox_id, folder_key }`, no path in the audit: the path is the server's, not mail data, but keys are enough) and update the in-memory map. The source of an original move is `email.folder` (INBOX in every planned case; the ensure also works from another folder).
    - After the ensure: `deps.beforeCommit?.()`; then one transaction: `updateEmailLocation(emailId, { folder: to, uid, inboxUid: to === INBOX ? uid : undefined, movedAt: to === INBOX ? null : now })`; `finishAction(applied, providerResult: { uid, moved_now, leftover_deleted })` (false → `lost`: the IMAP change stays, which is harmless because the next claimer locates the mail in the target); audit `action.applied` (`data: { action_type: "move", mailbox_id, folder_key, reverse, moved_now, leftover_deleted }`); for a reverse: `markUndone(original, { reason: "undo" })` + audit `action.undone`.
    - `ensureMoved` null → `failed` / `mail_not_found` (one transaction, audit, no notice, D7). A move whose `email.folder` already equals the target (the sync marked the mail returned while the reverse waited, or a double plan) is the "target only" case: no IMAP write.
    - Error mapping as in stage 8 (soft → retry without a count; hard → count; auth → `auth_error`). A `HardError("no UIDPLUS")` from `deleteMessage` or the COPY path counts as hard and ends in `failed` after 3 tries with a notice: it can only happen when the stored capabilities lie (the policy keeps moves `log only` without MOVE and UIDPLUS).
  - Test (`actions-move.test.ts`, `withRollback`, fake with `capabilities: { move: false, uidplus: true }` and `keepUidOnCopy: true` unless said otherwise; fixtures): (1) `info` mail in INBOX with `move` ready → after `applyAction`: the fake INBOX has no copy, `AI/Info` has one; `emails.folder` = `AI/Info`, `uid` = the target UID, `inbox_uid` unchanged, `moved_at` = now; action `applied` with `provider_result.moved_now` true; one `action.applied` audit row; (2) the same on a fake with `move: true` and without `keepUidOnCopy` (RFC shape) → `uid` = the new UID from `newUid`; (3) `copyUidMap: false` → `uid` found by the locate in the target; (4) **crash test (done-when):** `beforeCommit` throws once → `applyAction` rejects; the row is still `ready` and locked; the fake target has one copy, the source none; a second `applyAction` with the same claimed action → `applied`, `moveMessage` called once in total (`fake.calls`), the target still has exactly one copy, one `action.applied` row, `emails.folder` updated; (5) leftover: the test delivers the same message into `AI/Info` by hand (a COPY before a crash) and keeps the INBOX copy → `deleteMessage` called, `moveMessage` not called, INBOX empty, `applied` with `leftover_deleted` true; (6) target only (the test moves the mail by hand with `userMove`) → applied with no IMAP write (`fake.calls` has no `moveMessage`, no `deleteMessage`); (7) nowhere → `failed` / `mail_not_found`; (8) reverse move: a mail in `AI/Info` with an `applied` original move and a reverse `ready` → the mail is in INBOX, `emails.folder` INBOX, `uid` and `inbox_uid` = the INBOX UID, `moved_at` null; the reverse `applied`; the original `undone` / `undo` with an `action.undone` audit row; (9) reverse when the user already moved the mail back (the fake has it in INBOX; the row says `AI/Info` with `returned_at` set) → applied with no IMAP write;

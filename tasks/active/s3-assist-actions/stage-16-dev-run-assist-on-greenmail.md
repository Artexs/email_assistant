## Stage 16 — Dev run: `assist` on GreenMail with the dev bot (user checkpoint 3) [risky]

- [ ] **16.1 The user tries S3 on the Mac with GreenMail and the dev bot**
  - Goal: the done-when items work end to end on a real phone and a real (local) IMAP server before anything goes to the VPS.
  - Files: this task file ("Results": the measured facts, no mail data, no chat id, no token; one log line).
  - Interfaces: none (operations). Dev DB shell: `D="docker compose -f deploy/compose.yaml -f deploy/compose.dev.yaml --env-file .env"`; SQL with `$D exec -T db psql -U postgres -d email_assistant -c "<SQL>"`. GreenMail IMAP on `127.0.0.1:3143`, auth off.
  - Decisions:
    - The main session runs the commands; the user uses the phone and reports what they see. The agent never prints `.env`. The dev bot token must be in `.env` (S2 stage 21); without it, the Telegram steps (6, 7) are replaced by the SQL checks named there, and the stage log says so.
    - Only synthetic mail goes to the LLM and to the committer: `TRIAGE_LLM_SCOPE=synthetic ACTIONS_SCOPE=synthetic` on the command line of this run, not in `.env`.
    - The dev org and GreenMail mailbox from the S1b and S2 dev runs are used (`select o.id, mb.id, mb.address from organizations o join mailboxes mb on mb.org_id = o.id;`). If none: `bun run org:create …` and `bun run mailbox:connect` against GreenMail (`deploy/README.md`, `notes/2026-11-03-greenmail-facts.md`).
    - A GreenMail mail cannot be moved by hand in a client: the "user move back" step uses a one-off `bun -e` snippet with `imapflow` against GreenMail (dev only; it runs on the Mac against the local test server and never against Interia):
      `bun -e 'const {ImapFlow}=require("imapflow");const c=new ImapFlow({host:"127.0.0.1",port:3143,secure:false,auth:{user:process.argv[1],pass:"x"},logger:false});await c.connect();const l=await c.getMailboxLock(process.argv[2]);try{await c.messageMove(process.argv[3],"INBOX",{uid:true})}finally{l.release()}await c.logout()' <address> <folder path> <uid>`.
  - Steps:
    1. `bun run dev:up && bun run db:migrate`. `bun run mailbox:settings mode --org-id <org> --mailbox-id <mb> --mode assist` → the table shows `assist`, switches move/mark_read/flag ON. `bun run mailbox:settings auto … --category info --value on --force`, the same for `notification` and `spam` (no real labels in the dev DB: `--force`, exit 0 with `FORCED`).
    2. Start the server in its own terminal: `TRIAGE_LLM_SCOPE=synthetic ACTIONS_SCOPE=synthetic bun run dev`. The log has `actions committer applies mailbox changes to synthetic mail only`, `triage takes only synthetic mail`, and `telegram: polling as @<dev bot>` (when the token is set).
    3. Write `t0` (UTC). `TEST_MAILBOX_ADDRESS=<GreenMail address> bun run mailbox:seed --org-id <org> --mailbox-id <mb> --eval-cases synthetic --per-category 1` (about 5 mails).
    4. Within 6 minutes (sync 5 min + triage + committer ticks): SQL `select e.folder, e.uid, e.inbox_uid, e.moved_at is not null as moved, a.type, a.status, a.applied_at is not null as applied from emails e join actions a on a.email_id = e.id where e.mailbox_id = '<mb>' and e.created_at > '<t0>' order by e.received_at, a.type;` → the `info` mail: `save_summary` and `move` applied, folder `AI/Info` (or the GreenMail spelling, see `folder_map`); `notification`: `mark_read` + `move` applied, folder `AI/Notifications`; `spam`: `move` applied; `urgent`: `flag` applied, folder INBOX; `needs_reply`: no action. Write `t1` = the time of the last `applied_at`; check `t1 − t0 ≤ 7 min`. `select folder_map from mailboxes where id = '<mb>';` shows the real paths (GreenMail delimiter). `select event, count(*) from audit_log where created_at > '<t0>' and event like 'action.%' group by 1;` → `action.applied` = the number of applied rows, `action.planned` as before.
    5. Mail state on the server: the server log has `committer <mb>: applied <n>, failed 0, retry 0`; `bun run mailbox:check --org-id <org> --mailbox-id <mb>` lists the `AI/*` folders.
    6. Phone: `/digest` → the lines show `done: mark read, move to AI/Notifications` etc.; the `info`, `notification`, `spam` and `urgent` lines have `↩️ n`; the `needs_reply` line has no ↩️. Tap ↩️ on the `info` line → toast `↩️ Undo started: the mail goes back within a minute.`; within 30 s SQL: the mail's `folder` INBOX, `moved_at` null, the originals `undone` / `undo`, two reverse rows `applied`; `select verdict, source from triage_feedback order by created_at desc limit 1;` → `wrong`, `undo`. Tap ↩️ again → `Undo was already requested for this mail.`; `/digest` again → that line shows `undone: move to AI/Info` and no ↩️.
    7. Phone, 15-line test of the keyboard: seed `--eval-cases all --per-category 3` (about 20 mails; free-tier calls), wait 6 minutes, `/digest` → a digest with 15 lines and up to 45 buttons arrives (if Telegram refuses the message, the outbox row is `failed` / `bad_request`: write it in "Results" and in the stage 13 decision: one line per row).
    8. User move back (below the cursor, Interia shape is not possible on GreenMail: this checks the S1a path): take the `notification` mail (`folder`, `uid` from SQL) → the `bun -e` snippet moves it to INBOX → within 6 minutes SQL: `returned_at` was set and cleared, `select source, count(*) from triage_feedback where email_id = '<id>' group by 1;` → one `imap_move` row; the move action `undone` / `user_moved_back`; no new `emails` row for that `Message-ID`.
    9. Second identical copy: `bun -e` with `messageCopy` of the `spam` mail from `AI/Spam` back to INBOX (a copy, not a move) → within 6 minutes a new `emails` row with `dedup_key` ending `#2`, status `triaged`, and the old row untouched in `AI/Spam`. Within one more minute the `#2` row's `move` is `applied` and `AI/Spam` holds two copies (B2: the committer moves the second copy and deletes neither); `select provider_result from actions where email_id = '<#2 id>' and type = 'move';` → `moved_now` true, `leftover_deleted` false.
    10. Failed action with a notice: SQL `insert` of a `ready` `move` action for a seeded mail with `payload = '{"folder":"nope"}'` and a new `idempotency_key` → within 30 s the action is `failed` / `bad_payload`; within another 30 s (outside quiet hours) the phone shows `⚠️ Could not move a mail` with the subject; `select kind, status from outbox order by created_at desc limit 1;` → `action_failed`, `sent`.
    11. Soft error: `docker stop email-assistant-greenmail-1`; seed is impossible now, so insert a `ready` `flag` action for a seeded mail by SQL; after two committer ticks: `attempts` 0, `next_attempt_at` null (the open fails, so the job calls `releaseActions`, which sets no wait: stage 8.2), `locked_at` null, `status` ready; the log has the warn line `committer <mb>: SoftError …; the next tick tries again` once per tick and `SoftError` labels only; no `retry 1` line (the per-run line counts only `applyAction` outcomes); `docker start email-assistant-greenmail-1` → within 6 minutes the action is `applied`.
    12. `/status` shows `Mode: assist`, `Actions: test mail only (ACTIONS_SCOPE=synthetic) · last 24 h: applied <n>, undone <m>, failed 1` (`<n>` counts mailbox actions only, not summaries). Undo held (Q5 default): `/pause` on the phone, then tap ↩️ on the `urgent` line (its `flag` is applied) → the toast `Undo is not possible now: mailbox changes are off or the mailbox is paused.`; SQL: no reverse row for that mail. `/resume`.
    13. Stop the server with Ctrl+C → it ends within 15 s. Check the terminal output: no subject, no address of a seeded mail, no summary, no token.
    14. Reset: `bun run mailbox:settings mode … --mode shadow` (the dev mailbox goes back to shadow).
  - Test: none (operations). The automated tests of stages 5–13 cover the same paths.
  - Check: steps 4–13 give the results above; `t0`, `t1` and the LLM call count of the run (`select reason_code, count(*) from audit_log where event = 'llm.call' and created_at > '<t0>' group by 1;`) are in "Results".
  - Done when: the user confirms steps 6–12 on the phone and the checks pass.
  - Out of scope: the VPS (stage 19); real mail.

## Goal

In mode `assist` the system changes the mailbox for real (folder moves, mark read, flag, summaries), only for categories that passed the S1b go/no-go table. Every change has Undo.

## Done when

- One week of `assist` mode with at most N = 3 wrong moves, found by Undo or feedback (user decision P2, 2026-11-06).
- The Undo button restores the mail (folder, read state, flag) and writes feedback (test).
- A user move back to INBOX after a system move gives exactly one `imap_move` feedback row; after an Undo it gives none; a second identical copy of a moved mail is stored and triaged as a new mail (tests).
- Every applied action has an audit row.
- A test stops the process between the IMAP call and the DB commit; after restart there is no double action.
- Soft errors do not count toward the 3 tries; after 3 hard errors the action is `failed` and the user gets a notice.
- Backups run (from S1a) and one restore test is logged.

### Input from S1a (2026-11-03): Interia cannot search by `Message-ID`

- Interia `UID SEARCH HEADER Message-ID <id>` returns no match, also for mail that is in the folder (also with the id without `<>`). `SEARCH HEADER Subject` works. Facts: `notes/2026-11-03-interia-imap-capabilities.md`.
- `ImapMailProvider.findByMessageId` (`apps/server/src/modules/mail/imap/client.ts`) uses that search. At Interia it always returns null, so the sync treats every known mail that comes back to INBOX as "returned", also when it is a second identical copy.
- S1a is not affected (shadow mode moves nothing). This plan replaces `findByMessageId` with `locateMessage` (D3, stage 5).

### Input from S1a (2026-11-04): Interia keeps the UID on a move

- The user moved a stored mail (UID 38829) from INBOX to a new folder and back. It came back with UID 38829. A mail moved into the new folder kept its INBOX UID (38831) there too. RFC 3501 does not allow this, but Interia does it.
- So the S1a sync rule "known mail back in INBOX = a mail above the UID cursor" never fires at Interia: a returned mail is below the cursor. This plan adds the below-cursor check (D4, stage 6).

### Design decisions (main session, 2026-11-06; why in each line)

- **D1 Write port.** `MailProvider` gets folder-aware write and read methods: `ensureFolder`, `moveMessage`, `deleteMessage`, `setFlags`, `fetchMetaIn`, `searchSinceIn`, `fetchByUidsIn`. `findByMessageId` is removed (it does not work at Interia). The IMAP adapter moves with `UID MOVE` when the live connection has MOVE, else with its own `UID COPY` + `UID EXPUNGE` (`messageDelete` sets `\Deleted` itself; needs UIDPLUS; a plain EXPUNGE is never sent). It never uses imapflow's built-in MOVE fallback, because that fallback deletes the source also when the COPY failed. Every `false` from an imapflow write is a `HardError` (stage 4). The fake provider and the GreenMail contract suite cover both paths (an adapter option `forceCopyMove` runs the COPY path on GreenMail, which has MOVE).
- **D2 `emails` columns.** `uid` = the UID in `folder` (as today). New: `inbox_uid` = the last known INBOX UID (set on insert, on `update_uid` and on a return; kept on a system move), `moved_at` = the time of the last system move. The below-cursor check (D4) reads `inbox_uid`; the Undo window and the metric read `moved_at` and `actions.applied_at`.
- **D3 Locate by identity, not by header search.** `locateMessage(provider, folder, key)` (mail module, built on the port): first `fetchMetaIn(folder, hintUid)` and an identity compare; else `searchSinceIn(folder, key.receivedAt − 1 day)` + `fetchByUidsIn` in chunks of 100 + the compare. Identity = normalized `Message-ID` + `content_hash` (the S1a dedup key), pure function `sameMailIdentity` in `sync-rules.ts`. Stage 1 checks at Interia that a COPY keeps RFC822.SIZE and INTERNALDATE; if the size changes, the compare drops the size (mode `no_size`: `Message-ID` + From + INTERNALDATE to the second; the stored `received_at` is INTERNALDATE, the `Date` header is not stored), decided in stage 5 from the stage 1 facts. If both the size and INTERNALDATE change, the build stops at checkpoint 1 for a new design. `locateMessage` skips every message with the `\Deleted` flag (an expunge that failed is not a copy) and every UID in `excludeUids` (the UIDs that other `emails` rows of the same identity hold in that folder: `listFolderUids`), so two identical copies are never taken for one mail.
- **D4 Returned mail below the cursor.** At the end of each incremental sync: rows with `folder <> 'INBOX'` and `moved_at` in the last 7 days (at most 500, newest `moved_at` first: the newest moves are the ones the user most likely puts back) → `fetchByUidsIn(INBOX, inbox_uids and uids)` in chunks of 100 rows → an identity match at the row's `inbox_uid` or `uid` (not `\Deleted`) is a hit (build fix 2026-11-07: a webmail move back at Interia keeps the folder UID of a system COPY). Every hit gets a folder check: `locateMessage` in the row's folder. Gone from the folder = the user put the mail back → `markEmailReturned` (as in S1a). Still in the folder = a copy below the cursor (Interia may keep the UID on a COPY back too): log and count it, no return; storing such a copy is a follow-up. A new copy above the cursor goes through the S1a path (`check_folder` → `locateMessage` in the folder → still there → `#2`). On an RFC server a returned mail also comes above the cursor; the S1a path marks it first, and the check then finds `folder = INBOX` and does nothing.
- **D5 Committer = "make it so".** Idempotent actions (`move`, `flag`, `mark_read`, `save_summary`) go `ready → applied` with no `applying` status (architecture §4.1 rule 6). A move is an ensure. First rule: when the source folder equals the target (for example a reverse after the sync marked the mail returned), locate in the target only and never delete. Else locate the mail in the target folder and in the source folder (both with `excludeUids`, D3); in both → delete the source copy (a leftover of a COPY before a crash; a leftover is only a target copy that no other `emails` row holds) → applied; only in the target → applied (the IMAP part was done before a crash); only in the source → move → applied; nowhere → `failed` with `status_reason = mail_not_found` at once (an original gets no notice: the user moved or deleted it; a reverse gets one, D7). After the IMAP call, the committer writes `emails.folder`, `uid`, `moved_at`, the action status, `applied_at` and the audit row in one transaction. A crash between the IMAP call and the commit leaves the action `ready`; the next run finds the mail in the target and writes the DB rows without a second IMAP change (done-when test, stage 9).
- **D6 One connection per mailbox per run; order per mail.** The committer runs every 15 s. Per active mailbox: count claimable actions (no connection when there is nothing); claim with `FOR UPDATE SKIP LOCKED` (`locked_at` = the JS `now`, the token for every later conditional update; stale after 10 min); open one IMAP connection only when a mailbox-changing action is claimed; apply in the order `save_summary`, `flag`, `mark_read`, `move` per mail (flags on the known UID first, the move last, because a move can change the UID); close. `save_summary` is DB only and is applied under every scope.
- **D7 Errors on the action row (architecture §4.1 rule 7).** `SoftError` (connection) → release without a count, `next_attempt_at` = now + 5 min, and stop this mailbox for this run. `MailAuthError` → mailbox `auth_error` (the S2 notice), release the batch without a count. `HardError` → `attempts + 1`, `next_attempt_at` = now + 5 min; at 3 → `failed` (`status_reason` = the error code) and the owners get a notice (D11). `mail_not_found` → `failed` at once, no count; no notice for an original row (the user moved or deleted the mail), a notice for a reverse row (the user tapped Undo and was told "the mail goes back"; Q1 default). A stale claim (`locked_at` older than 10 min) is taken back without a count (idempotent actions).
- **D8 `ACTIONS_SCOPE` (P1).** `off` (default) = the committer applies no mailbox change (only `save_summary`); `synthetic` = mailbox changes only for mail with a synthetic `Message-ID` (`@ea-seed.test>`), in every mailbox; `all` = every mail (real and synthetic) of the mailbox `TEST_MAILBOX_ADDRESS`, and no mailbox change in any other mailbox. One pure helper `claimFilterFor(scope, mailboxAddress)` (stage 8.2) maps the scope to the claim filter for the committer and for the Undo tap. The server refuses `all` without `TEST_MAILBOX_ADDRESS`. Actions that the scope holds back stay `ready` and are not claimed (the digest says "will move"; `/status` shows the scope). An Undo tap that the scope or a paused mailbox would hold back creates nothing and answers "Undo is not possible now: mailbox changes are off or the mailbox is paused." (Q5 default). `synthetic` is not a security boundary (any sender can write such an id); it is a test gate for the build and the VPS seed run.
- **D9 Folders.** `ensureFolder(name)` (adapter): LIST; when missing, it creates each missing level, parent first (checkpoint 1: Interia refuses a nested CREATE without the parent; imapflow joins the parts with the server's delimiter) and LIST again; it returns the path as the server lists it. The committer calls it once per target per run (cached) and, when the real path differs from `folder_map[key]`, writes the real path into `mailboxes.folder_map` (audit `mailbox.folder_created`). `emails.folder` always holds the real path. Stage 1 prints the Interia delimiter.
- **D10 Undo = reverse actions per mail.** `actions.undo(db, ctx, emailId, { now, userId, scope })`: in one transaction, lock the mail's original actions (`FOR UPDATE`: the returned job takes the same lock, D12); when the scope or the mailbox status would hold a reverse back → `held`, nothing written (D8); for every original action (`reverses_action_id IS NULL`) of type `move`, `flag` or `mark_read` with status `applied`, `applied_at` within 7 days and no reverse row yet: insert a reverse row (same `type`, `payload` = the original payload, `reverses_action_id` = the original id, `idempotency_key` = `${originalId}:undo`, status `ready`), audit `action.undo_requested`; the mail's `ready` original mailbox-changing rows (a move in a retry wait) become `expired` (`status_reason = undo`, audited), so they never run after the Undo. A `ready` row that a committer run holds at the second of the tap (a fresh `locked_at`) is not expired: it finishes `applied` after the toast, and the next digest shows ↩️ again for it (the runbook says: tap ↩️ again; re-review Rm8). The committer applies a reverse row as the inverse operation: move → ensure the mail in INBOX; flag → remove `\Flagged`; mark_read → remove `\Seen`; then sets the original to `undone` in the same transaction (architecture §4.4). The caller (the Telegram callback) writes the feedback row (`wrong`, source `undo`) when at least one reverse row was created and the latest category is not `unsure`.
- **D11 Notice `action_failed`.** A new outbox kind. One notice per failed action (dedup `action_failed:<actionId>`) to the linked owners, text: the action verb, the cleaned subject, "tried 3 times", what the mail state is (stays in INBOX, or for a failed Undo: stays in `AI/…`, move it by hand; for a reverse with `mail_not_found`: the mail was not found, it was moved or deleted in the mail client). The detector sets `actions.notified_at` in the same transaction as the outbox insert, so a second run makes no second row. The detector lists every unnotified failed row (no time filter: each listed row gets `notified_at`, so the list stays short); a row older than 24 h is marked notified without an outbox row. An original row with `mail_not_found` gives no notice (D7).
- **D12 User move back → feedback (architecture §4.4).** A new job `triage.returned` (every 15 s, always on, no LLM): for each row with `returned_at` set, one transaction: lock the mail's last original `move` action (`FOR UPDATE`, the same lock as Undo, so the two never both write feedback), then read its reverse row; when the move is `applied` and has no reverse row, or only a `failed` reverse → set it `undone` (`status_reason = user_moved_back`); write one feedback row only when there is no reverse row at all (`wrong`, source `imap_move`; none when the latest category is `unsure`, because `recordFeedback` refuses a verdict without a category there; none when the latest feedback row of the mail has a `true_category`, so a ✏️ label is kept); audit `email.returned`; in every case clear `returned_at`. A mail returned after an Undo has its move `undone` already → no feedback row (done-when). By design a second return of the same mail at Interia is not seen: the row says INBOX after the first return, so it leaves the below-cursor list (stage 19 expects one return).
- **D13 CLI `mailbox:settings`.** Subcommands: `show`; `mode shadow|assist` (on `assist` it sets the P3 switches unless `--keep-switches`); `auto <category> on|off [--threshold 0.nn] [--force]` (`on` runs the real-mail eval report of the mailbox: precision ≥ 98% with ≥ 30 kept rows, else it refuses unless `--force`; refuses `unsure` and `delegation`); `switch <name> on|off`. Each change writes an audit row (`mailbox.mode_changed`, `mailbox.policy_changed`, `mailbox.switch_changed`, with `forced` in the data). A mode change acts on new triage: `logged` rows of the shadow time are never applied later. A change that closes a gate (`mode shadow`, `auto … off`, `switch … off`) also sets the mailbox's `ready` original rows that the new setting makes `log only` to `expired` (`status_reason = policy_changed`, one `action.expired` audit row each) in the same transaction, so a gate change stops the moves at once. `expire-ready` expires every `ready` original mailbox-changing row of the mailbox (the step before `ACTIONS_SCOPE=all`, stage 20). Rows that a committer run holds right now (`locked_at` not stale) finish as `applied` and keep their Undo.
- **D14 Undo button in the digest (P4).** `ActionView` gets `id`, `reverse`, `reversesActionId`, `appliedAt`; `describeActions` skips reverse rows (the original shows `undone:`); a pure `isUndoable(actions, now)` says whether the line gets `↩️ n` (`fu:<emailId>`, callback kind `undo`). The tap answers with a toast only (the digest text is not edited): "↩️ Undo started: the mail goes back within a minute.", "Undo was already requested for this mail.", "Nothing to undo.", "Too old to undo (7 days).", or "This mail is not in your account." (the same text as the feedback buttons: no leak). The urgent notice gets no Undo button (a flag is harmless; the digest line of the mail has it).
- **D15 Audit events (new):** `action.applied`, `action.failed`, `action.expired`, `action.undo_requested`, `action.undone`, `email.returned`, `mailbox.folder_created`, `mailbox.mode_changed`, `mailbox.policy_changed`, `mailbox.switch_changed`. Data: ids, types, folder keys, attempts, codes, booleans. No mail text.
- **D16 Module borders.** `actions` owns the committer, the undo service and the claim queries; it imports `mail` (port, `locateMessage`, `updateEmailLocation`) and `audit`. `triage` owns the returned job (`triage → actions` exists). `channels → actions` for the Undo tap (modules §2). `mail` never imports `actions` or `triage`. `reports → actions` and `actions → mail` exist. One new edge: `config → audit` (the setters write audit rows). A setter that closes a gate expires the `ready` rows in its transaction (D13) through the required dependency `SettingsDeps.expireReady`, which the caller passes from the `actions` index. `config` never imports `actions` at run time (only `import type`), because `mail/connect.ts` already imports `config` (`insertDefaultSettings`): `config → actions → mail → config` would be a cycle (re-review RM1). `MAILBOX_ACTION_TYPES` lives in `packages/core` for the same reason. `audit` imports nothing. The committer reads no settings (the policy already decided at triage time), and the settings CLI composes `triage` (the eval report) and `config` (the setter) in the script, so `config` never imports `triage`.
- **D17 Logs.** Ids, counts, types, folder keys, codes and times only. Never a subject, an address, a folder path that the user typed, or an error message (`describeError` only). The stage 15 log test proves it.
- **D18 The `mailbox:audit` tool is unchanged.** `listInboxEmailKeys` reads only rows with `folder = 'INBOX'`, so mail that the system moved is not counted; a user move out of INBOX still shows as a "duplicate" (S1a check, 2026-11-06). Stage 18 writes this meaning into the runbook.
- **D19 Migration `<next free version>_assist_actions.sql` (stage 2; the next version after the highest file in `db/migrations/`).** `actions.applied_at`; `emails.inbox_uid`, `emails.moved_at`; indexes `emails_claim_idx (mailbox_id, status, received_at)` (closes `tasks/planned/s1b-claim-index.md`), `emails_moved_idx (mailbox_id, moved_at) WHERE folder <> 'INBOX'`, `emails_returned_idx (mailbox_id) WHERE returned_at IS NOT NULL`, `actions_email_type_idx (email_id, type)`, a partial unique index on `actions (reverses_action_id) WHERE reverses_action_id IS NOT NULL`; the `outbox.kind` check gets `action_failed`.
- **D20 Tests with two connections** (the crash test, the claim test) use their own organization and delete it at the end; the dev DB can hold other active mailboxes, so job tests call `pauseOtherMailboxes(trx)` first (S1b rule).
- **D21 Stale `ready` originals expire.** The committer claims an original mailbox-changing action (`move`, `flag`, `mark_read`, `reverses_action_id IS NULL`) only within 24 h of its `created_at` and only for mail received in the last 7 days (`e.received_at`: a backfill or a re-queue triages older mail, `triageOne` skips the age rule for `backfilled_at` mail; such rows expire by the 24-h rule). At the start of each mailbox run it sets older `ready` originals to `expired` (`status_reason = stale`, audit `action.expired`) in one batch update. Why: a mode or scope change, or a long outage, must not move mail from days ago that the user has handled by hand (stage 19 runs `assist` with scope `synthetic` for days while real mail gets `ready` rows). Reverse rows and `save_summary` never expire. `describeActions` shows an `expired` row as nothing (the line says "stays in INBOX").

### Rules for every step (read before each step)

- Code rules: `docs/code-patterns.md`. `packages/core` has no I/O and no `process.env`. Other modules import a module only through its `index.ts`. Every repository function takes a `TenantContext` and filters by `org_id`, except the scheduler entry points (`listSyncTargets`, `claimDueOutbox`, `listLinkedChats`, and the S3 ones named in a stage). Template literals, no `+` for strings. `createLog("<module>")`, never `console.log`. A status change and its `audit_log` row go in one transaction. Conditional updates (`WHERE status = … AND locked_at = …`) guard every status change.
- **Only the committer changes a mailbox.** No other code path (CLI, test tool, job) may move, flag or delete real mail. The exceptions are the test tools that refuse every address except `TEST_MAILBOX_ADDRESS` (`mailbox:seed`, the stage 1 `mailbox:probe-move`).
- **No mail body, subject, address, summary, folder path from mail data or secret in a log line or an error message.** Log ids, counts, types, folder keys, codes and times only. For an error use `describeError(error)`; for a Telegram error `telegramErrorLabel(error)`.
- **Scope gates:** `ACTIONS_SCOPE` keeps its default `off`; no step changes `.env`. Only stage 16 sets `synthetic` on the command line on the Mac; only stages 19 and 20 set it on the VPS (the user edits the VPS `.env`). `TRIAGE_LLM_SCOPE` is S1b's: S3 does not change it.

- Do not commit (the main session commits each stage after the review). Never run `bun run format` or `prettier --write` outside the step's files (S2 incident).

  - `bun run lint && bun run typecheck && bun run test:unit`

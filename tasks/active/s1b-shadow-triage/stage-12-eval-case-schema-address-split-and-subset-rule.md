## Stage 12 — Eval case schema, address split and subset rule [risky]

- [ ] **12.1 Case schema, `splitAddress`, `selectCases`, empty case files with structural checks**
  - Goal: the case schema, one address split rule for the eval runner and the seed script, one rule that picks the same subset every time, and the case files with their structural test (cases come in stages 13–15).
  - Files: create `packages/core/src/triage/eval-case.ts` (Zod schema, `EVAL_RECEIVED_AT`, `selectCases`), `packages/core/src/triage/address.ts` (`splitAddress`), `packages/core/src/triage/eval-case.test.ts`, `packages/core/src/triage/address.test.ts`; export all from `packages/core/src/triage/index.ts`; create `evals/README.md`, `evals/cases/synthetic.json` (content `[]`), `evals/cases/injection.json` (content `[]`), `apps/server/src/modules/triage/eval-cases.test.ts`.
  - Interfaces:
    - `evalCaseSchema = z.object({ id: z.string().regex(/^[a-z0-9-]+$/), kind: z.enum(["synthetic", "injection"]), lang: z.enum(["pl", "en"]), from: z.string(), to: z.array(z.string()).min(1), cc: z.array(z.string()).default([]), subject: z.string(), body: z.string(), thread: z.array(z.object({ from: z.string(), subject: z.string(), body: z.string() })).default([]), senderRules: z.array(z.object({ pattern: z.string(), kind: z.enum(senderRuleKinds) })).default([]), expected: z.object({ category: z.enum(["urgent", "needs_reply", "info", "notification", "spam"]) }), note: z.string().optional() })`; a file is `z.array(evalCaseSchema)`; `type EvalCase`.
    - `EVAL_RECEIVED_AT = new Date("2026-11-02T09:00:00Z")` (a Monday): the `receivedAt` of every case in the eval (step 17.1). "Today" in a case text = 2026-11-02.
    - `splitAddress(value: string): { name: string | null; address: string }` (`address.ts`): when the value matches `/^\s*(.*?)\s*<([^<>\s]+)>\s*$/` → `name` = the part before `<`, trimmed, with surrounding double quotes removed (empty → `null`), `address` = the part inside `<>`; else `name` = `null`, `address` = the trimmed value. The address keeps its case (`applyHardRules` compares in lower case). Used by `toClassifierInput` (step 17.1) and by the seed script (step 29.1): one rule for both (review finding 5).
    - `selectCases(cases: readonly EvalCase[], opts: { perCategory?: number }): EvalCase[]` — without `perCategory`: all cases, sorted by `id`. With `perCategory = n`: `synthetic` cases → `n` per expected category by the priority order below; `injection` cases → the first `n` by `id` in total. Result sorted by `id`.
  - Decisions:
    - Never real mail in git (ADR 0007, architecture §9). Use made-up names and only reserved domains: `*.test`, `example.com`, `example.org`, `example.net`. The user's address in cases: `szef@firma.test`. `from` is either a bare address or `Display Name <address>`; the address part is ASCII only (Polish letters only in the display name).
    - Subset priority per expected category (review finding 20), so a small subset always tests the sender rules: (1) the first case by `id` that has a `whitelist` or `vip` rule; (2) the first case by `id` that has a `blocklist` rule and no `whitelist` / `vip` rule; (3) the cases without any sender rule, by `id`; (4) the other cases, by `id`. Take the first `n` of this order. A step that is empty is passed over.
    - Case markers for the count tests (stages 13–15): a borderline case has a `note` that starts with `borderline:`; an injection case has a `note` that starts with `attack:`. A "whitelist/VIP case" = a case with a `whitelist` or `vip` rule that matches its `from` through `applyHardRules(splitAddress(from).address, senderRules)`.
    - `evals/README.md`: what each file holds, the data rule above, the markers, `EVAL_RECEIVED_AT` ("today" = 2026-11-02), how to run `bun run eval` (stage 18), the subset rule with its priority, that eval results can change between runs (no generation settings, step 10.1), and that real labels stay in the DB (`triage_feedback`), never in git.
  - Test:
    - `address.test.ts`: `"Łukasz Nowak <lukasz@firma.test>"` → name `Łukasz Nowak`, address `lukasz@firma.test`; `'"Nowak, Jan" <jan@firma.test>'` → name `Nowak, Jan`; `"anna@firma.test"` → name `null`, address `anna@firma.test`; `" <a@x.test> "` → name `null`, address `a@x.test`.
    - `eval-case.test.ts` (pure, hand-made list): `selectCases` gives `n` per synthetic category and `n` injection cases; the same ids on two calls and on a shuffled input; all cases without `perCategory`; priority: in a category with cases `a-plain`, `b-plain`, `y-block` (blocklist rule) and `z-white` (whitelist rule), `n = 1` gives `z-white`, `n = 2` gives `y-block` and `z-white`, `n = 3` adds `a-plain`; a category without rule cases gives the first `n` by `id`; the schema rejects an upper-case id, an unknown category and `to: []`.
    - `eval-cases.test.ts` (reads `evals/cases/*.json` from the repo root: `resolve(import.meta.dir, "../../../../../evals/cases")`): both files parse with `z.array(evalCaseSchema)`; ids are unique across files; every case in `synthetic.json` has `kind: "synthetic"`, every case in `injection.json` has `kind: "injection"`; every address (`from`, `to`, `cc`, thread `from`, through `splitAddress`) has a domain in the reserved list and is ASCII; every `senderRules` pattern is in lower case. These checks pass on the empty files. Stages 13–15 add the count tests to this file.
  - Check: `bun run lint && bun run typecheck && bun run test:unit && bunx prettier --check evals/README.md evals/cases/synthetic.json evals/cases/injection.json`
  - Done when: the tests pass.
  - Out of scope: case content (stages 13–15), the runner, any LLM call.

## Stage 4 — Email claim and release queries [risky]

- [x] **4.1 Mail repository functions for the triage worker**
  - Goal: the triage worker can claim, release and finish emails safely with `FOR UPDATE SKIP LOCKED` and conditional updates.
  - Files: change `apps/server/src/modules/mail/repo.ts`; change `apps/server/src/modules/mail/index.ts` (export `claimEmails`, `releaseEmail`, `finishEmail`, `listThreadContext`, `type ClaimedEmail`, and also the existing `getMailbox` and `listSyncTargets`, which the triage job needs; export `SYNTHETIC_MESSAGE_ID_DOMAIN`, `SYNTHETIC_MESSAGE_ID_LIKE` and `isSyntheticMessageId`); change `apps/server/src/modules/mail/seed.ts` (export `SYNTHETIC_MESSAGE_ID_DOMAIN = "ea-seed.test"`, `SYNTHETIC_MESSAGE_ID_LIKE = "%@ea-seed.test>"` and `isSyntheticMessageId(messageId: string | null): boolean` = `messageId !== null && messageId.toLowerCase().endsWith("@ea-seed.test>")`) and `apps/server/src/modules/mail/tools.ts` (use the domain constant in the seed Message-ID); change `apps/server/src/modules/mail/seed.test.ts` (`isSyntheticMessageId` cases); change `apps/server/test/integration/fixtures.ts` (new `insertTestEmail`); create `apps/server/test/integration/mail-claim.test.ts`.
  - Interfaces (all take `db: Db | Transaction<DB>, ctx: TenantContext` first and filter by `org_id`):
    - `interface ClaimedEmail { id: string; mailbox_id: string; locked_at: Date; attempts: number; next_attempt_at: Date | null; backfilled_at: Date | null; received_at: Date; from_address: string | null; to_addresses: string[]; cc_addresses: string[]; subject: string | null; body_text: string | null; thread_key: string; message_id_header: string | null }`.
    - `claimEmails(db, ctx, mailboxId, opts: { now: Date; limit: number; staleBefore: Date; syntheticOnly: boolean }): Promise<ClaimedEmail[]>`.
    - `releaseEmail(db, ctx, emailId, lockedAt: Date, opts: { nextAttemptAt: Date | null; countAttempt: boolean }): Promise<boolean>` — `status = 'pending'`, `locked_at = NULL`, `next_attempt_at = opts.nextAttemptAt`, `attempts + 1` only when `countAttempt`; `WHERE org_id = … AND id = … AND status = 'processing' AND locked_at = lockedAt`. A mail that was claimed but not tried is released with its old `next_attempt_at` (the caller passes `email.next_attempt_at` from the claim), so one bad mail never pushes the others back (review finding 4).
    - `finishEmail(trx, ctx, emailId, lockedAt: Date, next: { status: "triaged" } | { status: "skipped"; skipReason: "too_old" }): Promise<boolean>` — same guard; sets `skip_reason` for `skipped`; clears `locked_at` and `next_attempt_at`.
    - `listThreadContext(db, ctx, mailboxId, threadKey: string, before: Date, excludeId: string, opts: { syntheticOnly: boolean }): Promise<{ from_address: string | null; subject: string | null; received_at: Date; body_excerpt: string | null }[]>` — last 3 mails with the same `thread_key` and `received_at < before`, newest first, `body_excerpt` = `left(body_text, 500)` in SQL. With `syntheticOnly`: also `message_id_header ILIKE SYNTHETIC_MESSAGE_ID_LIKE` (review finding 19: a synthetic mail's prompt never holds real excerpts; step 20.1 passes `syntheticOnly: isSyntheticMessageId(email.message_id_header)`).
    - Test fixture: `insertTestEmail(trx, ctx: { orgId: string }, mailboxId: string, overrides?: Partial<NewEmail> & { status?: string; attempts?: number; next_attempt_at?: Date | null; locked_at?: Date | null; backfilled_at?: Date | null }): Promise<string>` — a direct insert into `emails` with defaults (`dedup_key` and `thread_key` = `test:${randomUUID()}`, `content_hash` `"h"`, `uid` 1, `received_at` `new Date()`, status `pending`) and `returning("id")`.
  - Decisions:
    - Claim form (review finding 11): one statement with a CTE. `WITH picked AS (SELECT id FROM emails WHERE <candidates> ORDER BY received_at, id LIMIT $limit FOR UPDATE SKIP LOCKED) UPDATE emails e SET status = 'processing', locked_at = $now FROM picked WHERE e.id = picked.id AND e.org_id = $org RETURNING <ClaimedEmail columns>`. Write it with Kysely `db.with("picked", …).updateTable("emails").from("picked")…` [not verified that the installed Kysely types allow `from` on an update with a CTE]; if they do not, use Kysely's `sql` template with the same SQL. `RETURNING` has no order: sort the result in JS by `received_at`, then `id`.
    - Candidates: same org and mailbox, and (`status = 'pending'` and (`next_attempt_at IS NULL` or `next_attempt_at <= $now`)) or (`status = 'processing'` and `locked_at < $staleBefore`). With `syntheticOnly`: also `message_id_header ILIKE SYNTHETIC_MESSAGE_ID_LIKE`.
    - `locked_at` = the JS `opts.now`, never SQL `now()`. The `locked_at` value is the token for `releaseEmail` and `finishEmail`. A JS `Date` has millisecond precision and Postgres stores microseconds, so a JS value survives the round trip exactly; a SQL `now()` value loses its microseconds in JS and the equality check would fail.
    - The claim and the LLM call are not in one transaction (an LLM call takes up to 30 s): the claim commits `processing` + `locked_at` first. A crash leaves `processing`; a later claim takes it back after `staleBefore` (the worker passes now − 5 min).
    - Work items are claimed with `FOR UPDATE SKIP LOCKED`; conditional updates (`WHERE status = …`) guard every status change (code-patterns). The worker reuses `listSyncTargets` (active mailboxes) as its scheduler entry point: no new function without `TenantContext`. Synthetic mail = `message_id_header` ends with `@ea-seed.test>` (the gate rule above).
  - Test (`mail-claim.test.ts`):
    - claim returns only pending rows with a due `next_attempt_at`, oldest first, up to `limit`; the returned `locked_at.getTime()` equals `opts.now.getTime()`; release with that returned `locked_at` returns `true` (round trip of the token);
    - it takes a stale `processing` row and leaves a fresh one; `syntheticOnly` returns only `@ea-seed.test>` ids; another org's rows never come back;
    - release with a wrong `locked_at` returns `false`; release with `countAttempt` adds 1, without it adds 0; release with `nextAttemptAt: null` sets NULL;
    - `finishEmail` sets `triaged` / `skipped` + `skip_reason`; `listThreadContext` returns max 3 older mails of the same thread and the same org only; with `syntheticOnly: true` a thread of 2 synthetic and 2 real older mails returns only the 2 synthetic ones, with `false` all 4 up to the limit of 3;
    - `isSyntheticMessageId` (unit test in `seed.test.ts`): `<a@ea-seed.test>` and `<A@EA-SEED.TEST>` → true; `<a@ea-seed.test.evil>`, `a@ea-seed.test` (no `>`) and `null` → false.
    - Two-connection test (deterministic; own org, committed rows, no rollback; delete the org in `finally`): insert 6 pending rows. In `db.transaction().execute(async (trx1) => { … })`: `a = claimEmails(trx1, …, { limit: 3 })` (trx1 stays open and holds the row locks), then `b = claimEmails(db, …, { limit: 3 })` on a second pool connection. Expect 3 + 3 ids, no id in both.

## Stage 12 — Committer: `send` (approved → applying → SMTP → applied), the stage rule, the Sent copy, the crash tests [risky]

Why risky: this is the one code path that sends mail to a person. At most once: never a second SMTP call after an error whose stage is unknown, after an error after the content, or after a crash in `applying`.

Checkpoint 1 input: stage 1 settled whether Interia saves sent mail by itself (`sentAutosave.foundInSent`) and what it answers to DATA (`dataReplyCode`). The Sent copy below locates first, so the rule holds in both cases; the main session notes the Interia answers here.

- [ ] **12.1 `applySend`: the happy path, the error outcomes, the Sent copy, the hooks, the draft reverse (D9, D10, D11, D13)**
  - Goal: an approved send goes out once; after the 250 the row is `applied` at once with the delegation `sent`; the Sent copy and the draft removal follow and can fail without touching the send's outcome.

    - `applyAction` routes `send` rows to `applySend`; `deps.sender` null → the job never applies an `approved` send without a sender (it opens one when the claimed batch holds an `approved` send, M9); a recovery row (`applying`, 12.2) needs no sender; keep a guard for an `approved` row: `releaseAction({ toStatus: action.status, … no count })` + an error line → `retry` soft.
    - `applySend`, status `approved`, in this order: (1) `draft = getDraft(depends_on_action_id)` (must be `applied`; else `releaseAction` to `approved` with no count and a warn line: the claim already checks it, this is a race guard); the payloads: `sendPayloadSchema.parse(action.payload)` and `draftPayloadSchema.parse(draft.payload)`; a parse failure → `failed` / `bad_payload` with the send-failure transaction below, but with `from: ["approved"]` (the row is still `approved`: `markApplying` comes in step 2; review round 2 N6) and `providerResult: { stage: "payload" }` (no SMTP call); `message = buildDraftMessage(deps, { …action, id: draft.id, created_at: draft.created_at, payload: draft.payload })` (the draft's id and `created_at` make the same `Message-ID`, `Date` and header as the draft APPEND: D9); `raw = await deps.compose(message)`; another error in this step (compose, a missing owner) → the S3 hard-count rule: `releaseAction({ toStatus: "approved", nextAttemptAt: now + 5 min, countAttempt: true })`, at 3 → `failed` / `smtp_error` with `last_error` = `describeError`, `providerResult: { stage: "compose" }`, `from: ["approved"]` (N6; the result notice names the cause: D20). (2) own commit: `markApplying(id, lockedAt, { outgoingMessageId: message.messageId })` + audit `action.applying`; false → `lost` (nothing was sent). (3) `deps.beforeSend?.()`; `result = await deps.sender.send({ envelope: { from: deps.mailbox.address, to: payload.to }, raw })`. (4) `deps.afterSend?.()`; **at once** one transaction: `finishAction(applied, { providerResult: { response: result.response, accepted: result.accepted.length, message_id: message.messageId, sent_copy: "pending" } }, { from: ["applying"] })` (false → `lost`: the mail went out; the row stays `applying` and a recovery run (12.2) ends it as `outcome_unknown` with a notice), audit `action.applied` (`data: { action_type: "send", kind, recipients: 1, delegation_id, reminder }`), then by payload: `delegation_id` without `reminder` → `hooks.onSent(trx, ctx, { delegationId, sentMessageId: message.messageId, sentAt: now, dueAtWhenNull: now + 3 days })`; with `reminder` → `hooks.onReminderSent`; then when `deps.mailbox.capabilities.uidplus` → `insertReverse(trx, ctx, { id: draft.id, emailId, type: "create_draft", payload: { kind, folder: draft.provider_result.folder, uid: draft.provider_result.uid, reason: "sent" } })`. (5) `deps.beforeSentCopy?.()` (a test hook outside the step's `try`: a throw there leaves `sent_copy` `pending`, as a crash would); then the Sent copy, outside the `applied` transaction: `sentFolder = await deps.folders.resolve("sent")`; `found = await locateByActionId(provider, sentFolder, { actionId: draft.id, hintUid: null, since: draft.created_at })`; found → `updateProviderResult(id, { sent_copy: "found" })`; else `await provider.appendMessage(sentFolder, raw, ["\\Seen"], now)` → `{ sent_copy: "appended" }`; any error in step 5 → `updateProviderResult(id, { sent_copy: "failed" })` + audit `action.sent_copy_failed` (`data: { error: describeError(error) }`) + a warn line; the outcome stays `applied` (done-when: "sent; no copy in Sent", never `outcome_unknown`). - [ ] **12.2 Recovery of a stale `applying` send and the crash tests (D11)**
  - Goal: a send that crashed in `applying` never goes out a second time by itself; the user gets the `outcome_unknown` notice unless the Sent folder proves the send; an error during the recovery never puts the row back to `approved`.
  - Files: change `apps/server/src/modules/actions/send.ts`, `apps/server/test/integration/actions-send.test.ts`, `apps/server/test/integration/actions-committer.test.ts` (S3 stage 8.2).
  - Decisions:
    - `applySend` with a claimed row in status `applying` (recovery; `locked_at` was null or stale): no `markApplying`, no SMTP call. `draft` and `message` as in 12.1 (the id is the same, so the Sent locate key is the same); `found = locateByActionId(provider, sentFolder, { actionId: draft.id, hintUid: null, since: draft.created_at })` → found → the `applied` transaction of 12.1 step 4 with `providerResult: { recovered: true, sent_copy: "found", message_id }` and the hooks; not found → one transaction `finishAction(failed, { reason: "outcome_unknown", lastError: "crash_in_applying", providerResult: { stage: "unknown", recovered: true } }, { from: ["applying"] })`, audit `action.failed` (`reason_code: "outcome_unknown"`, `data: { recovered: true }`), `hooks.onCancelled(…, "outcome_unknown")`. At Interia the Sent folder never shows the mail (stage 1), so a crash in `applying` there always ends `outcome_unknown` (the user gets the notice with "Send again").
    - **Errors inside the recovery path** (the folder resolve, the locate, a DB error): `MailAuthError` → `auth_error` (the row stays `applying` and unlocked through `releaseActions`); `SoftError` → `releaseAction({ toStatus: "applying", nextAttemptAt: now + 5 min, countAttempt: false })`; any other error → `attempts + 1 >= SEND_HARD_TRIES` ? the `outcome_unknown` transaction above (`lastError: describeError`) : `releaseAction({ toStatus: "applying", nextAttemptAt: now + 5 min, countAttempt: true })`. The recovery never returns a row to `approved` (reviewer finding 4): the S3 `sendOutcomeOf` mapping of 12.1 is not used here.
    - A row in `applying` with `locked_at` null comes only from a row that this run or a crashed run marked `applying` (the batch release of 12.1 never changes a status), so the recovery path is reached only by rows whose SMTP call may have started.

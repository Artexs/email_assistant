Delegation and clarification drafts, approval with Telegram buttons, send by SMTP only after approval, delegation tracking and chaser. Safe against prompt injection.

## Done when

- A delegation goes out only after a button tap and is followed up by the chaser.
- Tests: no code path sends without an approval row; two taps send once; an expired or rejected approval cannot send.
- Crash tests in `applying`: no second draft (Drafts lookup by `X-EA-Action-Id`); a send is at most once (found in Sent → `applied`; not found → `failed`, reason `outcome_unknown`, notice, no automatic resend).

- The approval request goes out only after its draft is `applied`; a missing draft expires the send (`draft_missing`).

- **D10 `MailSender` port and the SMTP adapter** (`mail/port.ts`, `mail/imap/smtp.ts`, `mail/fake/sender.ts`; stage 5). `interface MailSender { send(input: { envelope: { from: string; to: string[] }; raw: Buffer }): Promise<SendResult>; close(): Promise<void> }`, `SendResult = { response: string; accepted: string[]; rejected: string[] }`. Errors: `class SmtpSendError extends Error { stage: "connect" | "login" | "envelope" | "content" | "unknown"; code: string /* nodemailer code */; responseCode: number | null; permanent: boolean; soft: boolean }` plus `MailAuthError` for `EAUTH` (login). The adapter uses `SMTPConnection` (`nodemailer/lib/smtp-connection`) directly with three steps: `connect()` → stage `connect`; `login()` → stage `login`; `send(envelope, raw)` → an error with `command` `MAIL FROM` / `RCPT TO` / `DATA` and `code` `EENVELOPE` → stage `envelope`; `code` `EMESSAGE` (the server refused the content after DATA) → stage `content`; `code` `ECONNECTION` / `ETIMEDOUT` / `ESOCKET` (`command` `CONN`) → stage `envelope` when the content phase has not begun, else `unknown`. **Content phase began** = the adapter's own logger hook saw a server reply after the client `DATA` line: `SMTPConnection` gets `transactionLog: true` and a `logger` object whose methods only set two flags (`dataSent` when a `tnx: "client"` entry's text is `DATA`; `contentStarted` when a `tnx: "server"` entry arrives after `dataSent`) and store nothing (probe 4: the hook sees the client lines and the server replies, never the message content, and the AUTH line is masked). The reply code does not matter: nodemailer accepts any 2xx or 3xx reply to DATA (`_actionDATA`), so a server that answers `250` instead of `354` is covered. **The DATA reply is counted, not guessed:** the hook counts the server replies after the client `MAIL FROM` line and sets `contentStarted` at reply number `2 + <RCPT TO lines>` once the client `DATA` line was written (nodemailer logs one server entry per reply, in command order; with `PIPELINING` it writes MAIL FROM, every RCPT TO and DATA in one batch, so the first reply after `DATA` is the MAIL FROM reply: review round 2 N9, see the PIPELINING fact). If the hook saw no client line at all (`clientLines === 0`: an unknown nodemailer build), every error inside `send()` other than `EENVELOPE` / `EMESSAGE` is `unknown` (the safe side; stage 5.2 states the same rule). `lastServerResponse` is not used for the stage. `soft` = `ETIMEDOUT`, `ECONNECTION`, `ESOCKET` with a connection `originalCode`, `EDNS`, and 4xx replies (`permanent` false); `permanent` = 5xx; permanent wins over soft (a 5xx reply is never soft, whatever the code). `name` option = `ea-mail` (EHLO name; probe 1 showed the machine host name). `secure` true except loopback (as `smtpTransportOptions`); TLS certificates always checked. One `MailSender` per mailbox per committer run, opened only when a send is claimed (S3 D6 shape), closed in `finally`.

### Rules for every step (read before each step)
